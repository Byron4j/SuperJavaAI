## 引言：你的对象比想象中更胖

```java
// 猜猜这两个类的对象各占多少字节？

// 类 A：3 个字段
class A {
    byte  b;   // 1 byte
    int   i;   // 4 bytes
    byte  c;   // 1 byte
}

// 类 B：同样的 3 个字段，换了顺序
class B {
    byte  b;   // 1 byte
    byte  c;   // 1 byte
    int   i;   // 4 bytes
}

// 答案（64 位 JVM，压缩指针开启）：
// A 的实例大小：24 bytes
// B 的实例大小：16 bytes
// 同样的字段，同样的类型，只因为顺序不同，A 比 B 大了 50%！
```

```
┌─────────────────────────────────────────────────────────────┐
│               A 与 B 的内存布局对比                            │
│                                                             │
│  Class A (24 bytes):         Class B (16 bytes):            │
│  ┌────┬────┬────┬────┐      ┌────┬────┬────┬────┐          │
│  │Header   │ b  │pad │      │Header   │ b  │ c  │           │
│  ├────┼────┼────┼────┤      ├────┼────┼────┼────┤          │
│  │ i  (4B aligned)  │      │ i  (4B aligned)  │           │
│  ├────┼────┼────┼────┤      └────┴────┴────┴────┘          │
│  │ c  │pad │pad │pad │                                     │
│  └────┴────┴────┴────┘                                     │
│                                                             │
│  A: b(1) + pad(3) + i(4) + c(1) + pad(3) = 24 bytes       │
│  B: b(1) + c(1) + pad(2) + i(4)                = 16 bytes  │
│                                                             │
│  结论：字段声明顺序 = 内存用量                                  │
└─────────────────────────────────────────────────────────────┘
```

**核心洞察**：内存对齐不是无理取闹——不满足对齐的访问在大多数 CPU 上会触发硬件异常，在允许非对齐访问的 CPU（如 x86）上则会付出性能代价。Java 通过**字段重排**和**对齐填充**在两者之间平衡。

## 内存对齐的铁律：从硬件到 JVM

### 2.1 CPU 的对齐要求

```
┌─────────────────────────────────────────────────────────────┐
│             CPU 访问内存的三条铁律                             │
│                                                             │
│  1. 数据类型的地址必须是其大小的整数倍                            │
│     1 byte  → 任意地址，                                      │
│     2 bytes → 地址 % 2 == 0  (halfword aligned)              │
│     4 bytes → 地址 % 4 == 0  (word aligned)                  │
│     8 bytes → 地址 % 8 == 0  (doubleword aligned)            │
│                                                             │
│  2. 为什么？因为总线物理宽度                                    │
│     32 位总线一次读 4 字节，必须从 4 的倍数地址开始              │
│     否则需要两次总线操作 + 拼接 → 性能损失 2-3x                │
│                                                             │
│  3. x86 允许非对齐访问，但会做两次总线操作                       │
│     ARM/MIPS/SPARC：非对齐访问直接 SIGBUS 信号崩溃！           │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 对齐与非对齐的硬件操作对比

```
场景：读取地址 0x05 处的 4 字节 int（非对齐）

x86 CPU 的两次总线访问：
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 0x00│0x04│0x08│0x0C│    │    │    │    │
├────┼────┼────┼────┼────┼────┼────┼────┤
│ W0 │ W1 │ W2 │ W3 │    │    │    │    │
└────┴────┴────┴────┴────┴────┴────┴────┘
   │          │
   │     ┌────┘
   ▼     ▼
  读取 0x04 的 4 字节 = 字节 4,5,6,7
  读取 0x08 的 4 字节 = 字节 8,9,10,11
  再拼接：取前者[1:3] + 后者[0] → 最终值

vs 对齐访问（地址 0x04）：
  一次总线读 0x04 → 直接得到 4 字节

结论：非对齐访问消耗 2x 总线带宽 + 拼接的额外周期
```

### 2.3 JVM 的对齐策略

```
JVM 的三层对齐保证：

  Level 1: 对象起始地址 → 8 字节对齐（堆对齐）
    -XX:ObjectAlignmentInBytes=8（默认）
    最小对象大小 = 8 bytes

  Level 2: 字段在对象内的偏移 → 按字段类型大小对齐
    long/double: 8 字节对齐
    int/float:   4 字节对齐
    short/char:  2 字节对齐
    byte/boolean: 1 字节对齐（任意地址）

  Level 3: 对象总大小 → 8 字节对齐
    JVM 自动在末尾填充 padding
    保证下一个对象在堆内存中也是 8 字节对齐的
```

## C 语言视角：struct 的填充规则

### 3.1 C struct 的内存计算

```c
// C 语言中的 struct 填充与 Java 的 Object 布局有统一的算法

struct Example {
    char  a;    // 1 byte,  offset 0
    // padding: 3 bytes (因为 int 需要 4 字节对齐)
    int   b;    // 4 bytes, offset 4
    short c;    // 2 bytes, offset 8
    // padding: 2 bytes (因为整个 struct 大小要能整除最大成员的大小)
};
// 总大小：1+3+4+2+2 = 12 bytes
// sizeof(struct Example) = 12

// 优化版——大的字段放前面
struct Optimized {
    int   b;    // 4 bytes, offset 0
    short c;    // 2 bytes, offset 4
    char  a;    // 1 byte,  offset 6
    // padding: 1 byte
};
// 总大小：4+2+1+1 = 8 bytes
// sizeof(struct Optimized) = 8

// 同样 3 个字段，节省 33% 内存
```

### 3.2 通用填充公式

```
任意 struct 的内存大小计算：

  1. 每个字段的 offset = 该字段类型大小的最小整数倍
     该倍数 ≥ 前一个字段结束位置

  2. struct 总大小 = 最大字段类型大小的最小整数倍
     该倍数 ≥ 最后一个字段结束位置

  例如：{ char, int, char }
    字段1 (char):  offset=0, size=1, 结束=1
    字段2 (int):   offset=4 (下一个 4 的倍数≥1), size=4, 结束=8
    字段3 (char):  offset=8, size=1, 结束=9
    总大小=12 (下一个 4 的倍数≥9, 4 是最大字段 int 的大小)
```

## Java 对象内存布局：字段重排的艺术

### 4.1 JVM 对象的三段式结构

```
┌─────────────────────────────────────────────────────────────┐
│                JVM 对象内存布局（64-bit，压缩指针开启）          │
│                                                             │
│  ┌──────────────┬──────────────┬────────────────────────┐   │
│  │ Object Header│ Instance Data│   Padding (对齐填充)    │   │
│  │   12 bytes   │  (你的字段)   │   0-7 bytes           │   │
│  └──────────────┴──────────────┴────────────────────────┘   │
│                                                             │
│  Object Header 详解：                                        │
│  ┌─────────────────┬──────────────┐                         │
│  │ Mark Word (8B)  │ Klass (4B)   │  ← 压缩指针开启         │
│  │ Mark Word (8B)  │ Klass (8B)   │  ← 压缩指针关闭         │
│  │ 锁状态/GC信息    │ 指向 Class    │                         │
│  └─────────────────┴──────────────┘                         │
│                                                             │
│  压缩指针 (-XX:+UseCompressedOops, 默认开启)：               │
│    将 64 位指针压缩为 32 位，利用 8 字节对齐的低 3 位          │
│    不是"只能寻址 4GB"，而是 "32GB"（8字节对齐 × 2³²）        │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 JVM 的字段重排策略

```
HotSpot 的字段重排规则（非 @Contended 时）：

  1. 父类字段 → 子类字段（先父后子）

  2. 同一优先级内，按类型大小降序排列：
     double (8B) / long (8B)      ← 先放
     int (4B) / float (4B)        ←
     short (2B) / char (2B)       ←
     byte (1B) / boolean (1B)     ← 后放

  3. 同类型字段按声明顺序排列

  4. 引用类型字段 (4B 压缩, 8B 未压缩)
     与 int/double 等混合排序

  重点：JVM 自动做了"大字段放前面"的优化，
        绝大多数情况你不需要手动排序。
        但继承层次打破了这一优化——父类的 byte 字段
        和子类的 int 字段之间可能有不可预见的空隙。
```

### 4.3 继承破坏对齐的案例

```java
class Parent {
    byte  a;   // 1B → parent offset 12 (header 12 + 0)
    // padding: 3B
}

class Child extends Parent {
    int  b;    // 4B → 必须放在父类末尾之后
}
// 父类的 padding 无法被子类字段"填补"
// 结果：Child 实例 = 12 (header) + 1 (a) + 3 (pad) + 4 (b) + 4 (end pad) = 24 bytes

// 如果把 b 放在 Parent 中：
class Fixed {
    int  b;
    byte a;
}
// 结果：12 (header) + 4 (b) + 1 (a) + 3 (end pad) = 20 bytes
// 继承平白多占了 4 字节
```

## JOL 实战：亲手解剖你的对象

### 5.1 JOL 快速入门

```java
// 依赖: org.openjdk.jol:jol-core:0.17
import org.openjdk.jol.info.ClassLayout;
import org.openjdk.jol.info.GraphLayout;

public class JOLLab {
    static class BadLayout {
        byte  a;    // 偏移 12
        long  b;    // 偏移 16 (8B 对齐 → 跳过 13,14,15)
        byte  c;    // 偏移 24
        int   d;    // 偏移 28
    }

    static class GoodLayout {
        long  b;    // 偏移 12 (8B 对齐，直接放)
        int   d;    // 偏移 20
        byte  a;    // 偏移 24
        byte  c;    // 偏移 25
    }

    public static void main(String[] args) {
        System.out.println("=== Bad ===");
        System.out.println(ClassLayout.parseClass(BadLayout.class).toPrintable());
        System.out.println("\n=== Good ===");
        System.out.println(ClassLayout.parseClass(GoodLayout.class).toPrintable());

        // 运行时对象图大小
        BadLayout obj = new BadLayout();
        System.out.println("\n=== 对象图总大小 ===");
        System.out.println(GraphLayout.parseInstance(obj).toFootprint());
    }
}
```

```
JOL 输出示例 (64-bit, CompressedOops)：

=== Bad ===
 OFFSET  SIZE   TYPE DESCRIPTION
      0    12        (object header)
     12     1   byte BadLayout.a
     13     3        (alignment/padding gap)  ← JOL 标注的空隙！
     16     8   long BadLayout.b
     24     1   byte BadLayout.c
     25     3        (alignment/padding gap)
     28     4    int BadLayout.d
     32     4        (object alignment)       ← 末尾对齐
Instance size: 36 bytes

=== Good ===
 OFFSET  SIZE   TYPE DESCRIPTION
      0    12        (object header)
     12     8   long GoodLayout.b
     20     4    int GoodLayout.d
     24     1   byte GoodLayout.a
     25     1   byte GoodLayout.c
     26     6        (object alignment)
Instance size: 32 bytes

Good 比 Bad 节省了 4 字节 (36→32)
```

## TLAB 与堆内存碎片：JVM 的防御体系

### 6.1 碎片从哪里来

```
堆内存碎片的三种成因：

  1. 对象大小不均（内存分配碎片化）
     TLAB 内：
     ┌────┬──┬────┬──────┬──┬──┬────┬────┬──┬────┐
     │16B │4B│24B │ 8B   │4B│4B│16B │32B │8B│free│
     └────┴──┴────┴──────┴──┴──┴────┴────┴──┴────┘
     GC 回收小对象 → 留下多个小空洞 → 碎片

  2. 老生代长期存活对象（CMS 的致命问题）
     老生代中散布着长期存活的对象
     GC 只能回收死亡对象 → 存活对象像"钉子"钉在内存中

  3. 不同大小对象的混合（Heap 分块策略失效）
     JVM 的 free list 管理：大空洞被切碎 → 碎片

  解决方案：TLAB（线程本地分配缓冲）
```

### 6.2 TLAB 的工作原理

```
┌─────────────────────────────────────────────────────────────┐
│                    TLAB 机制                                  │
│                                                             │
│  Eden 区被划分为多个线程私有的 TLAB：                          │
│                                                             │
│  ┌──────────────────────────────────────────────┐           │
│  │              Eden 区                          │           │
│  │  ┌──────────┬──────────┬──────────┬───────┐  │           │
│  │  │ TLAB T0  │ TLAB T1  │ TLAB T2  │ ...   │  │           │
│  │  └──────────┴──────────┴──────────┴───────┘  │           │
│  └──────────────────────────────────────────────┘           │
│                                                             │
│  每个 TLAB 内部：bump-the-pointer (指针碰撞) 分配             │
│  ┌────────────────────────────┬──────────────────┐         │
│  │ 已使用                     │  未使用 (top→end) │         │
│  │                            │  ← top 指针       │         │
│  └────────────────────────────┴──────────────────┘         │
│                                                             │
│  分配对象 = top += objectSize → 返回旧 top                    │
│  开销：1 次指针加操作！（极快，单周期）                         │
│                                                             │
│  TLAB 耗尽时：                                               │
│  1. 分配新 TLAB（从 Eden 剩余空间获取）                       │
│  2. 如果 Eden 也不够了 → Minor GC                           │
│                                                             │
│  为什么快：                                                  │
│  • 私有不需同步（无锁）                                      │
│  • bump-the-pointer = 单指令分配                            │
│  • 对象销毁时整个 TLAB 统一回收（无碎片）                     │
└─────────────────────────────────────────────────────────────┘
```

### 6.3 大对象的直接晋升

```java
// 大对象——直接进老生代（跳过 TLAB 和 Eden）
byte[] bigArray = new byte[2 * 1024 * 1024];  // 2MB

// 阈值：-XX:PretenureSizeThreshold=1048576
// 大于此值的对象直接分配到老生代

```

## 数组、String、集合的内存精算

### 7.1 数组的内存开销

```java
/**
 * 数组 = 对象头 + 长度(int) + N × 元素大小 + 对齐填充
 */
// int[10]:
// 12 (header) + 4 (length) + 10 × 4 (elements) + 0 (pad) = 56 bytes

// byte[10]:
// 12 (header) + 4 (length) + 10 × 1 (elements) + 6 (pad) = 32 bytes

// char[10]:
// 12 (header) + 4 (length) + 10 × 2 (elements) + 4 (pad) = 40 bytes

// Object[10]:
// 12 (header) + 4 (length) + 10 × 4 (compressed refs) + 0 = 56 bytes

// boolean[] vs BitSet:
// boolean[1024] = 12+4+1024×1+4 = 1044 bytes
// BitSet(1024)   ≈ 128 bytes (底层是 long[])
// 差距 ≈ 8x！
```

### 7.2 String 的内存解剖

```java
/**
 * JDK 9+ String 内存布局（紧凑字符串）
 */
// String s = "abc";

// String 对象本身：24 bytes (Header 12 + value(ref) 4 + coder(byte) 1 + hash(int) 4 + pad 3)

// 底层 byte[] (紧凑存储)：
// 12 (header) + 4 (length) + 3 × 1 (bytes) + 5 (pad) = 24 bytes

// 总计：24 + 24 = 48 bytes 存储 "abc" 3 个字符
// 平均：48/3 = 16 bytes/char

// 如果是 JDK 8 (无紧凑字符串，使用 char[])：
// char[3]: 12+4+3×2+2 = 24 bytes (比 byte[] 多 0 bytes？刚好对齐相同)
// 对 3 字符无差异，但对 1 字符的 "a":
//   JDK 9: byte[1] = 12+4+1+7(pad) = 24 bytes
//   JDK 8: char[1] = 12+4+2+6(pad) = 24 bytes
//   还是无差异——因为对齐填充抹平了
// 但长字符串和大量短字符串时，紧凑存储优势明显
```

### 7.3 ArrayList vs LinkedList 的空间战

```java
// ArrayList<Integer> (10 个元素):
// ArrayList 对象: 24B
// Object[] 数组: 12+4+10×4+0 = 56B
// 10×Integer 对象: 10 × 16B = 160B
// 总计: 24+56+160 = 240B

// LinkedList<Integer> (10 个元素):
// LinkedList 对象: 24B
// 10×Node 对象: 10 × (12+4(int)+4(ref)+4(ref)+0) = 240B
// 10×Integer 对象: 160B
// 总计: 24+240+160 = 424B

// 结论：LinkedList 比 ArrayList 多占 76% 内存（Node 开销）
//       且 LinkedList 节点不连续 → 缓存不友好 → 遍历更慢
```

### 7.4 HashMap 的内部开销

```java
// HashMap<String, Integer> (1000 条目):
// 默认容量 16, 装载因子 0.75, 触发阈值 12

// Node[] 桶数组: 12+4+(N×4) ≈ 12+4+16×4 = 80B (容量16)
// 每个 Node: 12(header)+4(key ref)+4(value ref)+4(hash)+4(next ref)+4(pad) = 32B
// 1000 个 Node: 32,000B
// + key String 对象 + value Integer 对象
//
// 总内存 ≈ 数组扩容到 ~2048(3次扩容) + 节点 + 键值

//        ≈ 8,208 + 32,000 + 48,000 + 16,000
//        ≈ 104,208 bytes ≈ 102 KB
// 1000 条目 ≈ 100KB → 约 100 bytes/条目（含键值）
```

## 数据结构设计中的空间优化

### 8.1 字段排序——用空间换性能

```java
/**
 * 优化前：随机排列 → JVM 自动重排可能有空隙
 */
class Unoptimized {
    byte  flags;        // 1B
    long  timestamp;    // 8B
    int   count;        // 4B
    short port;         // 2B
    byte  type;         // 1B
    // 实际大小：24B (header) + 1+7 + 8 + 4+2+1+1(end) = 48B
}

/**
 * 优化后：手动按大小降序排列
 */
class Optimized {
    long  timestamp;    // 8B  ← 偏移12
    int   count;        // 4B  ← 偏移20
    short port;         // 2B  ← 偏移24
    byte  flags;        // 1B  ← 偏移26
    byte  type;         // 1B  ← 偏移27
    // 实际大小：24B + 8+4+2+1+1+4(end pad) = 44B
    // 节省 4B ≈ 8% 
}
```

### 8.2 用基本类型数组替代对象数组

```java
/**
 * 图算法中的邻接表——空间优化
 */

// ❌ 每个 Node 对象 24B 开销
class Edge {
    int to;       // 4B
    int weight;   // 4B
    Edge next;    // 4B (compressed oop)
    // 实例大小: 12(header) + 4+4+4+4(pad) = 28B
}
// 100 万条边 = 28MB → GC 压力 + 缓存不友好

// ✅ 基本类型数组：两个并行 int[]
int[] toArray = new int[N];
int[] weightArray = new int[N];
int[] nextArray = new int[N];
// 100 万条边 = 3 × (100万×4B) = 12MB → 省 57% 内存
// 且连续存储，缓存局部性优秀

// ★ 在超大规模图计算中（如社交网络、知识图谱），
//    这种优化是 OOM 和跑得动的分水岭
```

### 8.3 位域组合标志位

```java
/**
 * 用 int 的每个 bit 表示一个布尔标志
 * 1 个 int = 32 个 boolean → 节省 32 × (1+3pad) - 4 = 124 字节
 */
public class BitFieldFlags {
    private int flags = 0;

    // 位址常量
    private static final int IS_ADMIN     = 1 << 0;  // bit 0
    private static final int IS_ACTIVE    = 1 << 1;  // bit 1
    private static final int IS_VIP       = 1 << 2;  // bit 2
    private static final int HAS_PAID     = 1 << 3;  // bit 3
    // ... 最多 32 个标志

    public boolean isAdmin()    { return (flags & IS_ADMIN)  != 0; }
    public void setAdmin()      { flags |= IS_ADMIN; }
    public void clearAdmin()    { flags &= ~IS_ADMIN; }
    public void toggleAdmin()   { flags ^= IS_ADMIN; }
    // 一次 & 操作检查多个标志
    public boolean canAccess()  { return (flags & (IS_ADMIN | IS_ACTIVE)) != 0; }
}
```

### 8.4 享元模式（Flyweight Pattern）

```java
/**
 * 用享元模式减少重复对象的空间开销
 * 案例：文本编辑器——每个字符都是一个对象？
 *       100 万字 = 100 万个对象 = 1.6GB → OOM
 */

// ❌ 每个字符一个对象
class Character {
    char c;        // 2B
    String font;   // 4B (ref)
    int size;      // 4B
    int color;     // 4B
    // 实例: 12+2+2(pad)+4+4+4 = 28B
}

// ✅ 享元：共享属性对象，只保留位置信息
class Glyph {
    char c;                  // 2B
    TextStyle style;         // 4B (ref) ← 共享
    // 实例: 12+2+2+4 = 20B
}
class TextStyle {
    String font; int size; int color;
    // 12+4+4+4 = 24B，但被数万个 Glyph 共享
}
// 100万 Glyph × 20B + 50种 TextStyle × 24B ≈ 20MB (vs 1.6GB)
// 节省 ≈ 80 倍！
```

## 对象池与直接内存：粉粹碎片的工业方案

### 9.1 JVM 的对象池替代

```java
// JVM 本身不鼓励通用对象池（逃逸分析 + TLAB 已足够高效）
// 但特定场景仍有价值：

// Netty 的 Recycler（对象回收器）——避免频繁分配 ByteBuf
import io.netty.util.Recycler;

static class PooledBuffer {
    byte[] data = new byte[4096];

    private static final Recycler<PooledBuffer> RECYCLER =
        new Recycler<PooledBuffer>() {
            @Override
            protected PooledBuffer newObject(Handle<PooledBuffer> handle) {
                return new PooledBuffer();
            }
        };

    static PooledBuffer acquire() {
        return RECYCLER.get();  // 从池中获取或新建
    }

    void release() {
        RECYCLER.recycle(this, RECYCLER.newHandle(this));
    }
}
// 原理：Netty 的 Recycler 使用线程绑定的栈来快速回收/分配
//       避免了 GC 频繁回收和碎片化
```

### 9.2 直接内存与 Unsafe

```java
// 堆外内存——手动管理，零 GC 开销
import java.nio.ByteBuffer;

// 方式 1: DirectByteBuffer（推荐）
ByteBuffer direct = ByteBuffer.allocateDirect(1024 * 1024 * 100); // 100MB
// 不在堆内，不受 GC 管理，适合长期持有的大块数据

// 方式 2: Unsafe（非法）——更精细的控制
// 用于中间件开发，业务代码严禁使用
// Unsafe.allocateMemory(size);
// Unsafe.freeMemory(address);
```

### 9.3 压缩指针的配置

```bash
# 默认开启，寻址 32GB
-XX:+UseCompressedOops

# 在 32GB 堆以下自动开启，超过自动关闭
# 如果堆在 32-48GB 之间，关闭压缩指针反而更好（降低算术开销）

# 扩展压缩指针范围（Java 9+）
-XX:ObjectAlignmentInBytes=16   # 改为 16 字节对齐 → 寻址 64GB
# 代价：最小对象大小 16B（浪费 4B），但保留了 4B 指针
```

## 常见陷阱与最佳实践

### 陷阱 1：误以为 JVM 总是帮你优化字段顺序

```java
// ⚠️ JVM 不会跨继承层次重排字段
class Base {
    byte a;  // ← 这里的 3 字节 padding 子类无法利用
}

class Derived extends Base {
    int b;   // ← 不能填充到 Base 的空隙中
}
// 考虑用组合替代继承，或把 Base 设计为抽象类 + 内部 static 工厂
```

### 陷阱 2：日志/监控中频繁创建临时字符串

```java
// ❌ 每条日志创建大量 String 对象（碎片化元凶之一）
log.debug("User " + user.getName() + " did action " + action);
// 4 个临时对象：1 StringBuilder + 1 String + 2 char[] (JDK 8)

// ✅ 用参数化日志
log.debug("User {} did action {}", user.getName(), action);
// 如果没有打开 debug 级别 → 零对象创建
```

### 陷阱 3：ArrayList 默认容量

```java
// ArrayList 默认容量 10
// 如果存放 10000 个元素 → 经过 ≈ 10 次扩容
// 每次扩容创建新数组 + 拷贝 = 大量临时对象 + 碎片

// ✅ 预估大小
List<String> list = new ArrayList<>(10000);

// 创建约 16 倍对象数量的 gap = 大量临时数组被 GC
```

### 最佳实践清单

1. **用 JOL 检查内部类/POJO 的内存布局**——可视化 > 猜测
2. **字段按大小降序排列**：double/long → int → short → byte
3. **基本类型数组替代对象数组**——在超大规模数据处理中
4. **ArrayList 预分配容量**——避免重复扩容的临时数组
5. **BitSet 替代 boolean[]**——超过 64 个 flag 时
6. **避免短生命周期的临时对象**——学会用参数化日志和 StringBuilder reuse

## 面试题与参考答案

### Q1：一个 `new Object()` 占多少字节？

**参考答案**：
64 位 JVM 下：压缩指针开启时 16 字节（Mark Word 8B + Klass 4B + 对齐填充 4B），关闭时 16 字节（Mark Word 8B + Klass 8B，无需填充正好 16B）。没有实例字段，所以只有对象头。这是 Java 中最小的堆对象。

### Q2：JVM 的字段重排规则是什么？为什么子类字段不能填充父类的空隙？

**参考答案**：
规则：字段按类型大小降序排列（double/long → int/float → short/char → byte/boolean），同类型按声明顺序。子类字段不能填充父类空隙，因为 JVM 需要保证父类对象的内存布局在子类中是完整且一致的（子类对象可以被安全地向上转型为父类引用，GC 在回收时也需要通过 Klass 指针确定对象的真实类型和大小边界）。

### Q3：TLAB 为什么能减少堆碎片？

**参考答案**：
TLAB 内部采用 bump-the-pointer（指针碰撞）分配——所有对象紧密排列，无须维护 free list。TLAB 耗尽时整块被填满，没有内部碎片。GC 时整个 Eden 区被整体清理（复制或回收），不产生小空洞。对比：没有 TLAB 时，多线程同时从全局堆分配需要复杂的 free list 管理，容易产生碎片。

### Q4：为什么 `boolean[1024]` 占 1000+ 字节而 `BitSet(1024)` 只占约 128 字节？

**参考答案**：
boolean 数组用 byte[] 实现（JVM 中 boolean 底层为 byte），每个 boolean 占 1 字节 + 对象头开销。BitSet 底层是 long[]，1 个 long 存储 64 个 boolean 信息，长期来看 ≈ 1 bit/flag。1024 个标志位只需 1024/64 = 16 个 long = 128 字节，vs boolean[1024] ≈ 1044 字节。差距 ≈ 8 倍，且 BitSet 支持位运算（AND/OR/XOR）批量操作。

### Q5：设计一个"订单"类，包含 userId(long)、orderId(long)、amount(long)、status(byte)、type(byte)、paid(boolean)、timestamp(long)，写出最优的内存布局。

**参考答案**：
```java
class Order {
    long userId;      // 8B ← offset 12
    long orderId;     // 8B ← offset 20
    long timestamp;   // 8B ← offset 28
    long amount;      // 8B ← offset 36
    byte status;      // 1B ← offset 44
    byte type;        // 1B ← offset 45
    boolean paid;     // 1B ← offset 46
    // 对齐填充 5B

    // 实例大小: 12(header) + 32(lists) + 3(flags) + 5(pad) = 52B
}
```
所有 long 字段先放（8B 对齐），byte/boolean 后放（节省 8*3 = 24B 对齐填充）。如果 paid 和 type/status 合并到位域 int，能再省一些但降低可读性。

## 小结

```
┌─────────────────────────────────────────────────────────────┐
│              内存优化决策矩阵                                   │
│                                                             │
│  ┌──────────────────────────────────────────────────────┐   │
│  │ 场景                    │  优化策略                   │   │
│  ├────────────────────────┼────────────────────────────┤   │
│  │ POJO/Entity 类         │  字段按大小降序排列         │   │
│  │ 大数组 (>10K)           │  基本类型数组（非对象数组）  │   │
│  │ 密集 flag               │  BitSet 或位域 int          │   │
│  │ 缓存/热点对象            │  @Contended 防伪共享       │   │
│  │ 图/索引结构              │  基本类型数组 + 池化       │   │
│  │ 批量数据                │  直接内存 ByteBuffer        │   │
│  │ 诊断工具                │  JOL                        │   │
│  └────────────────────────┴────────────────────────────┘   │
│                                                             │
│  口诀：大的放前、小的放后、数组用基本、共享用防伪               │
└─────────────────────────────────────────────────────────────┘
```

**最终建议**：内存布局优化是"终极优化"——当算法和数据结构已经没有改进空间时，字段顺序和对象布局可以再挤出 10-30%。但日常代码中不要过度优化，可读性优先；仅在 HotSpot（JMH 确认）和 OOM 场景才动用这些技巧。

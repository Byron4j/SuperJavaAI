## 引言：一段跑 10 万次才崩一次的代码

下面这段代码，在 x86 架构上也**有可能**输出 `r1=0, r2=0`：

```java
// 初始：x = 0, y = 0

// 线程 1              线程 2
x = 1;                y = 1;
r1 = y;               r2 = x;

// 直觉：至少一个 r 为 1（不可能同时为 0）
// 现实：CPU 和 JIT 的指令重排可以让 r1=0 且 r2=0！
```

```
指令重排如何制造"不可能"：

线程 1（原始顺序）         线程 1（重排后）         线程 2
─────────────────        ─────────────────       ─────────────────
x = 1                    r1 = y  ← 重排到前面    y = 1
r1 = y     ──────►       x = 1                  r2 = x

内存视角：CPU0 的 StoreBuffer 中有 x=1，但尚未刷新到缓存
          CPU1 读 x 时看到的是旧值 0
```

**核心洞察**：指令重排是性能之源，也是并发 Bug 之源。CPU 和编译器不遵守"你写的顺序就是执行的顺序"，它们只遵守"单线程看起来没区别"。多线程下，这个假象被撕碎。

## 指令重排：CPU 和编译器的双重优化

### 2.1 重排的两大来源

```
┌─────────────────────────────────────────────────────────────┐
│                 谁在重排你的指令？                              │
│                                                             │
│   ┌──────────────────────┐     ┌──────────────────────┐     │
│   │   编译器（JIT/C2）    │     │     CPU 硬件          │     │
│   │                      │     │                      │     │
│   │ • 消除公共子表达式     │     │ • StoreBuffer 写缓冲  │     │
│   │ • 循环不变量外提       │     │ • InvalidateQueue    │     │
│   │ • 无用代码消除        │     │ • 乱序执行引擎        │     │
│   │ • 指令调度重排        │     │ • 推测执行            │     │
│   │                      │     │                      │     │
│   │ 目标：减少指令数       │     │ 目标：填满流水线      │     │
│   └──────────────────────┘     └──────────────────────┘     │
│                                                             │
│   Java 层面用 内存屏障 约束两者，用 happens-before 定义规则    │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 CPU 写缓冲区的隐蔽延迟

```
┌─────────────────────────────────────────────────────────────┐
│         StoreBuffer——导致"写入可见延迟"的元凶                   │
│                                                             │
│  Core 0 流水线：                                              │
│  ┌─────────────────────────┐                                │
│  │ EX → 写结果到 StoreBuffer │  ← 写入完成（本核心视角）        │
│  │ StoreBuffer → L1 (延迟)  │  ← 实际刷入缓存（其他核心视角）    │
│  └─────────────────────────┘                                │
│                                                             │
│  问题：写入在 StoreBuffer 中时，其他核心看不到！                 │
│                                                             │
│  StoreBuffer 设计理由：                                       │
│  • L1 写回需要几十个周期，CPU 不等——先写缓冲、继续执行后续指令     │
│  • 代价：写入对其他核心的可见性延迟                             │
│  • 解决：用 StoreLoad 屏障强制刷新 StoreBuffer                 │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 四种经典重排模式

```java
// 重排模式 1：Store-Store 重排（写入顺序被打乱）
// 线程 1：
a = 1;     // Store a
flag = true; // Store flag
// 可能被重排为：flag=true 先于 a=1 对其他核心可见

// 重排模式 2：Load-Load 重排（读取顺序被打乱）
// 线程 2：
r1 = a;    // Load a
r2 = b;    // Load b
// 可能被重排为：先读 b 再读 a

// 重排模式 3：Load-Store 重排（读写在单线程中倒序）
// 线程 1：
r1 = x;    // Load x
y = 1;     // Store y
// 可能被重排为：y=1 先执行，r1=x 后执行（x86 极少见，ARM 可能）

// 重排模式 4：Store-Load 重排（最常见也最危险）
// 线程 1：
x = 1;     // Store x
r1 = y;    // Load y
// Store x 进入 StoreBuffer
// Load y 可能比 Store x 先完成（因为不必等 Store 刷入缓存）
```

## 内存屏障：不可逾越的栅栏

### 3.1 什么是内存屏障

内存屏障（Memory Barrier / Memory Fence）是一条特殊的 CPU 指令，它告诉 CPU 和编译器：**屏障前后的指令不能跨越屏障重排**。

```
┌─────────────────────────────────────────────────────────────┐
│                   内存屏障的视觉效果                            │
│                                                             │
│   无屏障时（可重排）：                                        │
│   ...                                                       │
│   Store x     ────────────────────┐                         │
│   Load y                          │  随意穿越                │
│   Store z     ←───────────────────┘                         │
│                                                             │
│   有屏障时（禁止重排）：                                      │
│   ...                                                       │
│   Store x                                                   │
│   Store z                                                   │
│   ──── 内存屏障 ────  ← 不可逾越的栅栏                        │
│   Load y                                                    │
│   ...                                                       │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 x86 架构的屏障指令

```asm
; x86-64 的三条屏障指令
sfence   ; Store Fence —— 刷新 StoreBuffer，保证之前的所有 Store 完成
lfence   ; Load Fence  —— 保证之前的所有 Load 完成，后续 Load 不提前
mfence   ; Memory Fence —— Store + Load 的全屏障，最强也最慢

; x86 的特殊性：TOTAL STORE ORDER (TSO) 模型
; 天然保证 Store-Load 之外的三种顺序
; 只有 Store-Load 可能被重排（因为有 StoreBuffer）
; 所以 x86 上 volatile 写只需要一个 StoreLoad 屏障
```

```
硬件内存模型对比：

  ┌──────────────────┬──────────┬──────────┬──────────┐
  │  重排类型         │   x86    │   ARM    │  PowerPC │
  ├──────────────────┼──────────┼──────────┼──────────┤
  │  Load-Load       │    否    │    可能   │    可能   │
  │  Store-Store     │    否    │    可能   │    可能   │
  │  Load-Store      │    否    │    可能   │    可能   │
  │  Store-Load      │   可能   │    可能   │    可能   │
  │  模型名          │   TSO   │ Relaxed  │ Relaxed  │
  └──────────────────┴──────────┴──────────┴──────────┘

关键：越弱的模型（ARM/PowerPC）越需要更多屏障，
      代码越可移植；但 x86 的强模型让很多"侥幸"代码能跑，
      一旦移植到 ARM 就崩溃
```

## 四大屏障：LoadStore、StoreStore、StoreLoad、LoadLoad

### 4.1 JMM 定义的四种屏障

```
┌─────────────────────────────────────────────────────────────┐
│                JMM 四大内存屏障                                │
│                                                             │
│  LoadLoad    = Load1; LoadLoad; Load2                       │
│  含义：Load1 一定在 Load2 之前完成                            │
│  用途：确保先读到标志再读数据                                  │
│                                                             │
│  StoreStore  = Store1; StoreStore; Store2                   │
│  含义：Store1 的写入一定对 Store2 之前的所有处理器可见          │
│  用途：确保先写完数据再写标志                                  │
│                                                             │
│  LoadStore   = Load1; LoadStore; Store2                     │
│  含义：Load1 一定在 Store2 的写入被其他处理器可见之前完成       │
│  用途：确保读完旧值再写新值                                    │
│                                                             │
│  StoreLoad   = Store1; StoreLoad; Load2                     │
│  含义：Store1 写入对所有处理器可见后，Load2 才能执行           │
│  用途：确保写完的值能被读到                                    │
│  开销：最昂贵，需要刷新 StoreBuffer + 等待 Invalidate 确认    │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 从 Java 到汇编的映射

```java
// Java 代码
volatile int v = 0;
int a = 0;

// 写 volatile
a = 1;          // 普通写
v = 1;          // volatile 写
// JMM 保证：a=1 在 v=1 之前对所有线程可见

// volatile 写的屏障插入：
//   StoreStore 屏障（a=1 先于 v=1 刷入内存）
//   a = 1;
//   StoreStore
//   v = 1;  ← volatile 写
//   StoreLoad 屏障（后续读操作不能提前到 volatile 写之前）
```

```asm
; 上面 Java 代码 JIT 编译后的 x86-64 汇编（概念级）
mov    [a], 1       ; 普通写 a=1
; ★ 在 x86 上，mov 指令本身有序，StoreStore 不需要额外指令
mov    [v], 1       ; volatile 写 v=1
lock addl $0, (%rsp) ; ★ StoreLoad 屏障！lock 前缀刷 StoreBuffer +
                     ;   阻止后续 Load 越过此屏障
; lock addl 是一个"假写"——加 0 到栈顶，实际只消耗屏障效果
```

## volatile 的底层真相：四条汇编指令

### 5.1 volatile 写——JIT 生成的屏障

```
volatile 写的完整过程：

Java:  volatileVar = newValue;

JMM 规范要求的屏障序列：
  StoreStore 屏障 ─── 确保 volatile 写之前的所有普通写都完成
  写入 volatileVar  ─── 实际写入
  StoreLoad 屏障  ─── 确保 volatile 写之后的所有 Load 不提前

x86 实际汇编（HotSpot C2）：
  mov    [volatileVar], newValue   ; 普通 mov 已有 StoreStore 效果
  lock addl $0, (%rsp)              ; mfence 的轻量替代，StoreLoad 屏障

ARM 实际汇编：
  dmb ishst                         ; StoreStore 屏障
  str  newValue, [volatileVar]      ; 写入
  dmb ish                           ; 全屏障（StoreLoad）
```

### 5.2 volatile 读——极低的代价

```
volatile 读的完整过程：

Java:  localVar = volatileVar;

JMM 规范要求的屏障序列：
  读取 volatileVar  ─── 实际读取
  LoadLoad 屏障     ─── 后续 Load 不提前
  LoadStore 屏障    ─── 后续 Store 不提前

x86 实际汇编：
  mov eax, [volatileVar]   ; 普通 mov，x86 不重排 Load-Load 和 Load-Store
  ; 没有额外屏障指令！volatile 读在 x86 上几乎零开销

ARM 实际汇编：
  ldr  r0, [volatileVar]   ; 读取
  dmb ishld                 ; LoadLoad + LoadStore 屏障
```

### 5.3 volatile 的性能画像

```
┌─────────────────────────────────────────────────────────────┐
│              volatile 读写开销（相对普通变量）                  │
│                                                             │
│  操作        x86               ARM                性能说明   │
│  ──────    ──────            ──────              ────────   │
│  volatile读   1x              1.2x             几乎免费      │
│  volatile写   1.3x~2x         3x~5x             StoreLoad贵  │
│  CAS          2x~5x           5x~10x            lock前缀开销 │
│                                                             │
│  结论：volatile 读 ≈ 普通读；volatile 写 ≈ 1.3倍普通写        │
│        比 synchronized 快很多（无锁，不阻塞）                   │
│        但比普通变量多了一个 StoreLoad 屏障                     │
└─────────────────────────────────────────────────────────────┘
```

## final 域的内存语义：构造函数逃逸与冻结

### 6.1 final 域的两层语义

```java
/**
 * final 域的内存语义：构造函数安全发布
 */
public class FinalFieldSemantics {
    private final int x;
    private int y;

    public FinalFieldSemantics() {
        x = 1;          // final 域写入
        y = 2;          // 普通域写入
    } // ← 构造函数末尾，JMM 插入 StoreStore 屏障（冻结 final 域）

    // JMM 保证：只要对象被安全发布（不从构造函数中逸出 this），
    // 其他线程看到的 x 一定是正确的初始值，
    // 但 y 可能为 0（未初始化的默认值）
}
```

### 6.2 构造函数末尾的"冻结"

```
final 域写入的屏障机制：

1. 构造函数内写入 final 域：
   StoreStore 屏障 ─── 确保 final 域写入不重排到构造函数之外
   写入 x = 1

2. 构造函数末尾：
   StoreStore 屏障 ─── "冻结"——确保 final 域值对其他线程可见
                        （在这个屏障之前的所有写入完成后，
                          final 域的值被固化）

3. 读取 final 域：
   LoadLoad 屏障 ─── 确保先读到 final 域引用，再访问其成员
   读取 x

结果：安全发布的前提下，final 域没有"半初始化"问题。
```

### 6.3 构造函数逃逸——final 失效的根源

```java
/**
 * ❌ 危险：在构造函数中让 this 逃逸
 * final 域的保证将被破坏！
 */
public class UnsafePublication {
    private final int x;
    private static UnsafePublication instance;

    public UnsafePublication() {
        instance = this;  // ❌ this 逃逸！其他线程可能看到未构造完的对象
        x = 42;           // final 域的"冻结"还来不及发生
    }

    public static UnsafePublication getInstance() {
        UnsafePublication ref = instance;
        if (ref != null) {
            // ⚠️ 可能读到 x = 0（默认值）而不是 42
            return ref;
        }
        return new UnsafePublication();
    }
}
// 正确做法：不要在构造函数中注册回调、启动线程、发布 this 引用
```

## JMM 的 happens-before：口诀式记忆法

### 7.1 八大规则速查表

```
┌─────────────────────────────────────────────────────────────┐
│                happens-before 八大规则                        │
│                                                             │
│  1. 程序顺序规则：单线程内，前面的操作 happens-before 后面的    │
│     a = 1;          // 1                                     │
│     b = 2;          // 2，1 happens-before 2                 │
│                                                             │
│  2. 监视器锁规则：unlock happens-before 同一个锁的 lock        │
│     synchronized(m) { ... } ⇒ 释放 happens-before 后续获取    │
│                                                             │
│  3. volatile 规则：volatile 写 happens-before 后续 volatile 读│
│     v = 1;  ⇒  读 v 一定能看到 1                             │
│                                                             │
│  4. 传递性：A hb B, B hb C ⇒ A hb C                         │
│     通过 volatile 可以将普通变量的可见性"顺带"传递             │
│                                                             │
│  5. start() 规则：Thread.start() hb 该线程的任何操作           │
│     启动前的共享变量修改，对新线程可见                          │
│                                                             │
│  6. join() 规则：线程所有操作 hb Thread.join() 返回            │
│     线程A中 t.join() 后，A 能看到 t 的所有修改                 │
│                                                             │
│  7. 中断规则：Thread.interrupt() hb 被中断线程检测到中断       │
│                                                             │
│  8. 终结器规则：构造函数结束 hb finalize() 开始                │
│     （不推荐使用 finalize，了解即可）                          │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 happens-before 不等于"时间上先发生"

```java
// happens-before 是 JMM 定义的可见性保证，不是时钟顺序
int a = 0;
volatile int v = 0;

// 线程 1                // 线程 2
a = 1;                   if (v == 1) {
v = 1;                       // v=1 hb 读 v → 必然看到 a=1
                             assert a == 1;  // 一定为 true
                         }

// 如果线程 2 读到 v == 1：
//   volatile 写 v=1  happens-before  volatile 读 v=1
//   程序顺序：a=1  happens-before  v=1（单线程内）
//   传递性：a=1  happens-before  读 v=1
//   所以读 v=1 之后必然看到 a=1
//   这就是 volatile 的"附带可见性"——连锁保证
```

## DCL 单例：被破坏与修复的完整演进

### 8.1 最危险的 DCL（双重检查锁定）

```java
/**
 * ❌ 臭名昭著的错误 DCL——指令重排的教科书反例
 */
public class BrokenDCL {
    private static BrokenDCL instance;  // ❌ 没有 volatile

    public static BrokenDCL getInstance() {
        if (instance == null) {                    // 第一次检查
            synchronized (BrokenDCL.class) {
                if (instance == null) {            // 第二次检查
                    instance = new BrokenDCL();    // ❌ 问题在这里！
                }
            }
        }
        return instance;
    }
}
```

### 8.2 `new` 操作不是原子的

```java
// instance = new BrokenDCL(); 被分解为三条伪指令：
memory = allocate();           // 1. 分配内存
ctorInstance(memory);          // 2. 调用构造函数初始化
instance = memory;             // 3. 将引用赋值给 instance

// ★ 重排！CPU/JIT 可能把 2 和 3 交换：
memory = allocate();           // 1. 分配内存
instance = memory;             // 3. 引用赋值（提前了！）
ctorInstance(memory);          // 2. 构造函数初始化（滞后了！）

// 时间轴上的灾难：
// T1: instance = memory (此时 instance != null, 但初始化未完成!)
// T2: if (instance == null) → false → return instance
// T2: 使用 instance.getXxx() → 吃到半初始化的对象 → 💥
```

### 8.3 volatile 修复——一行代码的差距

```java
/**
 * ✅ 正确的 DCL——volatile 禁止了 2 和 3 的重排
 */
public class CorrectDCL {
    private static volatile CorrectDCL instance;  // ← volatile！

    public static CorrectDCL getInstance() {
        if (instance == null) {
            synchronized (CorrectDCL.class) {
                if (instance == null) {
                    instance = new CorrectDCL();
                }
            }
        }
        return instance;
    }
}
// volatile 的作用：
// 1. 写 instance 时插入 StoreLoad 屏障
// 2. 保证"初始化对象→写 instance 引用"的顺序不可逆
// 3. instance 变更对其他线程立即可见
```

### 8.4 现代方案：Holder 模式（无锁，无 volatile）

```java
/**
 * ✅ 利用类加载机制的天然线程安全性
 * JVM 保证类初始化锁，且类加载时有一个隐式屏障
 */
public class HolderSingleton {
    private HolderSingleton() {}

    private static class Holder {
        static final HolderSingleton INSTANCE = new HolderSingleton();
    }

    public static HolderSingleton getInstance() {
        return Holder.INSTANCE;
    }
}
// 原理：
// 1. 首次访问 Holder.INSTANCE 触发 Holder 类加载
// 2. JVM 对类加载过程加锁（ClassLoader.loadClass 内部同步）
// 3. 类加载完成后，所有 final static 域对所有线程可见（JMM final 语义）
// 无需显式 volatile，无需 synchronized，零开销
```

## 实战场景：屏障在框架中的运用

### 9.1 Disruptor 的 Sequence 屏障

```java
// Disruptor 核心：生产者写入数据后，更新 sequence 触发消费者
// sequence 必须是 volatile —— 保证生产者写入的数据先于 sequence 更新被消费者看到

// 生产者伪代码：
ringBuffer[index] = event;          // 普通写——先写数据
sequence.set(index);                // volatile 写——再更新序号
// StoreStore 屏障：数据写入先于 sequence 写入对其他核心可见
//                   消费者看到 sequence 更新时，必然看到完整数据
```

### 9.2 Netty 的 EventLoop 线程切换

```java
// Netty 将 Channel 从 EventLoop A 切换到 EventLoop B
// 依赖 volatile 保证线程安全移交

// 线程 A（原 EventLoop）：
channel.unsafe().unregister();      // 注销
nextEventLoop.execute(() -> {
    channel.unsafe().register();    // 线程 B 注册
});
// execute() 内部的 volatile 写入（任务队列）保证了
// unregister 的结果对线程 B 可见
```

### 9.3 JDK 中的屏障使用示例

```java
// Unsafe 提供的显式屏障方法（JDK 9+）
import jdk.internal.misc.Unsafe;

Unsafe U = Unsafe.getUnsafe();

U.storeFence();    // StoreStore + LoadStore 屏障
U.loadFence();     // LoadLoad + LoadStore 屏障
U.fullFence();     // StoreLoad 全屏障（最昂贵）

// VarHandle 提供更优雅的屏障（JDK 9+）
import java.lang.invoke.VarHandle;

VarHandle.storeStoreFence();
VarHandle.loadLoadFence();

// VarHandle 的 acquire/release 语义
VarHandle.releaseFence();   // StoreStore + LoadStore
VarHandle.acquireFence();   // LoadLoad + LoadStore
VarHandle.fullFence();      // StoreLoad
```

## 常见陷阱与最佳实践

### 陷阱 1：误以为 volatile 是原子操作

```java
volatile int count = 0;
// ❌ count++ 不是原子操作！它等于 count = count + 1
// volatile 只保证可见性，不保证原子性
// 正确做法：AtomicInteger.incrementAndGet()
```

### 陷阱 2：依赖 x86 的强内存模型

```java
// ❌ 这段代码在 x86 上"侥幸"能跑，在 ARM 上会崩
int data;
boolean ready;

 // 线程 1：
 data = 42;
 ready = true;   // 没加 volatile

 // 线程 2：
 if (ready) {
     System.out.println(data);  // ARM 上可能打印 0！
 }
 // 修复：把 ready 声明为 volatile
```

### 陷阱 3：synchronized 中的重排仍然存在

```java
// ⚠️ synchronized 保证互斥，但不完全禁止内部指令重排！
synchronized (lock) {
    a = 1;
    b = 2;
}
// 在锁的临界区内，a=1 和 b=2 可能被重排（单线程视角无影响）
// 但锁的释放边界有屏障保证，不会重排到临界区外面
```

### 陷阱 4：Unsafe 直接内存与屏障

```java
// ❌ 使用 Unsafe 读写堆外内存时，不会自动加屏障
Unsafe U = Unsafe.getUnsafe();
long directAddr = U.allocateMemory(1024);
U.putLong(directAddr, 42L);  // 普通写，无屏障
// 其他线程读 directAddr 可能看到旧值
// 需要手动加屏障：U.fullFence() 或 U.storeFence()
```

### 最佳实践清单

1. **用 volatile 替代显式屏障**：volatile 的语义是经过 JMM 精心设计的，比自己插 barrier 更安全
2. **x86 开发，ARM 测试**：在 x86 上开发可能掩盖重排 Bug，务必在 ARM/M1 上验证
3. **DCL 标配 volatile**：哪怕 x86 上没出过问题，也不要省这个 volatile
4. **单例优先 Holder 模式**：无锁、无 volatile、懒加载、优雅
5. **用 AtomicXxx 替代 volatile + 自增**：自带原子性和屏障
6. **理解而不滥用 Unsafe**：Unsafe 的屏障方法是为框架作者准备的，业务代码不要碰

## 面试题与参考答案

### Q1：volatile 的两大语义是什么？分别靠什么机制实现？

**参考答案**：
1. **可见性**：volatile 写对后续 volatile 读立即可见。实现：写后插入 StoreLoad 屏障（x86 上为 `lock addl`），将 StoreBuffer 刷新到缓存，并使其他核心的缓存行失效
2. **禁止指令重排**（JDK 5+ 增强）：volatile 写之前的操作不能重排到写之后，volatile 读之后的操作不能重排到读之前。实现：写前后、读前后插入对应的 JMM 屏障（StoreStore、StoreLoad、LoadLoad、LoadStore）

### Q2：为什么 `(x = 1; y = 2;)` 可能被重排？什么时候会出问题？

**参考答案**：
编译器/CPU 优化：如果 `y = 2` 的地址恰好在 L1 缓存中而 `x = 1` 的地址不在，CPU 可能先执行 `y = 2` 以减少流水线停顿。单线程下无影响（x 和 y 互不依赖），多线程下如果另一个线程在轮询 `y` 作为"数据已就绪"标志，看到 `y = 2` 时可能 `x` 还是旧值。解决方案：`y` 声明为 `volatile`。

### Q3：什么是 StoreLoad 屏障？为什么它是最昂贵的？

**参考答案**：
StoreLoad 屏障确保一个 Store 操作完成后（对全部核心可见）才执行后续的 Load 操作。它昂贵的原因：
1. 必须等待 StoreBuffer 全部排空（几十个周期）
2. 必须等待其他核心的 Invalidate Acknowledge（总线通信延迟）
3. 这是唯一能阻止 Store-Load 重排的屏障，而 Store-Load 是最容易发生的重排
4. 在 x86 上 `mfence` 或 `lock addl` 实现；在 ARM 上用 `dmb ish` 实现

### Q4：写出一个依赖 happens-before 传递性的完整示例。

**参考答案**：
```java
// 线程 1              // 线程 2              // 线程 3
a = 1;                 if (b == 2) {
b = 2;  // volatile       c = 3; // volatile      if (c == 3) {
                             ─────                   assert a == 1; // ✅
                         }                         }
// 传递链：a=1 hb b=2（程序顺序）
//         b=2 hb c=3（volatile 写→读）
//         因此 a=1 hb 线程 3 读 c=3
```

### Q5：`final` 域的"冻结"是如何实现的？构造函数中启动线程有什么风险？

**参考答案**：
JMM 在构造函数末尾插入 StoreStore 屏障（"冻结操作"），确保 final 域的写入在这个屏障之前完成且对所有处理器可见。如果在构造函数中启动线程（或让 this 逃逸），线程可能在冻结之前就拿到对象引用，从而看到未初始化的 final 域（值为默认值 0/null）。所以**永远不要在构造函数中启动线程、注册监听器、将 this 赋给静态变量**。

**最终建议**：记住两条黄金法则——**共享变量要么用锁保护，要么声明 volatile**；**DCL 单例的 instance 必须加 volatile**。理解屏障不是为了手写它，而是为了理解为什么你一省掉 volatile，代码就在 ARM 服务器上崩了。

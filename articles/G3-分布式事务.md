## 引言：分布式事务的本质与挑战

分布式事务（Distributed Transaction）不是"让多个数据库同时成功或失败"的简单操作，而是一套**在不可靠网络上保证多个节点数据状态收敛**的分布式一致性协议。

核心认知：

```
本地事务的本质：P(成功) = P(步骤1) * P(步骤2) * ... * P(步骤N)
                    原子性由数据库的ACID保证

分布式事务的本质：P(成功) = P(步骤1|网络正常) * P(步骤2|网络正常) * ... 
                    * P(协调者可用) * P(参与者可用)
                    原子性需要额外的协议保证

质量差异的根源：
- 差的方案：追求绝对一致性，牺牲可用性
- 好的方案：根据业务场景选择合适的一致性级别
```

**关键洞察**：分布式事务的设计不取决于技术完美主义，而取决于**业务对一致性的真实容忍度**。

## 理论基础：分布式系统的数据一致性原理

### 1. ACID与BASE的辩证关系

#### ACID理论

```
ACID属性（单机数据库）：

Atomicity（原子性）：
- 定义：事务中的所有操作要么全部成功，要么全部失败
- 实现：Undo Log + Redo Log
- 局限：在分布式环境下难以保证

Consistency（一致性）：
- 定义：事务执行前后，数据库从一个一致状态变为另一个一致状态
- 实现：约束检查、触发器、级联操作
- 注意：这里的Consistency是数据库一致性，非分布式一致性

Isolation（隔离性）：
- 定义：并发事务之间相互隔离
- 级别：读未提交 < 读已提交 < 可重复读 < 串行化
- 问题：脏读、不可重复读、幻读

Durability（持久性）：
- 定义：事务提交后，数据永久保存
- 实现：WAL（Write-Ahead Logging）
```

#### BASE理论

```
BASE理论（分布式系统）：

Basically Available（基本可用）：
- 系统出现故障时，允许损失部分可用性
- 例如：响应时间延长（10ms → 100ms）、功能降级（关闭推荐）

Soft state（软状态）：
- 允许系统中的数据存在中间状态
- 例如：订单状态"待支付"、库存"已冻结"

Eventually consistent（最终一致）：
- 不保证实时一致，但保证最终达到一致
- 时间边界：取决于业务容忍度（秒级到分钟级）

ACID vs BASE对比：
┌─────────────────────────────────────────┐
│  特性        ACID          BASE         │
│  ─────────────────────────────────────  │
│  一致性     强一致性       最终一致性    │
│  可用性     低             高           │
│  性能       低（锁竞争）    高          │
│  复杂度     低（数据库保证） 高（业务保证）│
│  适用场景   金融核心        互联网业务    │
└─────────────────────────────────────────┘
```

### 2. CAP定理与分布式事务

```
CAP定理（Brewer, 2000）：

分布式系统最多同时满足以下两项：
- Consistency（一致性）：所有节点在同一时间看到相同的数据
- Availability（可用性）：每个请求都能收到非错误的响应
- Partition tolerance（分区容错性）：系统在网络分区时仍能继续运行

分布式事务的CAP选择：

CP方案（强一致性）：
- 2PC/3PC：牺牲可用性保证数据一致
- 适用：金融转账、库存扣减（绝对不允许超卖）
- 代价：协调者宕机时整个系统不可用

AP方案（最终一致性）：
- TCC/Saga/本地消息表：牺牲实时一致性保证可用性
- 适用：电商订单、积分发放
- 代价：可能出现短暂不一致，需要业务补偿

微服务场景的选择：
┌─────────────────────────────────────────┐
│  业务场景          推荐方案    CAP选择   │
│  ─────────────────────────────────────  │
│  银行转账          2PC/XA      CP       │
│  电商下单          TCC/Saga    AP       │
│  积分发放          本地消息表   AP       │
│  数据同步          最大努力通知 AP       │
│  秒杀扣库存        乐观锁+Redis AP      │
└─────────────────────────────────────────┘
```

### 3. FLP不可能定理

```
FLP不可能定理（Fischer, Lynch, Paterson, 1985）：

"在异步分布式系统中，即使只有一个进程故障，
 也不存在确定性的共识算法。"

含义：
- 在网络延迟不确定的异步系统中
- 无法设计一个算法保证所有非故障节点达成一致
- 实际系统通过超时机制绕过FLP（将异步转为同步）

对分布式事务的启示：
1. 超时是分布式事务的核心机制
2. 无法保证100%一致性，只能降低不一致概率
3. 需要人工介入处理极端异常情况
```

### 4. 一致性模型谱系

```
一致性强度谱系（从强到弱）：

线性一致性（Linearizability）
  ↓
顺序一致性（Sequential Consistency）
  ↓
因果一致性（Causal Consistency）
  ↓
会话一致性（Session Consistency）
  ↓
单调读一致性（Monotonic Reads）
  ↓
最终一致性（Eventual Consistency）

分布式事务通常保证：
- 2PC/XA：接近线性一致性
- TCC：最终一致性
- Saga：最终一致性
- 本地消息表：最终一致性

业务选择原则：
- 金融核心：线性一致性（2PC + 人工对账）
- 电商交易：最终一致性（TCC/Saga）
- 日志收集：最终一致性（异步批量）
```

## 核心方案深度解析

### 1. 2PC两阶段提交

#### 执行流程

```
2PC两阶段提交：

参与者A和B分别拥有数据库DB_A和DB_B

阶段1：投票（Vote Phase）
┌─────────┐         ┌─────────┐         ┌─────────┐
│Coordinator│         │Participant│         │Participant│
│  协调者   │         │  参与者A  │         │  参与者B  │
└────┬────┘         └────┬────┘         └────┬────┘
     │                   │                   │
     │────CanCommit?────→│                   │
     │                   │ 执行本地事务       │
     │                   │ 记录Undo/Redo     │
     │                   │ 不提交            │
     │←────Yes/No────────│                   │
     │                   │                   │
     │────CanCommit?───────────────────────→│
     │                   │                   │ 执行本地事务
     │                   │                   │ 记录Undo/Redo
     │                   │                   │ 不提交
     │←────────────Yes/No───────────────────│
     │                   │                   │

阶段2：提交（Commit Phase）
     │                   │                   │
     │ 如果所有Yes:       │                   │
     │                   │                   │
     │────Commit────────→│                   │
     │                   │ 提交本地事务       │
     │                   │ 释放锁            │
     │←────Ack───────────│                   │
     │                   │                   │
     │────Commit───────────────────────────→│
     │                   │                   │ 提交本地事务
     │                   │                   │ 释放锁
     │←────────────────Ack──────────────────│
     │                   │                   │
     │ 如果有No:          │                   │
     │────Rollback──────→│                   │
     │                   │ 回滚本地事务       │
     │                   │ 释放锁            │
     │←────Ack───────────│                   │
     │────Rollback─────────────────────────→│
     │                   │                   │ 回滚本地事务
     │                   │                   │ 释放锁
```

#### XA协议实现

```java
// Java XA实现
public class XADemo {
    
    public void execute() throws Exception {
        // 获取XA数据源
        XADataSource orderDs = createXADataSource("jdbc:mysql://order-db:3306/order");
        XADataSource inventoryDs = createXADataSource("jdbc:mysql://inventory-db:3306/inventory");
        
        // 创建XA资源
        XAResource orderXaRes = orderDs.getXAConnection().getXAResource();
        XAResource inventoryXaRes = inventoryDs.getXAConnection().getXAResource();
        
        // 事务管理器
        Xid xid = new MyXid(100, new byte[]{0x01}, new byte[]{0x02});
        
        try {
            // 阶段1：准备
            orderXaRes.start(xid, XAResource.TMNOFLAGS);
            // 执行订单SQL...
            orderXaRes.end(xid, XAResource.TMSUCCESS);
            int orderRet = orderXaRes.prepare(xid);  // 投票
            
            inventoryXaRes.start(xid, XAResource.TMNOFLAGS);
            // 执行库存SQL...
            inventoryXaRes.end(xid, XAResource.TMSUCCESS);
            int inventoryRet = inventoryXaRes.prepare(xid);  // 投票
            
            // 阶段2：提交
            if (orderRet == XAResource.XA_OK && inventoryRet == XAResource.XA_OK) {
                orderXaRes.commit(xid, false);
                inventoryXaRes.commit(xid, false);
                System.out.println("Transaction committed successfully");
            } else {
                orderXaRes.rollback(xid);
                inventoryXaRes.rollback(xid);
                System.out.println("Transaction rolled back");
            }
        } catch (XAException e) {
            // 异常处理：需要人工介入或定时对账
            log.error("XA transaction failed", e);
            throw new DistributedTransactionException("Transaction failed", e);
        }
    }
}
```

#### 2PC的问题与改进

```
2PC的缺陷：

1. 同步阻塞
   - 参与者需要锁定资源等待协调者指令
   - 事务期间资源被占用，其他请求无法访问
   - 性能差：RT = 2次网络往返 + 2次数据库提交

2. 单点故障
   - 协调者宕机，参与者一直阻塞
   - 解决方案：协调者高可用（主备）+ 超时机制

3. 数据不一致
   - 协调者发送Commit后宕机
   - 部分参与者收到Commit，部分没收到
   - 解决方案：协调者记录事务日志，恢复后重发

4. 脑裂
   - 网络分区导致部分提交、部分回滚
   - 解决方案：人工介入 + 对账机制

改进方向：
- 3PC：引入超时机制和CanCommit阶段
- Percolator：基于时间戳的乐观锁
- Raft/Paxos：分布式共识替代单点协调者
```

### 2. 3PC三阶段提交

```
3PC三阶段提交：

阶段1：CanCommit（询问）
协调者询问参与者是否可以执行事务
参与者不锁定资源，只检查状态（如磁盘空间、权限）
返回Yes/No

阶段2：PreCommit（预提交）
协调者收到所有Yes后，发送PreCommit
参与者锁定资源，执行本地事务（不提交）
返回Ack

阶段3：DoCommit（提交）
协调者收到所有Ack后，发送DoCommit
参与者提交本地事务，释放锁

改进点：
- 引入超时机制
- CanCommit阶段不锁定资源，减少阻塞时间
- 协调者宕机后，参与者可通过超时继续

缺点：
- 网络开销更大（3轮通信）
- 实现复杂
- 极端情况下仍有数据不一致
- 实际生产中使用较少
```

### 3. TCC补偿事务

#### 原理与架构

```
TCC：Try - Confirm - Cancel

┌─────────────────────────────────────────┐
│           TCC事务协调器                   │
│  ┌─────────────────────────────────────┐│
│  │  事务日志：记录每个分支事务状态         ││
│  │  调度器：按顺序调用Try/Confirm/Cancel ││
│  │  超时处理：重试或触发补偿              ││
│  └─────────────────────────────────────┘│
└────────┬────────────────┬───────────────┘
         │                │
    ┌────┴────┐      ┌────┴────┐
    ↓         ↓      ↓         ↓
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
│  Try   │ │Confirm │ │  Try   │ │Confirm │
│ 预留   │ │ 确认   │ │ 预留   │ │ 确认   │
└────────┘ └────────┘ └────────┘ └────────┘
┌────────┐          ┌────────┐
│ Cancel │          │ Cancel │
│ 取消   │          │ 取消   │
└────────┘          └────────┘

订单示例：
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   Order     │     │  Payment    │     │  Inventory  │
│  Service    │     │  Service    │     │  Service    │
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │                   │                   │
Try:   │ 创建订单（待支付）  │ 冻结金额           │ 冻结库存
       │                   │                   │
       │←────成功──────────│←────成功──────────│
       │                   │                   │
Confirm:│ 更新为已支付      │ 扣减冻结金额        │ 扣减冻结库存
       │                   │                   │
       │←────成功──────────│←────成功──────────│
       │                   │                   │
Cancel:│ 删除/取消订单     │ 释放冻结金额        │ 释放冻结库存
       │                   │                   │
```

#### TCC实现

```java
// TCC服务接口
public interface TccAction {
    /**
     * Try阶段：预留资源
     */
    boolean tryCommit(BusinessActionContext context);
    
    /**
     * Confirm阶段：确认执行
     */
    boolean confirm(BusinessActionContext context);
    
    /**
     * Cancel阶段：取消回滚
     */
    boolean cancel(BusinessActionContext context);
}

// 订单TCC实现
@Component
public class OrderTccAction implements TccAction {
    
    @Autowired
    private OrderDao orderDao;
    @Autowired
    private TccLogDao tccLogDao;
    
    @Override
    @Transactional
    public boolean tryCommit(BusinessActionContext context) {
        String businessId = context.getActionContext("businessId");
        String userId = context.getActionContext("userId");
        String productId = context.getActionContext("productId");
        int quantity = Integer.parseInt(context.getActionContext("quantity"));
        
        // 1. 幂等检查
        if (tccLogDao.exists(businessId, "TRY")) {
            return true;
        }
        
        // 2. 创建待支付订单（预留）
        Order order = new Order();
        order.setBusinessId(businessId);
        order.setUserId(userId);
        order.setProductId(productId);
        order.setQuantity(quantity);
        order.setStatus(OrderStatus.PENDING);
        order.setCreateTime(LocalDateTime.now());
        orderDao.insert(order);
        
        // 3. 记录TCC日志
        tccLogDao.insert(businessId, "TRY", JsonUtils.toJson(order));
        
        return true;
    }
    
    @Override
    @Transactional
    public boolean confirm(BusinessActionContext context) {
        String businessId = context.getActionContext("businessId");
        
        // 1. 幂等检查
        if (tccLogDao.exists(businessId, "CONFIRM")) {
            return true;
        }
        
        // 2. 更新订单为已支付
        orderDao.updateStatusByBusinessId(businessId, OrderStatus.PAID);
        
        // 3. 记录TCC日志
        tccLogDao.insert(businessId, "CONFIRM", "");
        
        return true;
    }
    
    @Override
    @Transactional
    public boolean cancel(BusinessActionContext context) {
        String businessId = context.getActionContext("businessId");
        
        // 1. 幂等检查
        if (tccLogDao.exists(businessId, "CANCEL")) {
            return true;
        }
        
        // 2. 取消订单（软删除或更新状态）
        orderDao.updateStatusByBusinessId(businessId, OrderStatus.CANCELLED);
        
        // 3. 记录TCC日志
        tccLogDao.insert(businessId, "CANCEL", "");
        
        return true;
    }

        return true;
    }

    @Transactional
    public boolean confirm(BusinessActionContext context) {
        String businessId = context.getActionContext("businessId");
        String productId = context.getActionContext("productId");
        int quantity = Integer.parseInt(context.getActionContext("quantity"));
        
        if (tccLogDao.exists(businessId, "CONFIRM")) {
            return true;
        }
        
        // 将冻结库存转为实际扣减
        inventoryDao.confirmDeduct(productId, quantity);
        tccLogDao.insert(businessId, "CONFIRM", "");
        return true;
    }
    
    @Override
    @Transactional
    public boolean cancel(BusinessActionContext context) {
        String businessId = context.getActionContext("businessId");
        String productId = context.getActionContext("productId");
        int quantity = Integer.parseInt(context.getActionContext("quantity"));
        
        if (tccLogDao.exists(businessId, "CANCEL")) {
            return true;
        }
        
        // 释放冻结库存
        inventoryDao.releaseStock(productId, quantity);
        tccLogDao.insert(businessId, "CANCEL", "");
        return true;
    }

// TCC协调器
@Component
public class TccCoordinator {
    
    @Autowired
    private List<TccAction> tccActions;
    @Autowired
    private TccTransactionDao transactionDao;
    
    @Transactional
    public boolean executeTcc(String businessId, Map<String, String> context) {
        String xid = UUID.randomUUID().toString();
        
        try {
            // 1. 记录事务开始
            transactionDao.insert(xid, businessId, TccStatus.TRYING);
            
            // 2. Try阶段
            for (TccAction action : tccActions) {
                boolean success = action.tryCommit(
                    new BusinessActionContext(xid, businessId, context)
                );
                if (!success) {
                    throw new TccException("Try phase failed");
                }
            }
            
            // 3. Confirm阶段
            transactionDao.updateStatus(xid, TccStatus.CONFIRMING);
            for (TccAction action : tccActions) {
                boolean success = action.confirm(
                    new BusinessActionContext(xid, businessId, context)
                );
                if (!success) {
                    // 重试Confirm
                    retryConfirm(action, xid, businessId, context);
                }
            }
            
            transactionDao.updateStatus(xid, TccStatus.CONFIRMED);
            return true;
            
        } catch (Exception e) {
            // 4. Cancel阶段
            transactionDao.updateStatus(xid, TccStatus.CANCELLING);
            for (TccAction action : tccActions) {
                try {
                    action.cancel(new BusinessActionContext(xid, businessId, context));
                } catch (Exception cancelEx) {
                    log.error("Cancel failed, needs manual intervention", cancelEx);
                }
            }
            transactionDao.updateStatus(xid, TccStatus.CANCELLED);
            return false;
        }
    }
    
    private void retryConfirm(TccAction action, String xid, String businessId, 
                              Map<String, String> context) {
        int maxRetries = 3;
        for (int i = 0; i < maxRetries; i++) {
            try {
                Thread.sleep(1000 * (i + 1));  // 指数退避
                boolean success = action.confirm(
                    new BusinessActionContext(xid, businessId, context)
                );
                if (success) return;
            } catch (Exception e) {
                log.error("Confirm retry {} failed", i + 1, e);
            }
        }
        throw new TccException("Confirm failed after retries");
    }
}
```

### 4. Saga长事务

#### 原理与两种模式

```
Saga模式：

将一个长事务拆分为多个本地事务，
每个本地事务有对应的补偿操作。

执行成功：
T1 → T2 → T3 → T4 → 完成

执行失败（T3失败）：
T1 → T2 → T3(失败) → C2 → C1 → 回滚完成

两种实现模式：

1. 编排式（Choreography）：事件驱动
┌─────────┐     ┌─────────┐     ┌─────────┐
│ Order   │────→│ Inventory│────→│ Payment │
│ Service │ Event│ Service │ Event│ Service │
└─────────┘     └─────────┘     └─────────┘
   ↑                                    │
   └──────────── Event ←────────────────┘

特点：
- 服务间通过消息事件通信
- 去中心化，无单点故障
- 但事务状态分散，难以追踪

2. 协调式（Orchestration）：中心协调器
┌─────────────────────────────────────────┐
│           Saga协调器                     │
│  ┌─────────────────────────────────────┐│
│  │  状态机：定义事务流程和补偿顺序        ││
│  │  调度器：按顺序执行T1→T2→T3          ││
│  │  补偿器：失败时执行C2→C1            ││
│  └─────────────────────────────────────┘│
└────────┬────────────────┬───────────────┘
         │                │
    ┌────┴────┐      ┌────┴────┐
    ↓         ↓      ↓         ↓
┌────────┐ ┌────────┐ ┌────────┐
│   T1   │ │   T2   │ │   T3   │
│ Order  │ │Inventory│ │Payment │
└────────┘ └────────┘ └────────┘

特点：
- 中心化管理事务状态
- 容易追踪和监控
- 存在单点故障风险（协调器需高可用）
```

### 5. 本地消息表

#### 原理与架构

```
本地消息表（最终一致性）：

┌─────────────┐     ┌─────────────┐
│  Business   │     │   Message   │
│    DB       │     │    Table    │
│             │     │             │
│ 订单表       │     │ 消息ID       │
│ 库存表       │     │ 业务类型     │
│ 用户表       │     │ 业务ID       │
└──────┬──────┘     │ 状态（待发送）│
       │            │ 内容(JSON)   │
       │            │ 重试次数     │
       │            │ 创建时间     │
       │            └──────┬──────┘
       │                   │
       │  同一个本地事务     │
       │                   │
       ↓                   ↓

│              ↓                      │

│              ↓                      │

1. 业务操作和消息记录在同一个本地事务中
2. 定时任务补偿，避免消息丢失
3. 消费者幂等，防止重复消费
4. 消息表需要索引优化（按状态+时间查询）
```

```java
@Component
public class MessageSenderJob {
    
    @Autowired
    private LocalMessageDao messageDao;
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    
    @Scheduled(fixedRate = 5000)  // 每5秒执行
    public void sendPendingMessages() {
        // 查询待发送消息（创建时间超过30秒的，避免事务未提交）
        List<LocalMessage> pendingMessages = messageDao
            .selectByStatusAndCreateTimeBefore(
                0,  // 待发送
                LocalDateTime.now().minusSeconds(30)
            );
        
        for (LocalMessage message : pendingMessages) {
            try {
                rocketMQTemplate.asyncSend(
                    message.getTopic(),
                    message.getBody(),
                    new SendCallback() {
                        @Override
                        public void onSuccess(SendResult sendResult) {
                            messageDao.updateStatus(message.getId(), 1);  // 已发送
                            log.info("Message sent successfully: {}", message.getMsgId());
                        }
                        @Override
                        public void onException(Throwable e) {
                            log.error("Failed to send message: {}", message.getMsgId(), e);
                            // 增加重试次数
                            messageDao.increaseRetryCount(message.getId());
                        }
                    }
                );
            } catch (Exception e) {
                log.error("Message send exception: {}", message.getMsgId(), e);
                messageDao.increaseRetryCount(message.getId());

        }
        
        // 处理发送失败的消息（重试次数超过3次，告警人工处理）
        List<LocalMessage> failedMessages = messageDao
            .selectByStatusAndRetryCountGreaterThan(3, 3);
        
        for (LocalMessage message : failedMessages) {
            log.error("Message failed after retries, needs manual handling: {}", 
                message.getMsgId());
            // 发送告警通知
            alertService.sendAlert("Message failed: " + message.getMsgId());
        }
    }
```

### 6. 最大努力通知

```
最大努力通知：

- 最大努力通知：不保证发出，靠接收方主动查询
```

```java
@Service
public class BestEffortNotifyService {

    private NotifyRecordDao notifyRecordDao;
    @Autowired
    private RestTemplate restTemplate;

     * 发送通知
     */

        NotifyRecord record = new NotifyRecord();
        record.setNotifyUrl(url);
        record.setNotifyBody(JsonUtils.toJson(params));
        record.setStatus(NotifyStatus.PENDING);
        record.setRetryCount(0);
        notifyRecordDao.insert(record);

        asyncSend(record);
    }
    
    /**
     * 定时任务重试
     */
    @Scheduled(fixedRate = 60000)  // 每分钟
    public void retryPendingNotifies() {
        List<NotifyRecord> pendingRecords = notifyRecordDao
            .selectByStatusAndRetryCountLessThan(
                NotifyStatus.PENDING, 
                5  // 最多重试5次
            );
        
        for (NotifyRecord record : pendingRecords) {
            asyncSend(record);
        }
    }
    
    private void asyncSend(NotifyRecord record) {
        try {
            ResponseEntity<String> response = restTemplate.postForEntity(
                record.getNotifyUrl(),
                record.getNotifyBody(),
                String.class
            );
            
            if (response.getStatusCode().is2xxSuccessful()) {
                notifyRecordDao.updateStatus(record.getId(), NotifyStatus.SUCCESS);
            } else {
                notifyRecordDao.increaseRetryCount(record.getId());
            }
        } catch (Exception e) {
            log.error("Notify failed: {}", record.getId(), e);
            notifyRecordDao.increaseRetryCount(record.getId());
        }
    }
}
```

### 7. Seata AT模式

```
Seata AT模式（Auto Transaction）：

┌─────────────────────────────────────────┐
│           Seata Server                   │
│  ┌─────────────────────────────────────┐│
│  │  TC (Transaction Coordinator)       ││
│  │  全局事务协调器                       ││
│  │  维护全局事务和分支事务状态            ││
│  └─────────────────────────────────────┘│
└────────┬────────────────┬───────────────┘
         │                │
    ┌────┴────┐      ┌────┴────┐
    ↓         ↓      ↓         ↓
┌────────┐ ┌────────┐ ┌────────┐
│  RM    │ │  RM    │ │  RM    │
│(Order) │ │(Payment)│ │(Inventory)│
└────────┘ └────────┘ └────────┘

AT模式原理：
1. 一阶段：业务SQL直接提交，Seata解析SQL生成Undo Log
2. 二阶段：
   - 成功：异步删除Undo Log
   - 失败：根据Undo Log回滚

优势：
- 对业务零侵入
- 自动解析SQL生成反向SQL
- 性能较好（一阶段直接提交）

劣势：
- 需要支持SQL解析的数据库
- 隔离性依赖全局锁
- 不适合复杂业务场景
```

```java
@Component
public class InventoryTccActionImpl implements InventoryTccAction {
    
    @Autowired
    private InventoryDao inventoryDao;
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    @Override
    @Transactional
    public boolean tryDeduct(BusinessActionContext context) {
        String productId = context.getActionContext("productId");
        int quantity = Integer.parseInt(context.getActionContext("quantity"));
        
        // 1. Redis预扣减（防止超卖）
        String stockKey = "stock:" + productId;
        Long remain = redisTemplate.opsForValue().decrement(stockKey, quantity);
        if (remain == null || remain < 0) {
            // 回滚Redis
            redisTemplate.opsForValue().increment(stockKey, quantity);
            throw new BizException("库存不足");
        }
        
        // 2. 数据库冻结库存
        int updated = inventoryDao.freezeStock(productId, quantity);
        if (updated == 0) {
            // 回滚Redis
            redisTemplate.opsForValue().increment(stockKey, quantity);
            throw new BizException("库存冻结失败");
        }
        
        return true;
    }
    
    @Override
    @Transactional
    public boolean confirmDeduct(BusinessActionContext context) {
        String productId = context.getActionContext("productId");
        int quantity = Integer.parseInt(context.getActionContext("quantity"));
        
        // 将冻结库存转为实际扣减
        inventoryDao.confirmDeduct(productId, quantity);
        return true;
    }
    
    @Override
    @Transactional
    public boolean cancelDeduct(BusinessActionContext context) {
        String productId = context.getActionContext("productId");
        int quantity = Integer.parseInt(context.getActionContext("quantity"));
        
        // 释放冻结库存，回滚Redis
        inventoryDao.releaseStock(productId, quantity);
        redisTemplate.opsForValue().increment("stock:" + productId, quantity);
        return true;
    }
}

@Service
public class OrderCreationService {
    
    @Autowired
    private OrderTccAction orderTccAction;
    @Autowired
    private InventoryTccAction inventoryTccAction;
    @Autowired
    private PaymentTccAction paymentTccAction;
    @Autowired
    private TransactionLogDao transactionLogDao;
    
    @Transactional
    public OrderCreationResult createOrder(CreateOrderRequest request) {
        String businessId = generateBusinessId();
        String xid = UUID.randomUUID().toString();
        
        // 记录事务开始
        transactionLogDao.insert(xid, businessId, TransactionStatus.TRYING);
        
        Map<String, String> context = new HashMap<>();
        context.put("businessId", businessId);
        context.put("userId", request.getUserId());
        context.put("productId", request.getProductId());
        context.put("quantity", String.valueOf(request.getQuantity()));
        context.put("amount", request.getAmount().toString());
        
        try {
            // 1. Try阶段
            boolean orderTry = orderTccAction.tryCreateOrder(
                new BusinessActionContext(xid, businessId, context)
            );
            if (!orderTry) throw new TccException("Order try failed");
            
            boolean inventoryTry = inventoryTccAction.tryDeduct(
                new BusinessActionContext(xid, businessId, context)
            );
            if (!inventoryTry) throw new TccException("Inventory try failed");
            
            boolean paymentTry = paymentTccAction.tryFreeze(
                new BusinessActionContext(xid, businessId, context)
            );
            if (!paymentTry) throw new TccException("Payment try failed");
            
            // 2. Confirm阶段
            transactionLogDao.updateStatus(xid, TransactionStatus.CONFIRMING);
            
            orderTccAction.confirmCreateOrder(
                new BusinessActionContext(xid, businessId, context)
            );
            inventoryTccAction.confirmDeduct(
                new BusinessActionContext(xid, businessId, context)
            );
            paymentTccAction.confirmFreeze(
                new BusinessActionContext(xid, businessId, context)
            );
            
            transactionLogDao.updateStatus(xid, TransactionStatus.CONFIRMED);
            
            return OrderCreationResult.success(businessId);
            
        } catch (Exception e) {
            log.error("Order creation failed, rolling back", e);
            
            // 3. Cancel阶段
            transactionLogDao.updateStatus(xid, TransactionStatus.CANCELLING);
            
            try {
                paymentTccAction.cancelFreeze(
                    new BusinessActionContext(xid, businessId, context)
                );
            } catch (Exception ex) {
                log.error("Payment cancel failed", ex);
            }
            
            try {
                inventoryTccAction.cancelDeduct(
                    new BusinessActionContext(xid, businessId, context)
                );
            } catch (Exception ex) {
                log.error("Inventory cancel failed", ex);
            }
            
            try {
                orderTccAction.cancelCreateOrder(
                    new BusinessActionContext(xid, businessId, context)
                );
            } catch (Exception ex) {
                log.error("Order cancel failed", ex);
            }
            
            transactionLogDao.updateStatus(xid, TransactionStatus.CANCELLED);
            
            return OrderCreationResult.fail(e.getMessage());
        }
    }
}
```

```java
// 定时对账任务
@Component
public class ReconciliationJob {
    
    @Autowired
    private OrderDao orderDao;
    @Autowired
    private InventoryDao inventoryDao;
    @Autowired
    private PaymentDao paymentDao;
    @Autowired
    private AlertService alertService;
    
    /**
     * 每日对账
     */
    @Scheduled(cron = "0 0 2 * * ?")  // 每天凌晨2点
    public void dailyReconciliation() {
        LocalDate yesterday = LocalDate.now().minusDays(1);
        
        // 1. 查询昨日订单
        List<Order> orders = orderDao.selectByDate(yesterday);
        
        for (Order order : orders) {
            // 2. 检查库存记录
            InventoryRecord inventoryRecord = inventoryDao
                .selectByBusinessId(order.getBusinessId());
            
            // 3. 检查支付记录
            PaymentRecord paymentRecord = paymentDao
                .selectByBusinessId(order.getBusinessId());
            
            // 4. 一致性检查
            boolean consistent = checkConsistency(order, inventoryRecord, paymentRecord);
            
            if (!consistent) {
                log.error("Inconsistency found: {}", order.getBusinessId());
                alertService.sendAlert("数据不一致: " + order.getBusinessId());
                
                // 自动修复（根据策略）
                autoFix(order, inventoryRecord, paymentRecord);
            }
        }
    }
    
    private boolean checkConsistency(Order order, 
                                     InventoryRecord inventory, 
                                     PaymentRecord payment) {
        // 检查逻辑：
        // 1. 已支付订单必须有库存扣减和支付记录
        // 2. 已取消订单必须没有库存扣减和支付记录
        // 3. 待支付订单可以有库存冻结
        
        if (order.getStatus() == OrderStatus.PAID) {
            return inventory != null && inventory.getStatus() == InventoryStatus.DEDUCTED
                && payment != null && payment.getStatus() == PaymentStatus.PAID;
        } else if (order.getStatus() == OrderStatus.CANCELLED) {
            return (inventory == null || inventory.getStatus() == InventoryStatus.RELEASED)
                && (payment == null || payment.getStatus() == PaymentStatus.CANCELLED);
        }
        
        return true;
    }
    
    private void autoFix(Order order, InventoryRecord inventory, PaymentRecord payment) {
        // 自动修复策略（谨慎使用）
        if (order.getStatus() == OrderStatus.PAID) {
            if (inventory == null || inventory.getStatus() != InventoryStatus.DEDUCTED) {
                // 补扣库存
                inventoryDao.deduct(order.getProductId(), order.getQuantity());
            }
            if (payment == null || payment.getStatus() != PaymentStatus.PAID) {
                // 补扣余额（需人工确认）
                alertService.sendAlert("需人工补扣余额: " + order.getBusinessId());
            }
        }
    }
}
```

## 性能分析与优化策略

### 1. 各方案性能对比

```
┌─────────────────────────────────────────┐
│        分布式事务性能对比（本地测试）       │
│                                         │
│  方案        吞吐量(TPS)    延迟(P99)     │
│  ─────────────────────────────────────  │
│  本地事务     10000        5ms          │
│  2PC/XA      500          200ms         │

│                                         │

└─────────────────────────────────────────┘

性能影响因素：
1. 网络往返次数
   - 2PC: 2次往返（Prepare + Commit）
   - TCC: 2次往返（Try + Confirm）
   - Saga: 1次往返（每个步骤）
   - 本地消息表: 0次（异步）

2. 资源锁定时间
   - 2PC: 整个事务期间锁定
   - TCC: Try阶段预留，Confirm立即释放
   - Saga: 一阶段提交，无锁定

3. 协调者开销
   - 2PC/TCC: 需要协调者维护状态
   - Saga: 协调式需要状态机
   - 本地消息表: 无协调者
```

### 2. 2PC性能优化

```
2PC优化策略：

1. 异步提交
   - 协调者记录日志后异步发送Commit
   - 参与者收到Commit后异步执行
   - 风险：极端情况下可能不一致

2. 批量提交
   - 多个事务合并提交
   - 减少网络往返次数
   - 适用于高并发场景

3. 协调者高可用
   - 主备部署，故障自动切换
   - 日志同步到备机
   - 避免单点故障

4. 超时优化
   - 合理设置超时时间（根据网络延迟）
   - 超时后自动回滚或提交
   - 根据业务特点选择（偏向回滚或提交）
```

### 3. TCC性能优化

```
TCC优化策略：

1. 异步Confirm
   - Try成功后立即返回用户
   - Confirm异步执行
   - 提升用户体验

2. 批量Confirm
   - 多个TCC事务合并Confirm
   - 减少数据库操作次数

3. 缓存优化
```

## 常见陷阱与最佳实践

### 陷阱1：滥用强一致性方案

```
❌ 错误做法：
电商下单使用2PC/XA，追求强一致性
→ 性能急剧下降（同步阻塞，锁定资源）
→ 库存服务短暂不可用导致整个下单链路不可用
→ 峰值QPS从10000降到500

✅ 最佳实践：
1. 评估业务是否真的需要强一致性
   - 金融转账：必须强一致
   - 电商下单：最终一致即可
   
2. 99%场景最终一致性即可
   - 下单后发MQ扣库存
   - 库存不足时异步通知用户退款
   
3. 金融转账等极少数场景才用2PC
   - 且配合人工对账
   
4. 优先考虑异步方案
   - 本地消息表
   - MQ事务消息
```

### 陷阱2：TCC幂等性保障缺失

```java
❌ 风险场景：
Try阶段网络超时，实际服务端已执行
客户端重试Try → 重复冻结金额/库存

✅ 最佳实践：
1. TCC三阶段都必须保证幂等
2. 使用幂等键（如businessId）去重
3. 记录事务日志（状态机：INIT→TRYING→CONFIRMED/CANCELLED）
4. Seata框架内置幂等控制，建议优先使用框架

// 幂等控制示例
public boolean tryFreeze(String businessId, BigDecimal amount) {
    // 1. 先查是否已处理（使用唯一索引）
    if (tccLogDao.exists(businessId, "TRY")) {
        return true; // 已处理，直接返回
    }
    
    // 2. 执行业务逻辑
    // ...
    
    // 3. 记录日志（INSERT IGNORE或UPSERT）
    try {
        tccLogDao.insert(businessId, "TRY", amount);
    } catch (DuplicateKeyException e) {
        // 并发插入，忽略
        return true;
    }
    
    return true;
}
```

### 陷阱3：Saga补偿顺序错误

```
❌ 错误顺序：
正向：T1(扣款) → T2(扣库存) → T3(创建订单)
补偿：C1(退款) → C3(删订单) → C2(回库存)
→ 先退款但库存未回，用户可再次购买但无库存

✅ 最佳实践：
1. 补偿必须按正向的逆序执行
2. 正确顺序：C3 → C2 → C1
3. 使用协调式Saga（Orchestration），中心控制器管理顺序
4. 补偿也必须幂等，支持重试

// 协调式Saga补偿顺序
public void compensateSaga(String sagaId) {
    // 查询已执行的步骤（按执行顺序）
    List<SagaStep> executedSteps = sagaLogDao
        .selectBySagaIdOrderByExecuteTimeDesc(sagaId);
    
    // 按逆序补偿
    for (SagaStep step : executedSteps) {
        try {
            step.getCompensateAction().execute();
        } catch (Exception e) {
            log.error("Compensation failed: {}", step.getStepName(), e);
            // 记录失败，人工介入
            alertService.sendAlert("Compensation failed: " + sagaId);
        }
    }
}
```

### 陷阱4：忽略空回滚与防悬挂

```
❌ 问题场景：

空回滚（Empty Rollback）：
- Try阶段未执行（如网络超时）
- Cancel阶段执行了
- 结果：没有预留资源，但执行了释放操作

悬挂（Hang）：
- Try阶段超时，实际后到达
- Cancel先执行，Try后到达
- 结果：Try执行后没有Confirm/Cancel，资源一直预留

✅ 解决方案：

1. 空回滚处理
- Cancel时检查是否已Try
- 如果未Try，记录空回滚日志，直接返回成功

2. 防悬挂处理
- Try时检查是否已Cancel
- 如果已Cancel，拒绝Try，记录异常日志

// 实现

    String businessId = context.getActionContext("businessId");
    
    // 检查是否已Try
    if (!tccLogDao.exists(businessId, "TRY")) {
        // 空回滚，记录日志
        tccLogDao.insert(businessId, "EMPTY_ROLLBACK", "");
        return true;
    }
    
    // 正常Cancel逻辑
    // ...
}

public boolean tryCommit(BusinessActionContext context) {
    String businessId = context.getActionContext("businessId");
    
    // 检查是否已Cancel（防悬挂）
    if (tccLogDao.exists(businessId, "CANCEL") || 
        tccLogDao.exists(businessId, "EMPTY_ROLLBACK")) {
        log.warn("Try after cancel detected: {}", businessId);
        return false; // 拒绝Try
    }
    
    // 正常Try逻辑
    // ...
}
```

### 最佳实践总结

```
分布式事务最佳实践清单：

1. 设计原则
   □ 根据业务场景选择合适的一致性级别
   □ 优先使用最终一致性，避免滥用2PC
   □ 设计补偿机制，假设事务可能失败
   □ 保证幂等性，所有操作支持重试

2. TCC实践
   □ 三阶段都必须幂等
   □ 处理空回滚和防悬挂
   □ Try阶段预留资源，立即释放
   □ Confirm/Cancel支持异步和重试

3. Saga实践
   □ 补偿按正向逆序执行
```

## 面试题与参考答案

**Q1：2PC和3PC的区别是什么？3PC解决了什么问题？**

> **区别**：
> - **2PC**：投票阶段+提交阶段，协调者宕机后参与者一直阻塞
> - **3PC**：CanCommit（询问）+ PreCommit（预提交）+ DoCommit（提交）
>
> **3PC改进**：
> 1. 引入超时机制，协调者宕机后参与者可通过超时继续
> 2. CanCommit阶段不锁定资源，减少阻塞时间
> 3. 但网络开销更大，实现复杂，实际生产中使用较少

**Q2：TCC和2PC有什么区别？**

> | 维度 | 2PC/XA | TCC |
> |------|--------|-----|
> | 一致性 | 强一致 | 最终一致 |
> | 性能 | 低（同步阻塞） | 高（异步） |
> | 资源锁定 | 整个事务期间锁定 | Try阶段预留，立即释放 |
> | 业务侵入 | 低（数据库层） | 高（需实现3个接口） |
> | 回滚 | 数据库自动回滚 | 业务实现Cancel逻辑 |
>
> TCC性能更好，但业务侵入大，需要业务方实现Try/Confirm/Cancel。

**Q3：Saga模式和TCC模式如何选择？**

> - **Saga**：适用于长事务、业务流程长的场景（如旅游预订：订机票→订酒店→租车）
>   - 优点：一阶段提交本地事务，性能高
>   - 缺点：没有隔离性，可能出现更新丢失、脏读
>
> - **TCC**：适用于短事务、性能要求高的场景（如电商下单）
>   - 优点：有预留资源机制，隔离性较好
>   - 缺点：业务侵入大，需实现3个方法
>
> 建议：业务流程长选Saga，性能要求高选TCC。

**Q4：本地消息表如何保证最终一致性？**

> **原理**：
> 1. 业务操作和消息记录在同一个本地事务中
> 2. 定时任务扫描待发送消息
> 3. 发送消息到MQ，成功则更新状态为已发送
> 4. 消费者处理消息并执行业务
> 5. 消费失败可重试，保证最终一致
>
> **关键点**：
> - 消息表和业务表在同一个数据库，保证原子性
> - 定时任务补偿，避免消息丢失
> - 消费者幂等，防止重复消费

**Q5：什么是最大努力通知？适用于什么场景？**

> **最大努力通知**：业务方执行本地事务后，通过MQ通知对方，对方可多次接收和处理。
>
> 特点：
> - 单向通知，不保证对方一定收到
> - 接收方可主动查询对账
> - 实现简单，性能高
>
> **适用场景**：对账场景、支付回调、短信通知等容忍延迟的场景。不适合强一致性要求场景。

**Q6：分布式事务方案选型？**

> | 场景 | 推荐方案 | 原因 |
> |------|---------|------|
> | 金融转账 | 2PC/XA | 强一致性要求 |
> | 电商下单 | TCC或Saga | 高性能，可补偿 |
> | 订单完成后发短信 | 本地消息表 | 异步，简单 |
> | 数据同步 | 最大努力通知 | 简单，容忍延迟 |
> | 秒杀扣库存 | 乐观锁+Redis | 高并发，最终一致 |

**Q7：什么是Seata的AT模式？**

> **AT模式（Auto Transaction）**：
> - 一阶段：业务SQL直接提交，Seata解析SQL生成Undo Log
> - 二阶段成功：异步删除Undo Log
> - 二阶段失败：根据Undo Log回滚
>
> 优势：对业务零侵入，自动解析SQL
> 劣势：需要SQL解析支持，隔离性依赖全局锁

**Q8：TCC如何处理幂等性？**

> 1. **唯一键去重**：使用businessId作为幂等键
> 2. **状态机控制**：INIT→TRYING→CONFIRMED/CANCELLED
> 3. **数据库唯一索引**：防止并发插入重复记录
> 4. **空回滚处理**：Cancel时检查是否已Try
> 5. **防悬挂**：Try时检查是否已Cancel

**Q9：分布式事务的性能优化手段？**

> 1. **异步化**：Try成功后立即返回，Confirm异步执行
> 2. **批量处理**：批量Confirm，减少数据库操作
> 3. **缓存优化**：Redis预扣减，减少数据库压力
> 4. **连接池优化**：合理设置连接池大小
> 5. **网络优化**：长连接、连接池复用
> 6. **监控优化**：及时发现慢事务，优化热点

**Q10：如何处理分布式事务的异常情况？**

> 1. **超时处理**：设置合理超时，超时后回滚或重试
> 2. **补偿机制**：设计完善的补偿逻辑
> 3. **定时对账**：每日对账，发现不一致
> 4. **人工介入**：复杂差异人工处理
> 5. **监控告警**：实时告警异常事务
> 6. **演练**：定期演练故障恢复

## 引言：垃圾回收的本质

垃圾回收（Garbage Collection, GC）不是"自动清理内存"的简单工具，而是一门**管理堆内存对象生命周期的系统工程**。

核心认知：

```
GC的本质：自动识别并回收不再被程序使用的内存对象

内存管理的三层模型：
┌─────────────────────────────────────────┐
│  应用层：业务对象创建与引用关系           │
│     ↓                                   │
│  GC层：可达性分析 + 回收算法              │
│     ↓                                   │
│  操作系统层：虚拟内存分配与物理内存映射    │
└─────────────────────────────────────────┘

GC的设计挑战：
- 识别精度：不能误杀（回收存活对象）
- 回收效率：快速回收，减少STW（Stop-The-World）
- 内存碎片：避免碎片化导致大对象分配失败
- 吞吐量：GC耗时不能占用太多CPU时间
```

**关键洞察**：GC算法的选择不是"哪个最好"，而是**在延迟、吞吐量、内存占用之间做权衡**。

## 理论基础：为什么需要垃圾回收

### 1. 手动内存管理的困境

#### C/C++时代的内存问题

```c
// C语言手动管理内存的典型问题
void process_data() {
    char* buffer = (char*)malloc(1024);
    
    // 问题1：忘记释放
    if (some_error()) {
        return;  // buffer泄漏！
    }
    
    // 问题2：重复释放
    free(buffer);
    free(buffer);  // 双重释放，导致堆损坏
    
    // 问题3：使用已释放内存
    strcpy(buffer, "data");  // use-after-free
}
```

**统计**：据微软研究，70%的安全漏洞与内存管理错误有关。

```
自动内存管理 vs 手动内存管理：

┌──────────────────┬──────────────────┬──────────────────┐
```

### 2. 对象存活的理论基础

#### 引用计数法的数学原理

```
引用计数法的基本假设：

对象O的引用计数：ref_count(O)

初始状态：ref_count(O) = 0
对象被引用：ref_count(O)++
引用被释放：ref_count(O)--
回收条件：ref_count(O) == 0

数学表达：
回收对象集合 R = { O | ref_count(O) = 0 }

致命缺陷 - 循环引用：
对象A → 对象B （A持有B的引用）
对象B → 对象A （B持有A的引用）

ref_count(A) = 1（被B引用）
ref_count(B) = 1（被A引用）

即使外部没有任何引用指向A或B：
ref_count(A) = 1 ≠ 0
ref_count(B) = 1 ≠ 0

→ A和B都无法被回收，造成内存泄漏
```

**Python也使用引用计数**，但通过"循环垃圾回收器"（cycle detector）解决循环引用问题。

#### 可达性分析算法的图论基础

```
可达性分析的数学模型：

将内存中的对象引用关系建模为有向图：
G = (V, E)

其中：
- V：所有对象的集合（顶点）
- E：引用关系（有向边），若对象A引用对象B，则存在边 A → B

GC Roots集合：R = { r₁, r₂, ..., rₙ }

可达对象集合：Reachable = { v ∈ V | ∃r ∈ R, 存在路径 r →* v }

不可达对象（垃圾）：Garbage = V - Reachable

关键性质：
1. 任何被GC Roots直接或间接引用的对象都是存活的
2. 不存在从GC Roots到垃圾对象的路径
3. 循环引用问题天然解决：循环中的对象如果没有外部引用，都是不可达的
```

**GC Roots的完整列表**：

```
GC Roots来源详解：

1. 虚拟机栈（栈帧中的本地变量表）
   ┌─────────────────┐
   │  栈帧1          │
   │  - localVar1 ────┼──→ Object A
   │  - localVar2     │
   ├─────────────────┤
   │  栈帧2          │
   │  - localVar3 ────┼──→ Object B
   └─────────────────┘

2. 方法区中类静态属性引用的对象
   Class MyClass {
       static Object staticRef = new Object();  // GC Root
   }

3. 方法区中常量引用的对象
   Class MyClass {
       static final String CONST = "value";  // 常量池引用
   }

4. 本地方法栈中JNI（Native方法）引用的对象
   native void nativeMethod();
   // C/C++代码中创建的全局引用

5. 所有被同步锁（synchronized关键字）持有的对象
   synchronized(obj) {
       // obj是GC Root
   }

6. JVM内部的特殊引用
   - 基本数据类型对应的Class对象（如Integer.TYPE）
   - 系统类加载器
   - 异常对象（如NullPointerException实例）
```

## 来龙去脉：垃圾回收算法的发展史

### 第一阶段：手动管理时代（1950s-1960s）

```
早期编程语言（Fortran、LISP前身）：

- 无自动内存管理
- 程序员手动分配和释放内存
- LISP（1958）首次提出垃圾回收概念
- John McCarthy发明了标记-清除算法
```

### 第二阶段：引用计数时代（1960s-1970s）

```
引用计数法的兴起：

1960年：George E. Collins提出引用计数
- 原理简单，实现容易
- 实时回收，延迟低
- 但循环引用问题始终未解决

典型应用：
- Smalltalk（早期版本）
- Perl
- Python（配合循环检测器）
```

### 第三阶段：追踪式GC时代（1970s-1990s）

```
追踪式GC的重大突破：

1970年：标记-清除算法（Mark-Sweep）
- 解决循环引用问题
- 但产生内存碎片

1978年：复制算法（Copying）
- Cheney提出半区复制
- 无碎片，但内存利用率50%

1984年：标记-整理算法（Mark-Compact）
- 解决了标记-清除的碎片问题
- 但需要移动对象，STW时间长

1989年：分代收集（Generational GC）
- David Ungar提出分代假说
- 年轻代 + 老年代的不同策略
- 现代GC的理论基础
```

### 第四阶段：JVM垃圾收集器演进（1990s-2010s）

```
Java垃圾收集器发展时间线：

1996年：JDK 1.0
- Serial收集器（单线程）
- 标记-复制（年轻代）+ 标记-整理（老年代）

2002年：JDK 1.4.2
- Parallel Scavenge / Parallel Old（吞吐量优先）
- 多线程并行收集

2004年：JDK 5.0
- CMS（Concurrent Mark Sweep）收集器
- 首次实现并发低延迟收集
- 标记-清除算法（老年代）

2014年：JDK 8u40
- G1（Garbage First）收集器成熟
- 区域化分代收集
- 可预测的停顿时间模型

2017年：JDK 9
- G1成为默认收集器
- CMS被标记为废弃
```

### 第五阶段：低延迟GC时代（2010s-2024）

```
现代低延迟垃圾收集器：

2018年：JDK 11
- ZGC（The Z Garbage Collector）
- 目标：<10ms停顿，TB级堆
- 着色指针 + 读屏障
- 并发整理

2018年：JDK 11
- Shenandoah（Red Hat开源）
- 与ZGC类似的目标
-  Brooks指针 + 转发指针

2021年：JDK 17
- ZGC正式支持生产环境
- Shenandoah成熟

2024年：JDK 21
- Generational ZGC（分代ZGC）
- 性能大幅提升
- 成为新一代低延迟GC标准
```

### 第六阶段：2026年现状

```
当前GC技术的工业标准：

1. 默认选择：G1 GC
   - 适用于大多数应用
   - 平衡吞吐量和延迟

2. 低延迟场景：ZGC / Shenandoah
   - 金融交易、游戏服务器
   - 延迟敏感型微服务

3. 大数据场景：Parallel GC
   - 批处理、数据分析
   - 追求最大吞吐量

4. 容器化时代的新挑战：
   - 内存限制下的GC调优
   - 快速启动（GraalVM Native Image）
   - Serverless场景下的GC策略
```

## 核心算法深度解析

### 1. 标记-清除算法（Mark-Sweep）

#### 算法原理的数学表达

```
标记-清除算法的形式化描述：

输入：堆内存对象集合 V，GC Roots集合 R
输出：回收后的堆内存

阶段1 - 标记（Mark）：
  Reachable = ∅
  Queue = R
  while Queue ≠ ∅:
      obj = Queue.dequeue()
      if obj ∉ Reachable:
          Reachable.add(obj)
          for ref in obj.references:
              Queue.enqueue(ref)
  
  // Reachable现在包含所有可达对象

阶段2 - 清除（Sweep）：
  for obj in V:
      if obj ∉ Reachable:
          free(obj.memory)
          obj.mark = DEAD

时间复杂度：O(V + E)
- V：对象数量
- E：引用关系数量
```

#### 执行过程图解

```
标记-清除算法完整执行流程：

初始状态：
┌─────────────────────────────────────────────────────┐
│ 对象A │ 对象B │ 对象C │ 对象D │ 对象E │ 对象F │ 对象G │
│ 存活  │ 存活  │ 死亡  │ 存活  │ 死亡  │ 存活  │ 死亡  │
└─────────────────────────────────────────────────────┘
        ↑                    ↑              ↑
      Root引用            Root引用       Root引用

阶段1：标记（从GC Roots开始DFS/BFS遍历）
┌─────────────────────────────────────────────────────┐
│ [存活]│ [存活]│ [死亡]│ [存活]│ [死亡]│ [存活]│ [死亡]│
│   ✓   │   ✓   │       │   ✓   │       │   ✓   │       │
│ 标记  │ 标记  │       │ 标记  │       │ 标记  │       │
└─────────────────────────────────────────────────────┘
   ↑              ↑                             ↑
 RootA ──────→ RootB                         RootC

阶段2：清除（回收未标记对象）
┌─────────────────────────────────────────────────────┐
│ [存活]│ [存活]│ [空闲]│ [存活]│ [空闲]│ [存活]│ [空闲]│
│   ✓   │   ✓   │       │   ✓   │       │   ✓   │       │
└─────────────────────────────────────────────────────┘
              ↑              ↑              ↑
            碎片           碎片           碎片

最终状态：
┌─────────────────────────────────────────────────────┐
│ 对象A │ 对象B │ 碎片1 │ 对象D │ 碎片2 │ 对象F │ 碎片3 │
│       │       │  2KB  │       │  2KB  │       │  2KB  │
└─────────────────────────────────────────────────────┘

问题：需要分配4KB连续内存时，虽然总空闲6KB，但分配失败！
```

#### Java实现模拟

```java
/**
 * 标记-清除算法的简化模拟
 * 注意：这仅用于理解原理，真实JVM实现复杂得多
 */
public class MarkSweepSimulator {
    
    // 模拟堆内存
    static class HeapObject {
        String name;
        boolean marked = false;
        List<HeapObject> references = new ArrayList<>();
        int size;  // 对象大小（字节）
        
        HeapObject(String name, int size) {
            this.name = name;
            this.size = size;
        }
        
        void addReference(HeapObject obj) {
            references.add(obj);
        }
        
        @Override
        public String toString() {
            return name + "(" + size + "B, " + (marked ? "存活" : "死亡") + ")";
        }
    }
    
    static class Heap {
        List<HeapObject> objects = new ArrayList<>();
        List<HeapObject> gcRoots = new ArrayList<>();
        int totalSize = 1024 * 1024;  // 1MB
        int usedSize = 0;
        
        void addObject(HeapObject obj) {
            objects.add(obj);
            usedSize += obj.size;
        }
        
        void addGCRoot(HeapObject obj) {
            gcRoots.add(obj);
            if (!objects.contains(obj)) {
                objects.add(obj);
            }
        }
        
        // 标记阶段
        void mark() {
            System.out.println("=== 标记阶段 ===");
            Set<HeapObject> marked = new HashSet<>();
            Queue<HeapObject> queue = new LinkedList<>(gcRoots);
            
            while (!queue.isEmpty()) {
                HeapObject obj = queue.poll();
                if (!marked.contains(obj)) {
                    marked.add(obj);
                    obj.marked = true;
                    System.out.println("标记: " + obj.name);
                    
                    for (HeapObject ref : obj.references) {
                        if (!marked.contains(ref)) {
                            queue.add(ref);
                        }
                    }
                }
            }
        }
        
        // 清除阶段
        void sweep() {
            System.out.println("\n=== 清除阶段 ===");
            Iterator<HeapObject> it = objects.iterator();
            while (it.hasNext()) {
                HeapObject obj = it.next();
                if (!obj.marked) {
                    System.out.println("回收: " + obj.name + ", 释放 " + obj.size + "B");
                    usedSize -= obj.size;
                    it.remove();
                } else {
                    obj.marked = false;  // 重置标记，为下次GC准备
                }
            }
        }
        
        // 执行GC
        void gc() {
            System.out.println("\n=== 开始GC ===");
            System.out.println("GC前已用内存: " + usedSize + "B");
            mark();
            sweep();
            System.out.println("GC后已用内存: " + usedSize + "B");
            System.out.println("释放内存: " + (totalSize - usedSize) + "B\n");
        }
        
        void printHeap() {
            System.out.println("\n堆内存状态:");
            for (HeapObject obj : objects) {
                System.out.println("  " + obj);
            }
            System.out.println("总大小: " + totalSize + "B, 已用: " + usedSize + "B");
        }
    }
    
    public static void main(String[] args) {
        Heap heap = new Heap();
        
        // 创建对象
        HeapObject objA = new HeapObject("A", 1024);
        HeapObject objB = new HeapObject("B", 2048);
        HeapObject objC = new HeapObject("C", 512);
        HeapObject objD = new HeapObject("D", 1024);
        HeapObject objE = new HeapObject("E", 256);
        
        // 建立引用关系
        objA.addReference(objC);  // A -> C
        objB.addReference(objD);  // B -> D
        // E没有引用，也没有被引用
        
        // 添加到堆
        heap.addObject(objA);
        heap.addObject(objB);
        heap.addObject(objC);
        heap.addObject(objD);
        heap.addObject(objE);
        
        // 设置GC Roots
        heap.addGCRoot(objA);  // A是GC Root
        heap.addGCRoot(objB);  // B是GC Root
        // E不是GC Root
        
        heap.printHeap();
        heap.gc();
        heap.printHeap();
    }
}
```

#### 优缺点深度分析

```
标记-清除算法的完整评估：

优点：
1. 算法简单，实现容易
2. 不移动对象，对象地址稳定
3. 适合存活率高的场景（老年代）

缺点：
1. 效率问题：标记和清除都需要遍历整个堆
   - 标记：DFS/BFS遍历对象图
   - 清除：遍历整个堆（包括死亡对象）

2. 内存碎片：
   
   碎片形成过程：
   ┌────────────────────────────────────┐
   │ [2KB] [空闲4KB] [3KB] [空闲5KB]    │
   └────────────────────────────────────┘
   
   分配6KB对象时：
   - 总空闲：4KB + 5KB = 9KB
   - 但最大连续空间：5KB
   - 分配失败！

3. STW（Stop-The-World）：
   - 标记和清除期间，所有应用线程暂停
   - 堆越大，STW时间越长

4. 分配速度下降：
   - 需要维护空闲列表（free list）
   - 分配时需要遍历空闲列表找合适空间
   - 时间复杂度：O(n)，n为空闲块数量
```

### 2. 复制算法（Copying）

#### 算法原理

```
复制算法的核心思想：

将内存分为两块：From空间和To空间
每次只使用其中一块（From）
GC时，将From中存活对象复制到To空间
然后清空From空间，交换From和To

内存布局：
┌──────────────────┬──────────────────┐
│    From空间      │     To空间       │
│   （当前使用）    │    （空闲）       │
│                  │                  │
│  [A] [B] [C]    │                  │
│                  │                  │
└──────────────────┴──────────────────┘
        ↓ GC触发
┌──────────────────┬──────────────────┐
│    From空间      │     To空间       │
│    （清空）       │   （存活对象）    │
│                  │                  │
│                  │  [A] [B]        │
│                  │                  │
└──────────────────┴──────────────────┘

伪代码：
function copying_gc():
    // 标记阶段隐含在复制中
    for obj in from_space:
        if obj.is_alive:
            copy_obj = copy(obj, to_space)
            obj.forwarding_pointer = copy_obj  // 设置转发指针
            
    // 更新引用
    for obj in to_space:
        for ref in obj.references:
            ref = ref.forwarding_pointer
            
    // 清空from空间
    from_space.clear()
    swap(from_space, to_space)
```

#### Appel式回收（半区复制优化）

```
年轻代的Appel式回收（8:1:1比例）：

年轻代内存布局：
┌──────────────────────────────────────────────────┐
│                   年轻代（Young Gen）              │
│                                                  │
│  ┌────────────────────────┐ ┌─────┐ ┌─────┐     │
│  │        Eden            │ │ S0  │ │ S1  │     │
│  │       (80%)            │ │(10%)│ │(10%)│     │
│  │                        │ │     │ │     │     │
│  │   新对象分配区域        │ │From │ │ To  │     │
│  │                        │ │     │ │     │     │
│  └────────────────────────┘ └─────┘ └─────┘     │
│                                                  │
│  总年轻代大小：假设10MB                            │
│  Eden：8MB，S0：1MB，S1：1MB                      │
└──────────────────────────────────────────────────┘

对象分配与晋升流程：

1. 新对象分配在Eden区
   Eden: [新对象A] [新对象B] [新对象C] ...
   S0:   [空]
   S1:   [空]

2. Eden满，触发Minor GC
   - Eden存活对象 → 复制到S0
   - Eden清空
   
   Eden: [空]
   S0:   [A] [B] (存活对象，年龄=1)
   S1:   [空]

3. 继续分配新对象
   Eden: [新对象D] [新对象E] ...
   S0:   [A] [B] (年龄=1)
   S1:   [空]

4. 再次Minor GC
   - Eden存活对象 → 复制到S1
   - S0存活对象 → 复制到S1，年龄+1
   - Eden和S0清空
   
   Eden: [空]
   S0:   [空]
   S1:   [A] [B] (年龄=2) [D] [E] (年龄=1)

5. 对象年龄达到阈值（默认15）→ 晋升老年代
   
为什么不是50%利用率？
- 实际使用Eden + 一个Survivor = 90%
- 只有GC时需要一个Survivor作为To空间
- 正常对象分配在Eden，不在Survivor
```

#### 优缺点深度分析

```
复制算法的完整评估：

优点：
1. 无内存碎片：
   存活对象被紧凑地复制到To空间
   分配新对象时只需移动指针（bump-the-pointer）
   分配时间复杂度：O(1)

2. 实现简单：
   标记和清除合为一个步骤
   不需要维护空闲列表

3. 高效：
   只需遍历存活对象（通常很少）
   不需要遍历死亡对象

缺点：
1. 内存利用率低：
   标准复制：50%
   Appel式回收：90%（但Eden GC时还是只剩10%可用）

2. 对象存活率高时效率低：
   如果存活率 > 50%，复制开销超过收益
   极端情况：100%存活，全部复制，等于内存交换

3. 需要额外空间：
   需要To空间作为复制目的地
   对象在堆中移动，需要更新所有引用

4. 对象地址变化：
   复制后对象地址改变
   需要更新所有指向该对象的引用
   增加了GC的复杂度和时间

适用场景：
- 年轻代（存活率低，<10%）
- 内存资源充足
- 追求低延迟、无碎片
```

### 3. 标记-整理算法（Mark-Compact）

#### 算法原理

```
标记-整理算法的三个阶段：

阶段1：标记（与标记-清除相同）
阶段2：整理（Compact）
阶段3：清除（释放尾部空间）

整理过程详解：

初始状态（标记后）：
┌─────────────────────────────────────────────────────┐
│ [存活]│ [存活]│ [死亡]│ [存活]│ [死亡]│ [存活]│ [死亡]│
│   ✓   │   ✓   │       │   ✓   │       │   ✓   │       │
└─────────────────────────────────────────────────────┘

整理过程（将存活对象移动到一端）：
步骤1：计算每个存活对象的新地址
  存活对象A（原位置0）→ 新位置0
  存活对象B（原位置1）→ 新位置1
  存活对象D（原位置3）→ 新位置2
  存活对象F（原位置5）→ 新位置3

步骤2：更新引用
  所有指向B的引用 → 新位置1
  所有指向D的引用 → 新位置2
  所有指向F的引用 → 新位置3

步骤3：移动对象
  将对象按新地址顺序排列

整理后：
┌─────────────────────────────────────────────────────┐
│ [存活]│ [存活]│ [存活]│ [存活]│ [空闲]│ [空闲]│ [空闲]│
│   A   │   B   │   D   │   F   │       │       │       │
└─────────────────────────────────────────────────────┘
        ↑                              ↑
      对象区                          空闲区

伪代码：
function mark_compact_gc():
    // 阶段1：标记
    mark_all_reachable()
    
    // 阶段2：计算转发地址
    forward_ptr = heap_start
    for obj in heap:
        if obj.marked:
            obj.forwarding_address = forward_ptr
            forward_ptr += obj.size
    
    // 阶段3：更新引用
    for obj in heap:
        if obj.marked:
            for ref in obj.references:
                ref = ref.forwarding_address
    
    // 阶段4：移动对象
    for obj in heap:
        if obj.marked:
            move(obj, obj.forwarding_address)
            obj.marked = false
    
    // 阶段5：重置分配指针
    allocation_ptr = forward_ptr
```

#### 优缺点深度分析

```
标记-整理算法的完整评估：

优点：
1. 无内存碎片：
   整理后所有存活对象紧凑排列
   空闲空间连续，便于大对象分配

2. 内存利用率高：
   不需要额外的To空间
   100%内存可用于对象分配

3. 分配速度快：
   使用bump-the-pointer分配
   只需移动分配指针

缺点：
1. STW时间长：
   整理阶段需要移动对象
   需要更新所有引用
   对象越多，STW越长

2. 对象移动开销：
   大对象移动成本高（需要复制内存）
   移动期间需要保证对象一致性

3. 引用更新复杂：
   需要遍历整个堆更新引用
   包括栈上的引用、寄存器中的引用

4. 需要额外数据结构：
   需要保存对象的转发地址（forwarding address）
   增加了内存开销

适用场景：
- 老年代（存活率高，不适合复制）
- 需要避免内存碎片
- 可以容忍较长STW（如后台批处理）
```

### 4. 分代收集算法（Generational GC）

#### 分代假说的理论基础

```
分代收集的理论基础 - 弱分代假说（Weak Generational Hypothesis）：

"绝大多数对象都是朝生夕死的"

实验数据（来自Sun/Oracle的研究）：
- 新创建的对象中，90%-98%在第一次GC时被回收
- 经过一次GC存活的对象，下一次GC仍有80%被回收
- 只有少量对象（<5%）会长期存活

强分代假说（Strong Generational Hypothesis）：
"熬过越多次垃圾收集过程的对象就越难以消亡"

基于这两个假说，JVM将堆分为：
┌──────────────────────────────────────────┐
│              堆（Heap）                    │
│  ┌──────────────────────────────────┐    │
│  │         年轻代（Young Gen）       │    │
│  │  特点：对象存活率低，<10%          │    │
│  │  策略：复制算法                    │    │
│  │  GC频率：高（几分钟一次）          │    │
│  │  GC类型：Minor GC                  │    │
│  │  目标：快速回收短命对象            │    │
│  ├──────────────────────────────────┤    │
│  │         老年代（Old Gen）         │    │
│  │  特点：对象存活率高，>90%          │    │
│  │  策略：标记-清除 / 标记-整理       │    │
│  │  GC频率：低（几小时一次）          │    │
│  │  GC类型：Major GC / Full GC        │    │
│  │  目标：回收长期存活对象            │    │
│  └──────────────────────────────────┘    │
└──────────────────────────────────────────┘
```

#### 对象晋升策略

```java
/**
 * 对象在分代收集中的生命周期
 */
public class ObjectLifecycle {
    
    private static final int _1MB = 1024 * 1024;
    
    /**
     * 对象分配与晋升演示
     * 
     * VM参数：
     * -Xms40m -Xmx40m          // 堆40MB
     * -Xmn20m                   // 年轻代20MB
     * -XX:SurvivorRatio=8       // Eden:S0:S1 = 16:2:2
     * -XX:MaxTenuringThreshold=15
     * -XX:+PrintGCDetails
     * -XX:+PrintTenuringDistribution
     */
    public static void main(String[] args) {
        
        // 阶段1：对象在Eden分配
        // Eden: 16MB
        // S0/S1: 各2MB
        
        byte[] obj1 = new byte[2 * _1MB];   // 在Eden分配
        byte[] obj2 = new byte[2 * _1MB];   // 在Eden分配
        byte[] obj3 = new byte[2 * _1MB];   // 在Eden分配
        
        // Eden已用6MB
        
        // 阶段2：触发Minor GC
        // Eden满（分配大对象或空间不足）
        byte[] obj4 = new byte[8 * _1MB];   // 尝试分配8MB
        
        // 如果obj1、obj2、obj3存活：
        // - 它们被复制到S0（From Survivor）
        // - 年龄设为1
        // - Eden清空
        
        // 阶段3：对象年龄增长
        // 每次Minor GC，存活对象的年龄+1
        // 当年龄达到MaxTenuringThreshold（默认15），晋升老年代
        
        // 阶段4：大对象直接进入老年代
        // -XX:PretenureSizeThreshold=4m
        byte[] bigObject = new byte[10 * _1MB];  // 直接进老年代
        
        // 阶段5：空间分配担保
        // Minor GC前，检查老年代最大可用连续空间
        // 如果不足，可能触发Full GC
    }
}
```

#### 空间分配担保

```
空间分配担保机制（Handle Promotion Failure）：

背景：
Minor GC时，存活对象需要复制到Survivor区
如果Survivor空间不足，需要老年代担保

担保流程：

1. Minor GC前检查：
   老年代最大可用连续空间 >= 年轻代所有对象总空间？
   
   是 → 直接Minor GC（安全）
   否 → 继续检查

2. 检查是否允许担保失败：
   -XX:+HandlePromotionFailure（JDK6+默认开启）
   
   不允许 → 直接Full GC
   允许 → 继续检查

3. 检查历史晋升平均值：
   老年代最大可用连续空间 >= 历次晋升到老年代对象的平均大小？
   
   是 → 尝试Minor GC（有风险）
   否 → Full GC

4. 如果Minor GC后确实担保失败：
   重新发起Full GC
   
   问题：浪费了一次Minor GC
   JDK6后优化：如果老年代空间充足，直接Minor GC

图解：

年轻代GC前：
┌──────────────────┐  ┌──────────┐
│   Eden (满)      │  │ 老年代   │
│ [A][B][C][D][E]  │  │ [空闲20MB]│
└──────────────────┘  └──────────┘

假设A、B、C存活，D、E死亡：
Survivor只有2MB，但存活对象需要3MB

有担保时：
┌──────────────────┐  ┌──────────┐
│   Eden (清空)    │  │ 老年代   │
│                  │  │ [A][B][C]│
│                  │  │ [空闲17MB]│
└──────────────────┘  └──────────┘
A、B、C提前晋升到老年代

无担保时（或担保失败）：
直接触发Full GC
```

```
│  GC线程：     [初  [标记    [重  [清              │

│               记]         记]                     │
│                                                     │

│                                                     │
│  四个阶段：                                         │

│     耗时：很短                                       │
│                                                     │
│  2. 并发标记（并发）：从GC Roots追踪引用链          │

│                                                     │
│  4. 并发清除（并发）：清理死亡对象                   │

└────────────────────────────────────────────────────┘

JVM参数：
-XX:+UseConcMarkSweepGC
```

### 3. GC Roots的枚举实现

```
HotSpot中GC Roots枚举的源码逻辑：

1. 虚拟机栈（Stack）：
   - 遍历所有Java线程
   - 对每个线程，遍历栈帧（Stack Frame）
   - 从栈帧的局部变量表和操作数栈中找引用

2. 方法区（Metaspace）：
   - 遍历所有加载的类（ClassLoaderDataGraph）
   - 从类的静态字段和常量池中找引用

3. JNI引用：
   - 遍历JNI全局引用表（JNIHandles）
   - 遍历JNI局部引用表（每个线程）

4. 同步锁：
   - 遍历所有Monitor
   - 找到被锁定的对象

关键代码路径（简化）：
void Threads::possibly_parallel_threads_do(...) {
    // 遍历所有线程
    for (JavaThread* p = _thread_list; p; p = p->next()) {
        // 处理每个线程的栈帧
        p->oops_do(f);
    }
}

void JavaThread::oops_do(OopClosure* f) {
    // 处理栈帧中的引用
    stack_frame_iterator().oops_do(f);
    
    // 处理JNI局部引用
    _active_handles->oops_do(f);
    
    // 处理Monitor锁
    _monitor_chunks->oops_do(f);
}
```

### 4. 写屏障（Write Barrier）原理

```
写屏障的作用：

问题：
在并发GC中，应用线程可能在GC标记过程中修改引用关系
例如：
- GC线程已标记对象A为存活
- 应用线程将A.references从B改为C
- 如果C尚未被标记，C会被错误地回收

解决方案：写屏障（Write Barrier）

在每次引用赋值时插入额外逻辑：

void set_reference(Object obj, Object ref) {
    // 原始赋值
    obj.reference = ref;
    
    // 写屏障（额外逻辑，由JVM自动插入）
    write_barrier(obj, ref);
}

写屏障类型：
1. 卡表（Card Table） - CMS/G1使用
   - 将堆划分为512字节的卡页
   - 引用修改时，标记对应的卡页为"脏"
   - GC时只扫描脏卡页

2. SATB（Snapshot-At-The-Beginning） - G1使用
   - 在并发标记开始时做快照
   - 记录标记期间的新引用
   - 在重新标记阶段处理

3. 增量更新（Incremental Update） - CMS使用
   - 标记期间记录被修改的白色对象
   - 重新标记阶段重新扫描

卡表实现：
┌─────────────────────────────────────────┐
│  堆内存（按512字节分块）                 │
│  ┌────┬────┬────┬────┬────┬────┐       │
│  │ 卡0 │ 卡1 │ 卡2 │ 卡3 │ 卡4 │ ...   │
│  └────┴────┴────┴────┴────┴────┘       │
│       ↑                                 │
│  卡表（字节数组）：                       │
│  ┌────┬────┬────┬────┬────┬────┐       │
│  │ 0  │ 0  │ 1  │ 0  │ 0  │ ... │       │
│  └────┴────┴────┴────┴────┴────┘       │
│           ↑                             │
│        卡2被标记为脏（有引用修改）        │
└─────────────────────────────────────────┘
```

### 案例3：内存泄漏排查

```java
/**
 * 内存泄漏排查实战
 * 
 * 症状：
 * - 堆内存持续增长，GC无法回收
 * - 最终OutOfMemoryError
 * - Full GC频繁但无效

public class MemoryLeakDetection {

    private static final List<Object> STATIC_LIST = new ArrayList<>();
    
    public void leak1() {
        // 每次调用都添加，但从不移除
        STATIC_LIST.add(new byte[1024 * 1024]);  // 1MB
    }
    
    // 泄漏场景2：未移除的监听器
    private final EventSource eventSource = new EventSource();
    private final List<Listener> listeners = new ArrayList<>();
    
    public void leak2() {
        // 每次创建新监听器并注册，但从不注销
        Listener listener = new Listener();
        eventSource.addListener(listener);
        listeners.add(listener);
    }
    
    // 泄漏场景3：ThreadLocal未清理
    private static final ThreadLocal<byte[]> THREAD_LOCAL = new ThreadLocal<>();
    
    public void leak3() {

        THREAD_LOCAL.set(new byte[1024 * 1024 * 10]);  // 10MB
```

### 2. GC性能指标

```java
/**
 * GC性能指标体系
 */
public class GCMetrics {
    
    /*
     * 核心指标：
     * 
     * 1. 吞吐量（Throughput）
     *    定义：应用程序运行时间 / (应用程序运行时间 + GC时间)
     *    目标：> 95%（批处理场景）
     *    
     * 2. 延迟（Latency）
     *    定义：单次GC造成的停顿时间
     *    目标：
     *    - 平均停顿：< 100ms
     *    - P99停顿：< 200ms
     *    - 最大停顿：< 500ms
     *    
     * 3. 频率（Frequency）
     *    定义：单位时间内的GC次数
     *    目标：
     *    - Minor GC：< 1次/分钟
     *    - Full GC：< 1次/小时
     *    
     * 4. 内存效率（Memory Efficiency）
     *    定义：有效对象内存 / 堆总内存
     *    目标：> 70%
     */
    
    public void calculateMetrics() {
        /*
         * 使用GC日志计算：
         * 
         * 1. 从日志提取所有GC事件
         * 2. 计算总GC时间和总运行时间
         * 3. 统计分析
         */
        
        // 示例计算
        long totalRuntime = 3600 * 1000;  // 1小时（毫秒）
        long totalGCTime = 120 * 1000;     // GC总耗时2分钟
        long gcCount = 50;                  // GC次数
        
        double throughput = 
            (double)(totalRuntime - totalGCTime) / totalRuntime * 100;
        double avgPause = (double)totalGCTime / gcCount;
        double frequency = (double)gcCount / (totalRuntime / 1000 / 60);  // 次/分钟
        
        System.out.println("吞吐量: " + throughput + "%");
        System.out.println("平均停顿: " + avgPause + "ms");
        System.out.println("GC频率: " + frequency + "次/分钟");
    }
}
```

## 常见陷阱与最佳实践

### 陷阱1：认为GC完全自动，无需关注

```
误区：
- "Java有GC，所以不会内存泄漏"
- "不需要关心对象回收"
- "GC会自动处理一切"

真相：
GC只能回收不可达对象
如果对象仍然被引用（即使是意想不到的引用），GC不会回收

常见泄漏源：
1. 静态集合类
   private static Map<String, Object> cache = new HashMap<>();
   // 无限增长，永不清除

2. 未注销的监听器
   eventSource.addListener(listener);
   // 忘记 eventSource.removeListener(listener);

3. ThreadLocal滥用
   threadLocal.set(largeObject);
   // 忘记 threadLocal.remove();

4. 数据库连接、流未关闭
   Connection conn = dataSource.getConnection();
   // 忘记 conn.close();

5. 内部类持有外部类引用
   public class Outer {
       private byte[] largeData = new byte[1024 * 1024 * 100];  // 100MB
       
       class Inner {
           // 隐式持有Outer.this引用
           void doSomething() {}
       }
   }
   // 如果Inner被静态持有，Outer也无法回收

最佳实践：
- 使用WeakReference管理缓存
- 及时注销事件监听器
- ThreadLocal使用完立即remove
- 使用try-with-resources管理资源
- 避免不必要的对象引用
```

### 陷阱2：混淆不同GC算法的适用场景

```
误区：
- "标记-清除算法适合年轻代"
- "复制算法适合老年代"
- "G1适合所有场景"

真相：
不同算法有不同的假设和适用条件

算法适用场景对比：

┌──────────────┬──────────────────┬──────────────────────────┐
│    算法      │    适用代        │         原因             │
├──────────────┼──────────────────┼──────────────────────────┤
│ 复制算法      │ 年轻代           │ 存活率低，复制开销小      │
├──────────────┼──────────────────┼──────────────────────────┤
│ 标记-整理     │ 老年代           │ 存活率高，无碎片需求      │
├──────────────┼──────────────────┼──────────────────────────┤
│ 标记-清除     │ 老年代（CMS）    │ 低延迟，容忍碎片          │
├──────────────┼──────────────────┼──────────────────────────┤
│ G1           │ 全堆（逻辑分代）  │ 平衡延迟和吞吐量          │
├──────────────┼──────────────────┼──────────────────────────┤
│ ZGC          │ 全堆             │ 超大堆，超低延迟          │
└──────────────┴──────────────────┴──────────────────────────┘

收集器选择决策树：

堆内存 < 4GB? 
  是 → Serial GC（单核/客户端）
  否 → 延迟要求 < 10ms?
         是 → ZGC/Shenandoah
         否 → 吞吐量优先?
                是 → Parallel GC
                否 → G1 GC（默认推荐）
```

### 陷阱3：忽视内存碎片问题

```java
/**
 * 内存碎片问题的演示和解决
 */
public class MemoryFragmentation {
    
    /**
     * 产生碎片的代码
     */
    public void createFragmentation() {
        List<byte[]> objects = new ArrayList<>();
        
        // 分配大小交替的对象
        for (int i = 0; i < 1000; i++) {
            // 分配大对象
            byte[] large = new byte[1024 * 100];  // 100KB
            objects.add(large);
            
            // 分配小对象
            byte[] small = new byte[1024];         // 1KB
            objects.add(small);
        }
        
        // 释放所有大对象
        Iterator<byte[]> it = objects.iterator();
        while (it.hasNext()) {
            if (it.next().length > 1024 * 50) {
                it.remove();
            }
        }
        
        // 现在堆中散布着大量1KB对象和100KB的空洞
        // 尝试分配200KB对象可能失败
        try {
            byte[] big = new byte[1024 * 200];  // 200KB
        } catch (OutOfMemoryError e) {
            System.out.println("分配失败，内存碎片！");
        }
    }
    
    /**
     * 减少碎片的策略
     */
    public void reduceFragmentation() {
        // 策略1：对象池化
        ObjectPool<byte[]> pool = new ObjectPool<>(() -> new byte[1024 * 100]);
        byte[] buffer = pool.borrow();
        // 使用buffer...
        pool.returnObject(buffer);  // 归还，而不是释放
        
        // 策略2：使用固定大小的块分配
        // 类似内存池的思想
        
        // 策略3：CMS/G1用户开启整理
        // -XX:+UseCMSCompactAtFullCollection
        // G1自动整理，无需配置
        
        // 策略4：定期Full GC（不推荐作为常规手段）
        // System.gc();
    }
}

class ObjectPool<T> {
    private final List<T> pool = new ArrayList<>();
    private final java.util.function.Supplier<T> factory;
    
    ObjectPool(java.util.function.Supplier<T> factory) {
        this.factory = factory;
    }
    
    synchronized T borrow() {
        if (pool.isEmpty()) {
            return factory.get();
        }
        return pool.remove(pool.size() - 1);
    }
    
    synchronized void returnObject(T obj) {
        pool.add(obj);
    }
}
```

```java
/**

public class FinalizerTrap {

     * 问题：
     * 1. Finalizer对象回收延迟（需要两次GC）
     * 2. Finalizer线程单线程执行，可能阻塞

            // 2. 可能永远不执行（Finalizer线程阻塞）

        }

    public class Resource implements AutoCloseable {
        private NativeResource nativeHandle;
        private volatile boolean closed = false;
        
        public void doSomething() {
            if (closed) {
                throw new IllegalStateException("Resource closed");
            }
            // 使用资源
        }
        
        @Override
        public void close() {

                closed = true;
                nativeHandle.release();

    }

    public class ModernResource {
```

## 面试题与参考答案

### Q1：引用计数法有什么缺陷？Java为什么不用它？

**答：**

引用计数法的原理：每个对象维护一个引用计数器，被引用时+1，引用失效时-1，计数为0时回收。

**主要缺陷：**

1. **无法解决循环引用**：
   ```java
   class Node {
       Node next;
   }
   Node a = new Node();
   Node b = new Node();
   a.next = b;  // b的引用计数=1
   b.next = a;  // a的引用计数=1
   a = null;    // a的引用计数=1（被b引用）
   b = null;    // b的引用计数=1（被a引用）
   // a和b都无法被回收，造成内存泄漏
   ```

2. **额外开销**：
   - 每次引用赋值都需要更新计数器
   - 计数器占用额外内存空间

3. **并发问题**：
   - 多线程下需要原子操作更新计数器
   - 高并发场景性能下降明显

4. **实时性要求**：
   - 计数器为0需要立即回收
   - 增加了回收的复杂度

**Java采用可达性分析算法**，通过GC Roots向下搜索，天然解决循环引用问题，且不需要维护引用计数。

### Q2：可达性分析的GC Roots有哪些？

**答：**

GC Roots包括以下六类：

1. **虚拟机栈引用**：栈帧中的局部变量表引用的对象
   ```java
   void method() {
       Object obj = new Object();  // obj是GC Root
   }
   ```

2. **方法区静态引用**：类静态属性引用的对象
   ```java
   class MyClass {
       static Object staticObj = new Object();  // GC Root
   }
   ```

3. **方法区常量引用**：常量引用的对象
   ```java
   class MyClass {
       static final String CONST = "value";  // 常量池引用
   }
   ```

4. **本地方法栈JNI引用**：Native方法引用的对象

5. **同步锁持有对象**：被`synchronized`持有的对象
   ```java
   synchronized(obj) {
       // obj是GC Root
   }
   ```

6. **JVM内部引用**：
   - 基本数据类型对应的Class对象
   - 系统类加载器
   - 异常对象（NullPointerException等）

### Q3：标记-清除、复制、标记-整理三种算法的优缺点？

**答：**

| 算法 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| **标记-清除** | 实现简单，不移动对象 | 效率低，内存碎片 | 老年代（早期） |
| **复制** | 无碎片，高效 | 内存利用率50% | 年轻代 |
| **标记-整理** | 无碎片，利用率高 | 移动对象，STW长 | 老年代 |

**详细说明：**

标记-清除：
- 优点：算法简单，实现容易；不移动对象，地址稳定
- 缺点：标记和清除都需要遍历整个堆，效率低；产生内存碎片；分配大对象时可能失败

复制：
- 优点：无内存碎片；分配速度快（只需移动指针）；只需遍历存活对象
- 缺点：内存利用率低（标准复制50%，Appel式90%）；存活率高时效率低；对象地址变化

标记-整理：
- 优点：无内存碎片；内存利用率高（100%）；分配速度快
- 缺点：需要移动对象，STW时间长；引用更新复杂；需要额外空间保存转发地址

### Q4：为什么年轻代用复制算法，老年代用标记-整理算法？

**答：**

**年轻代使用复制算法的原因：**

1. **对象存活率低**：根据弱分代假说，90%+的对象在第一次GC时被回收
2. **复制开销小**：只需复制少量存活对象，大部分对象直接丢弃
3. **无内存碎片**：复制后内存紧凑，利于后续分配
4. **分配速度快**：使用bump-the-pointer，O(1)时间复杂度
5. **Appel式优化**：Eden:S0:S1=8:1:1，实际利用率90%

**老年代使用标记-整理的原因：**

1. **对象存活率高**：长期存活对象多，>90%
2. **复制不划算**：如果复制，几乎要复制所有对象，开销巨大
3. **空间敏感**：不能浪费50%空间给To区
4. **避免碎片**：老年代对象生命周期长，碎片问题更严重
5. **大对象多**：老年代大对象多，需要连续空间

### Q5：什么是分代收集？有什么优势？

**答：**

分代收集是根据对象存活周期将堆划分为不同区域，使用不同回收策略的算法。

**分代结构：**

```
堆内存分代：
┌──────────────────────────────────────────┐
│              堆（Heap）                    │
│  ┌──────────────────────────────────┐    │
│  │         年轻代（Young Gen）       │    │
│  │  ┌──────────────┐               │    │
│  │  │   Eden       │               │    │
│  │  │  (80%)       │               │    │
│  │  ├──────────────┤               │    │
│  │  │ Survivor0    │               │    │
│  │  │  (10%)       │               │    │
│  │  ├──────────────┤               │    │
│  │  │ Survivor1    │               │    │
│  │  │  (10%)       │               │    │
│  │  └──────────────┘               │    │
│  │  算法：复制（Minor GC频繁）      │    │
│  └──────────────────────────────────┘    │
│  ┌──────────────────────────────────┐    │
│  │         老年代（Old Gen）         │    │
│  │  算法：标记-清除/标记-整理         │    │
│  │  GC：Major GC/Full GC（少）       │    │
│  └──────────────────────────────────┘    │
└──────────────────────────────────────────┘
```

**优势：**

1. **针对性强**：不同代使用最适合的算法
2. **减少GC范围**：Minor GC只回收年轻代，速度快
3. **提高回收效率**：避免全堆扫描
4. **符合对象生命周期**：大多数对象在年轻代被回收
5. **减少STW**：Minor GC停顿时间短

### Q6：Minor GC、Major GC和Full GC有什么区别？

**答：**

| GC类型 | 回收区域 | 触发条件 | 特点 |
|--------|---------|---------|------|
| **Minor GC** | 年轻代 | Eden满 | 频繁、快、影响小 |
| **Major GC** | 老年代 | 老年代满 | 较少、慢 |
| **Full GC** | 整个堆+元空间 | 老年代满/元空间满/System.gc() | 最少、最慢、影响大 |

**详细说明：**

**Minor GC（Young GC）：**
- 触发：Eden区空间不足
- 过程：复制Eden和From Survivor的存活对象到To Survivor
- 特点：
  - 频率高（几分钟一次）
  - 停顿时间短（通常<100ms）
  - 回收效率高（90%+对象被回收）

**Major GC（Old GC）：**
- 触发：老年代空间不足
- 过程：标记-清除或标记-整理老年代
- 特点：
  - 频率较低
  - 停顿时间较长
  - CMS中Major GC是并发执行的

**Full GC：**
- 触发：
  1. 老年代空间不足（包括分配担保失败）
  2. 元空间（Metaspace）不足
  3. 显式调用System.gc()
  4. CMS的Concurrent Mode Failure
- 过程：回收整个堆（年轻代+老年代）和元空间
- 特点：
  - 频率最低
  - 停顿时间最长（可能几秒）
  - 影响最大，应尽量避免

**注意：** 有些收集器中Major GC就是Full GC，具体取决于收集器实现。

### Q7：CMS收集器的工作流程和缺点？

**答：**

**CMS（Concurrent Mark Sweep）工作流程：**

1. **初始标记（Initial Mark）**：
   - STW（停顿时间短）
   - 标记GC Roots直接关联的对象

2. **并发标记（Concurrent Mark）**：
   - 与用户线程并发执行
   - 从GC Roots向下追踪引用链

3. **重新标记（Remark）**：
   - STW（停顿时间中等）
   - 修正并发标记期间变动的引用

4. **并发清除（Concurrent Sweep）**：
   - 与用户线程并发执行
   - 清理死亡对象

**CMS的缺点：**

1. **CPU敏感**：并发阶段占用CPU资源，降低吞吐量
2. **浮动垃圾**：并发清理时产生的新垃圾无法回收，需要预留空间
3. **内存碎片**：使用标记-清除算法，无整理过程
4. **Concurrent Mode Failure**：
   - 并发期间老年代空间不足
   - 退化为Serial Old收集器
   - 造成长时间STW

**CMS已废弃**，JDK14中移除，推荐使用G1或ZGC。

### Q8：G1收集器的Region设计和RSet作用？

**答：**

**G1的Region设计：**

```
G1将堆划分为多个Region（默认2048个，每个1-32MB）：

┌────┬────┬────┬────┬────┬────┬────┬────┐
│ E  │ S  │ S  │ O  │ O  │ H  │ O  │ O  │
│Eden│S0  │S1  │Old │Old │Hum │Old │Old │
└────┴────┴────┴────┴────┴────┴────┴────┘

Region类型：
- Eden Region：新对象分配
- Survivor Region：存活对象
- Old Region：老年代对象
- Humongous Region：大对象（>0.5 Region）
- Free Region：空闲

优势：
1. 细粒度管理：按需回收，不是整代回收
2. 可预测停顿：选择回收价值高的Region集合
3. 空间整合：复制算法避免碎片
```

**Remembered Set（RSet）作用：**

问题：回收一个Region时，如何知道其他Region是否有对象引用本Region的对象？

解决方案：每个Region维护一个RSet

```
Region A的RSet记录：
┌─────────────────────────────┐
│ Region B 引用 A中的对象X    │
│ Region C 引用 A中的对象Y    │
│ Region D 引用 A中的对象Z    │
└─────────────────────────────┘

回收Region A时：
- 只需扫描Region A的RSet
- 不需要扫描整个堆
- 找到引用A中对象的其他Region
```

**优势：**
- 避免全堆扫描
- 提高回收效率
- 支持并发标记

**代价：**
- 每个Region需要额外内存维护RSet
- 写操作需要维护RSet（写屏障开销）

### Q9：ZGC如何实现<10ms的停顿？

**答：**

ZGC实现超低延迟的核心技术：

1. **着色指针（Colored Pointers）**：
   - 利用64位指针的高16位存储元数据
   - 4位颜色信息：Marked0, Marked1, Remapped, Finalizable
   - 避免在对象头中设置标记位

2. **读屏障（Load Barrier）**：
   ```c
   Object* read_barrier(Object* ref) {
       if (ref != NULL && is_bad_color(ref)) {
           // 指针颜色不对，需要修复
           return fixup_ref(ref);
       }
       return ref;
   }
   ```
   - 在读取对象引用时触发
   - 修复指向已移动对象的指针

3. **并发整理（Concurrent Relocation）**：
   - 标记、转移、重映射全部并发执行
   - 应用线程和GC线程同时工作
   - 仅初始标记和最终标记需要极短STW

4. **多视图映射（Multi-Mapping）**：
   - 同一物理内存映射到多个虚拟地址
   - 支持不同颜色的指针访问同一对象

5. **不分代设计（JDK21前）**：
   - 简化GC逻辑
   - 避免跨代引用维护
   - JDK21引入Generational ZGC，进一步提升性能

**GC阶段：**

```
ZGC阶段（几乎全部并发）：

1. 并发标记（Concurrent Mark）
2. 并发预备重映射（Concurrent Prepare for Relocate）
3. 并发转移（Concurrent Relocate）
4. 并发重映射（Concurrent Remap）

STW阶段：
- 初始标记：< 1ms
- 最终标记：< 1ms
```

### Q10：如何排查线上Full GC频繁的问题？

**答：**

**排查步骤：**

1. **确认Full GC频率和原因**：
   ```bash
   # 查看GC日志
   grep "Full GC" gc.log | wc -l
   
   # 分析GC原因
   grep "Full GC" gc.log | head -20
   ```

2. **常见原因及解决**：

   a) **老年代空间不足**：
      - 检查晋升速率：`jstat -gcutil <pid> 1000`
      - 解决：增大老年代、优化对象生命周期

   b) **元空间不足**：
      - 原因：动态生成类（反射、CGLIB）
      - 解决：`-XX:MaxMetaspaceSize=512m`

   c) **System.gc()调用**：
      - 搜索代码中的System.gc()
      - 添加`-XX:+DisableExplicitGC`

   d) **CMS的Concurrent Mode Failure**：
      - 原因：并发期间老年代满
      - 解决：降低触发阈值、增大老年代、换G1/ZGC

   e) **内存泄漏**：
      - 生成堆转储：`jmap -dump:format=b,file=heap.hprof <pid>`
      - 使用MAT分析大对象

3. **调优参数**：
   ```bash
   # 切换到G1或ZGC
   -XX:+UseG1GC
   -XX:MaxGCPauseMillis=200
   
   # 或
   -XX:+UseZGC
   ```

4. **代码优化**：
   - 减少大对象创建
   - 及时释放不再使用的引用
   - 使用对象池

### Q11：什么是TLAB？有什么作用？

**答：**

**TLAB（Thread Local Allocation Buffer）**：

JVM为每个线程分配的私有内存区域，用于在Eden区分配对象。

**作用：**

1. **避免锁竞争**：
   - 无TLAB时，多线程分配对象需要同步
   - 有TLAB时，线程在私有缓冲区分配，无锁

2. **提高分配速度**：
   - TLAB内使用bump-the-pointer分配
   - 只需移动分配指针，O(1)复杂度

**工作流程：**

```
对象分配流程：
1. 线程尝试在TLAB中分配
   - 成功 → 快速分配（无锁）
   - 失败 → 继续下一步

2. 申请新TLAB
   - 需要同步（但频率低）
   - 新TLAB大小根据历史分配动态调整

3. 在共享Eden分配（TLAB不足）
   - 需要同步
   - 如果Eden不足 → 触发Minor GC
```

**JVM参数：**

```bash
-XX:+UseTLAB                 # 启用TLAB（默认开启）
-XX:TLABSize=2m             # 设置TLAB大小
-XX:+ResizeTLAB             # 自动调整TLAB大小
-XX:TLABWasteTargetPercent=1 # TLAB浪费百分比阈值
```

### Q12：写屏障（Write Barrier）在GC中的作用？

**答：**

**写屏障的作用：**

在并发GC中，应用线程可能在GC标记过程中修改对象引用关系。写屏障在每次引用赋值时插入额外逻辑，保证GC正确性。

**类型：**

1. **卡表（Card Table）**：
   - 将堆划分为512字节的卡页
   - 引用修改时标记卡页为"脏"
   - GC时只扫描脏卡页
   - 用于CMS/G1

2. **SATB（Snapshot-At-The-Beginning）**：
   - G1使用
   - 并发标记开始时做快照
   - 记录标记期间的新引用
   - 重新标记阶段处理

3. **增量更新（Incremental Update）**：
   - CMS使用
   - 记录被修改的白色对象
   - 重新标记阶段重新扫描

**实现：**

```java
// JVM在引用赋值时自动插入写屏障
void setField(Object obj, Object ref) {
    obj.field = ref;  // 原始赋值
    write_barrier(obj, ref);  // 写屏障
}
```

**代价：**
- 每次引用赋值都有额外开销
- 但保证了并发GC的正确性

## 引言：微服务架构的本质

微服务架构（Microservices Architecture）不是"把系统拆小"的技术操作，而是一套**围绕业务能力组织团队、以独立部署单元交付价值**的分布式系统工程方法论。

核心认知：

```
单体架构的本质：P(系统) = f(模块1, 模块2, ..., 模块N)
                    所有模块共享进程空间、数据空间、部署单元

微服务架构的本质：P(系统) = P(服务1) × P(服务2) × ... × P(服务N)
                    每个服务是独立的概率空间，通过明确定义的契约交互

质量差异的根源：
- 差的微服务：服务间强耦合，分布式单体，运维复杂度爆炸
- 好的微服务：高内聚低耦合，服务自治，演进式架构
```

**关键洞察**：微服务拆分的成功不取决于技术选型，而取决于**组织边界与业务边界是否对齐**（康威定律）。

## 理论基础：分布式系统的核心原理

### 1. CAP定理与微服务设计

#### CAP定理的数学本质

```
CAP定理（Brewer, 2000）：

分布式系统最多同时满足以下两项：
- Consistency（一致性）：所有节点在同一时间看到相同的数据
- Availability（可用性）：每个请求都能收到非错误的响应
- Partition tolerance（分区容错性）：系统在网络分区时仍能继续运行

证明思路：
假设网络发生分区，节点A和节点B无法通信：
- 如果保证一致性（C）：必须拒绝写入直到分区恢复 → 牺牲可用性（A）
- 如果保证可用性（A）：允许独立写入 → 牺牲一致性（C）

微服务设计启示：
┌─────────────────────────────────────────┐
│  CP系统（强一致性）                       │
│  - 金融核心交易（Zookeeper、etcd）         │
│  - 牺牲可用性保证数据一致                   │
├─────────────────────────────────────────┤
│  AP系统（最终一致性）                     │
│  - 电商订单、社交网络（Eureka、Cassandra）  │
│  - 牺牲一致性保证系统可用                   │
├─────────────────────────────────────────┤
│  CA系统（非分布式）                       │
│  - 传统单机数据库                          │
│  - 网络分区时系统整体不可用                  │
└─────────────────────────────────────────┘
```

**工程实践**：微服务通常选择AP，通过最终一致性保证可用性。

### 2. BASE理论与最终一致性

```
BASE理论（eBay, 2008）：

Basically Available（基本可用）：
- 响应时间延长（如查询从10ms变为100ms）
- 功能降级（如关闭推荐服务，保证核心下单链路）

Soft state（软状态）：
- 数据存在中间状态（如订单"待支付"状态）
- 不同节点数据暂时不一致

Eventually consistent（最终一致）：
- 不保证实时一致
- 保证在一定时间后达到一致

最终一致性的时间边界：
- 强一致性：T = 0（实时）
- 会话一致性：T < 会话超时时间
- 因果一致性：T < 因果传播延迟
- 最终一致性：T < 业务容忍时间（通常秒级到分钟级）
```

### 3. 康威定律与组织设计

```
康威定律（Conway, 1968）：
"设计系统的组织，其产生的设计等价于组织间沟通结构。"

微服务架构的组织映射：

┌─────────────────────────────────────────┐
│           电商平台业务领域                  │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐   │
│  │ 商品团队 │ │ 订单团队 │ │ 用户团队 │   │
│  │ 5-7人   │ │ 5-7人   │ │ 5-7人   │   │
│  └────┬────┘ └────┬────┘ └────┬────┘   │
│       │           │           │         │
│       ↓           ↓           ↓         │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐   │
│  │ Product │ │  Order  │ │  User   │   │
│  │ Service │ │ Service │ │ Service │   │
│  └─────────┘ └─────────┘ └─────────┘   │
└─────────────────────────────────────────┘

反模式：
❌ 按技术层拆分团队：
   - 前端团队、后端团队、DBA团队、运维团队
   - 结果：一个需求需要4个团队协调，沟通成本高

✅ 按业务能力拆分团队（DevOps文化）：
   - 商品团队：包含前端、后端、测试、运维
   - 结果：团队自治，端到端交付
```

## 来龙去脉：微服务架构的发展史

### 第一阶段：单体时代（1990s-2005）

```
单体架构的黄金时代：

┌─────────────────────────────────────────┐
│           Monolithic Application         │
│  ┌─────────────────────────────────────┐│
│  │           Presentation Layer         ││
│  │        JSP / Servlet / Thymeleaf    ││
│  ├─────────────────────────────────────┤│
│  │           Business Layer             ││
│  │        Service / Manager / BO        ││
│  ├─────────────────────────────────────┤│
│  │           Data Access Layer          ││
│  │        DAO / Mapper / Repository     ││
│  ├─────────────────────────────────────┤│
│  │           Database                   ││
│  │        MySQL / Oracle / SQL Server   ││
│  └─────────────────────────────────────┘│
└─────────────────────────────────────────┘

优势：
- 开发简单，IDE支持好
- 部署方便，一个WAR包/JAR包
- 事务简单，本地事务即可
- 测试容易，集成测试覆盖全链路

劣势（随着规模增长）：
- 代码耦合严重，一个改动影响多个模块
- 编译时间长（>10分钟）
- 技术栈锁定，无法升级
- 扩展性差，必须整体扩容
```

```

┌─────────────┐ ┌─────────────┐ ┌─────────────┐
```

#### 聚合根设计

```java
// 聚合根：Order
public class Order extends AggregateRoot<OrderId> {
    private OrderId id;
    private UserId userId;
    private List<OrderItem> items;      // 内部实体
    private OrderStatus status;
    private Money totalAmount;
    private Address shippingAddress;     // 值对象
    private LocalDateTime createdAt;
    
    // 工厂方法
    public static Order create(UserId userId, List<OrderItem> items, Address address) {
        Order order = new Order();
        order.id = OrderId.generate();
        order.userId = userId;
        order.items = new ArrayList<>(items);
        order.status = OrderStatus.PENDING;
        order.shippingAddress = address;
        order.totalAmount = calculateTotal(items);
        order.createdAt = LocalDateTime.now();
        
        // 注册领域事件
        order.registerEvent(new OrderCreatedEvent(order.id));
        return order;
    }
    
    // 业务方法
    public void pay(PaymentId paymentId) {
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException("Order already paid or cancelled");
        }
        this.status = OrderStatus.PAID;
        this.paymentId = paymentId;
        registerEvent(new OrderPaidEvent(this.id, paymentId));
    }
    
    public void cancel() {
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException("Cannot cancel order in status: " + status);
        }
        this.status = OrderStatus.CANCELLED;
        registerEvent(new OrderCancelledEvent(this.id));
    }
    
    public void ship(TrackingNumber trackingNumber) {
        if (status != OrderStatus.PAID) {
            throw new IllegalStateException("Order must be paid before shipping");
        }
        this.status = OrderStatus.SHIPPED;
        this.trackingNumber = trackingNumber;
        registerEvent(new OrderShippedEvent(this.id, trackingNumber));
    }
    
    private static Money calculateTotal(List<OrderItem> items) {
        return items.stream()
            .map(OrderItem::getSubTotal)
            .reduce(Money.ZERO, Money::add);
    }
}

// 内部实体：OrderItem
public class OrderItem extends Entity {
    private ProductId productId;
    private String productName;
    private int quantity;
    private Money unitPrice;
    
    public Money getSubTotal() {
        return unitPrice.multiply(quantity);
    }
}

// 值对象：Money
public class Money implements ValueObject {
    private final BigDecimal amount;
    private final Currency currency;
    
    public Money add(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException("Cannot add different currencies");
        }
        return new Money(this.amount.add(other.amount), this.currency);
    }
    
    public Money multiply(int factor) {
        return new Money(this.amount.multiply(BigDecimal.valueOf(factor)), this.currency);
    }
}
```

### 2. CQRS与事件溯源

```
CQRS（Command Query Responsibility Segregation）：

┌─────────────────────────────────────────┐
```

```java
// Sentinel限流规则
@Configuration
public class SentinelConfig {
    
    @PostConstruct
    public void initRules() {
        List<FlowRule> rules = new ArrayList<>();
        
        // 1. QPS限流：每秒最多1000个请求
        FlowRule qpsRule = new FlowRule();
        qpsRule.setResource("createOrder");
        qpsRule.setGrade(RuleConstant.FLOW_GRADE_QPS);
        qpsRule.setCount(1000);
        qpsRule.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_WARM_UP);
        qpsRule.setWarmUpPeriodSec(10);  // 预热10秒
        rules.add(qpsRule);
        
        // 2. 并发线程数限流：最多50个并发
        FlowRule threadRule = new FlowRule();
        threadRule.setResource("queryOrder");
        threadRule.setGrade(RuleConstant.FLOW_GRADE_THREAD);
        threadRule.setCount(50);
        rules.add(threadRule);
        
        // 3. 热点参数限流：针对某个用户ID限流
        ParamFlowRule paramRule = new ParamFlowRule();
        paramRule.setResource("createOrder");
        paramRule.setParamIdx(0);  // 第1个参数（userId）
        paramRule.setCount(10);    // 每个用户每秒最多10个请求
        rules.add(paramRule);
        
        FlowRuleManager.loadRules(rules);
    }
}

// 限流算法对比：
// 1. 计数器算法：简单，但存在临界问题（1秒内最后和最开始同时突发）
// 2. 滑动窗口算法：平滑，但内存开销大
// 3. 令牌桶算法：允许突发流量，平滑限流（推荐）
// 4. 漏桶算法：固定速率输出，无法应对突发流量
```

```java
// 订单服务核心业务
@Service
public class OrderApplicationService {
    
    @Autowired
    private OrderRepository orderRepository;
    @Autowired
    private DomainEventPublisher eventPublisher;
    @Autowired
    private IdempotencyGuard idempotencyGuard;
    
    /**
     * 创建订单（幂等设计）
     */
    @Transactional
    public OrderDTO createOrder(CreateOrderCommand command) {
        // 1. 幂等检查
        if (!idempotencyGuard.tryProcess(command.getIdempotencyKey(), "CREATE_ORDER")) {
            log.info("Duplicate request detected: {}", command.getIdempotencyKey());
            return orderRepository.findByIdempotencyKey(command.getIdempotencyKey())
                .map(this::convertToDTO)
                .orElseThrow(() -> new DuplicateRequestException("Processing, please wait"));
        }
        
        // 2. 创建领域对象
        Order order = Order.create(
            new UserId(command.getUserId()),
            command.getItems().stream()
                .map(item -> new OrderItem(
                    new ProductId(item.getProductId()),
                    item.getProductName(),
                    item.getQuantity(),
                    new Money(item.getUnitPrice())
                ))
                .collect(Collectors.toList()),
            new Address(command.getShippingAddress())
        );
        
        // 3. 保存订单
        orderRepository.save(order);
        
        // 4. 发布领域事件
        eventPublisher.publish(new OrderCreatedEvent(
            order.getId().getValue(),
            command.getUserId(),
            command.getItems(),
            order.getTotalAmount().getAmount()
        ));
        
        return convertToDTO(order);
    }
    
    /**
     * 支付回调处理
     */
    @Transactional
    public void handlePaymentCallback(PaymentCallback callback) {
        Order order = orderRepository.findById(new OrderId(callback.getOrderId()))
            .orElseThrow(() -> new OrderNotFoundException(callback.getOrderId()));
        
        if (callback.isSuccess()) {
            order.pay(new PaymentId(callback.getPaymentId()));
        } else {
            order.cancel();
        }
        
        orderRepository.save(order);
    }
}

    private PaymentRepository paymentRepository;
    
    @Transactional
    public PaymentDTO createPayment(CreatePaymentCommand command) {
        Payment payment = Payment.create(
            new OrderId(command.getOrderId()),
            new Money(command.getAmount()),
            command.getPaymentMethod()
        );
        
        // 调用第三方支付
        PaymentResult result = paymentGateway.charge(
            payment.getId().getValue(),
            command.getAmount(),
            command.getPaymentMethod(),
            command.getPaymentToken()
        );
        
        if (result.isSuccess()) {
            payment.markAsPaid(result.getTransactionId());
        } else {
            payment.markAsFailed(result.getErrorMessage());
        }
        
        paymentRepository.save(payment);
        return convertToDTO(payment);
    }
}
```

```java
     */
    @Scheduled(fixedRate = 5000)

            .findByStatusAndCreateTimeBefore(
                MessageStatus.PENDING,
                LocalDateTime.now().minusMinutes(5)
            );

                rocketMQTemplate.asyncSend(
                    message.getTopic(),
                    message.getBody(),
                    new SendCallback() {
                        @Override

                            messageRepository.updateStatus(message.getId(), MessageStatus.SENT);
                        }
                        @Override
                        public void onException(Throwable e) {
                            log.error("Failed to send message: {}", message.getId(), e);
                        }
                    }
                );
            } catch (Exception e) {
                log.error("Message send exception: {}", message.getId(), e);

        }
```

## 性能分析与优化策略

### 1. RPC性能对比

```
┌─────────────────────────────────────────┐
│        RPC框架性能对比（本地测试）          │
│                                         │
│  框架        吞吐量(QPS)    延迟(P99)     │
│  ─────────────────────────────────────  │
│  HTTP/REST    10,000       50ms         │
│  gRPC         50,000       10ms         │
│  Dubbo        80,000       5ms          │
│  Thrift       100,000      3ms          │
│  本地调用     1,000,000     0.1ms        │
│                                         │
│  结论：RPC框架比HTTP快5-10倍              │
└─────────────────────────────────────────┘

影响RPC性能的因素：
1. 序列化方式
   - JSON: 文本格式，可读性好，性能一般
   - Protobuf: 二进制，紧凑，性能高（推荐）
   - Hessian: 二进制，Java生态性能好
   - Kryo: 二进制，需要注册类，性能最高

2. 网络模型
   - BIO: 阻塞IO，一个连接一个线程（Tomcat默认）
   - NIO: 非阻塞IO，少量线程处理大量连接（Netty）
   - AIO: 异步IO，内核回调（Linux支持有限）

3. 连接管理
   - 短连接：每次请求新建连接（HTTP/1.0）
   - 长连接：连接复用（HTTP/1.1 Keep-Alive）
   - 连接池：预先建立连接，减少建立开销
```

### 3. 网关性能优化

```
API Gateway性能优化策略：

1. 异步化
   ┌─────────────────────────────────────────┐
   │  同步模式（Tomcat阻塞）                  │
   │  请求 → 线程池等待 → 后端响应 → 返回      │

   - Brotli压缩：比Gzip再小20-30%
```

## 常见陷阱与最佳实践

### 陷阱1：分布式单体（Distributed Monolith）

```
❌ 反模式：分布式单体

┌─────────┐     ┌─────────┐     ┌─────────┐
│ Order   │────→│Payment  │────→│Inventory│
│ Service │     │ Service │     │ Service │
└────┬────┘     └────┬────┘     └────┬────┘
     │               │               │
     └───────────────┼───────────────┘
                     ↓
              ┌─────────────┐
              │  Shared DB  │
              │ (同一个数据库) │
              └─────────────┘

问题：
- 所有服务共享一个数据库
- 服务间通过数据库直接关联
- 一个表变更影响所有服务
- 无法独立部署（数据库Schema变更需要协调）

✅ 最佳实践：数据库按服务隔离

┌─────────┐     ┌─────────┐     ┌─────────┐
│ Order   │     │Payment  │     │Inventory│
│ Service │     │ Service │     │ Service │
└────┬────┘     └────┬────┘     └────┬────┘
     │               │               │
     ↓               ↓               ↓
┌─────────┐     ┌─────────┐     ┌─────────┐
│ Order   │     │ Payment │     │Inventory│
│   DB    │     │   DB    │     │   DB    │
└─────────┘     └─────────┘     └─────────┘

规则：
- 每个服务拥有独立的数据库
- 服务间只能通过API通信
- 禁止直接访问其他服务的数据库
```

### 陷阱2：服务粒度过细

```
❌ 过度拆分示例：
┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
│Create   │ │Cancel   │ │Query    │ │Update   │
│Order    │ │Order    │ │Order    │ │Order    │
│Service  │ │Service  │ │Service  │ │Service  │
└─────────┘ └─────────┘ └─────────┘ └─────────┘

问题：
- 运维成本爆炸（4套CI/CD、监控、日志）
- 分布式事务复杂（一个操作调4个服务）
- 网络RTT累积：4次调用 = 40-80ms额外延迟
- 代码重复（4个服务都有Order模型）

✅ 最佳实践：按业务领域合并
┌─────────────────┐
│   Order Service │
│   - 创建订单    │
│   - 取消订单    │
│   - 查询订单    │
│   - 更新订单    │
└─────────────────┘

- 2披萨团队原则：5-9人维护1-3个服务
- 代码量控制在1-2万行
- 服务数量 = 团队数 * 1.5（经验公式）
```

### 陷阱3：忽略数据一致性与分布式事务

```
❌ 常见错误：
订单服务创建订单后，直接同步调用库存服务扣减

┌─────────┐     ┌─────────┐
│  Order  │────→│ Inventory│
│ Service │  RPC │ Service │
└────┬────┘     └────┬────┘
   创建成功        扣减失败
→ 数据不一致（有订单无库存）

✅ 最佳实践：
1. 优先使用最终一致性（消息队列+本地消息表）
2. 核心链路使用TCC或Saga
3. 避免在微服务中追求强一致性（2PC性能差）
4. 设计补偿机制：订单创建失败回滚库存
```

### 陷阱4：循环依赖

```java
❌ 循环依赖问题：
// OrderService依赖PaymentService
@Service
public class OrderService {
    @Autowired
    private PaymentService paymentService;

// PaymentService依赖OrderService

    private EventPublisher eventPublisher;

@Service

    @EventListener
    public void onOrderCreated(OrderCreatedEvent event) {
        // 处理支付逻辑
    }

// 方案2：分层依赖（单向依赖）
// 应用层 → 领域层 → 基础设施层
// 上层依赖下层，下层不依赖上层
```

### 陷阱5：缺乏可观测性

```
❌ 反模式：
- 没有统一日志规范，排查问题困难
- 没有链路追踪，不知道请求经过哪些服务
- 没有指标监控，无法及时发现性能退化
- 没有告警机制，故障后知后觉

✅ 最佳实践：可观测性三大支柱

1. 日志（Logging）
   - 统一格式：时间 | 级别 | TraceId | SpanId | 服务名 | 消息
   - 集中收集：ELK（Elasticsearch + Logstash + Kibana）
   - 结构化日志：JSON格式，便于查询

2. 指标（Metrics）
   - 业务指标：订单量、支付成功率
   - 系统指标：CPU、内存、磁盘、网络
   - 应用指标：QPS、延迟、错误率
   - 存储：Prometheus + Grafana

3. 链路追踪（Tracing）
   - 每个请求生成唯一TraceId
   - 记录每个Span的耗时和状态
   - 可视化调用链：Jaeger / Zipkin
```

### 最佳实践总结

```
微服务架构最佳实践清单：

1. 设计原则
   □ 按业务能力拆分，而非技术层次
   □ 服务自治：独立代码库、数据库、部署
   □ API优先：先定义契约，再实现服务
   □ 容错设计：假设依赖服务会失败

2. 通信策略
   □ 内部服务用gRPC/Dubbo（高性能）
   □ 外部API用REST（兼容性）
   □ 异步流程用消息队列（解耦）
   □ 避免同步调用链过长（<3层）

3. 数据管理
   □ 每个服务一个数据库
   □ 使用Saga或TCC处理分布式事务
   □ 读写分离，读多写少用CQRS
   □ 缓存策略：本地缓存+分布式缓存

4. 运维保障
   □ CI/CD自动化部署
   □ 蓝绿部署/金丝雀发布
   □ 自动化测试（单元/集成/契约）
   □ 完善的监控告警体系

5. 安全设计
   □ 零信任架构：服务间也需要认证
   □ API网关统一鉴权
   □ 敏感数据加密传输（TLS/mTLS）
   □ 限流防刷，防止DDoS
```

## 面试题与参考答案

**Q1：微服务拆分有哪些原则？**

> 核心原则包括：
> 1. **单一职责**：一个服务只负责一个业务领域，如订单服务只处理订单
> 2. **高内聚低耦合**：服务内部紧密相关，服务间通过接口通信
> 3. **服务自治**：独立代码库、独立数据库、独立部署、独立团队
> 4. **2披萨团队**：5-9人团队维护，避免过大或过小
> 5. **康威定律对齐**：组织架构与服务边界匹配

**Q2：DDD中的聚合和实体有什么区别？**

> - **实体（Entity）**：有唯一标识，标识不变属性可变，如User（userId不变）
> - **值对象（Value Object）**：无唯一标识，不可变，如Address、Money
> - **聚合（Aggregate）**：一组相关对象的集合，有根实体，外部只能通过根实体访问内部对象
>
> 示例：Order聚合包含Order（根实体）、OrderItem（实体）、Money（值对象）

**Q3：什么是CQRS模式？**

> **CQRS（Command Query Responsibility Segregation）**：命令与查询职责分离。
>
> - **写模型（Command）**：处理业务逻辑，写入Event Store
> - **读模型（Query）**：从Read DB查询，数据通过Projection同步
>
> 优势：读写分离可独立优化，读模型可冗余存储提升查询性能。适用于读多写少、查询模型复杂的场景。

**Q4：微服务间通信如何选择同步还是异步？**

> | 维度 | 同步（REST/gRPC） | 异步（消息队列） |
> |------|------------------|-----------------|
> | 一致性 | 强一致性 | 最终一致性 |
> | 性能 | 有网络延迟 | 低延迟，削峰填谷 |
> | 耦合 | 调用方依赖被调用方 | 解耦 |
> | 适用场景 | 实时查询、简单调用 | 订单创建、事件通知 |
>
> 建议：核心业务流程用异步保证可用性，查询场景用同步保证实时性。

**Q5：单体应用如何平滑迁移到微服务？**

> **演进式拆分路径**：
> 1. **数据库拆分**：先垂直分库，按领域拆分数据库（低风险）
> 2. **代码拆分**：提取独立模块为Jar包，保持单体部署
> 3. **服务提取**：将稳定模块抽取为独立服务（如用户服务）
> 4. **流量切换**：使用Feature Switch灰度切换流量
> 5. **数据同步**：双写或监听Binlog保证数据一致
>
> 关键：不要一次性全拆，优先拆分边界清晰的模块，逐步验证。

**Q6：BFF模式解决了什么问题？**

> **BFF（Backend for Frontend）**：为不同客户端提供专门的API层。
>
> 解决的问题：
> 1. 移动端和Web端数据需求不同，直接调用后端服务导致过多请求或数据冗余
> 2. 前端需要聚合多个服务数据，逻辑放在前端不合理
>
> 实现：Web BFF和Mobile BFF分别聚合底层服务，提供定制化API。

**Q7：什么是服务网格（Service Mesh）？**

> **服务网格**：将服务治理能力从业务代码中抽离，下沉到基础设施层。
>
> 架构：每个Pod部署一个Sidecar代理（如Envoy），接管所有网络通信。
>
> 优势：
> - 业务代码零侵入
> - 多语言支持
> - 集中式流量管理
>
> 劣势：
> - 增加延迟（Sidecar转发）
> - 资源开销（每个Pod额外消耗）
> - 运维复杂度增加

**Q8：熔断器的工作原理是什么？**

> 熔断器三种状态：
> 1. **Closed（关闭）**：正常放行请求
> 2. **Open（打开）**：失败率超过阈值，拒绝请求快速失败
> 3. **Half-Open（半开）**：超时后允许少量请求试探
>
> 关键参数：失败率阈值、慢调用阈值、半开状态请求数、打开状态持续时间。

**Q9：如何保证微服务的数据一致性？**

> 方案选择：
> - **强一致性**：2PC/XA（金融转账，性能差）
> - **最终一致性**：
>   - TCC：Try-Confirm-Cancel，适合电商下单
>   - Saga：长事务拆分，适合旅游预订
>   - 本地消息表：异步场景，简单可靠
>   - MQ事务消息：RocketMQ半消息
>
> 建议：99%场景用最终一致性，只有极少数金融场景需要强一致。

**Q10：微服务架构的性能优化手段有哪些？**

> 1. **通信优化**：gRPC替代REST，连接池，长连接
> 2. **缓存优化**：多级缓存（本地+分布式），缓存预热
> 3. **数据库优化**：分库分表，读写分离，索引优化
> 4. **异步化**：MQ削峰，异步处理非核心流程
> 5. **服务治理**：熔断限流，防止雪崩
> 6. **序列化优化**：Protobuf/Kryo替代JSON
> 7. **JVM优化**：GC调优，内存分配

## 引言：设计模式的本质

设计模式（Design Patterns）不是"代码模板"，而是**在特定场景下解决特定问题的经过验证的面向对象设计经验**。

核心认知：

```
设计模式的本质：

┌─────────────────────────────────────────┐
│  设计模式 = 问题 + 场景 + 解决方案       │
│                                         │
│  问题（Problem）：                       │
│  - 如何在保证线程安全的前提下延迟初始化？ │
│  - 如何解耦对象的创建和使用？             │
│  - 如何实现对象间的一对多通知？           │
│                                         │
│  场景（Context）：                       │
│  - 高并发环境                            │
│  - 多态创建需求                          │
│  - 事件驱动架构                          │
│                                         │
│  解决方案（Solution）：                   │
│  - 单例模式（Singleton）                 │
│  - 工厂模式（Factory）                   │
│  - 观察者模式（Observer）                │
│                                         │
│  关键洞察：                              │
│  设计模式不是发明，而是发现              │
│  是前人踩坑后的经验总结                  │
└─────────────────────────────────────────┘

设计模式的价值：
1. 复用经验：避免重复踩坑
2. 统一语言：团队成员能快速理解设计意图
3. 提高可维护性：代码结构清晰，易于扩展
4. 不是银弹：不能滥用，需结合实际场景

设计模式的局限：
- 过度设计：简单问题复杂化
- 性能损耗：增加抽象层次
- 学习成本：需要理解模式意图
```

## 理论基础：面向对象设计原则

### 1. SOLID原则

```
SOLID原则：面向对象设计的五大原则

┌─────────────────────────────────────────┐
│  S - 单一职责原则（Single Responsibility）│
│  一个类只负责一件事                       │
│                                         │
│  反例：                                   │
│  class UserService {                      │
│      void createUser() {}                 │
│      void sendEmail() {}    ← 邮件发送    │
│      void generateReport() {} ← 报表生成  │
│      void backupData() {}   ← 数据备份    │
│  }                                        │
│                                         │
│  正例：                                   │
│  class UserService { void createUser() {} }│
│  class EmailService { void sendEmail() {} }│
│  class ReportService { void generateReport() {} }│
│  class BackupService { void backupData() {} }│
├─────────────────────────────────────────┤
│  O - 开闭原则（Open/Closed）              │
│  对扩展开放，对修改关闭                     │
│                                         │
│  反例：                                   │
│  if (type.equals("ALI")) {                │
│      // 支付宝支付逻辑                     │
│  } else if (type.equals("WECHAT")) {      │
│      // 微信支付逻辑                       │
│  }                                        │
│                                         │
│  正例：                                   │
│  interface Payment { void pay(); }        │
│  class AliPay implements Payment { ... }  │
│  class WeChatPay implements Payment { ... }│
│  // 新增支付方式只需新增类，不修改已有代码  │
├─────────────────────────────────────────┤
│  L - 里氏替换原则（Liskov Substitution）  │
│  子类可以替换父类而不影响程序正确性          │
│                                         │
│  反例：                                   │
│  class Rectangle {                        │
│      void setWidth(int w) { this.width = w; }│
│      void setHeight(int h) { this.height = h; }│
│  }                                        │
│  class Square extends Rectangle {         │
│      void setWidth(int w) {               │
│          this.width = w;                  │
│          this.height = w;  ← 破坏了父类行为│
│      }                                    │
│  }                                        │
│                                         │
│  正例：Square不应该继承Rectangle          │
│       应该作为独立类或使用组合              │
├─────────────────────────────────────────┤
│  I - 接口隔离原则（Interface Segregation）│
│  客户端不应该依赖它不需要的接口              │
│                                         │
│  反例：                                   │
│  interface Worker {                       │
│      void work();                         │
│      void eat();                          │
│  }                                        │
│  class Robot implements Worker {          │
│      void work() {}                       │
│      void eat() { throw new UnsupportedOperationException(); }│
│  }                                        │
│                                         │
│  正例：                                   │
│  interface Workable { void work(); }      │
│  interface Eatable { void eat(); }        │
│  class Robot implements Workable { ... }  │
│  class Human implements Workable, Eatable { ... }│
├─────────────────────────────────────────┤
│  D - 依赖倒置原则（Dependency Inversion） │
│  高层模块不应该依赖低层模块，两者都应该依赖抽象│
│                                         │
│  反例：                                   │
│  class OrderService {                     │
│      private MySQLRepository repo = new MySQLRepository();│
│  }                                        │
│                                         │
│  正例：                                   │
│  interface OrderRepository { ... }        │
│  class OrderService {                     │
│      private OrderRepository repo;        │
│      OrderService(OrderRepository repo) { │
│          this.repo = repo;                │
│      }                                    │
│  }                                        │
└─────────────────────────────────────────┘
```

### 2. 其他重要设计原则

```
其他设计原则：

1. DRY（Don't Repeat Yourself）：
   - 不要重复自己
   - 提取公共逻辑到方法/类/模块

2. KISS（Keep It Simple, Stupid）：
   - 保持简单
   - 能用简单方案就不用复杂方案

3. YAGNI（You Aren't Gonna Need It）：
   - 不要提前实现不需要的功能
   - 避免过度设计

4. 组合优于继承（Composition over Inheritance）：
   - 优先使用组合实现代码复用
   - 继承是强耦合，组合是松耦合

5. 迪米特法则（Law of Demeter）：
   - 一个对象应该对其他对象有最少的了解
   - 不要调用"朋友的的朋友"
```

#### 饿汉式（Eager Initialization）

```java
/**
 * 饿汉式单例
 * 
 * 原理：类加载时就创建实例
 * 优点：简单，线程安全
 * 缺点：不延迟加载，可能浪费资源
 */
public class SingletonHungry {
    
    // 类加载时立即创建实例
    private static final SingletonHungry INSTANCE = new SingletonHungry();
    
    // 私有构造器
    private SingletonHungry() {
        // 防止反射攻击
        if (INSTANCE != null) {
            throw new RuntimeException("单例已存在，禁止反射创建");
        }
    }
    
    public static SingletonHungry getInstance() {
        return INSTANCE;
    }
    
    // 业务方法
    public void doSomething() {
        System.out.println("Doing something...");
    }
    
    // 防止序列化破坏单例
    private Object readResolve() {
        return INSTANCE;
    }
}
```

#### DCL双检锁（Double-Checked Locking）

```java
/**
 * DCL双检锁单例
 * 
 * 原理：两次检查 + synchronized + volatile
 * 优点：延迟加载，线程安全，高性能
 * 缺点：代码较复杂
 */
public class SingletonDCL {
    
    /**
     * volatile关键字的作用：
     * 1. 保证可见性：一个线程修改后，其他线程立即可见
     * 2. 禁止指令重排序：防止 new 操作的重排序问题
     * 
     * 为什么需要volatile？
     * instance = new SingletonDCL() 分为三步：
     * 1. 分配内存空间
     * 2. 初始化对象
     * 3. 将引用指向内存地址
     * 
     * 编译器/CPU可能重排序为 1 -> 3 -> 2
     * 如果线程A执行到3但还没执行2，线程B检查发现 instance != null
     * 直接返回未初始化的对象，调用方法会NPE
     * 
     * volatile通过内存屏障禁止重排序，保证 2 在 3 之前执行
     */
    private static volatile SingletonDCL instance;
    
    private SingletonDCL() {
        if (instance != null) {
            throw new RuntimeException("单例已存在");
        }
    }
    
    public static SingletonDCL getInstance() {
        // 第一次检查（无锁）
        if (instance == null) {
            // 同步块
            synchronized (SingletonDCL.class) {
                // 第二次检查（有锁）
                if (instance == null) {
                    instance = new SingletonDCL();
                }
            }
        }
        return instance;
    }
}
```

#### 静态内部类（Static Inner Class）★推荐

```java
/**
 * 静态内部类单例 ★最推荐的Java实现
 * 
 * 原理：利用类加载机制保证线程安全
 * 
 * JVM保证：
 * 1. 类加载是线程安全的（JVM内部加锁）
 * 2. 静态内部类只有被使用时才加载（延迟加载）
 * 
 * 优点：
 * - 线程安全（JVM保证）
 * - 延迟加载（内部类首次调用时加载）
 * - 无锁（性能最高）
 * - 代码简洁
 */
public class SingletonStatic {
    
    private SingletonStatic() {
        // 防反射
        if (Holder.INSTANCE != null) {
            throw new RuntimeException("单例已存在");
        }
    }
    
    /**
     * 静态内部类
     * - SingletonStatic加载时，Holder不会加载
     * - 只有调用getInstance()时，Holder才加载
     * - Holder加载时创建INSTANCE（线程安全）
     */
    private static class Holder {
        private static final SingletonStatic INSTANCE = new SingletonStatic();
    }
    
    public static SingletonStatic getInstance() {
        return Holder.INSTANCE;
    }
    
    private Object readResolve() {
        return Holder.INSTANCE;
    }
}
```

#### 枚举（Enum）★最推荐

```java
/**
 * 枚举单例 ★最推荐的实现（Joshua Bloch推荐）
 * 
 * 原理：枚举底层就是静态常量
 * 
 * 优点：
 * 1. 线程安全（类加载机制保证）
 * 2. 防反射（枚举构造器由JVM控制，反射newInstance()抛异常）
 * 3. 防序列化（反序列化时JVM直接返回枚举常量）
 * 4. 代码最简洁
 * 
 * 缺点：
 * 1. 不是懒加载（类加载时创建）
 * 2. 不能继承其他类（枚举隐式继承java.lang.Enum）
 */
public enum SingletonEnum {
    INSTANCE;
    
    // 可以定义字段和方法
    private String config;
    
    SingletonEnum() {
        // 初始化逻辑
        this.config = loadConfig();
    }
    
    public void doSomething() {
        System.out.println("Doing something with config: " + config);
    }
    
    private String loadConfig() {
        return "loaded config";
    }
}

// 使用
SingletonEnum.INSTANCE.doSomething();
```

#### 破坏与防护

```java
/**
 * 单例的破坏与防护
 */
public class SingletonDefense {
    
    private static final SingletonDefense INSTANCE = new SingletonDefense();
    
    /**
     * 防护1：防反射
     */
    private SingletonDefense() {
        if (INSTANCE != null) {
            throw new RuntimeException("单例已存在，禁止通过反射创建");
        }
    }
    
    public static SingletonDefense getInstance() {
        return INSTANCE;
    }
    
    /**
     * 防护2：防序列化
     * 
     * 原理：反序列化时会调用readResolve()方法
     * 如果定义了此方法，则返回该方法的返回值，而不是创建新对象
     */
    private Object readResolve() {
        return INSTANCE;
    }
    
    /**
     * 防护3：防克隆
     */
    @Override
    protected Object clone() throws CloneNotSupportedException {
        throw new CloneNotSupportedException("单例对象不允许克隆");
    }
}

/**
 * 攻击测试
 */
class SingletonAttackTest {
    public static void main(String[] args) throws Exception {
        // 1. 反射攻击（被防护）
        try {
            Constructor<SingletonDefense> constructor = SingletonDefense.class.getDeclaredConstructor();
            constructor.setAccessible(true);
            SingletonDefense s2 = constructor.newInstance();
        } catch (Exception e) {
            System.out.println("反射攻击失败：" + e.getMessage());
        }
        
        // 2. 序列化攻击（被防护）
        SingletonDefense s1 = SingletonDefense.getInstance();
        ByteArrayOutputStream baos = new ByteArrayOutputStream();
        ObjectOutputStream oos = new ObjectOutputStream(baos);
        oos.writeObject(s1);
        
        ByteArrayInputStream bais = new ByteArrayInputStream(baos.toByteArray());
        ObjectInputStream ois = new ObjectInputStream(bais);
        SingletonDefense s3 = (SingletonDefense) ois.readObject();
        
        System.out.println("s1 == s3: " + (s1 == s3)); // true
    }
}
```

### 2. 工厂模式（Factory）

#### 三种工厂模式对比

```
工厂模式家族：

┌─────────────────────────────────────────┐
│  简单工厂（Simple Factory）              │
│  - 一个工厂类创建多种产品                │
│  - 不符合开闭原则                        │
│  - 适合产品类型少且稳定                  │
│                                         │
│  工厂方法（Factory Method）              │
│  - 一个工厂创建一种产品                  │
│  - 符合开闭原则                          │
│  - 产品类型可能扩展                      │
│                                         │
│  抽象工厂（Abstract Factory）            │
│  - 一个工厂创建一组产品族                │
│  - 适合创建多个相关/依赖的产品           │
│  - 如：UI组件（Button + Text + Checkbox）│
└─────────────────────────────────────────┘
```

#### 简单工厂

```java
/**
 * 简单工厂模式
 * 
 * 场景：根据类型创建不同的支付渠道
 */
// 产品接口
public interface Payment {
    void pay(BigDecimal amount);
    void refund(String orderId);
}

// 具体产品
public class AliPay implements Payment {
    @Override
    public void pay(BigDecimal amount) {
        System.out.println("支付宝支付: ¥" + amount);
    }
    
    @Override
    public void refund(String orderId) {
        System.out.println("支付宝退款, 订单: " + orderId);
    }
}

public class WeChatPay implements Payment {
    @Override
    public void pay(BigDecimal amount) {
        System.out.println("微信支付: ¥" + amount);
    }
    
    @Override
    public void refund(String orderId) {
        System.out.println("微信退款, 订单: " + orderId);
    }
}

public class UnionPay implements Payment {
    @Override
    public void pay(BigDecimal amount) {
        System.out.println("银联支付: ¥" + amount);
    }
    
    @Override
    public void refund(String orderId) {
        System.out.println("银联退款, 订单: " + orderId);
    }
}

// 简单工厂
public class PaymentFactory {
    
    /**
     * 根据类型创建支付渠道
     * 
     * 问题：新增支付渠道需要修改此类，违反开闭原则
     */
    public static Payment createPayment(String type) {
        switch (type.toUpperCase()) {
            case "ALI":

│                                         │
│  5. 对象参数很多，且大部分是可选的？      │
│     → 建造者模式（Builder）★推荐         │
└─────────────────────────────────────────┘
```

│     → 外观模式（Facade）                 │

│  4. 需要将抽象和实现解耦？                │
│     → 桥接模式（Bridge）                 │
│                                         │
│  5. 需要共享大量细粒度对象？              │
│     → 享元模式（Flyweight）              │
└─────────────────────────────────────────┘
```

## 性能分析：设计模式的代价与优化

### 1. 单例模式性能分析

```
单例模式性能对比：

┌─────────────────────────────────────────┐
│  实现方式        获取实例耗时            │
│  ─────────────────────────────────────  │
│  饿汉式          ~1ns（直接返回常量）    │
│  懒汉式          ~5ns（需要判断）        │
│  同步方法        ~50ns（需要加锁）       │

│  静态内部类      ~1ns（类加载时已创建）  │
│  枚举            ~1ns（常量访问）        │
│                                         │
│  结论：单例模式性能开销极小              │
│  推荐使用：静态内部类或枚举              │
└─────────────────────────────────────────┘
```

### 2. 工厂模式性能分析

```
工厂模式性能开销：

简单工厂：
- 一次switch判断：~5ns
- 可忽略

工厂方法：
- 创建工厂对象：~10ns
- 创建产品对象：取决于产品复杂度
- 可忽略

抽象工厂：
- 创建工厂对象：~10ns
- 创建一组产品：取决于产品复杂度

## 常见陷阱与最佳实践

### 陷阱1：单例被序列化/反射破坏却未防护

```java
// 错误：没有readResolve和构造器防护
public class Singleton implements Serializable {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }
}

// 问题：反序列化会创建新实例
Singleton s1 = Singleton.getInstance();
Singleton s2 = (Singleton) new ObjectInputStream(...).readObject();
System.out.println(s1 == s2); // false

// 最佳实践：
// 1. 添加 readResolve() 返回 INSTANCE
// 2. 构造器中判断 if (INSTANCE != null) throw new RuntimeException(...)
// 3. 或者直接用枚举（最省心）
```

### 陷阱2：简单工厂变成"上帝类"

```java
// 错误：一个工厂创建所有产品
public class GodFactory {
    public static Object create(String type) {
        if (type.equals("A")) return new ProductA();
        if (type.equals("B")) return new ProductB();
        // ... 几十种产品
        return null;
    }
}

// 最佳实践：
// 1. 产品过多时升级到工厂方法或抽象工厂
// 2. 用Map + Spring依赖注入自动收集策略
// 3. 每个工厂只负责一个产品族或一类产品

// 优化：使用Map自动注册
@Component
public class PaymentFactory {
    private final Map<String, Payment> paymentMap = new HashMap<>();
    
    @Autowired
    public PaymentFactory(List<Payment> payments) {
        for (Payment payment : payments) {
            paymentMap.put(payment.getType(), payment);
        }
    }
    
    public Payment getPayment(String type) {
        return paymentMap.get(type);
    }
}
```

### 陷阱3：观察者模式中忘记移除监听者导致内存泄漏

```java
// 错误：注册了观察者但从不注销
publisher.registerObserver(this);
// 对象用完不remove，Observer一直持有引用，GC无法回收

// 最佳实践：
// 1. 在 destroy()、close() 或 @PreDestroy 中注销观察者
// 2. 使用弱引用（WeakReference）存储观察者
// 3. 或者使用Guava EventBus的 @AllowConcurrentEvents 配合自动注销机制

// 弱引用示例
public class WeakSubject {
    private List<WeakReference<Observer>> observers = new ArrayList<>();
    
    public void notifyObservers() {
        Iterator<WeakReference<Observer>> it = observers.iterator();
        while (it.hasNext()) {
            Observer observer = it.next().get();
            if (observer == null) {
                it.remove();  // 自动清理已回收的观察者
            } else {
                observer.update(message);
            }
        }
    }
}
```

### 陷阱4：滥用单例导致全局状态难以测试

```java
// 错误：到处直接调用 Singleton.getInstance()
public void process() {
    ConfigManager.getInstance().getXxx(); // 硬编码依赖
}

// 最佳实践：
// 1. 通过构造器或Setter注入单例对象，方便Mock测试
// 2. Spring中直接 @Autowired 注入，不要手动 getInstance()
// 3. 单例只应保存无状态或不可变状态

// 优化：依赖注入
@Service
public class OrderService {
    @Autowired
    private ConfigManager configManager;  // 可Mock
    
    public void process() {
        configManager.getXxx();
    }
}
```

### 陷阱5：过度设计——简单问题复杂化

```
❌ 错误：
一个简单的工具类，用了工厂+单例+代理+装饰器

public class StringUtils {
    private static StringUtils instance;
    
    public static StringUtils getInstance() {
        if (instance == null) {
            synchronized (StringUtils.class) {
                if (instance == null) {
                    instance = new StringUtils();
                }
            }
        }
        return instance;
    }
    
    private StringUtils() {}
    
    public String trim(String str) {
        return str.trim();
    }
}

✅ 最佳实践：
1. 简单问题用简单方案
2. 模式是为了解决问题，不是炫技
3. YAGNI原则：不需要就不要做
4. KISS原则：保持简单

StringUtils的正确写法：
public final class StringUtils {
    private StringUtils() {}
    
    public static String trim(String str) {
        return str == null ? null : str.trim();
    }
}
```

## 面试题与参考答案

### Q1：单例模式有几种实现方式？各有什么优缺点？

**答：**

| 实现 | 线程安全 | 延迟加载 | 性能 | 推荐度 |
|------|---------|---------|------|--------|
| 饿汉式 | ✓ | ✗ | 高 | ⭐⭐⭐ |
| 懒汉式 | ✗ | ✓ | 低 | ⭐ |
| 同步方法 | ✓ | ✓ | 低 | ⭐⭐ |
| DCL双检锁 | ✓ | ✓ | 高 | ⭐⭐⭐⭐ |
| 静态内部类 | ✓ | ✓ | 高 | ⭐⭐⭐⭐⭐ |
| 枚举 | ✓ | ✗ | 高 | ⭐⭐⭐⭐⭐ |

**推荐**：静态内部类（延迟加载+高性能）或枚举（防反射+防序列化）。

### Q2：DCL为什么要用volatile？不用会有什么后果？

**答：**

`instance = new Singleton()` 不是原子操作，分为三步：
1. 分配内存
2. 初始化对象
3. 引用指向内存地址

编译器/CPU可能指令重排为 `1 → 3 → 2`。如果线程A执行到3但还没执行2，线程B检查发现 `instance != null` 直接返回，此时拿到的是**未初始化的对象**，调用方法会NPE或产生不可预期行为。

`volatile` 通过内存屏障禁止指令重排，保证 `2` 在 `3` 之前执行。

### Q3：简单工厂、工厂方法、抽象工厂的核心区别是什么？

**答：**

| 维度 | 简单工厂 | 工厂方法 | 抽象工厂 |
|------|---------|---------|---------|
| 产品数量 | 一个工厂创建多种产品 | 一个工厂创建一种产品 | 一个工厂创建一组产品族 |
| 扩展性 | 修改工厂类，不符合开闭原则 | 新增工厂类即可，符合开闭原则 | 新增产品族需新增工厂 |
| 复杂度 | 低 | 中 | 高 |
| 适用场景 | 产品类型少且稳定 | 产品类型可能扩展 | 需要创建多个相关/依赖的产品 |

### Q4：观察者模式和发布-订阅模式有什么区别？

**答：**

- **观察者模式**：Subject和Observer直接耦合，Subject维护Observer列表，直接调用 `update()`
- **发布-订阅模式**：引入事件中心（Broker），发布者和订阅者不直接知道对方，通过Broker中转

在代码实现上，Spring的 `@EventListener` 和Guava EventBus更接近发布-订阅，因为存在中间调度层。

### Q5：Spring框架用到了哪些设计模式？

**答：**

1. **工厂模式**：BeanFactory、ApplicationContext
2. **单例模式**：Bean默认作用域为singleton
3. **代理模式**：AOP（JDK动态代理、CGLIB代理）
4. **观察者模式**：事件机制（ApplicationEvent、@EventListener）
5. **模板方法模式**：JdbcTemplate、RestTemplate
6. **装饰器模式**：HttpServletRequestWrapper
7. **适配器模式**：HandlerAdapter、AnnotationMethodHandlerAdapter
8. **策略模式**：@Transactional的传播行为、资源加载策略
9. **责任链模式**：Interceptor链

### Q6：策略模式和状态模式有什么区别？

**答：**

- **策略模式**：客户端主动选择策略，策略之间是平行的替换关系。如：排序算法（冒泡、快速、归并）。
- **状态模式**：状态转换由内部规则驱动，状态之间有流转关系。如：订单状态（待支付→已支付→已发货→已完成）。

**关键区别**：策略模式是"选择"，状态模式是"流转"。

### Q7：代理模式和装饰器模式有什么区别？

**答：**

- **代理模式**：控制访问，代理类和被代理类通常实现相同接口，客户端不直接访问被代理类。如：权限控制、延迟加载。
- **装饰器模式**：动态添加功能，装饰器和被装饰器实现相同接口，可以嵌套多个装饰器。如：Java IO流（BufferedInputStream装饰FileInputStream）。

**关键区别**：代理模式强调"控制访问"，装饰器模式强调"增强功能"。

### Q8：什么是设计模式的"反模式"（Anti-pattern）？

**答：**

反模式是看似正确但实际上会导致问题的常见做法：

1. **上帝类（God Class）**：一个类做所有事情
2. **贫血模型（Anemic Domain Model）**：只有getter/setter，没有业务逻辑
3. **循环依赖（Circular Dependency）**：A依赖B，B依赖A
4. **硬编码（Hard Coding）**：配置写死在代码中
5. **复制粘贴编程（Copy-Paste Programming）**：重复代码
6. **过度工程（Over-engineering）**：简单问题复杂化

### Q9：在实际项目中，如何避免过度使用设计模式？

**答：**

1. **YAGNI原则**：不需要就不要做
2. **KISS原则**：保持简单
3. **先实现，后优化**：先写简单方案，需要时再重构
4. **代码 review**：团队成员互相审查
5. **性能测试**：证明模式带来的性能损耗可接受
6. **文档说明**：使用模式时注释说明为什么用

### Q10：手写一个线程安全的单例，要求懒加载且高性能

**答：**

**推荐静态内部类写法：**

```java
public class Singleton {
    private Singleton() {
        if (Holder.INSTANCE != null) {
            throw new RuntimeException("单例已存在");
        }
    }
    
    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }
    
    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
    
    private Object readResolve() {
        return Holder.INSTANCE;
    }
}
```

- **懒加载**：`Holder` 类只有被调用时才加载
- **线程安全**：类加载机制天然保证
- **无锁**：无需 `synchronized`，性能最高

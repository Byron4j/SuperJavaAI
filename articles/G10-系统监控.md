## 引言：可观测性的本质

系统监控与可观测性（Observability）不是"装个Prometheus看看CPU使用率"的入门操作，而是一门**通过外部输出推断内部系统状态**的工程技术。

核心认知：

```
监控 vs 可观测性：

监控（Monitoring）：
- 回答："系统是否正常工作？"
- 方式：预设指标 + 阈值告警
- 局限：只能发现已知问题

可观测性（Observability）：
- 回答："系统为什么不正常？"
- 方式：Metrics + Logging + Tracing 组合探索
- 能力：发现未知问题，定位根因

┌─────────────────────────────────────────┐
│         可观测性三大支柱                  │
│                                         │
│  Metrics（指标）：发生了什么？            │
│  - QPS、RT、错误率、饱和度                │
│  - CPU、内存、磁盘、网络                  │
│  - 业务指标（订单量、支付成功率）          │
│                                         │
│  Logging（日志）：为什么发生？            │
│  - 应用日志、访问日志、审计日志            │
│  - 错误堆栈、上下文信息                    │
│                                         │
│  Tracing（链路）：在哪里发生？            │
│  - 请求全链路追踪                          │
│  - 服务调用关系、性能瓶颈定位              │
│                                         │
│  ┌─────────────────────────────────┐    │
│  │  三者关系：                      │    │
│  │  Metrics发现异常 → Tracing定位  │    │
│  │  服务 → Logging查看详细错误      │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────┘
```

**关键洞察**：可观测性的度量不是"采集了多少指标"，而是**从发现问题到定位根因的平均时间（MTTR）**。

## 理论基础：监控体系的科学原理

### 1. 可观测性的数学基础

#### 控制论与可观测性

```
控制论中的可观测性（Observability）：

系统状态：x(t) ∈ R^n
系统输出：y(t) = C · x(t)

可观测性定义：
如果通过有限时间内的输出 y(t)，
可以唯一确定系统的初始状态 x(0)，
则称该系统是完全可观测的。

软件系统的可观测性：
系统内部状态：内存、线程、连接池、业务逻辑...
系统外部输出：Metrics、Logs、Traces

完全可观测条件：
1. Metrics覆盖关键状态变量
2. Logs包含足够的上下文信息
3. Traces覆盖所有请求路径
```

#### 信息论视角

```
监控系统的信息熵分析：

日志的信息量：
H(Log) = -Σ P(event_i) · log₂ P(event_i)

- ERROR日志：概率低，信息量大
- INFO日志：概率高，信息量小
- DEBUG日志：概率极高，信息量极小

优化原则：
1. 高信息量事件（错误、异常）必须记录
2. 低信息量事件（正常心跳）采样记录
3. 避免信息过载（告警疲劳 = 高熵噪声）
```

### 2. Metrics的科学分类

#### 四种核心指标类型

```
Prometheus指标类型：

┌─────────────────────────────────────────┐
│ 1. Counter（计数器）                     │
│                                         │
│    特征：单调递增，只能增加或重置为0      │
│    数学：f(t) ≥ f(t-1)                   │
│    示例：                                 │
│    - http_requests_total                 │
│    - errors_total                        │
│    - bytes_sent_total                    │
│                                         │
│    使用：rate(http_requests_total[5m])   │
│    → 计算每秒请求率                       │
├─────────────────────────────────────────┤
│ 2. Gauge（仪表盘）                       │
│                                         │
│    特征：可增可减的瞬时值                 │
│    数学：f(t) ∈ R                        │
│    示例：                                 │
│    - cpu_usage_percent                   │
│    - memory_used_bytes                   │
│    - queue_length                        │
│    - temperature                         │
│                                         │
│    使用：直接查询当前值                   │
├─────────────────────────────────────────┤
│ 3. Histogram（直方图）                   │
│                                         │
│    特征：采样分布，分到预设bucket中       │
│    结构：                                 │
│    - <basename>_bucket{le="0.1"}        │
│    - <basename>_bucket{le="0.5"}        │
│    - <basename>_bucket{le="1"}          │
│    - <basename>_bucket{le="+Inf"}       │
│    - <basename>_sum                      │
│    - <basename>_count                    │
│                                         │
│    使用：histogram_quantile(0.99, ...)   │
│    → 计算P99分位数                        │
├─────────────────────────────────────────┤
│ 4. Summary（摘要）                       │
│                                         │
│    特征：客户端计算分位数                 │
│    结构：                                 │
│    - <basename>{quantile="0.5"}         │
│    - <basename>{quantile="0.99"}        │
│    - <basename>_sum                      │
│    - <basename>_count                    │
│                                         │
│    特点：分位数准确，但无法跨实例聚合     │
└─────────────────────────────────────────┘
```

**Histogram vs Summary 选择指南**：

```
选择Histogram的情况：
- 需要跨实例聚合分位数
- 需要自定义bucket边界
- 服务端计算分位数可接受
- 典型：HTTP请求延迟

选择Summary的情况：
- 需要精确的分位数
- 不需要跨实例聚合
- 客户端计算性能更好
- 典型：JVM GC暂停时间
```

### 3. Google SRE的监控哲学

#### 四个黄金指标

```
Google SRE《Site Reliability Engineering》定义：

┌─────────────────────────────────────────┐
│ 1. 延迟（Latency）                       │
│    - 服务处理请求所需时间                 │
│    - 区分成功请求和失败请求的延迟         │
│    - 关注分位数（P50, P99, P99.9）        │
│                                         │
│ 2. 流量（Traffic）                       │
│    - 系统承载的请求量                     │
│    - QPS（每秒查询数）、RPS               │
│    - 网络带宽（Mbps/Gbps）                │
│                                         │
│ 3. 错误（Errors）                        │
│    - 请求失败的比率                       │
│    - HTTP 5xx、4xx                        │
│    - 业务错误（如支付失败）               │
│                                         │
│ 4. 饱和度（Saturation）                  │
│    - 资源使用接近容量的程度               │
│    - CPU使用率、内存使用率                │
│    - 连接池使用率、队列长度               │
│    - 饱和度接近100%时性能急剧下降         │
└─────────────────────────────────────────┘
```

#### RED方法与USE方法

```
微服务监控方法论：

RED方法（面向服务）：
- Rate（率）：每秒请求数
- Errors（错误）：每秒错误数
- Duration（持续时间）：请求延迟分布

USE方法（面向资源）：
- Utilization（利用率）：资源忙碌时间百分比
- Saturation（饱和度）：资源排队工作量
- Errors（错误）：错误计数

两者互补：
RED监控服务健康度 → 业务视角
USE监控资源健康度 → 基础设施视角
```

#### PromQL核心查询

```promql
# 1. 瞬时向量选择器
http_requests_total                    # 所有实例
http_requests_total{job="api-server"}  # 按标签过滤
http_requests_total[5m]                # 范围向量（最近5分钟）

# 2. 速率计算（Counter必须用rate）
rate(http_requests_total[5m])          # 每秒请求率
irate(http_requests_total[5m])         # 瞬时率（更灵敏）

# 3. 聚合操作
sum(rate(http_requests_total[5m])) by (status)
# 按状态码分组统计QPS

avg(http_request_duration_seconds)
# 平均延迟

histogram_quantile(0.99, 
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le))
# P99延迟

# 4. 二元操作
rate(http_requests_total{status=~"5.."}[5m]) 
/ 
rate(http_requests_total[5m])
# 错误率

# 5. 预测
disk_usage / disk_total > 0.8
and
predict_linear(disk_usage[6h], 7*24*3600) > disk_total
# 磁盘使用率>80% 且 预测7天后会满
```

#### Micrometer + Spring Boot集成

```java
/**
 * Spring Boot 3.x 监控配置
 * Micrometer是JVM应用的度量门面（类似SLF4J）
 */
@Configuration
public class MetricsConfig {
    
    @Bean
    MeterRegistryCustomizer<MeterRegistry> metricsCommonTags() {
        return registry -> registry.config()
            .commonTags("application", "order-service")
            .commonTags("env", "production")
            .commonTags("team", "platform");
    }
    
    /**
     * 自定义Counter：订单创建总数
     */
    @Bean
    Counter orderCounter(MeterRegistry registry) {
        return Counter.builder("orders.created")
            .description("Total orders created")
            .tag("service", "order")
            .register(registry);
    }
    
    /**
     * 自定义Timer：订单处理耗时
     */
    @Bean
    Timer orderTimer(MeterRegistry registry) {
        return Timer.builder("orders.processing.time")
            .description("Order processing time")
            .publishPercentiles(0.5, 0.95, 0.99)
            .register(registry);
    }
    
    /**
     * 自定义Gauge：待处理队列长度
     */
    @Bean
    Gauge queueGauge(MeterRegistry registry, Queue<Order> pendingQueue) {
        return Gauge.builder("orders.pending.queue.size", 
                pendingQueue, Queue::size)
            .description("Pending orders queue size")
            .register(registry);
    }
}

@Service
public class OrderService {
    
    private final Counter orderCounter;
    private final Timer orderTimer;
    
    public OrderService(MeterRegistry registry) {
        this.orderCounter = registry.counter("orders.created",
            "channel", "online");
        this.orderTimer = registry.timer("orders.processing.time");
    }
    
    public Order createOrder(CreateOrderRequest request) {
        // 记录耗时
        return orderTimer.record(() -> {
            // 创建订单逻辑
            Order order = doCreateOrder(request);
            
            // 计数器+1
            orderCounter.increment();
            
            return order;
        });
    }
    
    /**
     * 使用注解方式（更简洁）
     */
    @Timed(value = "orders.api.duration", 
           percentiles = {0.5, 0.99},
           description = "Order API latency")
    @Counted(value = "orders.api.calls", 
             description = "Total API calls")
    public Order createOrderV2(CreateOrderRequest request) {
        return doCreateOrder(request);
    }
}
```

### 2. Logging体系架构

#### 日志级别规范

```
日志级别使用规范：

┌─────────────────────────────────────────┐
│ FATAL（致命）                            │
│ - 系统无法继续运行                        │
│ - 例：数据库连接失败、核心组件初始化失败   │
│ - 操作：立即电话/短信告警                  │
├─────────────────────────────────────────┤
│ ERROR（错误）                            │
│ - 功能异常，但系统可继续运行              │
│ - 例：订单创建失败、支付超时              │
│ - 操作：实时告警，人工介入                 │
├─────────────────────────────────────────┤
│ WARN（警告）                             │
│ - 潜在问题，当前不影响功能                │
│ - 例：重试次数过多、资源接近阈值          │
│ - 操作：关注趋势，必要时告警               │
├─────────────────────────────────────────┤
│ INFO（信息）                             │
│ - 正常业务流程记录                        │
│ - 例：订单创建成功、用户登录              │
│ - 操作：保留7-15天，用于审计               │
├─────────────────────────────────────────┤
│ DEBUG（调试）                            │
│ - 详细调试信息                            │
│ - 例：请求参数、SQL语句、方法入参出参     │
│ - 操作：生产环境关闭，问题排查时临时开启   │
├─────────────────────────────────────────┤
│ TRACE（追踪）                            │
│ - 最详细的跟踪信息                        │
│ - 例：方法调用栈、循环内部状态            │
│ - 操作：极少使用，性能敏感                 │
└─────────────────────────────────────────┘

生产环境推荐配置：
- 根日志：INFO
- 核心业务包：INFO
- 第三方库：WARN
- 临时调试：单独设置DEBUG
```

/**
 * TraceId过滤器：为每个请求生成/传递TraceId
 */
public class TraceIdFilter implements Filter {
    
    private static final String TRACE_ID_HEADER = "X-Trace-Id";
    private static final String TRACE_ID_MDC = "traceId";
    
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, 
                        FilterChain chain) throws IOException, ServletException {
        
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        String traceId = httpRequest.getHeader(TRACE_ID_HEADER);
        
        // 如果没有传入TraceId，生成新的
        if (traceId == null || traceId.isEmpty()) {
            traceId = UUID.randomUUID().toString().replace("-", "");
        }
        
        // 放入MDC
        MDC.put(TRACE_ID_MDC, traceId);
        MDC.put("spanId", generateSpanId());
        MDC.put("userId", getUserId(httpRequest));
        
        try {
            // 将TraceId传递给下游服务
            if (response instanceof HttpServletResponse) {
                ((HttpServletResponse) response).setHeader(TRACE_ID_HEADER, traceId);
            }
            chain.doFilter(request, response);
        } finally {
            MDC.clear();
        }
    }
}

@Service

    private final Tracer tracer;
    
    public OrderService(OpenTelemetry openTelemetry) {
        this.tracer = openTelemetry.getTracer("order-service");
    }
    
    public Order createOrder(CreateOrderRequest request) {
        // 创建Span
        Span span = tracer.spanBuilder("createOrder")
            .setSpanKind(SpanKind.SERVER)
            .setAttribute("order.userId", request.getUserId())
            .setAttribute("order.amount", request.getAmount())
            .startSpan();
        
        try (Scope scope = span.makeCurrent()) {
            // 1. 校验库存（创建子Span）
            checkInventory(request);
            
            // 2. 创建订单
            Order order = orderDao.insert(request);
            span.setAttribute("order.id", order.getId());
            
            // 3. 发送消息（异步，需要传递Context）
            sendOrderCreatedEvent(order);
            
            span.setStatus(StatusCode.OK);
            return order;
            
        } catch (Exception e) {
            span.setStatus(StatusCode.ERROR, e.getMessage());
            span.recordException(e);
            throw e;
        } finally {
            span.end();
        }
    }
    
    private void checkInventory(CreateOrderRequest request) {
        Span span = tracer.spanBuilder("checkInventory")
            .setSpanKind(SpanKind.CLIENT)
            .setAttribute("inventory.items", request.getItems().size())
            .startSpan();
        
        try (Scope scope = span.makeCurrent()) {
            inventoryClient.check(request.getItems());
        } catch (Exception e) {
            span.recordException(e);
            throw e;
        } finally {
            span.end();
        }
    }
    
    /**
     * 跨线程传递Context
     */
    private void sendOrderCreatedEvent(Order order) {
        Context context = Context.current();
        
        CompletableFuture.runAsync(() -> {
            try (Scope scope = context.makeCurrent()) {
                Span span = tracer.spanBuilder("sendOrderEvent")
                    .setSpanKind(SpanKind.PRODUCER)
                    .startSpan();
                
                try {
                    kafkaTemplate.send("order-created", order);
                } finally {
                    span.end();
                }
            }
        });
    }
}

        return () -> {
            if (context != null) {
                MDC.setContextMap(context);
            }
            try {
                task.run();
            } finally {
                MDC.clear();

            } finally {
                MDC.clear();
            }

## 常见陷阱与最佳实践

### 陷阱1：监控指标过多，告警风暴导致"狼来了"

```yaml
# 错误：什么指标都告警，阈值设得太低
- alert: CpuHigh
  expr: cpu_usage > 50%  # 稍微高一点就告警
  
- alert: MemoryHigh
  expr: memory_usage > 60%  # 频繁触发

# 错误后果：
# - 每天收到100+告警邮件
# - 团队对告警麻木
# - 真正的问题被淹没
```

**最佳实践：**

```
告警设计原则：

1. 少而精：
   - 核心指标优先：错误率、P99延迟、饱和度
   - 业务指标优先：支付成功率、订单量
   - 系统指标其次：CPU、内存（通常有自动恢复机制）

2. 合理的阈值：
   - CPU > 80% 持续5分钟
   - 错误率 > 1% 持续2分钟
   - P99延迟 > 1秒 持续5分钟

3. 告警分级：
   ┌─────────────────────────────────────────┐
   │ P0（Critical）：立即处理                 │
   │ - 服务宕机、错误率飙升、支付失败         │
   │ - 通知方式：电话 + 短信 + 钉钉           │
   ├─────────────────────────────────────────┤
   │ P1（Warning）：30分钟内处理              │
   │ - 延迟升高、资源紧张                     │
   │ - 通知方式：钉钉 + 邮件                  │
   ├─────────────────────────────────────────┤
   │ P2（Info）：工作时间内处理               │
   │ - 趋势预警、非核心功能异常               │
   │ - 通知方式：邮件                         │
   └─────────────────────────────────────────┘

4. 告警收敛：
   - 相同根因合并通知
   - 使用group_by聚合
   - 设置repeat_interval避免轰炸
```

### 陷阱2：只有系统监控，没有业务监控

```
错误场景：
- CPU、内存、磁盘都正常
- 但订单量暴跌50%，支付成功率降到80%
- 没有任何告警
- 直到用户投诉才发现问题

根因：
- 系统正常 ≠ 业务正常
- 业务指标往往比系统指标更早发现问题
```

**最佳实践：**

```java
/**
 * 业务监控必须覆盖核心业务流程
 */
@Component
public class BusinessMetrics {
    
    @PostConstruct
    public void init() {
        // 核心业务流程指标
        Counter.builder("business.order.created")
            .description("订单创建数")
            .register(registry);
        
        Counter.builder("business.order.paid")
            .description("订单支付数")
            .register(registry);
        
        Counter.builder("business.payment.failed")
            .description("支付失败数")
            .register(registry);
        
        // 关键转化率
        Gauge.builder("business.conversion.rate",
                this, BusinessMetrics::calculateConversionRate)
            .description("订单转化率")
            .register(registry);
    }
    
    private double calculateConversionRate() {
        double created = getOrderCreatedCount();
        double paid = getOrderPaidCount();
        return created > 0 ? paid / created : 0;
    }
}
```

## 面试题与参考答案

### Q1：Metrics的四种类型（Counter/Gauge/Histogram/Summary）有什么区别？

**答：**

| 类型 | 特点 | 示例 |
|------|------|------|
| **Counter** | 单调递增的累加值，只能增加或重置为0 | 请求总数、错误总数 |
| **Gauge** | 可增可减的瞬时值 | 当前内存使用量、在线人数 |
| **Histogram** | 采样分布，分到预设的bucket中 | 请求延迟分布（0-10ms, 10-50ms...） |
| **Summary** | 计算滑动时间窗口内的分位数 | 过去10分钟的P99延迟 |

**Histogram vs Summary：**
- Histogram在服务端聚合，适合多实例场景，但bucket需要预先定义
- Summary在客户端计算，分位数准确，但无法跨实例聚合

**选择建议：**
- 需要跨实例聚合分位数 → Histogram
- 需要精确分位数且不需要聚合 → Summary

### Q2：可观测性（Observability）和监控（Monitoring）有什么区别？

**答：**

- **监控**：基于已知指标和阈值，被动告警。回答"系统是否正常工作？"
- **可观测性**：通过Metrics、Logging、Tracing的组合，主动探索未知问题。回答"系统为什么不正常？"

**类比：**
- 监控是"我知道可能会有什么问题，我盯着它"
- 可观测性是"我不知道会有什么问题，但我能通过数据推理出来"

**三大支柱关系：**
- Metrics发现异常 → Tracing定位服务 → Logging查看详细错误

### Q3：TraceId如何在分布式系统中传递？如果跨线程或跨MQ怎么办？

**答：**

**同步调用（HTTP/RPC）：**
- 通过Header传递，如 `X-B3-TraceId`、`traceparent`（W3C标准）
- Spring Cloud Sleuth自动注入和提取

**跨线程：**
- 使用 `MDC.getCopyOfContextMap()` 复制上下文
- 提交任务前将TraceId设置到新线程的MDC

```java
Map<String, String> context = MDC.getCopyOfContextMap();
CompletableFuture.runAsync(() -> {
    MDC.setContextMap(context);
    try {
        // 异步任务
    } finally {
        MDC.clear();
    }
});
```

**跨MQ：**
- 发送消息时将TraceId写入消息属性（Message Properties）
- 消费者从消息属性中提取并设置到当前上下文

```java
Message msg = new Message();
msg.putUserProperty("traceId", MDC.get("traceId"));
```

### Q4：Prometheus的pull模式和push模式各有什么优缺点？

**答：**

**Pull模式（默认）：**
- 优点：服务发现简单，目标不可用时自动感知；配置集中在Prometheus；易于调试（直接curl看指标）
- 缺点：短生命周期任务（如定时Job）可能抓不到；需要暴露端口

**Push模式（Pushgateway）：**
- 优点：适合批处理Job、定时任务；不暴露端口，安全
- 缺点：Pushgateway单点故障；需要手动管理实例标识；数据可能重复推送

**建议：**常驻服务用Pull，批处理任务用Pushgateway。

### Q5：如何设计一个有效的告警体系，避免告警疲劳？

**答：** 核心原则：**"高信噪比、分级响应、自动恢复"**

1. **少而精**：只告警需要人处理的问题（如服务宕机、错误率飙升），不需要人的用自动化修复
2. **分级**：P0（短信+电话，立即处理）、P1（钉钉/微信，30分钟内）、P2（邮件，明天看）
3. **收敛**：相同根因的告警合并，避免轰炸（如一台机器宕机只发一条，不要每个指标都发）
4. **可恢复**：告警恢复时发送恢复通知，让人知道问题已解决
5. **定期Review**：每周Review告警，关闭误报、调整阈值

### Q6：ELK和Prometheus+Grafana分别解决什么问题？能否互相替代？

**答：**

| 维度 | Prometheus+Grafana | ELK |
|------|-------------------|-----|
| 数据类型 | 时序指标（Metrics） | 非结构化/结构化日志 |
| 查询 | PromQL，适合聚合计算 | Lucene DSL，适合全文检索 |
| 存储 | 按时间序列存储，高效 | 倒排索引，适合文本搜索 |
| 适用场景 | 性能趋势、容量规划、告警 | 错误排查、审计、业务分析 |

**不能互相替代：**
- 只有Prometheus：知道QPS下降了，但不知道具体哪个请求报错
- 只有ELK：能在日志里搜到错误，但无法看到系统整体负载趋势
- 最佳实践：Metrics发现异常 → Tracing定位服务 → Logging查看详细错误

### Q7：什么是高基数（High Cardinality）问题？如何解决？

**答：**

**定义：**指标标签取值数量过多，导致时间序列数量爆炸。

**示例：**
```
http_requests_total{userId="12345"}  
# userId有100万个不同值 → 100万个时间序列
```

**解决方案：**
1. 避免将用户ID、订单ID等高基数字段作为Label
2. 使用Histogram替代精确值（将连续值分桶）
3. 高基数维度放到日志中，指标只做聚合统计
4. 定期审查指标基数：`topk(10, count by (__name__)({__name__=~".+"}))`

### Q8：Prometheus的rate()和irate()有什么区别？

**答：**

**rate()：**
- 计算时间范围内的平均每秒增长速率
- 适合用于告警和缓慢变化的Counter
- 平滑抖动，反应较慢
- 例：`rate(http_requests_total[5m])`

**irate()：**
- 使用最后两个数据点计算瞬时速率
- 适合用于Graph展示和快速变化的Counter
- 反应灵敏，但抖动较大
- 例：`irate(http_requests_total[5m])`

**选择建议：**
- 告警规则：rate()
- Dashboard展示：irate() 或 rate()
- 快速变化指标：irate()

### Q9：如何监控微服务架构中的依赖服务健康？

**答：**

**多层监控策略：**

1. **应用层：**
```java
// 记录下游调用指标
Timer.Sample sample = Timer.start(registry);
try {
    downstreamService.call();
    registry.counter("downstream.success", "service", "payment").increment();
} catch (Exception e) {
    registry.counter("downstream.error", "service", "payment", "error", e.getClass().getSimpleName()).increment();
    throw e;
} finally {
    sample.stop(registry.timer("downstream.duration", "service", "payment"));
}
```

2. **网络层：**
- Blackbox Exporter探测HTTP/TCP/DNS
- 检测服务是否可达、证书是否过期

3. **基础设施层：**
- Node Exporter监控服务器资源

### Q10：设计一个日志系统，要求支持每天10TB日志，查询延迟<1秒

**答：**

**架构设计：**

```
日志采集 → 预处理 → 分布式存储 → 索引 → 查询

1. 采集层：
   - Filebeat/Fluentd（每台服务器部署）
   - 本地缓冲，失败重试

2. 预处理层：
   - Kafka（削峰填谷）
   - Logstash/Fluentd（解析、过滤、enrich）

3. 存储层：
   - Elasticsearch集群（50+节点）
   - 按天滚动索引（logs-2024.01.01）
   - ILM策略：热节点（7天）→ 温节点（30天）→ 冷节点（1年）

4. 优化策略：
   - 索引分片：每个索引10-30个主分片
   - 字段映射：keyword用于过滤，text用于搜索
   - 压缩：启用best_compression
   - 查询优化：使用filter context（缓存），避免全扫描
   - 采样：DEBUG日志只采样10%
```

**容量规划：**
- 原始日志：10TB/天
- 索引后：约15TB/天（含倒排索引）
- 热存储（7天）：105TB
- 温存储（23天）：345TB
- 总存储需求：约500TB（含副本）

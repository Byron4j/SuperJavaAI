## 引言：缓存一致性的本质

缓存一致性（Cache Consistency）不是"怎么让Redis和MySQL数据相同"的简单问题，而是一门**在分布式系统约束下管理多副本数据状态**的工程技术。

核心认知：

```
缓存一致性的本质：
在CAP定理的约束下，根据业务对一致性、可用性、分区容错性的不同要求，
选择合适的一致性模型和同步策略，使得缓存层与持久化层的数据状态
在可接受的时间窗口内达到业务要求的等价性。

质量差异的根源：
- 差的方案：忽视业务特点，一刀切使用某种模式 → 要么性能低下，要么数据错乱
- 好的方案：基于业务对一致性的容忍度、读写比例、并发量，选择最合适的策略组合
```

**关键洞察**：缓存一致性的效果不取决于"用了什么工具"，而取决于**对业务一致性需求的精确理解**和**对系统边界的清晰划分**。

## 理论基础：CAP定理与一致性模型

### 1. CAP定理的缓存视角

CAP定理指出：分布式系统不可能同时满足一致性（Consistency）、可用性（Availability）、分区容错性（Partition Tolerance），最多只能同时满足两项。

```
CAP在缓存系统中的映射：

┌─────────────────────────────────────────┐
│            分布式缓存系统               │
├─────────────────────────────────────────┤
│  C - Consistency                        │
│  缓存与DB的数据一致性                    │
│  强一致性：每次读取都返回最新写入         │
│  最终一致性：允许短暂不一致，最终一致     │
├─────────────────────────────────────────┤
│  A - Availability                       │
│  缓存服务的可用性                        │
│  Redis集群在部分节点故障时仍可服务        │
├─────────────────────────────────────────┤
│  P - Partition Tolerance                │
│  网络分区容错性                          │
│  缓存节点间网络中断时系统仍能运行         │
└─────────────────────────────────────────┘

缓存系统的CAP选择：
- AP系统（大多数缓存场景）：优先保证可用性和分区容错性，接受最终一致性
- CP系统（库存、金融）：优先保证一致性和分区容错性，牺牲部分可用性
```

#### 数学表述

设缓存系统有N个副本，定义：

- **一致性（C）**：读操作返回最近一次成功写操作的结果
- **可用性（A）**：每个请求都能在有限时间内得到非错误响应
- **分区容错性（P）**：系统在网络分区情况下仍能继续运行

```
CAP不可能性的形式化表达：

∀分布式系统, ¬(C ∧ A ∧ P)

即：不存在同时满足C、A、P三者的分布式系统

缓存系统的权衡：
1. 选择CP：使用分布式锁、2PC、Paxos/Raft → 保证一致性，但增加延迟
2. 选择AP：使用异步同步、最终一致性 → 保证可用性，允许短暂不一致
3. 实践中：在AP基础上通过策略降低不一致窗口
```

### 2. 一致性模型谱系

```
一致性强度谱系（从强到弱）：

强一致性 ──────────────────────────────────────→ 弱一致性

├─ 线性一致性（Linearizability）
│  所有操作看起来像是在某个瞬间原子完成的
│  实现：分布式锁、Paxos、Raft
│  代价：高延迟、低吞吐
│
├─ 顺序一致性（Sequential Consistency）
│  所有进程看到的操作顺序一致
│  实现：内存屏障、总线锁
│
├─ 因果一致性（Causal Consistency）
│  有因果关系的操作保持顺序
│  实现：向量时钟、Happens-Before
│
├─ 会话一致性（Session Consistency）
│  同一会话内的读操作保证一致性
│  实现：客户端绑定、Session Sticky
│
├─ 单调读一致性（Monotonic Read）
│  一个进程读取某值后，后续读取不会读到更旧的值
│  实现：版本号、时间戳
│
└─ 最终一致性（Eventual Consistency）
   不保证立即一致，但保证在没有新更新的情况下最终一致
   实现：异步同步、消息队列、binlog监听
   代价：不一致窗口
```

### 3. 分布式事务基础

缓存一致性问题本质上是分布式事务问题的一个子集。

```
分布式事务的ACID在缓存中的映射：

原子性（Atomicity）：
- 缓存更新和DB更新要么都成功，要么都失败
- 挑战：缓存操作和DB操作通常不在同一个事务中

一致性（Consistency）：
- 事务执行前后，缓存和DB都处于有效状态
- 挑战：缓存和DB的数据约束可能不同

隔离性（Isolation）：
- 并发事务之间相互隔离
- 挑战：缓存的并发访问控制

持久性（Durability）：
- 一旦事务提交，数据就持久化
- 挑战：缓存是易失的，需要保证DB的持久性
```

#### BASE理论

```
BASE理论（对ACID的妥协）：

Basically Available（基本可用）：
- 系统出现故障时，允许损失部分可用性
- 缓存降级：Redis故障时直接查DB

Soft state（软状态）：
- 允许系统中的数据存在中间状态
- 缓存和DB不一致就是一种软状态

Eventually consistent（最终一致性）：
- 不需要实时一致，最终一致即可
- 这是缓存系统最常用的理论基础
```

## 核心缓存模式深度解析

### 1. Cache Aside模式（旁路缓存）

Cache Aside是最常用的缓存模式，应用程序直接管理缓存。

#### 读操作详细流程

```
Cache Aside Read Flow：

┌─────────┐         ┌─────────┐         ┌─────────┐
│  Client │────────→│   App   │────────→│  Cache  │
└─────────┘         └─────────┘         └────┬────┘
                                             │
                                    ┌────────┴────────┐
                                    ↓                 ↓
                              Cache Hit          Cache Miss
                              (返回数据)              │
                                    ↑                 ↓
                                    │           ┌─────────┐
                                    └───────────│   DB    │
                                                └────┬────┘
                                                     │
                                                     ↓
                                              ┌─────────┐
                                              │ 写入缓存  │
                                              │(设过期时间)│
                                              └─────────┘

详细时序：
T1: App发送读请求
T2: App查询Cache（耗时 ~1ms）
T3: Cache返回null（未命中）
T4: App查询DB（耗时 ~10ms）
T5: DB返回数据
T6: App写入Cache（耗时 ~1ms）
T7: App返回数据给Client

总耗时（Miss）：~12ms
总耗时（Hit）：~1ms
加速比：12x
```

#### 写操作详细流程

```
Cache Aside Write Flow：

┌─────────┐         ┌─────────┐         ┌─────────┐
│  Client │────────→│   App   │────────→│   DB    │
└─────────┘         └─────────┘         └────┬────┘
                                             │
                                    ┌────────┴────────┐
                                    ↓                 ↓
                               更新成功          更新失败
                                    │                 │
                                    ↓                 ↓
                              ┌─────────┐       ┌─────────┐
                              │ 删除缓存  │       │ 回滚事务 │
                              └─────────┘       └─────────┘

为什么删除而不是更新缓存？

场景对比：

更新缓存：
T1: App1更新DB为A
T2: App1更新Cache为A
T3: App2更新DB为B  
T4: App2更新Cache为B
T5: App1的Cache更新延迟到达，Cache变为A
结果：DB=B, Cache=A ❌ 长期不一致

删除缓存：
T1: App1更新DB为A
T2: App1删除Cache
T3: App2更新DB为B
T4: App2删除Cache
T5: 下一次读取时从DB加载最新值B
结果：DB=B, Cache=B ✓ 最终一致
```

#### Cache Aside代码实现

```java
@Service
public class CacheAsideService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private UserDao userDao;
    
    private static final Duration CACHE_TTL = Duration.ofMinutes(30);
    private static final String CACHE_PREFIX = "user:";
    
    /**
     * 读取操作：先读缓存，未命中再读DB
     */
    public User getUser(Long id) {
        String key = CACHE_PREFIX + id;
        
        // 1. 读缓存
        String json = redisTemplate.opsForValue().get(key);
        if (json != null) {
            // 防御性编程：防止缓存穿透时空字符串
            if ("null".equals(json)) {
                return null;
            }
            return JSON.parseObject(json, User.class);
        }
        
        // 2. 缓存未命中，查询数据库
        User user = userDao.getById(id);
        
        // 3. 写入缓存（包括空值，防止缓存穿透）
        if (user != null) {
            redisTemplate.opsForValue().set(key, JSON.toJSONString(user), CACHE_TTL);
        } else {
            // 缓存空值，过期时间较短
            redisTemplate.opsForValue().set(key, "null", Duration.ofMinutes(1));
        }
        
        return user;
    }
    
    /**
     * 写入操作：先更新DB，再删除缓存
     */
    @Transactional
    public void updateUser(User user) {
        String key = CACHE_PREFIX + user.getId();
        
        // 1. 更新数据库
        userDao.update(user);
        
        // 2. 删除缓存（不是更新缓存）
        redisTemplate.delete(key);
        
        // 3. 可选：发送缓存失效消息到MQ，用于多级缓存同步
        // messageProducer.send(new CacheInvalidationMessage(key));
    }
    
    /**
     * 删除操作：先删DB，再删缓存
     */
    @Transactional
    public void deleteUser(Long id) {
        String key = CACHE_PREFIX + id;
        
        // 1. 删除数据库记录
        userDao.deleteById(id);
        
        // 2. 删除缓存
        redisTemplate.delete(key);
    }
}
```

### 2. Read/Write Through模式（读写穿透）

Read/Write Through将缓存作为主要数据源，由缓存层负责与DB的交互。

```
Read/Write Through Architecture：

┌─────────┐         ┌─────────┐         ┌─────────┐
│  Client │────────→│   App   │────────→│  Cache  │
└─────────┘         └─────────┘         │  Layer  │
                                        │(中间件)  │
                                        └────┬────┘
                                             │
                                    ┌────────┴────────┐
                                    ↓                 ↓
                              Read Miss           Write
                                    ↓                 ↓
                              ┌─────────┐       ┌─────────┐
                              │ 自动加载  │       │ 同步写DB │
                              │ from DB │       │         │
                              └─────────┘       └─────────┘

实现方式：
1. 使用缓存中间件（如Redis的read-through插件）
2. 使用ORM框架的二级缓存（Hibernate Cache）
3. 使用Spring Cache抽象
```

#### Spring Cache实现

```java
@Configuration
@EnableCaching
public class CacheConfig {
    
    @Bean
    public CacheManager cacheManager(RedisConnectionFactory factory) {
        RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(30))
            .serializeKeysWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new StringRedisSerializer()))
            .serializeValuesWith(RedisSerializationContext.SerializationPair
                .fromSerializer(new GenericJackson2JsonRedisSerializer()));
        
        return RedisCacheManager.builder(factory)
            .cacheDefaults(config)
            .build();
    }
}

@Service
public class UserService {
    
    @Autowired
    private UserDao userDao;
    
    /**
     * @Cacheable: 先查缓存，未命中则执行方法并缓存结果
     * keyGenerator或key指定缓存键
     * unless表示条件满足时不缓存
     */
    @Cacheable(value = "user", key = "#id", unless = "#result == null")
    public User getUser(Long id) {
        return userDao.getById(id);
    }
    
    /**
     * @CachePut: 先执行方法，再更新缓存（常用于更新操作）
     */
    @CachePut(value = "user", key = "#user.id")
    @Transactional
    public User updateUser(User user) {
        userDao.update(user);
        return user; // 返回的对象会被写入缓存
    }
    
    /**
     * @CacheEvict: 执行方法后删除缓存
     * allEntries=true表示清空整个缓存区
     * beforeInvocation=true表示在方法执行前删除
     */
    @CacheEvict(value = "user", key = "#id")
    @Transactional
    public void deleteUser(Long id) {
        userDao.deleteById(id);
    }
    
    /**
     * 组合注解：批量清除多个缓存
     */
    @Caching(evict = {
        @CacheEvict(value = "user", key = "#id"),
        @CacheEvict(value = "userList", allEntries = true)
    })
    @Transactional
    public void updateUserWithListRefresh(Long id, User user) {
        userDao.update(user);
    }
}
```

#### Read Through的隐藏问题

```java
/**
 * Read Through的问题：缓存未命中时的"缓存雪崩"
 * 
 * 当大量并发请求同时访问一个未缓存的key时：
 * T1: Thread1读Cache未命中
 * T2: Thread2读Cache未命中  
 * T3: Thread3读Cache未命中
 * ...
 * Tn: 所有线程同时查DB，DB压力骤增
 */
public class CachePenetrationProblem {
    
    // 错误示范：未做并发控制
    @Cacheable(value = "hotData", key = "#id")
    public HotData getHotData(Long id) {
        // 当缓存失效瞬间，大量请求会同时执行到这里
        return hotDataDao.getById(id);
    }
    
    // 正确做法：使用同步（Spring Cache支持sync=true）
    @Cacheable(value = "hotData", key = "#id", sync = true)

### 3. Write Behind模式（异步写回）

Write Behind将写操作先记录到缓存，异步批量写回DB。

```
Write Behind Architecture：

┌─────────┐         ┌─────────┐         ┌─────────┐
│  Client │────────→│   App   │────────→│  Cache  │
└─────────┘         └─────────┘         │  Layer  │
                                        └────┬────┘
                                             │
                                             ↓
                                        ┌─────────┐
                                        │ 写队列   │
                                        │(Write    │
                                        │ Queue)   │
                                        └────┬────┘
                                             │
                                             ↓
                                        ┌─────────┐
                                        │ 批量写DB │
                                        │(异步线程) │
                                        └─────────┘

执行流程：
1. App写入Cache，立即返回成功
2. Cache将写操作放入队列
3. 后台线程定期（如1秒）批量消费队列
4. 批量写入DB（如每批100条）

优点：
- 写延迟极低（~1ms）
- DB压力小（批量写+合并）
- 天然合并同一key的多次更新

缺点：
- 数据丢失风险（Cache宕机且未刷盘）
- 一致性延迟（秒级~分钟级）
- 实现复杂（需要Write Queue和刷盘机制）
```

#### Write Behind实现

```java
@Component
public class WriteBehindCache {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private UserDao userDao;
    
    // 写队列：使用Disruptor或BlockingQueue
    private final BlockingQueue<WriteOperation> writeQueue = 
        new LinkedBlockingQueue<>(10000);
    
    // 批量写入大小
    private static final int BATCH_SIZE = 100;
    // 批量写入间隔（ms）
    private static final int FLUSH_INTERVAL = 1000;
    
    @PostConstruct
    public void init() {
        // 启动多个刷盘线程
        for (int i = 0; i < 3; i++) {
            Thread writer = new Thread(this::flushLoop);
            writer.setName("write-behind-flusher-" + i);
            writer.setDaemon(true);
            writer.start();
        }
    }
    
    /**
     * 异步写入
     */
    public void updateUser(User user) {
        String key = "user:" + user.getId();
        
        // 1. 立即更新缓存
        redisTemplate.opsForValue().set(key, JSON.toJSONString(user));
        
        // 2. 加入异步写队列
        WriteOperation op = new WriteOperation(OperationType.UPDATE, user);
        boolean offered = writeQueue.offer(op);
        if (!offered) {
            // 队列满，直接同步写DB（降级）
            userDao.update(user);
        }
    }
    
    /**
     * 刷盘循环
     */
    private void flushLoop() {
        List<WriteOperation> batch = new ArrayList<>(BATCH_SIZE);
        long lastFlushTime = System.currentTimeMillis();
        
        while (!Thread.currentThread().isInterrupted()) {
            try {
                //  drainTo: 批量取出，减少锁竞争
                writeQueue.drainTo(batch, BATCH_SIZE);
                
                long now = System.currentTimeMillis();
                if (!batch.isEmpty() && (batch.size() >= BATCH_SIZE || 
                    now - lastFlushTime >= FLUSH_INTERVAL)) {
                    
                    // 合并同一ID的多次更新（只保留最新的）
                    Map<Long, WriteOperation> merged = mergeOperations(batch);
                    
                    // 批量写入DB
                    batchWriteToDB(new ArrayList<>(merged.values()));
                    
                    batch.clear();
                    lastFlushTime = now;
                } else if (batch.isEmpty()) {
                    Thread.sleep(100);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                break;
            }
        }
    }
    
    /**
     * 合并操作：同一key只保留最后一次更新
     */
    private Map<Long, WriteOperation> mergeOperations(List<WriteOperation> ops) {
        Map<Long, WriteOperation> map = new LinkedHashMap<>();
        for (WriteOperation op : ops) {
            map.put(op.getEntityId(), op); // 后入覆盖先入
        }
        return map;
    }
    
    /**
     * 批量写入数据库
     */
    @Transactional
    public void batchWriteToDB(List<WriteOperation> ops) {
        if (ops.isEmpty()) return;
        
        List<User> users = ops.stream()
            .filter(op -> op.getType() == OperationType.UPDATE)
            .map(WriteOperation::getEntity)
            .collect(Collectors.toList());
        
        userDao.batchUpdate(users);
    }
    
    @Data
    @AllArgsConstructor
    static class WriteOperation {
        private OperationType type;
        private User entity;
        
        public Long getEntityId() {
            return entity.getId();
        }
    }
    
    enum OperationType {
        UPDATE, DELETE
    }
}
```

### 4. Write Around模式（绕写）

Write Around模式：写操作直接写DB，不经过缓存；读操作才使用缓存。

```

Write Path:
┌─────────┐         ┌─────────┐         ┌─────────┐

// RedissonLock.java 的 tryLockInnerAsync 方法
<T> RFuture<T> tryLockInnerAsync(long leaseTime, TimeUnit unit, 
    long threadId, RedisStrictCommand<T> command) {
    
    internalLockLeaseTime = unit.toMillis(leaseTime);
    
    return evalWriteAsync(getName(), LongCodec.INSTANCE, command,
        // 1. 检查锁是否存在
        "if (redis.call('exists', KEYS[1]) == 0) then " +
            // 2. 不存在则创建锁，设置过期时间
            "redis.call('hincrby', KEYS[1], ARGV[2], 1); " +
            "redis.call('pexpire', KEYS[1], ARGV[1]); " +
            "return nil; " +
        "end; " +
        // 3. 检查锁是否被自己持有（可重入）
        "if (redis.call('hexists', KEYS[1], ARGV[2]) == 1) then " +
            "redis.call('hincrby', KEYS[1], ARGV[2], 1); " +
            "redis.call('pexpire', KEYS[1], ARGV[1]); " +
            "return nil; " +
        "end; " +
        // 4. 锁被其他线程持有，返回剩余过期时间
        "return redis.call('pttl', KEYS[1]);",
        Collections.singletonList(getName()), 
        internalLockLeaseTime, 
        getLockName(threadId));
}

/**
 * KEYS[1]: 锁的名称（如 "lock:user:123"）
 * ARGV[1]: 锁的过期时间（毫秒）
 * ARGV[2]: 线程标识（UUID + threadId）
 * 
 * 为什么使用Hash而不是String？
 * - Hash支持可重入（hincrby记录重入次数）
 * - String只能记录锁是否存在
 */

/**
 * 解锁核心Lua脚本：
 */
protected RFuture<Boolean> unlockInnerAsync(long threadId) {
    return evalWriteAsync(getName(), LongCodec.INSTANCE, RedisCommands.EVAL_BOOLEAN,
        // 1. 检查锁是否存在
        "if (redis.call('hexists', KEYS[1], ARGV[3]) == 0) then " +
            // 2. 不是自己的锁，不能释放
            "return nil;" +
        "end; " +
        // 3. 减少重入计数
        "local counter = redis.call('hincrby', KEYS[1], ARGV[3], -1); " +
        // 4. 如果计数器为0，删除锁
        "if (counter > 0) then " +
            "redis.call('pexpire', KEYS[1], ARGV[2]); " +
            "return 0; " +
        "else " +
            "redis.call('del', KEYS[1]); " +
            // 5. 发布解锁消息（用于订阅的线程唤醒）
            "redis.call('publish', KEYS[2], ARGV[1]); " +
            "return 1; " +
        "end; " +
        "return nil;",
        Arrays.asList(getName(), getChannelName()), 
        LockPubSub.UNLOCK_MESSAGE, 
        internalLockLeaseTime, 
        getLockName(threadId));
}

@Component
public class RedisDelayQueue {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    private static final String DELAY_QUEUE_KEY = "delay:queue:cache";
    
    /**
     * 添加延迟任务
     */
    public void addDelayTask(String cacheKey, long delayMs) {
        long executeTime = System.currentTimeMillis() + delayMs;
        redisTemplate.opsForZSet().add(DELAY_QUEUE_KEY, cacheKey, executeTime);
    }
    
    /**
     * 消费到期任务
     * 使用定时任务每秒执行
     */
    @Scheduled(fixedRate = 1000)
    public void consumeDelayTasks() {
        long now = System.currentTimeMillis();
        
        // 1. 获取所有到期的任务（score <= now）
        Set<String> keys = redisTemplate.opsForZSet()
            .rangeByScore(DELAY_QUEUE_KEY, 0, now);
        
        if (keys == null || keys.isEmpty()) {
            return;
        }
        
        for (String key : keys) {
            // 2. 删除缓存
            redisTemplate.delete(key);
            
            // 3. 从队列中移除
            redisTemplate.opsForZSet().remove(DELAY_QUEUE_KEY, key);
        }
    }
}

/**
 * Spring Cache的核心拦截器：CacheInterceptor
 * 
 * 继承关系：
 * CacheAspectSupport
 *   └── CacheInterceptor (implements MethodInterceptor)
 * 
 * 核心方法：execute()
 */
public class CacheAspectSupport {
    
    protected Object execute(CacheOperationInvoker invoker, Object target, 
        Method method, Object[] args) {
        
        // 1. 获取缓存操作上下文
        CacheOperationContexts contexts = 
            new CacheOperationContexts(metadata, method, target, args, targetClass);
        
        // 2. 首先处理@CacheEvict（beforeInvocation=true的情况）
        processCacheEvicts(contexts.get(CacheEvictOperation.class), true);
        
        // 3. 检查缓存（@Cacheable）
        Cache.ValueWrapper cacheHit = findCachedItem(contexts.get(CacheableOperation.class));
        
        // 4. 如果没有命中，收集需要生成的key
        List<CachePutRequest> cachePutRequests = new LinkedList<>();
        if (cacheHit == null) {
            collectPutRequests(contexts.get(CacheableOperation.class), 
                result -> cachePutRequests.add(result));
        }
        
        // 5. 执行方法
        Object returnValue = invokeOperation(invoker);
        
        // 6. 将结果放入缓存
        for (CachePutRequest cachePutRequest : cachePutRequests) {
            cachePutRequest.apply(returnValue);
        }
        
        // 7. 处理@CachePut
        for (CachePutOperation operation : contexts.get(CachePutOperation.class)) {
            putCache(operation, returnValue);
        }
        
        // 8. 处理@CacheEvict（afterInvocation的情况）
        processCacheEvicts(contexts.get(CacheEvictOperation.class), false);
        
        return returnValue;
    }
}

/**
 * Spring Cache的sync=true实现
 * 
 * 使用Redis的SETNX实现互斥
 */
public class RedisCache {
    
    public ValueWrapper get(Object key, Callable<T> valueLoader) {
        // 1. 先尝试获取缓存
        ValueWrapper storeValue = get(key);
        if (storeValue != null) {
            return storeValue;
        }
        
        // 2. 缓存未命中，尝试获取锁
        String lockKey = getLockKey(key);
        boolean locked = false;
        try {
            // 使用SETNX获取锁
            locked = redisTemplate.opsForValue()
                .setIfAbsent(lockKey, "1", Duration.ofSeconds(30));
            
            if (locked) {
                // 3. 双重检查
                storeValue = get(key);
                if (storeValue != null) {
                    return storeValue;
                }
                
                // 4. 执行加载逻辑
                T value = valueLoader.call();
                put(key, value);
                return toValueWrapper(value);
            } else {
                // 5. 没获取到锁，等待后重试
                Thread.sleep(100);
                return get(key, valueLoader); // 递归重试
            }
        } catch (Exception e) {
            throw new ValueRetrievalException(key, valueLoader, e);
        } finally {
            if (locked) {
                redisTemplate.delete(lockKey);
            }
        }
    }
}

## 缓存一致性方案深度解析

### 1. 延时双删（Delayed Double Delete）

#### 原理深度分析

```
延时双删时序图：

场景：T1更新数据，T2并发读取

正常情况：
T1: 删除缓存 ──→ 更新DB ──→ 延时（500ms）──→ 再次删除缓存
T2:         读缓存Miss ──→ 读DB旧值 ──→ 写入旧缓存（被T1的第二次删除覆盖）
T3:                                             读缓存Miss ──→ 读DB新值 ──→ 写入新缓存

边界情况（延时不足）：
T1: 删除缓存 ──→ 更新DB ──→ 延时（100ms）──→ 再次删除缓存
T2:         读缓存Miss ──→ 读DB旧值 ──→ 写入旧缓存
T3: （T1第二次删除已执行，但T2还没写入）
T4:                                             T2的旧缓存写入成功
结果：缓存又变成旧值，直到过期

延时时间的计算：
delay > max(主从同步延迟) + max(业务读DB+写缓存耗时) + buffer

例如：
- 主从同步延迟：100ms
- 读DB耗时：20ms
- 写缓存耗时：5ms
- Buffer：50ms
- 建议延时：200ms
```

#### 延时双删的数学分析

```
不一致窗口计算：

设：
- T_db = 数据库更新时间
- T_del1 = 第一次删除缓存时间
- T_del2 = 第二次删除缓存时间
- T_read = 并发读操作开始时间
- T_write = 并发读操作写回缓存时间

不一致条件：
T_db < T_read < T_del2 < T_write

即：读操作在DB更新后开始，在第二次删除前开始写缓存，
    但第二次删除发生在写缓存完成之前。

概率模型：
假设更新操作和读操作都是泊松过程，到达率分别为λ_u和λ_r

P(不一致) ≈ λ_u * λ_r * E[T_delay] * (E[T_write] - E[T_delay])^+

其中：
- λ_u: 更新操作到达率
- λ_r: 读操作到达率  
- E[T_delay]: 平均延时时间
- E[T_write]: 平均写缓存时间

关键结论：
1. 延时越长，不一致概率越低，但用户体验越差
2. 读操作越频繁，不一致概率越高
3. 延时双删只能降低不一致概率，无法完全消除
```

#### 延时双删代码实现（完整版）

```java
@Service
public class DelayedDoubleDeleteService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private UserDao userDao;
    
    @Autowired
    private ThreadPoolExecutor asyncExecutor;
    
    private static final long DEFAULT_DELAY_MS = 500;
    
    /**
     * 延时双删实现
     */
    @Transactional
    public void updateUser(User user) {
        String key = "user:" + user.getId();
        
        // 1. 先删缓存
        redisTemplate.delete(key);
        
        // 2. 更新数据库
        userDao.update(user);
        
        // 3. 延时异步再次删除
        asyncExecutor.execute(() -> {
            try {
                // 延时时间应大于主从同步延迟 + 读DB写缓存耗时
                Thread.sleep(DEFAULT_DELAY_MS);
                
                // 再次删除缓存
                redisTemplate.delete(key);
                
                log.info("Delayed double delete executed for key: {}", key);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                log.error("Delayed delete interrupted", e);
            }
        });
    }
    
    /**
     * 更严谨的实现：基于Redis延迟队列
     * 避免应用重启导致第二次删除丢失
     */
    @Transactional
    public void updateUserWithRedisDelay(User user) {
        String key = "user:" + user.getId();
        
        // 1. 先删缓存
        redisTemplate.delete(key);
        
        // 2. 更新数据库
        userDao.update(user);
        
        // 3. 将延迟删除任务放入Redis Sorted Set
        long executeTime = System.currentTimeMillis() + DEFAULT_DELAY_MS;
        redisTemplate.opsForZSet()
            .add("delay:delete", key, executeTime);
    }
    
    /**
     * 定时消费延迟删除队列
     */
    @Scheduled(fixedRate = 1000)
    public void processDelayDeleteQueue() {
        long now = System.currentTimeMillis();
        
        Set<String> keys = redisTemplate.opsForZSet()
            .rangeByScore("delay:delete", 0, now);
        
        if (CollectionUtils.isEmpty(keys)) {
            return;
        }
        
        for (String key : keys) {
            redisTemplate.delete(key);
            redisTemplate.opsForZSet().remove("delay:delete", key);
            log.info("Processed delayed delete for key: {}", key);
        }
    }
}

@Component
public class CanalBinlogListener {
    
    @Autowired
    private CanalConnector canalConnector;
    
    @Autowired
    private CacheInvalidationService cacheService;
    
    @Autowired
    private ElasticsearchClient esClient;
    
    @PostConstruct
    public void startListening() {
        Thread thread = new Thread(() -> {
            while (true) {
                try {
                    // 批量获取消息（每次最多1000条）
                    Message message = canalConnector.getWithoutAck(1000);
                    long batchId = message.getId();
                    
                    if (batchId == -1 || message.getEntries().isEmpty()) {
                        Thread.sleep(1000);
                        continue;
                    }
                    
                    // 处理binlog事件
                    for (CanalEntry.Entry entry : message.getEntries()) {
                        if (entry.getEntryType() == CanalEntry.EntryType.TRANSACTIONBEGIN ||
                            entry.getEntryType() == CanalEntry.EntryType.TRANSACTIONEND) {
                            continue;
                        }
                        
                        CanalEntry.RowChange rowChange = 
                            CanalEntry.RowChange.parseFrom(entry.getStoreValue());
                        
                        String tableName = entry.getHeader().getTableName();
                        
                        for (CanalEntry.RowData rowData : rowChange.getRowDatasList()) {
                            handleRowChange(tableName, rowChange.getEventType(), rowData);
                        }
                    }
                    
                    // 确认消费
                    canalConnector.ack(batchId);
                    
                } catch (Exception e) {
                    log.error("Canal listening error", e);
                }
            }
        });
        thread.setName("canal-listener");
        thread.setDaemon(true);
        thread.start();
    }
    
    private void handleRowChange(String tableName, 
        CanalEntry.EventType eventType, CanalEntry.RowData rowData) {
        
        if ("user".equals(tableName)) {
            // 提取主键
            Long userId = extractId(rowData.getAfterColumnsList());
            String cacheKey = "user:" + userId;
            
            switch (eventType) {
                case INSERT:
                case UPDATE:
                    // 删除缓存（让下次读取重新加载）
                    cacheService.invalidate(cacheKey);
                    
                    // 更新ES索引
                    User user = buildUserFromColumns(rowData.getAfterColumnsList());
                    esClient.index(i -> i.index("user").id(userId.toString())
                        .document(user));
                    break;
                    
                case DELETE:
                    // 删除缓存
                    cacheService.invalidate(cacheKey);
                    
                    // 删除ES索引
                    esClient.delete(d -> d.index("user").id(userId.toString()));
                    break;
            }
        }
    }
    
    private Long extractId(List<CanalEntry.Column> columns) {
        return columns.stream()
            .filter(c -> "id".equals(c.getName()))
            .map(c -> Long.parseLong(c.getValue()))
            .findFirst()
            .orElse(null);
    }
}

### 3. 分布式锁方案

#### RedLock算法分析

```
RedLock算法（Redis Distributed Lock）：

问题：单机Redis的分布式锁在节点故障时可能丢失

RedLock解决方案：
使用N个（通常5个）独立的Redis Master节点

加锁流程：
1. 获取当前时间戳T1
2. 依次向N个Redis节点尝试加锁（使用相同的key和随机值）
3. 计算获取锁的总耗时T2 = now - T1
4. 如果成功加锁的节点数 >= N/2 + 1，且总耗时 < 锁的过期时间，则加锁成功
5. 如果加锁失败，向所有节点发送释放锁的请求

释放锁流程：
1. 向所有节点发送释放锁请求（使用Lua脚本保证原子性）
2. 无论之前是否成功加锁，都要尝试释放

Redisson实现：
```java
RedissonRedLock redLock = new RedissonRedLock(lock1, lock2, lock3);
redLock.lock();
try {
    // 执行业务逻辑
} finally {
    redLock.unlock();
}
```

争议：
- Redis作者antirez提出RedLock
- Martin Kleppmann批评RedLock在网络延迟和时钟漂移下不安全
- 实际生产环境建议：使用ZooKeeper/Etcd保证强一致性，或对RedLock加兜底（数据库唯一索引）
```

#### 分布式锁缓存一致性实现

```java
@Service
public class DistributedLockCacheService {
    
    @Autowired
    private RedissonClient redissonClient;
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private UserDao userDao;
    
    private static final String CACHE_PREFIX = "user:";
    private static final String LOCK_PREFIX = "lock:user:";
    private static final long LOCK_WAIT_TIME = 5;
    private static final long LOCK_LEASE_TIME = 30;
    
    /**
     * 使用分布式锁保证缓存一致性（读操作）
     * 
     * 解决：缓存击穿（热点key过期瞬间大量请求查DB）
     */
    public User getUserWithLock(Long id) {
        String cacheKey = CACHE_PREFIX + id;
        String lockKey = LOCK_PREFIX + id;
        
        // 1. 先读缓存
        String json = redisTemplate.opsForValue().get(cacheKey);
        if (json != null) {
            return JSON.parseObject(json, User.class);
        }
        
        // 2. 缓存未命中，获取分布式锁
        RLock lock = redissonClient.getLock(lockKey);
        boolean locked = false;
        
        try {
            locked = lock.tryLock(LOCK_WAIT_TIME, LOCK_LEASE_TIME, TimeUnit.SECONDS);
            
            if (!locked) {
                // 获取锁失败，可能是并发冲突，短暂等待后重试
                Thread.sleep(100);
                return getUserWithLock(id); // 递归重试
            }
            
            // 3. 双重检查（获取锁后再次检查缓存）
            json = redisTemplate.opsForValue().get(cacheKey);
            if (json != null) {
                return JSON.parseObject(json, User.class);
            }
            
            // 4. 查询数据库
            User user = userDao.getById(id);
            
            // 5. 写入缓存（设置随机过期时间，防止雪崩）
            if (user != null) {
                long expireSeconds = 30 * 60 + ThreadLocalRandom.current().nextInt(300);
                redisTemplate.opsForValue().set(cacheKey, 
                    JSON.toJSONString(user), expireSeconds, TimeUnit.SECONDS);
            }
            
            return user;
            
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException("Interrupted while waiting for lock", e);
        } finally {
            if (locked && lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
    
    /**
     * 使用分布式锁保证写操作一致性
     * 
     * 解决：并发更新导致的数据错乱
     */
    @Transactional
    public void updateUserWithLock(User user) {
        String cacheKey = CACHE_PREFIX + user.getId();
        String lockKey = LOCK_PREFIX + user.getId();
        
        RLock lock = redissonClient.getLock(lockKey);
        boolean locked = false;
        
        try {
            locked = lock.tryLock(LOCK_WAIT_TIME, LOCK_LEASE_TIME, TimeUnit.SECONDS);
            
            if (!locked) {
                throw new RuntimeException("Failed to acquire lock for user: " + user.getId());
            }
            
            // 1. 更新数据库
            userDao.update(user);
            
            // 2. 删除缓存
            redisTemplate.delete(cacheKey);
            
            // 3. 可选：写入新的缓存值（减少下次读取的延迟）
            // redisTemplate.opsForValue().set(cacheKey, JSON.toJSONString(user), ...);
            
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException("Interrupted", e);
        } finally {
            if (locked && lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
    
    /**
     * RedLock实现（多Redis节点）
     */
    public User getUserWithRedLock(Long id) {
        String cacheKey = CACHE_PREFIX + id;
        
        // 多个Redis节点上的锁
        RLock lock1 = redissonClient1.getLock("lock:user:" + id);
        RLock lock2 = redissonClient2.getLock("lock:user:" + id);
        RLock lock3 = redissonClient3.getLock("lock:user:" + id);
        
        RedissonRedLock redLock = new RedissonRedLock(lock1, lock2, lock3);
        boolean locked = false;
        
        try {
            locked = redLock.tryLock(LOCK_WAIT_TIME, LOCK_LEASE_TIME, TimeUnit.SECONDS);
            
            if (locked) {
                // 执行业务逻辑
                String json = redisTemplate.opsForValue().get(cacheKey);
                if (json != null) {
                    return JSON.parseObject(json, User.class);
                }
                
                User user = userDao.getById(id);
                if (user != null) {
                    redisTemplate.opsForValue().set(cacheKey, 
                        JSON.toJSONString(user), Duration.ofMinutes(30));
                }
                return user;
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            if (locked) {
                redLock.unlock();
            }
        }
        
        return null;
    }
}

### 4. 基于版本号的乐观锁方案

```java
/**
 * 基于版本号的缓存一致性方案
 * 
 * 核心思想：每个数据附带版本号，缓存也存储版本号
 * 更新时比较版本号，避免旧数据覆盖新数据
 */
@Service
public class VersionedCacheService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private ProductDao productDao;
    
    private static final String CACHE_PREFIX = "product:";
    private static final String VERSION_PREFIX = "version:";
    
    /**
     * 读取带版本号的数据
     */
    public Product getProduct(Long id) {
        String cacheKey = CACHE_PREFIX + id;
        String versionKey = VERSION_PREFIX + id;
        
        // 1. 读取缓存数据和版本号
        String json = redisTemplate.opsForValue().get(cacheKey);
        Long cacheVersion = getCacheVersion(versionKey);
        
        if (json != null && cacheVersion != null) {
            Product product = JSON.parseObject(json, Product.class);
            product.setVersion(cacheVersion);
            return product;
        }
        
        // 2. 缓存未命中，从DB加载
        Product product = productDao.getById(id);
        if (product != null) {
            redisTemplate.opsForValue().set(cacheKey, JSON.toJSONString(product));
            redisTemplate.opsForValue().set(versionKey, 
                String.valueOf(product.getVersion()));
        }
        
        return product;
    }
    
    /**
     * 乐观锁更新
     */
    @Transactional
    public boolean updateProduct(Product product) {
        String cacheKey = CACHE_PREFIX + product.getId();
        String versionKey = VERSION_PREFIX + product.getId();
        
        // 1. 获取当前版本号（从DB或缓存）
        Long currentVersion = productDao.getVersion(product.getId());
        
        // 2. 比较版本号
        if (!currentVersion.equals(product.getVersion())) {
            // 版本号不一致，数据已被修改
            throw new ConcurrentModificationException(
                "Product has been modified by another transaction");
        }
        
        // 3. 更新DB，版本号+1
        product.setVersion(currentVersion + 1);
        int updated = productDao.updateWithVersion(product);
        
        if (updated == 0) {
            // 更新失败（并发冲突）
            return false;
        }
        
        // 4. 删除缓存（下次读取重新加载）
        redisTemplate.delete(cacheKey);
        redisTemplate.delete(versionKey);
        
        return true;
    }
    
    /**
     * 解决"旧缓存覆盖"问题
     * 
     * 场景：T1更新DB并删除缓存，T2的延时缓存更新到达
     * 如果缓存中带版本号，旧版本的数据不会覆盖新版本
     */
    public void setCacheWithVersion(Long id, Product product) {
        String cacheKey = CACHE_PREFIX + id;
        String versionKey = VERSION_PREFIX + id;
        
        // 使用Lua脚本保证原子性
        String lua = 
            "local currentVersion = redis.call('get', KEYS[2]) " +
            "if currentVersion == false or tonumber(ARGV[2]) > tonumber(currentVersion) then " +
            "    redis.call('set', KEYS[1], ARGV[1]) " +
            "    redis.call('set', KEYS[2], ARGV[2]) " +
            "    return 1 " +
            "else " +
            "    return 0 " +
            "end";
        
        Long result = redisTemplate.execute(
            new DefaultRedisScript<>(lua, Long.class),
            Arrays.asList(cacheKey, versionKey),
            JSON.toJSONString(product),
            String.valueOf(product.getVersion())
        );
        
        if (result != null && result == 1) {
            log.info("Cache updated with version {}", product.getVersion());
        } else {
            log.info("Cache update skipped due to version conflict");
        }
    }
    
    private Long getCacheVersion(String versionKey) {
        String version = redisTemplate.opsForValue().get(versionKey);
        return version != null ? Long.parseLong(version) : null;
    }
}

/**
 * 基于事务消息的缓存一致性方案
 * 
 * 流程：
 * 1. 发送半消息（事务消息）
 * 2. 执行本地事务（更新DB）
 * 3. 提交或回滚半消息
 * 4. 消费者消费消息，删除缓存
 */
@Service
public class TransactionalMessageService {
    
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    
    @Autowired
    private UserDao userDao;
    
    /**
     * 使用事务消息保证最终一致性
     */
    public void updateUserWithTransactionMessage(User user) {
        String cacheKey = "user:" + user.getId();
        
        // 1. 发送事务消息（半消息）
        TransactionSendResult result = rocketMQTemplate.sendMessageInTransaction(
            "cache_sync_topic",
            MessageBuilder.withPayload(new CacheInvalidationMessage(cacheKey))
                .setHeader("userId", user.getId())
                .build(),
            user // 本地事务参数
        );
        
        if (!result.getLocalTransactionState().equals(LocalTransactionState.COMMIT_MESSAGE)) {
            throw new RuntimeException("Transaction message send failed");
        }
    }
    
    /**
     * 本地事务监听器
     */
    @RocketMQTransactionListener
    class CacheSyncTransactionListener implements RocketMQLocalTransactionListener {
        
        @Autowired
        private UserDao userDao;
        
        /**
         * 执行本地事务
         */
        @Override
        public RocketMQLocalTransactionState executeLocalTransaction(
            Message msg, Object arg) {
            
            User user = (User) arg;
            try {
                // 执行本地事务：更新数据库
                userDao.update(user);
                return RocketMQLocalTransactionState.COMMIT_MESSAGE;
            } catch (Exception e) {
                return RocketMQLocalTransactionState.ROLLBACK_MESSAGE;
            }
        }
        
        /**
         * 回查本地事务状态
         */
        @Override
        public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {
            Long userId = Long.valueOf(msg.getHeaders().get("userId").toString());
            
            // 检查DB中是否有该用户的更新记录
            User user = userDao.getById(userId);
            if (user != null && user.getUpdateTime() != null) {
                return RocketMQLocalTransactionState.COMMIT_MESSAGE;
            }
            
            return RocketMQLocalTransactionState.ROLLBACK_MESSAGE;
        }
    }
}

4. 评价数量：弱一致性（Write Behind，5分钟同步）

```java
@Service
public class ProductCacheService {
    
    @Autowired
    private RedissonClient redissonClient;
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private Cache caffeineCache;
    
    @Autowired
    private ProductDao productDao;
    
    /**
     * 商品详情读取（多级缓存）
     */
    public Product getProduct(Long productId) {
        String cacheKey = "product:" + productId;
        
        // L1: Caffeine本地缓存
        Product product = (Product) caffeineCache.getIfPresent(cacheKey);
        if (product != null) {
            return product;
        }
        
        // L2: Redis
        String json = redisTemplate.opsForValue().get(cacheKey);
        if (json != null) {
            product = JSON.parseObject(json, Product.class);
            caffeineCache.put(cacheKey, product);
            return product;
        }
        
        // L3: DB（带分布式锁防止缓存击穿）
        product = getProductFromDBWithLock(productId);
        return product;
    }
    
    /**
     * 价格更新（强一致性）
     */
    @Transactional
    public void updatePrice(Long productId, BigDecimal newPrice) {
        String cacheKey = "product:" + productId;
        String lockKey = "lock:product:" + productId;
        
        RLock lock = redissonClient.getLock(lockKey);
        try {
            lock.lock(10, TimeUnit.SECONDS);
            
            // 1. 更新DB
            productDao.updatePrice(productId, newPrice);
            
            // 2. 删除多级缓存
            caffeineCache.invalidate(cacheKey);
            redisTemplate.delete(cacheKey);
            
            // 3. 发送广播消息（其他节点的本地缓存）
            redisTemplate.convertAndSend("cache:invalidate", cacheKey);
            
            // 4. 延时双删（覆盖并发读导致的旧缓存）
            scheduleDelayedDelete(cacheKey, 500);
            
        } finally {
            lock.unlock();
        }
    }
    
    /**
     * 库存扣减（强一致性 + 防超卖）
     */
    @Transactional
    public boolean deductStock(Long productId, Integer quantity) {
        String stockKey = "stock:" + productId;
        String lockKey = "lock:stock:" + productId;
        
        RLock lock = redissonClient.getLock(lockKey);
        try {
            lock.lock(5, TimeUnit.SECONDS);
            
            // 1. 先查Redis库存（预扣减）
            Long stock = redisTemplate.opsForValue().decrement(stockKey, quantity);
            
            if (stock == null || stock < 0) {
                // 库存不足，回滚Redis
                redisTemplate.opsForValue().increment(stockKey, quantity);
                return false;
            }
            
            // 2. 更新DB库存
            int updated = productDao.deductStock(productId, quantity);
            
            if (updated == 0) {
                // DB扣减失败，回滚Redis
                redisTemplate.opsForValue().increment(stockKey, quantity);
                return false;
            }
            
            // 3. 删除商品缓存（下次读取重新加载最新库存）
            String cacheKey = "product:" + productId;
            redisTemplate.delete(cacheKey);
            caffeineCache.invalidate(cacheKey);
            
            return true;
            
        } finally {
            lock.unlock();
        }
    }
}
```

### 案例2：社交网络Feed流缓存一致性

**场景**：用户关注关系、Feed流、点赞数，读多写少，最终一致性即可

```
Feed流缓存架构：

┌─────────┐
│  Client │
└────┬────┘
     ↓
┌─────────┐     ┌─────────────────────────────┐

│         │     │                              │
│         │     │ 点赞数（String）             │
│         │     │ feed:like:{feedId}           │
└────┬────┘     └─────────────────────────────┘
     ↓
┌─────────┐
│   DB    │
└─────────┘

一致性策略：
1. 发Feed：Write Behind（先写Redis，异步写DB）
2. 点赞：Redis原子操作（INCR），异步同步DB
3. 关注关系：Cache Aside + Canal同步

@Service
public class FeedCacheService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private FeedDao feedDao;
    
    /**
     * 发布Feed（Write Behind模式）
     */
    public void publishFeed(Feed feed) {
        String feedKey = "feed:content:" + feed.getId();
        String timelineKey = "feed:timeline:" + feed.getUserId();
        
        // 1. 写入Redis（主流程）
        redisTemplate.opsForValue().set(feedKey, JSON.toJSONString(feed));
        redisTemplate.opsForZSet().add(timelineKey, feed.getId(), 
            feed.getCreateTime().getTime());
        
        // 2. 推送到关注者的Timeline（异步）
        asyncPushToFollowers(feed);
        
        // 3. 异步写入DB（Write Behind）
        feedQueue.offer(feed);
    }
    
    /**
     * 点赞（Redis原子操作）
     */
    public Long likeFeed(Long feedId, Long userId) {
        String likeCountKey = "feed:like:" + feedId;
        String userLikeKey = "feed:user:like:" + userId;
        
        // 1. 检查用户是否已点赞（Bitmap或Set）
        Boolean hasLiked = redisTemplate.opsForSet().isMember(
            userLikeKey, feedId.toString());
        
        if (Boolean.TRUE.equals(hasLiked)) {
            // 取消点赞
            redisTemplate.opsForSet().remove(userLikeKey, feedId.toString());
            Long count = redisTemplate.opsForValue().decrement(likeCountKey);
            asyncUnlikeToDB(feedId, userId);
            return count;
        }
        
        // 2. 点赞（Redis原子操作）
        redisTemplate.opsForSet().add(userLikeKey, feedId.toString());
        Long count = redisTemplate.opsForValue().increment(likeCountKey);
        
        // 3. 异步写DB
        asyncLikeToDB(feedId, userId);
        
        return count;
    }
}

### 案例3：库存系统强一致性方案

**场景**：秒杀、库存扣减，要求强一致性，不能超卖

```
库存系统架构：

┌─────────┐
│  Client │
└────┬────┘
     ↓
┌─────────┐     ┌─────────────────────────────┐

└────┬────┘     └─────────────────────────────┘
     ↓

│ Service │     │ Lua原子脚本保证不超卖         │
│         │     │                              │
│         │     │ 数据库最终扣减（事务消息）    │
└────┬────┘     └─────────────────────────────┘

┌─────────┐

└─────────┘

@Service
public class StockService {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private StockDao stockDao;
    
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    
    /**
     * 初始化库存到Redis
     */
    public void initStock(Long productId, Integer quantity) {
        String stockKey = "stock:" + productId;
        redisTemplate.opsForValue().set(stockKey, quantity.toString());
    }
    
    /**
     * 扣减库存（Redis + DB最终一致性）
     * 
     * 使用Lua脚本保证原子性
     */
    public boolean deductStock(Long productId, Integer quantity) {
        String stockKey = "stock:" + productId;
        
        String luaScript = 
            "local stock = tonumber(redis.call('get', KEYS[1])); " +
            "if stock == nil then return -1; end; " +
            "if stock >= tonumber(ARGV[1]) then " +
            "    redis.call('decrby', KEYS[1], ARGV[1]); " +
            "    return redis.call('get', KEYS[1]); " +
            "else " +
            "    return -2; " +
            "end;";
        
        Long result = redisTemplate.execute(
            new DefaultRedisScript<>(luaScript, Long.class),
            Collections.singletonList(stockKey),
            quantity.toString()
        );
        
        if (result == null || result == -1) {
            log.error("Stock not initialized for product: {}", productId);
            return false;
        }
        
        if (result == -2) {
            log.warn("Stock insufficient for product: {}", productId);
            return false;
        }
        
        // 发送事务消息，异步扣减DB库存
        rocketMQTemplate.sendMessageInTransaction(
            "stock_deduct_topic",
            MessageBuilder.withPayload(new StockDeductMessage(productId, quantity))
                .build(),
            null
        );
        
        return true;
    }
    
    /**
     * 定时校准：Redis库存与DB库存对齐
     */
    @Scheduled(fixedRate = 60000) // 每分钟执行
    public void syncStockToDB() {
        // 扫描Redis中所有库存key
        ScanOptions options = ScanOptions.scanOptions()
            .match("stock:*")
            .count(100)
            .build();
        
        Cursor<byte[]> cursor = redisTemplate.executeWithStickyConnection(
            redisConnection -> redisConnection.scan(options)
        );
        
        while (cursor.hasNext()) {
            String stockKey = new String(cursor.next());
            Long productId = Long.valueOf(stockKey.replace("stock:", ""));
            String stockStr = redisTemplate.opsForValue().get(stockKey);
            
            if (stockStr != null) {
                Integer redisStock = Integer.valueOf(stockStr);
                // 更新DB库存（以Redis为准，因为Redis是实际扣减的）
                stockDao.updateStock(productId, redisStock);
            }
        }
    }
}

### 缓存模式对比

## 性能分析：数学模型与量化计算

### 1. 缓存命中率与系统性能

```
缓存系统性能模型：

设：
- H = 缓存命中率（0 <= H <= 1）
- T_c = 缓存访问延迟（ms）
- T_d = 数据库访问延迟（ms）
- R = 读请求比例（0 <= R <= 1）
- W = 写请求比例（W = 1 - R）
- N = 并发请求数

平均响应时间：
T_avg = R * [H * T_c + (1-H) * (T_c + T_d)] + W * T_write

其中T_write取决于写策略：
- Cache Aside: T_write = T_d + T_c（更新DB + 删缓存）
- Write Through: T_write = max(T_d, T_c)（并行）
- Write Behind: T_write = T_c（仅写缓存）

示例计算：
H = 0.95, T_c = 1ms, T_d = 10ms, R = 0.9, W = 0.1

Cache Aside:
T_avg = 0.9 * [0.95*1 + 0.05*(1+10)] + 0.1 * (10+1)
      = 0.9 * [0.95 + 0.55] + 1.1
      = 0.9 * 1.5 + 1.1
      = 1.35 + 1.1
      = 2.45ms

无缓存:
T_avg = 0.9 * 10 + 0.1 * 10 = 10ms

加速比 = 10 / 2.45 ≈ 4.08x
```

### 2. 缓存一致性概率模型

```
不一致窗口计算：

Cache Aside模式的不一致概率：

设：
- λ_r = 读请求到达率（请求/秒）
- λ_w = 写请求到达率（请求/秒）
- T_window = 不一致窗口时间（秒）

假设读写请求服从泊松分布：

P(读在不一致窗口内到达) = 1 - e^(-λ_r * T_window)

P(读到旧值) = P(写操作发生) * P(读在不一致窗口内到达)
           ≈ λ_w * T_window * (1 - e^(-λ_r * T_window))

对于Cache Aside：
T_window = T_delete_cache - T_update_db ≈ 网络延迟（~1ms）

如果λ_r = 10000/s, λ_w = 100/s:
P(不一致) ≈ 100 * 0.001 * (1 - e^(-10000*0.001))
         ≈ 0.1 * (1 - e^(-10))
         ≈ 0.1 * 0.99995
         ≈ 0.1（10%）

这意味着在高并发下，Cache Aside有约10%的概率出现不一致！

延时双删优化：
T_window_optimized = T_second_delete - T_first_delete - T_db_update
                    ≈ 0（如果延时足够长）

实际上延时双删将不一致窗口从ms级缩短到几乎为0
（只要延时时间 > 主从同步延迟 + 读DB写缓存时间）
```

### 3. 分布式锁性能开销

```
分布式锁开销模型：

无锁操作耗时：
T_no_lock = T_cache_read

有锁操作耗时：
T_with_lock = T_lock_acquire + T_cache_read + T_lock_release

其中：
T_lock_acquire ≈ 2 * RTT(Redis) + T_setnx ≈ 2-5ms
T_lock_release ≈ 1 * RTT(Redis) + T_del ≈ 1-2ms

性能损失：
Overhead = T_with_lock / T_no_lock ≈ (5 + 1 + 2) / 1 = 8x

但在高并发下（1000并发）：
无锁：1000个请求同时查DB → DB QPS = 1000，可能打垮DB
有锁：1000个请求排队，1个查DB，其他等待 → DB QPS = 1，但平均等待时间增加

权衡：
- 低并发（<100 QPS）：不需要分布式锁
- 中等并发（100-1000 QPS）：分布式锁保护热点key
- 高并发（>1000 QPS）：本地锁 + 分布式锁双层保护，或改用Write Behind
```

### 4. Canal+MQ延迟分析

```
Canal+MQ端到端延迟：

T_total = T_binlog_generate + T_canal_pull + T_canal_parse + 
          T_mq_publish + T_mq_consume + T_cache_delete

各项延迟：
- T_binlog_generate: MySQL binlog写入延迟（~1ms）
- T_canal_pull: Canal拉取binlog（~10-100ms，取决于配置）
- T_canal_parse: 解析binlog（~1-5ms）
- T_mq_publish: MQ发送延迟（~1-5ms）
- T_mq_consume: MQ消费延迟（~1-10ms，取决于堆积情况）
- T_cache_delete: 删除缓存（~1ms）

总延迟范围：15ms ~ 120ms

优化手段：
1. Canal并行解析：多线程解析不同表的binlog
2. MQ批量消费：每次消费100条消息，减少网络往返
3. 本地缓存优先：Canal消息先更新本地缓存，再异步更新Redis
```

## 常见陷阱与最佳实践

### 陷阱1：先删缓存再更新DB

```java
/**
 * 错误示范：先删缓存，再更新DB
 * 
 * 时序问题：
 * T1: 删除缓存
 * T2: 读缓存未命中，读DB旧值
 * T3: T2写入旧值到缓存
 * T4: 更新DB为新值
 * 
 * 结果：缓存=旧值，DB=新值，长期不一致
 */
public void wrongOrder(User user) {
    String key = "user:" + user.getId();
    
    // 错误：先删缓存
    redisTemplate.delete(key);
    
    // 更新DB
    userDao.update(user);
}

/**
 * 正确做法：先更新DB，再删缓存
 * 
 * 不一致窗口极短（仅在DB更新完成到缓存删除之间）
 * 且需要读操作恰好在这个窗口内执行并写回缓存
 */
public void correctOrder(User user) {
    String key = "user:" + user.getId();
    
    // 1. 先更新DB
    userDao.update(user);
    
    // 2. 再删缓存
    redisTemplate.delete(key);
}
```

### 陷阱2：缓存与DB操作不在同一事务

/**
 * 错误示范：缓存操作在事务外

@Transactional

    rocketMQTemplate.sendMessageInTransaction("cache_invalidate_topic",

### 陷阱5：缓存穿透与并发重建

```java
/**
 * 缓存穿透：查询不存在的数据，绕过缓存直接查DB
 * 
 * 恶意攻击：请求大量不存在的ID
 */
public User wrongPenetration(Long id) {
    String key = "user:" + id;
    String json = redisTemplate.opsForValue().get(key);
    
    if (json != null) {
        return JSON.parseObject(json, User.class);
    }
    
    // 错误：DB没有就不缓存，每次都查DB
    User user = userDao.getById(id);
    return user;
}

/**
 * 正确做法：缓存空值 + 布隆过滤器
 */
@Service
public class CachePenetrationProtection {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private UserDao userDao;
    
    // 布隆过滤器（Guava或Redis布隆过滤器）
    private BloomFilter<Long> bloomFilter;
    
    @PostConstruct
    public void init() {
        // 初始化布隆过滤器（预期100万条数据，误判率1%）
        bloomFilter = BloomFilter.create(
            Funnels.longFunnel(), 
            1000000, 
            0.01
        );
        
        // 预热布隆过滤器
        List<Long> allIds = userDao.getAllIds();
        allIds.forEach(bloomFilter::put);
    }
    
    public User getUser(Long id) {
        String key = "user:" + id;
        
        // 1. 布隆过滤器预判
        if (!bloomFilter.mightContain(id)) {
            return null; // 一定不存在
        }
        
        // 2. 读缓存
        String json = redisTemplate.opsForValue().get(key);
        if (json != null) {
            if ("null".equals(json)) {
                return null; // 空值缓存
            }
            return JSON.parseObject(json, User.class);
        }
        
        // 3. 查DB
        User user = userDao.getById(id);
        
        // 4. 缓存空值（防止穿透）
        if (user == null) {
            redisTemplate.opsForValue().set(key, "null", 1, TimeUnit.MINUTES);
            return null;
        }
        
        // 5. 缓存数据
        redisTemplate.opsForValue().set(key, JSON.toJSONString(user), 
            30, TimeUnit.MINUTES);
        
        return user;
    }
}
```

### 最佳实践清单

```
缓存一致性最佳实践：

1. 写策略
   ✓ 先更新DB，再删除缓存
   ✓ 写操作不更新缓存，只删除
   ✓ 使用延时双删降低不一致概率
   ✓ 事务提交后再删除缓存

2. 读策略
   ✓ 先读缓存，未命中再读DB
   ✓ 缓存空值防止穿透
   ✓ 使用布隆过滤器预判
   ✓ 分布式锁防止缓存击穿

3. 过期策略
   ✓ 设置合理的过期时间（作为兜底）
   ✓ 过期时间加随机偏移（防止雪崩）
   ✓ 热点key永不过期，后台定时刷新

4. 多级缓存
   ✓ L1本地缓存（Caffeine）- 1分钟
   ✓ L2分布式缓存（Redis）- 30分钟
   ✓ L3持久化存储（DB）- 永久
   ✓ 多级缓存同步使用Canal+MQ

5. 监控与治理
   ✓ 监控缓存命中率（>90%）
   ✓ 监控大Key和热Key
   ✓ 定期巡检缓存一致性
   ✓ 缓存降级策略（Redis故障时查DB）
```

## 面试题与参考答案

### Q1：为什么推荐先更新DB再删缓存，而不是先删缓存再更新DB？

**参考答案：**

```
核心原因：两种方案的不一致窗口不同

方案1：先删缓存，再更新DB
时序：
T1: Thread1删除缓存
T2: Thread2读缓存未命中，读DB旧值
T3: Thread2写入旧值到缓存
T4: Thread1更新DB为新值

结果：缓存=旧值，DB=新值，长期不一致（直到缓存过期）
不一致窗口：从T1到缓存过期（可能数分钟）

方案2：先更新DB，再删缓存
时序：
T1: Thread1更新DB为新值
T2: Thread2读缓存（命中，返回旧值）——这是正常缓存未过期，不算不一致
T3: Thread1删除缓存
T4: Thread2读缓存未命中，读DB新值，写入新缓存

或者极端情况：
T1: Thread1更新DB为新值
T2: Thread2读缓存未命中（恰好在T1更新后，T1删除前）
T3: Thread2读DB新值（T1已提交）
T4: Thread1删除缓存
T5: Thread2写入新值到缓存

结果：最终一致
不一致窗口：仅在T1更新DB到T1删除缓存之间（通常几ms）

结论：方案2的不一致窗口远小于方案1
```

### Q2：延时双删的原理是什么？延时多久合理？有什么缺点？

**参考答案：**

```
原理：
在更新DB后，等待一段时间再次删除缓存，覆盖并发读线程可能写入的旧值。

完整流程：
1. 先删缓存
2. 更新DB
3. 休眠X毫秒
4. 再次删缓存

为什么有效？
T1: 删除缓存
T2: 更新DB
T3: 并发读线程读DB旧值（主从延迟）
T4: 并发读线程写入旧值到缓存
T5: 延时到达，再次删除缓存（覆盖T4写入的旧值）
T6: 后续读取重新加载新值

延时时间计算：
delay > max(主从同步延迟) + max(业务读DB+写缓存耗时) + buffer(50ms)

实际建议：
- 普通业务：200-500ms
- 高并发业务：500-1000ms
- 可自适应：根据主从延迟监控动态调整

缺点：
1. 阻塞主线程（可用异步线程池优化）
2. 增加写操作延迟
3. 无法100%保证一致（极端并发下仍可能失败）
4. 应用重启可能导致第二次删除丢失（可用Redis延迟队列解决）
```

### Q3：Canal监听binlog和应用程序直接删缓存相比，有什么优缺点？

**参考答案：**

```
Canal方案优点：
1. 业务代码无侵入，缓存逻辑与业务解耦
2. 天然支持多级缓存同步（Redis、ES、本地缓存）
3. 最终一致性不依赖应用正确执行
4. 支持数据库变更的全量捕获（包括后台脚本、手动修改）

Canal方案缺点：
1. 架构复杂，引入Canal、MQ等组件
2. 有延迟（通常几十ms~几秒）
3. 需要处理binlog解析异常、消息堆积、重复消费
4. 无法处理应用层逻辑（如软删除标志位、业务校验）
5. 单表变更可能导致大量缓存失效（需要精细过滤）

应用删缓存优点：
1. 简单、实时、易控制
2. 可以结合业务逻辑做精细化缓存管理
3. 无额外组件依赖

应用删缓存缺点：
1. 代码侵入性强
2. 有漏删风险（异常、事务回滚）
3. 难以同步多级缓存
4. 后台脚本或手动修改DB时无法触发缓存失效

生产环境建议：
- 核心数据：Canal+MQ为主，应用删缓存为辅（双保险）
- 简单业务：应用直接删缓存
- 多级缓存：必须使用Canal保证各级缓存一致
```

### Q4：分布式锁解决缓存一致性的原理是什么？有什么副作用？RedLock是否安全？

**参考答案：**

```
原理：
缓存未命中时，先用分布式锁保证只有一个线程查DB并写缓存，
其他线程等待或重试读缓存。

具体流程：
1. Thread1读缓存未命中
2. Thread1获取分布式锁（SETNX）
3. Thread1查DB并写入缓存
4. Thread1释放锁
5. Thread2（并发线程）读缓存未命中
6. Thread2尝试获取锁失败，等待100ms
7. Thread2再次读缓存（已命中）

副作用：
1. 性能下降：加锁/释放锁有开销（~5ms），高并发下竞争激烈
2. 复杂度上升：锁超时、锁续期、锁误释放等问题
3. 不是银弹：只能解决缓存重建的并发问题，
   不能解决DB和Cache之间的事务不一致

RedLock安全性争议：
- Redis作者antirez提出：N个独立Redis节点，加锁成功数>=N/2+1且耗时<过期时间
- Martin Kleppmann批评：
  1. 时钟漂移：如果Redis节点时钟不同步，可能导致锁提前过期
  2. 网络延迟：获取锁的过程中，某个节点宕机并恢复，可能导致多个客户端同时持有锁
  3. 没有fencing token机制，无法防止延迟包导致的冲突

实际建议：
- 一般场景：单Redis+Redisson（看门狗自动续期）
- 强一致性场景：使用ZooKeeper/Etcd（基于 Paxos/Raft）
- 金融场景：数据库唯一索引作为最终兜底
```

### Q5：缓存穿透、缓存击穿、缓存雪崩有什么区别？如何解决？

**参考答案：**

```
| 问题 | 定义 | 原因 | 解决方案 |
|------|------|------|---------|
| 缓存穿透 | 查询不存在的数据，绕过缓存直接查DB | 恶意攻击、大量无效ID查询 | 布隆过滤器、缓存空值（短过期）、参数校验 |
| 缓存击穿 | 热点key过期瞬间，大量请求打到DB | 热点数据过期、并发重建 | 互斥锁重建、逻辑过期、热点key永不过期 |
| 缓存雪崩 | 大量key同时过期，DB压力骤增 | 批量设置相同过期时间、Redis故障 | 过期时间加随机值、多级缓存、熔断降级、高可用架构 |

详细方案：

缓存穿透：
1. 布隆过滤器：预热所有有效ID，请求前预判
2. 缓存空值：DB没有也缓存"null"，过期时间1分钟
3. 参数校验：ID范围校验、格式校验
4. 限流：对单个IP/用户限流

缓存击穿：
1. 分布式锁：只有一个线程重建缓存
2. 逻辑过期：缓存中存数据+过期时间戳，异步线程重建
3. 热点key永不过期：后台定时刷新
4. 多级缓存：本地缓存抗住第一波流量

缓存雪崩：
1. 过期时间加随机值：30分钟 + random(0-5分钟)
2. 多级缓存：本地缓存+Redis+CDN
3. 熔断降级：DB压力过大时返回默认值或错误提示
4. 高可用：Redis Cluster、Sentinel保证可用性
5. 预热：系统启动时提前加载热点数据
```

### Q6：多级缓存（本地+Redis+CDN）如何保证一致性？

**参考答案：**

```
多级缓存一致性策略：

架构：
L1: CDN（静态资源）
L2: Nginx本地缓存（Lua共享内存）
L3: 应用本地缓存（Caffeine）
L4: Redis分布式缓存
L5: 数据库

一致性方案：

1. 失效广播
- 数据更新时，发送失效消息到MQ
- 各节点消费消息，清除本地缓存
- 同时清除Redis缓存

2. 版本号机制
- 每个数据附带版本号
- 读取时比较版本号，旧版本不覆盖新版本
- 适用于本地缓存和Redis之间

3. 短过期时间
- L1: 1分钟
- L2: 5分钟
- L3: 30分钟
- 通过短过期时间实现最终一致

4. 主动预热
- 数据更新后，主动推送到各级缓存
- 而不是等用户请求时才加载

5. Canal同步
- 监听MySQL binlog
- 统一分发缓存失效消息
- 保证各级缓存最终一致

注意事项：
- 多级缓存之间是一致性与性能的平衡
- 通常允许秒级~分钟级不一致
- 金融数据不建议使用多级缓存
```

### Q7：如何设计一个高并发场景下的库存扣减系统（防超卖）？

**参考答案：**

```
库存扣减系统架构：

1. 流量入口
- API网关限流（令牌桶）
- 请求去重（Redis SetNX）
- 验证码/滑块（防止脚本攻击）

2. 库存预扣减（Redis）
- 使用Lua脚本保证原子性
- Redis库存 >= 扣减量时，才扣减
- 扣减成功后，发送事务消息

3. 数据库扣减（最终一致）
- 消费事务消息
- 数据库乐观锁更新（version字段）
- 如果DB库存不足，回滚Redis库存

4. 库存回滚
- 订单超时未支付，释放库存
- 定时任务扫描超时订单
- 回滚Redis和DB库存

5. 库存校准
- 定时任务比对Redis库存和DB库存
- 以DB为准，修复Redis库存

核心代码：
```java
// Lua脚本保证原子性
String lua = 
    "local stock = tonumber(redis.call('get', KEYS[1])); " +
    "if stock == nil then return -1; end; " +
    "if stock >= tonumber(ARGV[1]) then " +
    "    redis.call('decrby', KEYS[1], ARGV[1]); " +
    "    return redis.call('get', KEYS[1]); " +
    "else " +
    "    return -2; " +
    "end;";
```

关键点：
- Redis预扣减保证高性能
- DB乐观锁保证不超卖
- 事务消息保证最终一致
- 定时校准保证数据对齐
```

### Q8：缓存和数据库如何保证事务一致性？

**参考答案：**

```
缓存和数据库的事务一致性是最终一致性，无法保证ACID。

原因：
1. 缓存操作和DB操作通常不在同一个事务中
2. 即使使用事务消息，也是最终一致
3. 分布式事务（2PC/XA）性能太差，不适合高并发

保证最终一致性的方案：

方案1：延时双删 + 消息队列
- 更新DB后删缓存
- 发送延时消息再次删缓存
- 消息队列保证至少一次删除

方案2：Canal监听binlog
- 监听MySQL binlog
- 根据binlog内容删除缓存
- 与业务代码解耦

方案3：事务消息（RocketMQ）
- 发送半消息
- 执行本地事务（更新DB）
- 提交消息，消费者删除缓存
- 提供回查机制

方案4：最大努力通知
- 更新DB后，多次尝试删除缓存
- 使用指数退避重试
- 最终保证缓存被删除

CAP选择：
- 缓存系统通常选择AP（可用性+分区容错性）
- 接受最终一致性
- 通过策略缩短不一致窗口
```

### Q9：大Key和热Key的治理方案？

**参考答案：**

```
大Key治理：

定义：单个key的value过大（>1MB）或包含过多元素（Hash/Set/ZSet成员数>1万）

危害：
1. 阻塞Redis单线程（删除、序列化耗时）
2. 网络传输慢
3. 内存碎片化
4. 主从同步延迟

检测：
1. redis-cli --bigkeys
2. Redis RDB工具分析
3. 内存采样（MEMORY USAGE key）

治理方案：
1. 拆分：将大Hash拆分成多个小Hash
   - 如：user:1000 → user:1000:profile, user:1000:orders
   
2. 压缩：使用压缩算法（Snappy、LZ4）
   
3. 本地缓存：大Key优先走本地缓存
   
4. 异步加载：大Key分片加载

热Key治理：

定义：某个key被频繁访问（QPS > 10000）

危害：
1. 单节点CPU打满
2. 网络带宽打满
3. 主从复制延迟

检测：
1. Redis监控（hotkeys参数）
2. 客户端统计
3. 代理层统计（如Twemproxy）

治理方案：
1. 本地缓存：热点数据缓存在应用本地
   
2. Key复制：将热Key复制多份
   - 如：hot_product:1000 → hot_product:1000_1, hot_product:1000_2
   - 读取时随机选择一个副本
   
3. 读写分离：从节点承担读流量
   
4. 打散：将热Key的访问分散到不同key
   - 如：使用user_id取模
```

### Q10：如何评估和监控缓存一致性？

**参考答案：**

```
缓存一致性评估指标体系：

1. 一致性检测
- 定期抽样比对缓存和DB的数据
- 使用校验和（CRC32/MD5）快速比对
- 不一致率 = 不一致样本数 / 总样本数

2. 监控指标
- 缓存命中率（目标>90%）
- 缓存穿透率（目标<1%）
- 缓存击穿次数（目标<10次/天）
- 缓存雪崩事件（目标0次）
- 缓存与DB延迟（目标<100ms）

3. 告警规则
- 命中率低于80%告警
- 穿透率高于5%告警
- 单Key QPS超过阈值告警
- 缓存与DB不一致率高于0.1%告警

4. 巡检工具
```java
@Component
public class CacheConsistencyChecker {
    
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    @Autowired
    private UserDao userDao;
    
    @Scheduled(cron = "0 0 2 * * ?") // 每天凌晨2点执行
    public void checkConsistency() {
        // 1. 随机抽样1000个key
        ScanOptions options = ScanOptions.scanOptions()
            .match("user:*")
            .count(1000)
            .build();
        
        Cursor<byte[]> cursor = redisTemplate.executeWithStickyConnection(
            conn -> conn.scan(options)
        );
        
        int total = 0;
        int inconsistent = 0;
        
        while (cursor.hasNext() && total < 1000) {
            String key = new String(cursor.next());
            Long userId = Long.valueOf(key.replace("user:", ""));
            
            // 2. 读取缓存
            String cacheJson = redisTemplate.opsForValue().get(key);
            User cacheUser = JSON.parseObject(cacheJson, User.class);
            
            // 3. 读取DB
            User dbUser = userDao.getById(userId);
            
            // 4. 比对
            if (!Objects.equals(cacheUser, dbUser)) {
                inconsistent++;
                log.warn("Inconsistent cache found: key={}", key);
                
                // 5. 修复：删除缓存，下次读取重新加载
                redisTemplate.delete(key);
            }
            
            total++;
        }
        
        double inconsistencyRate = (double) inconsistent / total;
        log.info("Cache consistency check completed. " +
            "Total: {}, Inconsistent: {}, Rate: {}%", 
            total, inconsistent, inconsistencyRate * 100);
    }
}
```

5. 一致性修复策略
- 自动修复：不一致时自动删除缓存
- 人工介入：不一致率过高时告警，人工排查
- 根因分析：定位是延时不足、消息丢失还是逻辑bug

目标：
- 不一致率 < 0.01%
- 不一致窗口 < 1秒
- 自动修复成功率 > 99.9%
```

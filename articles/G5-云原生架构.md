## 引言：云原生的本质

云原生（Cloud Native）不是"在云上运行程序"，而是一种**充分利用云计算弹性、分布式和自动化特性的软件工程方法论**。

核心认知：

```
软件交付的演进：

物理机时代（2000年前）：
┌─────────────┐
│  物理服务器  │
│  ┌─────────┐│
│  │  操作系统 ││
│  │  ┌─────┐││
│  │  │ App │││
│  │  └─────┘││
│  └─────────┘│
└─────────────┘
问题：资源利用率低（<20%），部署慢（周级）

虚拟化时代（2005-2015）：
┌─────────────┐
│  物理服务器  │
│  ┌─────────┐│
│  │ 虚拟化层 ││
│  │  ┌───┐  ││
│  │  │VM1│  ││
│  │  └───┘  ││
│  │  ┌───┐  ││
│  │  │VM2│  ││
│  │  └───┘  ││
│  └─────────┘│
└─────────────┘
进步：资源利用率提升（60%），部署加速（天级）
问题：VM启动慢（分钟级），镜像体积大（GB级）

容器时代（2013-至今）：
┌─────────────┐
│  物理服务器  │
│  ┌─────────┐│
│  │ 宿主机OS ││
│  │  ┌───┐  ││
│  │  │C1 │  ││  容器1（10MB）
│  │  └───┘  ││
│  │  ┌───┐  ││
│  │  │C2 │  ││  容器2（15MB）
│  │  └───┘  ││
│  └─────────┘│
└─────────────┘
进步：启动快（秒级），镜像小（MB级），密度高

云原生时代（2015-至今）：
┌─────────────────────────────────────────┐
│           Kubernetes集群                 │
│  - 自动调度                               │
│  - 自动扩缩容                             │
│  - 自动故障恢复                           │
│  - 声明式配置                             │
│  - 服务发现                               │
│  - 配置管理                               │
│  - 存储编排                               │
└─────────────────────────────────────────┘
本质：将运维能力平台化，开发者只需关注业务
```

**关键洞察**：云原生的核心不是容器，而是**不可变基础设施**和**声明式API**——你描述期望状态，系统自动达成。

## 理论基础：容器与编排的核心原理

### 1. Linux容器技术原理

#### Namespace隔离

```
Linux Namespace隔离机制：

┌─────────────────────────────────────────┐
│              宿主机                       │
│  ┌───────────────────────────────────┐  │
│  │  PID Namespace                     │  │
│  │  - 容器内PID 1是应用进程            │  │
│  │  - 宿主机看容器进程是普通进程        │  │
│  ├───────────────────────────────────┤  │
│  │  Network Namespace                 │  │
│  │  - 独立的网络栈（网卡、路由、iptables）│ │
│  │  - 容器间通过veth pair通信          │  │
│  ├───────────────────────────────────┤  │
│  │  Mount Namespace                   │  │
│  │  - 独立的文件系统视图               │  │
│  │  - 通过OverlayFS实现分层存储        │  │
│  ├───────────────────────────────────┤  │
│  │  UTS Namespace                     │  │
│  │  - 独立的主机名和域名               │  │
│  ├───────────────────────────────────┤  │
│  │  IPC Namespace                     │  │
│  │  - 独立的进程间通信（共享内存、信号量）│ │
│  ├───────────────────────────────────┤  │
│  │  User Namespace                    │  │
│  │  - 容器内root映射到宿主机普通用户    │  │
│  │  - 提升安全性                       │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘

容器 vs VM：
┌──────────────┬──────────────┬──────────────┐
│    特性      │    容器      │     VM       │
├──────────────┼──────────────┼──────────────┤
│ 隔离级别     │ 进程级       │ 操作系统级   │
│ 启动时间     │ 秒级         │ 分钟级       │
│ 镜像大小     │ MB级         │ GB级         │
│ 性能开销     │ <10%         │ 15-20%       │
│ 密度         │ 单机100+     │ 单机10-20    │
│ 安全性       │ 中           │ 高           │
│ 适用场景     │ 微服务       │ 传统应用     │
└──────────────┴──────────────┴──────────────┘
```

#### Cgroups资源限制

```
Cgroups（Control Groups）资源控制：

┌─────────────────────────────────────────┐
│  Cgroups子系统                           │
│                                         │
│  cpu：                                  │
│  - cpu.shares：CPU相对权重              │
│  - cpu.cfs_quota_us：CPU硬限制          │
│  - cpuacct.usage：CPU使用统计           │
│                                         │
│  memory：                               │
│  - memory.limit_in_bytes：内存限制      │
│  - memory.usage_in_bytes：内存使用      │
│  - memory.oom_control：OOM控制          │
│                                         │
│  blkio：                                │
│  - blkio.throttle.read_bps_device：读限速│
│  - blkio.throttle.write_bps_device：写限速│
│                                         │
│  pids：                                 │
│  - pids.max：最大进程数                 │
│                                         │
│  devices：                              │
│  - devices.allow：允许的设备            │
│  - devices.deny：禁止的设备             │
└─────────────────────────────────────────┘

K8s资源限制映射：
resources:
  requests:
    cpu: "500m"      → cpu.shares = 512
    memory: "512Mi"  → 不影响cgroups，仅用于调度
  limits:
    cpu: "1000m"     → cpu.cfs_quota_us = 100000
    memory: "1Gi"    → memory.limit_in_bytes = 1073741824
```

### 2. 容器镜像与分层存储

```
Docker镜像分层结构：

┌─────────────────────────────────────────┐
│  Layer 4: 应用层（可写）                  │
│  - 应用代码                               │
│  - 配置文件                               │
│  - 运行时数据                             │
├─────────────────────────────────────────┤
│  Layer 3: 应用依赖                        │
│  - JAR包 / Node_modules                   │
│  - 静态资源                               │
├─────────────────────────────────────────┤
│  Layer 2: 运行时                          │
│  - JDK / Node.js / Python                 │
├─────────────────────────────────────────┤
│  Layer 1: 基础镜像                        │
│  - Alpine / Debian / CentOS               │
│  - 系统库                                 │
└─────────────────────────────────────────┘

OverlayFS原理：
- Lower Dir：只读层（基础镜像层）
- Upper Dir：可写层（容器修改）
- Merged Dir：合并视图（容器看到的文件系统）
- Work Dir：工作目录

优势：
1. 分层复用：多个容器共享相同的基础镜像层
2. 写时复制（COW）：修改时才复制文件到可写层
3. 镜像体积小：只需存储差异层
```

### 3. 声明式API与控制器模式

```
声明式 vs 命令式：

命令式（Imperative）：
"给我创建一个Pod，使用nginx镜像，暴露80端口"
- 告诉系统"怎么做"
- 需要一步步执行
- 适合一次性操作

声明式（Declarative）：
"我期望的状态是：有3个nginx Pod在运行"
- 告诉系统"要什么"
- 系统自动达成期望状态
- 适合持续管理

K8s的声明式API：

用户提交YAML（期望状态）
        ↓
┌───────────────┐
│   API Server  │
│   (etcd存储)  │
└───────┬───────┘
        │  watch
        ↓
┌───────────────┐
│   Controller  │
│   (控制回路)   │
└───────┬───────┘
        │ 调谐
        ↓
┌───────────────┐
│   实际状态     │
└───────────────┘

控制器模式：
while (true) {
    实际状态 = 获取当前状态()
    期望状态 = 读取etcd()
    
    if (实际状态 != 期望状态) {
        执行调谐（Reconcile）
    }
    
    sleep(间隔)
}
```

## Kubernetes核心架构深度解析

### 1. K8s控制面（Master）组件

```
K8s控制面架构：

┌─────────────────────────────────────────┐
│           Master节点（控制面）            │
│                                         │
│  ┌─────────────┐  ┌───────────────────┐ │
│  │   API Server│  │   etcd            │ │
│  │   (kube-apiserver)                │ │
│  │             │  │   (数据存储)       │ │
│  │  - REST API入口                   │ │
│  │  - 认证鉴权                         │ │
│  │  - 请求校验                         │ │
│  │  - 所有组件通信中介                  │ │
│  │             │  │  - 分布式键值存储   │ │
│  │             │  │  - 存储集群状态     │ │
│  │             │  │  - 强一致性         │ │
│  └──────┬──────┘  └───────────────────┘ │
│         │                               │
│  ┌──────┴──────┐  ┌───────────────────┐ │
│  │   Scheduler │  │Controller Manager │ │
│  │   (kube-scheduler)                │ │
│  │             │  │   (kube-controller-manager)     │ │
│  │  - 调度Pod到节点                     │ │
│  │  - 预选策略（过滤）                  │ │
│  │  - 优选策略（打分）                  │ │
│  │             │  │  - Node Controller    │ │
│  │             │  │  - ReplicaSet Controller│ │
│  │             │  │  - Endpoint Controller│ │
│  │             │  │  - Service Controller │ │
│  └─────────────┘  └───────────────────┘ │
└─────────────────────────────────────────┘

API Server的关键作用：
1. 所有操作都通过API Server
2. 与etcd唯一交互的组件
3. 认证（Authentication）：谁发来的请求
4. 鉴权（Authorization）：能做什么操作
5. 准入控制（Admission Control）：请求是否合法

etcd为什么重要：
- K8s的唯一数据源（Single Source of Truth）
- 使用Raft算法保证一致性
- 默认监听2379端口
- 必须高可用部署（3或5节点集群）
```

#### 调度器（Scheduler）详解

```
调度流程：

1. 预选（Predicates）：过滤不满足条件的节点
   - PodFitsResources：资源是否足够
   - PodFitsHost：节点名称是否匹配
   - PodFitsHostPorts：端口是否冲突
   - NoDiskConflict：磁盘是否冲突
   - NoVolumeZoneConflict：存储区域是否冲突
   - MatchNodeSelector：标签选择器是否匹配
   - TaintsTolerations：污点和容忍

2. 优选（Priorities）：为剩余节点打分
   - LeastRequested：资源使用率低的节点优先
   - BalancedResourceAllocation：资源均衡的节点优先
   - ImageLocality：已有镜像的节点优先
   - Affinity/Anti-Affinity：亲和性/反亲和性

3. 绑定（Bind）：将Pod绑定到最优节点

调度算法示例：
┌─────────────────────────────────────────┐
│  节点1：CPU 80% / 内存 90%              │
│  节点2：CPU 50% / 内存 60%              │
│  节点3：CPU 30% / 内存 40%              │
│                                         │
│  预选结果：全部通过                      │
│  优选打分：                              │
│  - 节点1：10分（资源紧张）               │
│  - 节点2：50分（资源适中）               │
│  - 节点3：90分（资源充足）               │
│                                         │
│  选择：节点3                             │
└─────────────────────────────────────────┘
```

### 2. K8s工作节点（Worker）组件

```
K8s工作节点架构：

┌─────────────────────────────────────────┐
│           Worker节点（工作节点）          │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │           kubelet                  │  │
│  │  - 管理Pod生命周期                 │  │
│  │  - 与API Server通信                │  │

│  │  - 执行探针（Liveness/Readiness）  │  │

│  ┌─────────┐  ┌─────────────────────┐  │
│  │ Docker/ │  │     kube-proxy      │  │
│  │containerd│  │  - 网络代理          │  │
│  │         │  │  - 实现Service       │  │
│  │ 容器运行时│  │  - iptables/IPVS     │  │
│  └────┬────┘  └─────────────────────┘  │
│       │                                 │
│  ┌────┴────┐  ┌─────────────┐          │
│  │   Pod   │  │    Pod      │          │
│  │[Container]│  │[Container]│          │
│  │[Container]│  │[Container]│          │
│  └─────────┘  └─────────────┘          │
└─────────────────────────────────────────┘

kube-proxy的三种模式：

1. userspace模式（已废弃）：
   - kube-proxy作为用户态代理
   - 性能差，已不推荐使用

2. iptables模式（默认）：
   - 使用iptables规则实现负载均衡
   - 随机选择后端Pod
   - 连接数少时性能好

3. ipvs模式（推荐）：
   - 使用IPVS内核模块
   - 支持多种负载均衡算法（rr/wrr/lc/lh等）
   - 连接数多时性能更好

IPTables vs IPVS：
┌──────────────┬──────────────┬──────────────┐
│    特性      │   iptables   │     ipvs     │
├──────────────┼──────────────┼──────────────┤
│ 性能（1k服务）│  良好        │  良好        │
│ 性能（10k服务）│  下降        │  良好        │
│ 算法         │  随机        │  多种可选    │
│ 健康检查     │  依赖探针    │  内置        │
│ 连接亲和性   │  支持        │  支持        │
│ 内核要求     │  低          │  高（需模块）│
└──────────────┴──────────────┴──────────────┘
```

### 3. Pod与容器

#### Pod设计哲学

```
为什么需要Pod？

场景1：紧密耦合的容器
- Nginx + Logstash：Nginx生成日志，Logstash收集日志
- App + Sidecar Proxy：业务应用 + Envoy代理

场景2：共享资源
- 共享网络命名空间：同一个IP、Port空间
- 共享存储卷：数据在容器间共享

┌─────────────────────────────────────────┐
│  Pod（最小调度单元）                      │
│  ┌───────────────────────────────────┐  │
│  │  共享资源：                         │  │
│  │  - IP地址：10.244.1.5              │  │
│  │  - Port空间：8080, 9090            │  │
│  │  - Volume：/var/log/shared         │  │
│  │  - IPC命名空间                      │  │
│  ├───────────────────────────────────┤  │
│  │  Container A: App                 │  │
│  │  - 监听8080                        │  │
│  │  - 写入日志到/var/log/shared       │  │
│  ├───────────────────────────────────┤  │
│  │  Container B: Logstash            │  │
│  │  - 读取/var/log/shared日志         │  │
│  │  - 发送到Elasticsearch             │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘

Pod vs Container：
- Pod是K8s最小部署单元，可以包含多个Container
- Pod内所有容器共享网络和存储
- Pod内的容器总是调度到同一个节点
- Pod是临时的，不应被视为持久化实体
```

#### Pod生命周期与状态机

```
Pod状态机：

Pending → ContainerCreating → Running → Succeeded / Failed / Unknown
   ↓                          ↓
   └──── 镜像拉取中              └── 被驱逐（Evicted）
   
Pod Conditions：
- PodScheduled：已调度到节点
- ContainersReady：所有容器就绪
- Initialized：初始化容器完成
- Ready：Pod可以接收流量

Pod状态详解：
┌─────────────────────────────────────────┐
│  Pending                                │
│  - Pod已创建，但尚未调度                 │
│  - 原因：资源不足、污点不匹配、亲和性     │
├─────────────────────────────────────────┤
│  ContainerCreating                      │
│  - 正在拉取镜像、创建容器                │
│  - 可能失败：镜像不存在、拉取超时         │
├─────────────────────────────────────────┤
│  Running                                │
│  - Pod已绑定到节点，所有容器已创建       │
│  - 至少一个容器正在运行                  │
├─────────────────────────────────────────┤
│  Succeeded                              │
│  - 所有容器正常退出（exit 0）            │
│  - 适用于Job/CronJob                    │
├─────────────────────────────────────────┤
│  Failed                                 │
│  - 至少一个容器异常退出（exit != 0）     │
│  - 或容器被系统终止                      │
├─────────────────────────────────────────┤
│  Unknown                                │
│  - 无法获取Pod状态                       │
│  - 通常是节点与Master失联                │
└─────────────────────────────────────────┘
```

#### 探针（Probe）机制

```yaml
# 健康探针配置详解
apiVersion: v1
kind: Pod
metadata:
  name: health-check-demo
spec:
  containers:
  - name: app
    image: myapp:1.0
    ports:
    - containerPort: 8080
    
    # Liveness Probe：存活探针
    # 作用：判断容器是否还在运行
    # 失败：kubelet会重启容器
    livenessProbe:
      httpGet:
        path: /actuator/health/liveness
        port: 8080
        httpHeaders:
        - name: Custom-Header
          value: liveness
      initialDelaySeconds: 60   # 容器启动后60秒开始探测
      periodSeconds: 10         # 每10秒探测一次
      timeoutSeconds: 5         # 超时时间5秒
      failureThreshold: 3       # 连续3次失败才重启
      successThreshold: 1       # 连续1次成功就认为健康
    
    # Readiness Probe：就绪探针
    # 作用：判断容器是否准备好接收流量
    # 失败：Pod从Service的Endpoint中移除
    readinessProbe:
      httpGet:
        path: /actuator/health/readiness
        port: 8080
      initialDelaySeconds: 10   # 容器启动后10秒开始探测
      periodSeconds: 5          # 每5秒探测一次
      timeoutSeconds: 3
      failureThreshold: 3
    
    # Startup Probe：启动探针（K8s 1.16+）
    # 作用：判断容器是否启动完成
    # 在Startup Probe成功前，Liveness和Readiness不生效
    startupProbe:
      httpGet:
        path: /actuator/health
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 10
      timeoutSeconds: 5
      failureThreshold: 30      # 最多重试30次（300秒）

# 探针类型：
# 1. httpGet：HTTP请求，200-399为成功
# 2. tcpSocket：TCP连接，连接成功为成功
# 3. exec：执行命令，exit 0为成功
# 4. grpc：gRPC健康检查（K8s 1.24+）
```

### 7. 自动扩缩容

#### HPA（Horizontal Pod Autoscaler）

```yaml
# HPA：基于CPU和内存的自动扩缩容
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 3
  maxReplicas: 100
  metrics:
  # 基于CPU
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70      # CPU使用率目标70%
  
  # 基于内存
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80      # 内存使用率目标80%
  
  # 基于自定义指标（Prometheus）
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "1000"         # 每Pod 1000 RPS
  
  behavior:                          # 扩缩容行为（K8s 1.18+）
    scaleUp:
      stabilizationWindowSeconds: 60  # 扩容前等待60秒
      policies:
      - type: Percent
        value: 100                    # 每次最多扩容100%
        periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300 # 缩容前等待300秒
      policies:
      - type: Percent
        value: 10                     # 每次最多缩容10%
        periodSeconds: 60
```

#### VPA（Vertical Pod Autoscaler）与Cluster Autoscaler

```
三种自动扩缩容：

┌─────────────────────────────────────────┐
│  HPA（Horizontal Pod Autoscaler）        │
│  - 水平扩缩容：增加/减少Pod数量          │
│  - 指标：CPU、内存、自定义指标            │
│  - 适用：无状态应用                       │
│  - 速度：秒级                            │
├─────────────────────────────────────────┤
│  VPA（Vertical Pod Autoscaler）          │
│  - 垂直扩缩容：增加/减少Pod资源           │
│  - 指标：历史资源使用                     │
│  - 适用：有状态应用（数据库等）           │
│  - 速度：分钟级（需要重启Pod）            │
├─────────────────────────────────────────┤
│  Cluster Autoscaler                      │
│  - 集群扩缩容：增加/减少节点数量          │
│  - 触发：Pod无法调度（资源不足）          │
│  - 适用：云环境                           │
│  - 速度：分钟级（云厂商创建VM）           │
└─────────────────────────────────────────┘

三者协同：
1. 负载增加 → HPA扩容Pod
2. Pod无法调度 → Cluster Autoscaler扩容节点
3. 负载稳定 → VPA调整Pod资源请求（优化调度）
```

## 常见陷阱与最佳实践

### 陷阱1：应用非无状态化，依赖本地存储

```
❌ 错误做法：
应用将用户session、上传文件存储在容器本地磁盘
┌─────────────┐
│    Pod      │
│ [Container] │
│  /data/session│ ← 容器重启数据丢失
│  /data/upload │ ← 调度到新节点数据无法访问
└─────────────┘

✅ 最佳实践：
1. Session外置到Redis
2. 文件存储使用对象存储（OSS/S3）或共享存储（NFS/PV）
3. 应用设计为无状态，任何Pod随时可销毁重建
4. 配置使用ConfigMap/Secret，不硬编码
5. 日志输出到stdout/stderr，由日志收集器采集

无状态应用设计原则：
┌─────────────────────────────────────────┐
│  1. 不依赖本地文件系统                  │
│  2. 配置通过环境变量或配置文件注入        │
│  3. 会话数据外置到缓存（Redis）          │
│  4. 文件存储使用对象存储                 │
│  5. 日志输出到标准输出                   │
│  6. 启动时自动初始化（不依赖旧数据）      │
└─────────────────────────────────────────┘
```

### 陷阱2：资源限制配置缺失或不合理

```yaml
❌ 危险配置：
spec:
  containers:
  - name: app
    resources: {}  # 完全不设限制

问题：
- 某个Pod内存泄漏，耗尽节点资源，导致节点OOM Kill所有Pod
- CPU饥饿：重要服务抢不到CPU

✅ 最佳实践：
1. 必须设置requests和limits
2. requests用于调度，limits用于限制
3. requests ≤ limits，建议设置相等（避免节点超售）
4. 根据压测数据设置，java应用注意堆内存+容器内存的关系

resources:
  requests:
    memory: "512Mi"
    cpu: "500m"
  limits:
    memory: "1Gi"
    cpu: "1000m"

Java应用特别注意：
- JVM堆内存（-Xmx）应小于容器内存limit
- 建议：-Xmx = limit × 0.75
- 示例：limit=1Gi → -Xmx=768m
```

### 陷阱3：健康探针配置不当

```yaml
❌ 常见问题：
livenessProbe:
  httpGet:
    path: /actuator/health
    port: 8080
  initialDelaySeconds: 5   # 太短，应用还没启动
  periodSeconds: 3600       # 太长，故障发现不及时

问题：
- liveness太早触发 → 无限重启
- readiness缺失 → 流量打到未就绪Pod
- 探针路径太重 → 探针本身压垮服务

✅ 最佳实践：
1. liveness和readiness必须同时配置
2. initialDelaySeconds要大于应用启动时间（Java建议30-60s）
3. periodSeconds建议5-10s，超时时间3-5s
4. liveness用轻量级接口（/health/live），readiness检查依赖（/health/ready）
5. 失败阈值设置合理（failureThreshold: 3）
6. 使用startupProbe避免启动期间的误判

推荐配置：
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 60
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
  timeoutSeconds: 3
  failureThreshold: 3

startupProbe:
  httpGet:
    path: /actuator/health
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 30
```

```
❌ 安全问题：
1. Pod以root用户运行
2. 特权模式（privileged: true）
3. 没有ResourceQuota和LimitRange
4. RBAC权限过大
5. 镜像来自不可信源
```

## 面试题与参考答案

### Q1：Kubernetes的架构和核心组件有哪些？

**答：**

**Master节点（控制面）**：
- **API Server**：REST API入口，所有组件通信中介，认证鉴权
- **etcd**：分布式键值存储，保存集群状态，使用Raft算法保证一致性
- **Scheduler**：调度Pod到合适的Worker节点，预选+优选算法
- **Controller Manager**：维护集群状态（副本数、节点健康、Endpoint等）

**Worker节点（工作节点）**：
- **kubelet**：管理Pod生命周期，与Master通信，执行探针
- **kube-proxy**：网络代理，实现Service的负载均衡（iptables/IPVS）
- **Container Runtime**：容器运行时（Docker/containerd/CRI-O）

### Q2：Pod和Container的关系是什么？

**答：**

- **Pod是K8s最小部署单元**，一个Pod可以包含多个Container
- 同一个Pod的容器共享：网络命名空间（IP相同）、存储卷（Volume）、IPC命名空间
- 常见模式：主容器+Sidecar容器（如应用+Nginx代理/日志收集）

**设计原因**：
- 紧密耦合的容器需要共享资源
- Sidecar模式扩展功能无需修改主应用
- Pod作为调度单元，保证相关容器调度到同一节点

### Q3：Deployment的滚动更新策略有哪些参数？

**答：**

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1          # 更新时最多可多出的Pod数（绝对值或百分比）
    maxUnavailable: 0    # 更新时最多不可用的Pod数
```

- **maxSurge**：控制更新速度，值越大更新越快
- **maxUnavailable**：控制可用性，0表示更新过程中不能减少可用Pod
- 生产环境建议：maxSurge=1, maxUnavailable=0（保证始终有完整副本可用）

### Q4：Service的三种类型及适用场景？

**答：**

| 类型 | 说明 | 适用场景 |
|------|------|----------|
| **ClusterIP** | 集群内部虚拟IP，仅内部访问 | 微服务间调用 |
| **NodePort** | 在每个节点开放端口（30000-32767） | 测试环境、临时暴露 |
| **LoadBalancer** | 云厂商负载均衡器 | 生产环境公网暴露 |
| **Headless** | 无ClusterIP，直接返回Pod IP | StatefulSet（如Redis集群） |

生产环境推荐：LoadBalancer（云厂商）或Ingress（HTTP层路由）。

### Q5：Ingress和Service有什么区别？

**答：**

- **Service**：L4（传输层）负载均衡，基于IP+端口转发
- **Ingress**：L7（应用层）路由，基于HTTP路径、域名、Header等规则

Ingress需要Ingress Controller（如Nginx Ingress、Traefik）实现。

典型配置：
- `api.example.com/api/v1` → api-service
- `api.example.com/web` → web-service
- 支持TLS终止、重写、限流等高级功能

### Q6：ConfigMap和Secret有什么区别？

**答：**

| 维度 | ConfigMap | Secret |
|------|-----------|--------|
| 用途 | 普通配置（非敏感） | 敏感数据（密码、Token、证书） |
| 编码 | 明文存储 | Base64编码（非加密） |
| 大小限制 | 1MB | 1MB |
| 使用方式 | 环境变量、挂载卷 | 环境变量、挂载卷 |

**注意**：Secret只是Base64编码，不是加密。生产环境应：
1. 启用K8s etcd加密（Encryption at Rest）
2. 使用外部Secret管理工具（Vault、Sealed Secrets）
3. 限制Secret的RBAC权限

### Q7：HPA、VPA和Cluster Autoscaler有什么区别？

**答：**

- **HPA（Horizontal Pod Autoscaler）**：水平扩缩容，增加/减少Pod数量，基于CPU/内存/自定义指标，适合无状态应用
- **VPA（Vertical Pod Autoscaler）**：垂直扩缩容，增加/减少Pod资源（CPU/内存），适合有状态应用，需要重启Pod
- **Cluster Autoscaler**：集群扩缩容，增加/减少节点数量，触发条件是Pod无法调度（资源不足）

三者协同工作：负载增加时HPA扩容Pod，Pod无法调度时Cluster Autoscaler扩容节点，负载稳定后VPA优化Pod资源请求。

### Q8：StatefulSet和Deployment有什么区别？

**答：**

| 特性 | Deployment | StatefulSet |
|------|-----------|-------------|
| 适用场景 | 无状态应用 | 有状态应用 |
| Pod名称 | 随机哈希 | 有序序号（pod-0, pod-1） |
| 网络标识 | 不稳定 | 稳定（通过Headless Service） |
| 存储 | 共享PVC | 独立PVC（每个Pod一个） |
| 部署顺序 | 并行 | 有序（依次创建） |
| 扩缩容 | 并行 | 有序 |
| 典型应用 | Web应用、API服务 | 数据库、消息队列 |

### Q9：K8s中如何实现优雅停机（Graceful Shutdown）？

**答：**

1. **Pod设置terminationGracePeriodSeconds**：默认30秒，可根据应用调整
2. **应用监听SIGTERM信号**：收到信号后停止接收新请求，处理完现有请求后退出
3. **PreStop Hook**：在容器停止前执行清理操作
4. **Readiness Probe配合**：停机时Readiness失败，Service将其从Endpoint移除

```yaml
spec:
  terminationGracePeriodSeconds: 60
  containers:
  - name: app
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "sleep 15"]
```

### Q10：如何排查Pod启动失败？

**答：**

排查步骤：
1. `kubectl get pod <pod-name>` 查看状态和事件
2. `kubectl describe pod <pod-name>` 查看详细事件（Events）
3. `kubectl logs <pod-name>` 查看容器日志
4. `kubectl logs <pod-name> --previous` 查看上次退出的日志
5. `kubectl get events --field-selector involvedObject.name=<pod-name>` 查看相关事件

常见原因：
- **ImagePullBackOff**：镜像不存在或拉取失败
- **CrashLoopBackOff**：容器启动后崩溃，查看日志
- **Pending**：资源不足、污点不匹配、PVC未绑定
- **OOMKilled**：内存超限，增大limits
- **Error**：应用错误，查看日志

# 企业级 RAG 系统架构设计：数据注入 → 检索 → 生成的全链路，从 Demo 到生产差了一万个细节

> 别再拿 LangChain 那 30 行代码糊弄老板了，真正的企业级 RAG 远不止 `vectorStore.similaritySearch(query)` 这么简单。

---

## 一、开篇：为什么你的 RAG "Demo" 永远上不了生产

作为一个 Java 技术博主，我见过太多这样的场景——团队兴冲冲地用 LangChain + ChromaDB 搭了一个 RAG 原型，Demo 演示效果惊艳，老板拍板"下周上线"。结果真上了生产环境，问题一个接一个：

- 文档解析到一半 OOM，200MB 的 PDF 直接让服务挂掉
- 向量库查询延迟从 Demo 的 50ms 飙到 800ms，用户投诉"比百度还慢"
- 某高管上传的机密文档，被实习生用关键字搜了出来
- 知识库更新要全量重建索引，4 小时窗口期业务方根本不接受

**Demo 和生产的差距，不仅是代码量的差距，更是工程成熟度的差距。**

本文将带你从架构设计的高度，重新审视企业级 RAG 系统的完整技术图谱。我们不谈花哨的 prompt 技巧，只讲落地时必须面对的硬核问题——八层架构、非功能需求、容量规划、与传统搜索的融合。

## 三、逐层拆解与技术选型

### 3.1 数据源层：异构数据的统一接入

企业数据分散在方方面面，数据源层要解决的第一个问题是**连接器抽象**。

```java
public interface DataSourceConnector {
    
    String getSourceType(); // FILE, DATABASE, API, MESSAGE_QUEUE
    
    List<DocumentMetadata> listDocuments(DataSourceConfig config);
    
    InputStream fetchDocument(String documentId);
    
    DocumentChangeEvent subscribe(ChangeListener listener);
}
```

**技术选型矩阵：**

| 数据源类型 | 推荐方案 | 备选方案 |
|-----------|---------|---------|
| 本地文件系统 | Java NIO WatchService | Apache Commons VFS |
| 对象存储(S3/OSS/MinIO) | AWS SDK / MinIO SDK | S3Proxy |
| 关系型数据库 | JDBC + 分页查询 | Canal CDC |
| 网页内容 | Jsoup + Playwright | Selenium |
| 消息队列 | Kafka / RocketMQ | RabbitMQ |
| 企业应用(飞书/Slack/Confluence) | 各平台开放 API | Webhook |

**关键设计原则：** 所有连接器必须实现统一的 `DataSourceConnector` 接口，新增数据源只需实现这个接口即可，对下游完全透明。

### 3.2 预处理层：脏数据是 RAG 效果的头号杀手

这一层我后面有专门的文章讲，这里简要提几个关键选型：

```java
public class PreprocessingPipeline {
    
    private final List<DocumentProcessor> processors;
    
    public PreprocessingPipeline() {
        this.processors = List.of(
            new FormatParser(),        // PDF/Word/HTML → Markdown
            new HeaderFooterRemover(), // 去除页眉页脚
            new TableExtractor(),      // 表格结构化提取
            new ImageOCRProcessor(),   // 图片 OCR
            new MetadataExtractor(),   // 元数据提取
            new ContentDeduplicator()  // 内容去重
        );
    }
    
    public ProcessedDocument process(RawDocument raw) {
        ProcessedDocument doc = ProcessedDocument.from(raw);
        for (DocumentProcessor processor : processors) {
            doc = processor.process(doc);
        }
        return doc;
    }
}
```

### 3.4 存储层：向量数据库不是银弹

**向量数据库选型对比：**

| 数据库 | 类型 | 分布式 | 过滤能力 | 推荐场景 |
|--------|------|--------|---------|---------|
| Milvus | 专用向量库 | ✓ | ★★★★☆ | 亿级向量，高并发 |
| Qdrant | 专用向量库 | ✓ (企业版) | ★★★★☆ | 千万级，易部署 |
| Elasticsearch | 全文+向量 | ✓ | ★★★★★ | 需要混合检索 |
| PostgreSQL + pgvector | 传统+向量 | ✓ (Citus) | ★★★★★ | 中小规模，复用PG |
| Weaviate | 专用向量库 | ✓ | ★★★☆☆ | GraphQL 原生支持 |
| Pgvector (阿里云RDS) | 云托管 | ✓ | ★★★★★ | 免运维，阿里云生态 |

**我的推荐：**
- **中小企业（百万文档以内）：** PostgreSQL + pgvector，运维成本最低，SQL 过滤能力完爆一切专用向量库
- **中大型企业（千万到亿级）：** Elasticsearch 8.x+，同时满足全文检索和向量检索，混合检索方案最成熟
- **超大规模（十亿级以上）：** Milvus 分布式集群，有专门的索引优化和 GPU 加速

### 3.5 检索层：混合检索才是企业级标配

单一向量检索在企业场景下有致命缺陷——**精确匹配场景完全失效**。比如用户搜"合同编号 HT-2024-0001"，向量检索的余弦相似度毫无意义。

**混合检索架构：**

```java
@Service
public class HybridSearchService {
    
    private final VectorSearchService vectorSearch;
    private final FullTextSearchService fullTextSearch;
    private final RerankService rerankService;
    
    public SearchResult search(SearchRequest request) {
        // 1. 查询意图分类
        SearchIntent intent = classifyIntent(request.getQuery());
        
        // 2. 并行检索
        CompletableFuture<List<SearchHit>> vectorFuture = 
            CompletableFuture.supplyAsync(() -> vectorSearch.search(request));
        CompletableFuture<List<SearchHit>> fullTextFuture = 
            CompletableFuture.supplyAsync(() -> fullTextSearch.search(request));
        
        // 3. 结果融合 (RRF 算法)
        List<SearchHit> merged = rrf(
            vectorFuture.join(), 
            fullTextFuture.join(),
            intent.getVectorWeight(),   // 向量权重
            intent.getFullTextWeight()  // 全文权重
        );
        
        // 4. 重排序
        List<SearchHit> reranked = rerankService.rerank(request.getQuery(), merged);
        
        // 5. 权限过滤（关键！）
        List<SearchHit> filtered = permissionFilter.filter(
            request.getUserId(), reranked);
        
        // 6. 去重 & 截断
        return deduplicateAndTruncate(filtered, request.getTopK());
    }
}
```

**RRF (Reciprocal Rank Fusion) 融合算法：**

```java
public List<SearchHit> rrf(List<SearchHit> vectorResults, 
                            List<SearchHit> fullTextResults,
                            double vectorWeight, double fullTextWeight) {
    Map<String, Double> scoreMap = new HashMap<>();
    
    int k = 60; // RRF 常量
    
    for (int i = 0; i < vectorResults.size(); i++) {
        String id = vectorResults.get(i).getId();
        scoreMap.merge(id, vectorWeight / (k + i + 1), Double::sum);
    }
    
    for (int i = 0; i < fullTextResults.size(); i++) {
        String id = fullTextResults.get(i).getId();
        scoreMap.merge(id, fullTextWeight / (k + i + 1), Double::sum);
    }
    
    return scoreMap.entrySet().stream()
        .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
        .map(e -> resolveHit(e.getKey(), e.getValue()))
        .toList();
}
```

### 3.6 生成层：LLM 调用的工程化封装

```java
@Service
public class LLMGatewayService {
    
    private final Map<String, LLMProvider> providers;
    private final CircuitBreaker circuitBreaker;
    private final PromptTemplateManager promptManager;
    
    public GenerationResult generate(GenerationRequest request) {
        // 1. 上下文窗口计算（防止超过 token 限制）
        String prompt = promptManager.buildPrompt(
            request.getSystemPrompt(),
            request.getContext(),    // 检索到的文档
            request.getUserQuery(),
            request.getModel().getMaxTokens()
        );
        
        // 2. 熔断保护
        return circuitBreaker.executeWithFallback(
            () -> providers.get(request.getModel().getProvider()).call(prompt),
            () -> fallbackResponse(request)
        );
    }
    
    private GenerationResult fallbackResponse(GenerationRequest request) {
        // 降级：直接返回检索结果，不调用 LLM
        return GenerationResult.builder()
            .content("AI 服务暂时不可用，以下是检索到的相关内容...")
            .sources(request.getContext().getSources())
            .isFallback(true)
            .build();
    }
}
```

## 五、容量规划：别等爆了才想扩容

### 5.1 存储容量预估公式

```
向量存储容量 = 文档数 × 平均块数/文档 × 向量维度 × 4 bytes

示例：
- 100万份文档
- 平均每份文档 20 个 chunk
- 1536 维向量
- 单条: 1536 × 4 = 6KB (向量) + 2KB (文本+元数据) = 8KB
- 总向量存储: 100万 × 20 × 8KB ≈ 160GB
- 考虑索引开销(×1.5): ≈ 240GB
- 考虑副本(×2): ≈ 480GB
```

### 5.2 计算资源预估

```java
public class CapacityPlanner {
    
    public CapacityPlan estimate(IngestionRequirement req) {
        // Embedding 吞吐: text-embedding-3-small 约 2000 requests/min/A100
        int embeddingGPUs = (int) Math.ceil(
            req.getDailyDocs() * req.getAvgChunksPerDoc() / 2000.0 / 60 / 24);
        
        // LLM 吞吐: 假设每次生成 500 tokens, 1000 QPS
        int llmGPUs = (int) Math.ceil(
            req.getPeakQPS() * 500 / 50.0); // 50 tokens/s/GPU (保守估计)
        
        // 内存: Elasticsearch 建议 JVM heap 不超过 32GB
        int esNodes = (int) Math.ceil(
            req.getTotalStorageGB() / 200.0);
        
        return new CapacityPlan(embeddingGPUs, llmGPUs, esNodes);
    }
}
```

### 5.3 网络带宽

```
日常注入流量 = 日新增文档数 × 单文档平均大小
高峰期: 日常 × 3 (安全系数)

若日增 1000 份 10MB 文档:
- 日常: 10GB/天 ≈ 1Mbps 持续带宽
- 高峰期: 30GB/天 ≈ 3Mbps
- 建议带宽: 100Mbps (含检索和 API 调用)
```

## 六、与传统搜索系统的集成方案

企业不可能一夜之间废掉原有的 Elasticsearch 搜索，必须考虑共存和渐进式迁移。

### 6.1 混合检索网关模式

```java
@Component
public class UnifiedSearchGateway {
    
    @Autowired
    private LegacySearchService legacySearch;
    
    @Autowired
    private RAGSearchService ragSearch;
    
    public UnifiedSearchResponse search(UnifiedSearchRequest request) {
        
        // 并行调用两套系统
        CompletableFuture<SearchResult> legacyFuture = 
            CompletableFuture.supplyAsync(() -> legacySearch.search(request));
        CompletableFuture<SearchResult> ragFuture = 
            CompletableFuture.supplyAsync(() -> ragSearch.search(request));
        
        // 结果合并策略
        List<UnifiedSearchItem> items = mergeResults(
            legacyFuture.join(), 
            ragFuture.join(),
            request.getMergeStrategy() // RAG_FIRST / LEGACY_FIRST / INTERLEAVE
        );
        
        return UnifiedSearchResponse.builder()
            .items(items)
            .fromCache(false)
            .responseTime(System.currentTimeMillis() - request.getTimestamp())
            .build();
    }
    
    private List<UnifiedSearchItem> mergeResults(
            SearchResult legacyResult, SearchResult ragResult, 
            MergeStrategy strategy) {
        return switch (strategy) {
            case RAG_FIRST -> Stream.concat(
                ragResult.getItems().stream(),
                legacyResult.getItems().stream()
            ).distinct().limit(20).toList();
            
            case INTERLEAVE -> interleave(ragResult, legacyResult);
            
            case LEGACY_FIRST -> Stream.concat(
                legacyResult.getItems().stream(),
                ragResult.getItems().stream()
            ).distinct().limit(20).toList();
        };
    }
}
```

### 6.2 渐进式迁移策略

```
阶段1 (第1-2周): RAG 作为"AI 助手"，传统搜索不变
    ┌──────────┐     ┌──────────┐
    │  用户搜索  │────▶│ 传统搜索   │──▶ 结果列表
    └──────────┘     └──────────┘
         │
         └─────────▶│ RAG 助手  │──▶ "AI 帮你总结"
                    └──────────┘

阶段2 (第3-6周): 联邦搜索，双路召回
    ┌──────────┐     ┌──────────┐
    │  用户搜索  │──┬─▶│ 传统搜索   │──┐
    └──────────┘  │  └──────────┘  │
                  │  ┌──────────┐  │
                  └─▶│ RAG 检索  │──┤
                     └──────────┘  │
                          ┌────────▼────────┐
                          │  结果融合 + 重排    │
                          └─────────────────┘

阶段3 (第7周+): RAG 为主，传统搜索兜底
    ┌──────────┐     ┌──────────┐
    │  用户搜索  │────▶│ RAG 检索  │──▶ 结果列表
    └──────────┘     └──────────┘
                          │ (空结果/低置信度)
                          ▼
                     ┌──────────┐
                     │ 传统搜索   │──▶ 兜底结果
                     └──────────┘
```

## 七、总结

写了一万多字，最后帮你理一下核心思路：

1. **别被 Demo 迷惑：** LangChain 30 行代码只是玩具，真正的企业级 RAG 需要八层架构的协同。
2. **预处理是地基：** 脏数据进，垃圾出，文档清洗质量直接决定 RAG 效果上限。
3. **混合检索是标配：** 纯向量检索在企业场景有先天缺陷，必须结合全文检索。
4. **监控是刚需：** 没有可观测性的系统，出了问题你只能抓瞎。
5. **容量规划要前置：** 别等线上 OOM 了才想起扩容。

实际落地过程中，你会发现真正费时间的不是写代码，而是**数据清洗、效果调优、权限设计**这些"非算法"的工程问题。而这些，正是我接下来几篇文章要深入展开的内容。

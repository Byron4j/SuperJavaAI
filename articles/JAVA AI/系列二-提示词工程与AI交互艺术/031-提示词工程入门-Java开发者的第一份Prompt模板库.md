# 提示词工程入门：Java 开发者的第一份 Prompt 模板库，20 个模板直接复制使用

> 别再让 AI 瞎猜你的意图了。Prompt 工程不是你该"了解"的技能，而是你最该"精通"的技能——比学任何框架都值钱。

---

## 一、为什么说 Prompt 工程比学框架更值钱？

2024 年，Spring Boot 4 出了，Quarkus 火了，GraalVM 开始普及了——Java 开发者又要学新技术了。但你有没有发现一个趋势：**框架的门槛在降低，而"清晰地描述需求"的门槛在升高**。

过去，你需要手写 200 行代码来实现一个带缓存的查询接口。现在，你只需要用 20 行 Prompt 描述清楚需求，AI 帮你生成。问题来了：**这 20 行 Prompt，你写得清楚吗？**

我见过太多这样的场景：

```
开发者：帮我写一个查询用户订单的接口
AI：(生成了一堆东西，但不是你想要的)
开发者：不对，我要的是分页的，还要支持按状态筛选
AI：(又生成了一堆，但还是差一点)
开发者：算了，我自己写吧...
```

问题出在哪？**Prompt 太模糊**。你心里有完整的上下文，但没有传递给 AI。你以为 AI 懂你，但它只能用你给的有限信息去"猜"。

**Prompt 工程不是玄学，是结构化的软件需求描述。** 把 AI 当成一个"极度聪明但完全不了解你项目背景的新同事"——你给它的信息质量，直接决定它产出的代码质量。

## 三、代码生成类（5 个模板）

### 模板 1：标准 CRUD 接口生成

**适用场景**：需要快速生成一个标准的增删改查 REST 接口，包含参数校验和异常处理。

**Prompt 模板**：

```
你是一名资深 Java 后端开发，使用 Spring Boot 3 + MyBatis-Plus。

请为以下实体类生成完整的 CRUD REST 接口：
- 实体名：{EntityName}
- 实体字段：{filed1: type, field2: type, ...}
- 数据库表名：{table_name}

要求：
1. Controller 层使用 @RestController 和 @RequestMapping
2. Service 层包含业务逻辑和参数校验，使用 @Validated
3. 分页查询支持模糊搜索 {searchable_fields}
4. 统一返回格式 Result<T>（code, message, data）
5. 每个方法加简要注释
6. 异常使用全局异常处理器统一处理

请按以下顺序输出代码：
1. Entity 类
2. Mapper 接口
3. Service 接口 + ServiceImpl
4. Controller
```

**使用示例**：

```
实体名：Product
实体字段：id: Long, name: String, price: BigDecimal, category: String, stock: Integer, createTime: LocalDateTime
数据库表名：t_product
searchable_fields：name, category
```

**预期输出**：AI 会生成包含 ProductEntity、ProductMapper、ProductService、ProductServiceImpl、ProductController 的完整代码，分页查询自动添加 `like` 条件，所有方法返回 `Result<T>` 统一格式。

### 模板 11：NPE（NullPointerException）排查与修复

相关代码：
```java
{相关代码}
```

### 模板 14：死锁检测与修复

**Prompt 模板**：

```

```

要求：

   - 方案二：使用 tryLock 超时机制
   - 方案三：减少锁粒度或使用无锁数据结构
4. 比较各方案在吞吐量和复杂度上的取舍
5. 给出预防死锁的代码规范建议
```

**使用示例**：转账方法 `transfer(from, to, amount)`，先锁 from 账户再锁 to 账户，并发时 A→B 和 B→A 同时发生。

**预期输出**：AI 会画出循环等待图，分析死锁条件，建议按账户 ID 排序统一加锁顺序（`System.identityHashCode` 比较），或使用 `tryLock(500ms)` 超时回滚方案。

### 模板 15：数据不一致分析

**适用场景**：数据库中的数据与业务预期对不上，怀疑是代码的并发写入或事务边界问题。

**Prompt 模板**：

```
以下 Java 代码负责处理 {业务描述}，但生产环境出现数据不一致问题。请分析可能原因：

```java
{相关代码}
```

不一致现象：{具体描述，如：库存扣减了但订单状态未更新}

要求：
1. 检查事务边界（@Transactional 的作用范围）
2. 分析是否因"先查后改"导致的并发更新丢失
3. 检查是否有以下问题：
   - 事务传播机制不当（REQUIRES_NEW 导致外层事务回滚不完整）
   - 缓存与数据库未同步更新
   - 跨服务的分布式事务缺少最终一致性保证
4. 给出不同隔离级别下的行为分析
5. 修复方案考虑：乐观锁（版本号）、悲观锁（SELECT FOR UPDATE）、CAS 或分布式锁
```

**使用示例**：扣减库存后异步发送消息通知，但事务回滚时消息已发出。

**预期输出**：AI 会指出事务边界问题——消息发送应在事务提交成功后执行，建议使用 `TransactionSynchronizationManager.registerSynchronization` 在 afterCommit 中发送，或使用事务发件箱模式保障最终一致性。

### 模板 16：代码解释

**Prompt 模板**：

```
请逐行解释以下 Java 代码：

{代码片段}
```

要求：
1. 先一句话总结这段代码是做什么的
2. 逐行/逐块解释关键逻辑（重点关注不太直观的写法）
3. 如果有设计模式的应用，指出来

```

```
请对以下 Java 技术方案进行系统对比：

对比项：
- 方案A：{方案A名称}
- 方案B：{方案B名称}
- [方案C：{方案C名称}]

对比维度（请逐项分析）：

3. 学习成本与社区活跃度

```

**使用示例**：

方案B：Spring Data JPA（Hibernate）

```

### 模板 18：最佳实践推荐

**适用场景**：想实现某个功能，不确定业界的推荐做法是什么。

**Prompt 模板**：

```
我需要在 {技术栈/框架} 中实现 {功能描述}。请给出业界推荐的最佳实践方案：

项目背景：
- Java 版本：{java_version}
- 框架：{framework}
- 数据库：{database}
- 特殊约束：{constraints}

要求：
1. 给出 2-3 种实现方案，按推荐度排序
2. 每种方案包含：
   - 核心思路（2-3 句话）
   - 关键代码片段
   - 优点和缺点
3. 标注反模式（常见错误做法及为什么是错的）
4. 如果涉及安全性（SQL注入、XSS等），强调防护措施
5. 给出可参考的开源项目或源码文件
```

**使用示例**：

```
功能：REST API 的接口幂等性设计
Java 版本：17
框架：Spring Boot 3
数据库：MySQL 8.0 + Redis
特殊约束：需要支持分布式环境
```

**预期输出**：AI 会给出"Token 机制（Redis）"、"数据库唯一索引 + 状态机"、"分布式锁"三种方案，标注"纯客户端重试无幂等保护"为反模式，并给出每种的优缺点和适用场景。

### 模板 19：框架源码解读

关注点：

3. 用到了哪些设计模式，分别解决什么问题

### 模板 20：错误排查指南

**适用场景**：运行时出现错误日志/异常堆栈，需要快速定位根因和修复方向。

**Prompt 模板**：

```
在生产环境中遇到了以下错误/异常，请帮助分析根因和修复方向：

错误日志/堆栈：
{error_logs}

相关背景：
- 框架版本：{framework_version}
- 近期变更：{recent_changes}
- 触发条件：{trigger_condition}

要求：
1. 从堆栈最底层（根因）开始分析，逐层向上说明调用链路
2. 标注堆栈中与业务代码相关的位置（非框架内部代码）
3. 给出 3 个最可能的根因假设，按概率排序
4. 针对每个假设提供验证方法（加什么日志、查什么数据）
5. 给出每种假设对应的修复方案
6. 提供预防同类问题的建议（加什么单元测试、加什么监控指标）
```

**使用示例**：提交一段 `StackOverflowError` 的堆栈，近期变更是将某个 Service 的 `@Autowired` 改为构造器注入。

**预期输出**：AI 会分析可能是循环依赖导致——构造器注入 A 依赖 B，B 又依赖 A，形成无限递归。给出三种可能：循环注入、递归调用无终止条件、数据结构的循环引用导致 `toString` 无限递归。建议检查依赖图，改为 `@Lazy` 或重构依赖关系。

## 七、附赠：Prompt 质量自检清单

写 Prompt 就像写代码——好代码需要 code review，好 Prompt 也需要自检。提交 Prompt 前，过一遍这 5 个标准：

| # | 检查项 | 好 Prompt 的标准 | 坏 Prompt 的典型问题 |
|---|--------|------------------|---------------------|
| 1 | **上下文完整度** | 包含技术栈、版本号、代码片段、错误现象 | "帮我写一个接口"——AI 不知道你用什么框架 |
| 2 | **目标明确性** | 有清晰的输出格式要求（代码/分析报告/对比表） | "你觉得这段代码怎么样"——太开放，AI 会发散 |
| 3 | **约束精准度** | 明确标注"不要做什么"比"要做什么"更重要 | 只说要功能，没说限制条件，AI 可能引入过度设计 |
| 4 | **示例具体性** | 给出输入示例和期望输出，能极大提升准确度 | "给我一个工具类"——AI 不知道你期望的粒度 |
| 5 | **破立平衡** | 不仅指出问题，还要求给出修复后的代码 | "找出代码中的问题"——只诊断不治疗，还得再问一次 |

**快速自测**：如果你的 Prompt 不到 3 行，大概率质量不过关。一个好的 Prompt 通常在 10-30 行，包含背景、约束、输出格式、示例。

## 八、写在最后

回到开头那句话：**Prompt 工程不是玄学，是结构化的软件需求描述**。

这 20 个模板的本质，就是把"你脑子里的隐性知识"翻译成"AI 能理解的显性指令"。写代码时你不会对同事只说"帮我写个功能"——你会说表结构、说参数、说校验规则。对 AI 也一样。

建议你这样做：
1. **收藏这篇文章**，下次写 Prompt 时先找到对应模板
2. **微调而非重写**：每个模板根据实际场景增减约束条件
3. **迭代优化**：第一次 Prompt 如果不满意，不要放弃，加约束、加示例、重试

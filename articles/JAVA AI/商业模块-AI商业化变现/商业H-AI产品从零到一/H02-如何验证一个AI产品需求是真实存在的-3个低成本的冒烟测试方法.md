# 如何验证一个AI产品需求是真实存在的？3个低成本的冒烟测试方法

> 我见过太多人花3个月做了一个AI产品，上线后一个用户都没有。问题出在哪？出在他把一个"自己觉得"的需求当成"用户愿意付费"的需求。这篇文章告诉你如何在一个月内、用不到500块钱，完成需求验证。三个方法每个都经过实测。

---

## 一、为什么90%的AI产品死在"假需求"上？

先讲一个我朋友的惨痛教训。

他花了2个月做了一个"AI周报生成器"——输入你一周的工作碎片（聊天记录、邮件、会议记录），AI自动生成周报。逻辑上很完美：打工人最恨写周报。

但上线后发现：**根本没人用。**

他找了几十个朋友问为什么，答案是：

> "写周报确实烦，但也就10分钟的事。你的工具要我把所有聊天记录导出来、整理好再喂给你——比我自己写还麻烦。"

这就是典型的**"伪痛点"**：用户觉得痛，但不够痛到愿意改变现有的工作习惯。

怎么避免这种情况？三个冒烟测试方法帮你在一周内验证。

## 二、冒烟测试法一：The Mom Test（妈妈测试）

这是硅谷创业圈最经典的验证方法。核心原则很简单：

**不要问"你觉得我的想法怎么样？"**

这个问题得到的回答永远是正面但无用的。

正确的方法是去了解**用户的现有行为**：

### 2.1 Mom Test的核心问题清单

```
❌ 错误问题（不要问）：
"如果我做一个AI周报生成器，你会用吗？"
→ 别人出于礼貌会说"会啊，听起来不错"
→ 这个回答一文不值

✅ 正确问题（要问）：
"你上一次写周报是什么时候？花了多长时间？"
"你在写周报的过程中，最烦的是哪个环节？"
"你有没有试过什么办法让写周报变得更快？"
"如果写周报能自动化，你愿意为这个功能付多少钱？但说实话——不是对我礼貌，是对你自己的时间真实估值。"
```

### 2.2 Mom Test的实操流程

```java
// Mom Test访谈记录系统
@Service
public class MomTestInterview {
    
    /**
     * Mom Test 的标准访谈流程
     */
    public InterviewResult conduct(String userId, String problemArea) {
        List<QuestionResponse> responses = new ArrayList<>();
        
        // 阶段1：了解现状（5分钟）
        responses.add(askQuestion(userId, 
            "能给我讲讲你上一次[做这件事]的具体情况吗？",
            QuestionCategory.CURRENT_BEHAVIOR));
        // 追问：花了多久？遇到了什么问题？怎么解决的？
        
        // 阶段2：量化痛苦（5分钟）
        responses.add(askQuestion(userId,
            "你每周大概花多少时间在这件事上？如果满分10分，这件事有多烦人？",
            QuestionCategory.PAIN_QUANTIFICATION));
        // 只有8分以上的痛点才值得做
        
        // 阶段3：了解已有方案（5分钟）
        responses.add(askQuestion(userId,
            "你现在有没有用什么工具或方法来让这件事变得更容易？",
            QuestionCategory.EXISTING_SOLUTIONS));
        // 如果用户说"没有" → 痛点可能不够痛
        // 如果用户说"我用XX工具凑合" → 那才是你的竞品
        
        // 阶段4：试探付费（5分钟）
        responses.add(askQuestion(userId,
            "如果真的有一个工具能帮你省掉80%的时间，你觉得多少钱合适？",
            QuestionCategory.PAYMENT_WILLINGNESS));
        // 注意：用户说的数字打5折才是真实付费意愿
        
        // 阶段5：获取证据（5分钟）
        responses.add(askQuestion(userId,
            "你能给我看看你最近一次[做这件事]的产出吗？",
            QuestionCategory.EVIDENCE));
        // 如果用户拿不出来 → 要么他在说谎，要么问题不够频繁
        
        return new InterviewResult(userId, problemArea, responses);
    }
}
```

### 2.3 Mom Test的判断标准

完成5-10个访谈后，判断：

```
✓ 继续推进的信号：
- 超过70%的受访者说这件事"非常烦人"（8分以上）
- 超过50%的受访者已经试过至少一个不完美的解决方案
- 超过30%的受访者能给出具体的付费金额
- 超过50%的受访者能展示他们手动做这件事的证据

✗ 放弃的信号：
- 大多数人觉得"还好吧，不是特别烦"（5分以下）
- 没有人主动找过解决方案
- 没人能给出付费金额，都说是"看情况"
- "听起来不错"但无法展示任何具体的数据或证据
```

## 三、冒烟测试法二：Wizard of Oz（绿野仙踪测试）

Wizard of Oz测试的意思是：**产品看起来是自动的，但背后是人工在操作。**

这是验证AI产品最有效的方法——因为你不需要真的开发AI，你只需要模拟AI能做的事情。

### 3.1 一个真实的Wizard of Oz案例

我想验证"AI代码审查"的需求。但我没有先开发AI系统，而是这样做：

```
步骤1：做了一个GitHub App，让用户可以给PR打标签"Need AI Review"

步骤2：用户打了标签后，"AI"会在5分钟内给出审查意见
（实际上是我自己手动审查的）

步骤3：观察：有多少用户用了这个功能？他们对审查结果满意吗？
他们愿意在审查意见下面回复讨论吗？

结论：2周内有37个PR被打上了标签，我手动给了审查意见。
25个PR的作者回复了"Thanks, that's helpful"。
但没有人问"什么时候可以付费使用" → 需求存在，但付费意愿不确定。
→ 付费意愿需要进一步验证。
```

### 3.2 Wizard of Oz测试的设计原则

```java
// Wizard of Oz 测试的设计系统
public class WizardOfOzTest {
    
    /**
     * 设计一个Wizard of Oz测试的框架
     */
    public WOZTestDesign design(String productIdea) {
        // 原则1：用户看到的是"自动"，但背后是"人工"
        // 原则2：测试MVP功能，不是完整产品
        // 原则3：用户不知道是人工操作
        // 原则4：测试周期不超过2周（人工操作撑不住太久）
        
        return WOZTestDesign.builder()
            .userVisible("一个简单的UI/API，看起来是AI在运作")
            .behindTheScene("你自己手动操作")
            .coreMetric("用户回访率"） // 不是用户满意度，是用户会不会回来再用
            .duration(14) // 14天
            .maxUsers(30) // 你一个人最多服务30个用户的人工操作
            .successCriteria("回访率 > 30%")
            .build();
    }
    
    /**
     * AI代码审查的Wizard of Oz操作脚本
     */
    public void simulateAIReview(PullRequest pr) {
        // Step 1: 接收PR
        System.out.println("收到PR #" + pr.getNumber());
        
        // Step 2: 模拟AI审查（实际就是你手动审查）
        String reviewComment = """
            🤖 AI Code Review 结果：
            
            1. 在 UserService.java:45 行发现潜在N+1查询问题
               → 建议使用 @EntityGraph 或 JOIN FETCH
            
            2. 在 OrderController.java:120 行缺少参数校验
               → 建议添加 @Valid 注解
            
            3. 整体代码质量：良好
               建议：将部分业务逻辑从Controller迁移到Service层
            """;
        
        // Step 3: 以"AI"的身份发布审查意见
        postReviewComment(pr, reviewComment);
        
        // Step 4: 记录数据
        trackMetrics(pr.getAuthor(), 
            pr.getNumber(), 
            "AI_REVIEW_COMPLETED",
            System.currentTimeMillis()
        );
    }
}
```

### 3.3 Wizard of Oz的致命问题

唯一的风险：**用户发现你是人工在操作。**

```
应对策略：
1. 回复风格保持一致（你是在扮演"一个AI"，不是在扮演"你自己"）
2. 回复速度控制合理（太快太慢都不像AI）
3. 使用固定的回复模板（看起来像AI生成的）
4. 如果真的被发现了，坦诚告知：这是产品内测阶段，谢谢反馈
```

## 四、冒烟测试法三：Pre-sale预销售（终极验证）

这是最激进也最有效的方法：**在做出产品之前，先让人付钱。**

### 4.1 预销售的三种形式

**形式1：内部预售（最低风险）**

在你已有的粉丝群/朋友圈/同事圈预售。不用做大张旗鼓的推广，只要找到3-5个愿意付费的人：

```
"我正在做一个AI代码审查工具，概念是这样的：[一句话描述]。
如果你现在就预定，我按市场价的5折给你。产品一个月后上线，
这期间你有任何需求直接告诉我，我优先实现。"

如果3个朋友没人愿意付费 → 需求可能不够强
如果有3个人付费了 → 需求初步验证，继续推进
```

**形式2：预购页面+早期定价**

做一个购买页面，设计一个"早鸟价"，看看有没有人下单：

```html
<h1>AI代码审查助手 - 预购优惠</h1>

<p>产品将在30天后正式上线。现在预购享受终身5折优惠。</p>

<div class="pricing">
    <div class="plan">
        <h3>个人版</h3>
        <p>预购价：¥49/月（正式价¥99/月）</p>
        <p>包含每月100次AI审查</p>
        <a href="/buy/personal-preorder">立即预购 →</a>
    </div>
</div>

<p>不满意？30天内全额退款。</p>
```

**形式3：服务即预售**

最灵活的方式：先以咨询/服务的形式卖，验证需求后再做成产品：

```
"我为企业提供AI代码审查咨询服务，帮你分析代码质量。
收费：¥2000/次。"

先以服务形式交付。当你发现：
- 有这个需求的企业很多
- 你做服务的流程已经标准化了
→ 把服务产品化，做成SaaS
```

### 4.2 预销售判断标准

```java
public class PreSaleValidator {
    
    public ValidationResult validate(PreSaleCampaign campaign) {
        int impressions = campaign.getImpressions();     // 看到预售信息的人数
        int clicks = campaign.getClicks();               // 点击查看详情的人数
        int purchases = campaign.getPurchases();         // 实际付费的人数
        
        double clickRate = (double) clicks / impressions * 100;
        double conversionRate = (double) purchases / clicks * 100;
        
        // 判断标准
        if (conversionRate >= 5) {
            return ValidationResult.STRONG_SIGNAL(
                "转化率超过5%%，说明需求和定价都匹配得很好");
        } else if (conversionRate >= 2) {
            return ValidationResult.MODERATE_SIGNAL(
                "转化率2-5%%，需求存在但可能需要优化定价或信息传达");
        } else if (purchases > 0) {
            return ValidationResult.WEAK_SIGNAL(
                "有人付费但比例很低，需要更深入验证");
        } else {
            return ValidationResult.NO_SIGNAL(
                "没有人在产品做出来之前愿意付费");
        }
    }
}
```

## 五、三种方法的组合使用和成本预算

| 测试方法 | 时间 | 成本 | 覆盖用户 | 验证力度 |
|---------|------|------|---------|---------|
| Mom Test | 1周 | ¥0 | 5-10人 | 中（行为≠付费） |
| Wizard of Oz | 2周 | ¥50-200（工具订阅费） | 20-50人 | 中高（行为验证） |
| Pre-sale | 1周 | ¥100-300（购买页面） | 100-1000人 | 极高（真金白银） |

**推荐组合方案：**

```
第1周：Mom Test（免费）→ 确认需求方向
第2-3周：Wizard of Oz（低成本）→ 验证用户行为
第4周：Pre-sale（如果需要）→ 验证付费意愿

总时间：4周
总成本：<¥500
```

## 六、需求验证通过/不通过的决策标准

```java
public class GoOrNoGoDecision {
    
    public Decision make(double momTestScore, 
                          double wozRetentionRate, 
                          double preSaleConversionRate) {
        
        // 综合评分模型
        double overallScore = momTestScore * 0.3 
                            + wozRetentionRate * 0.3  
                            + preSaleConversionRate * 0.4;
        
        if (overallScore >= 7.0) {
            return Decision.GO("需求验证通过，建议全力推进MVP开发");
        } else if (overallScore >= 5.0) {
            return Decision.PIVOT("需求部分验证，建议调整方案后重新验证");
        } else {
            return Decision.NO_GO("需求验证未通过，建议放弃或寻找新的需求方向");
        }
    }
}
```

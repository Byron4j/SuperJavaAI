## 一、背景：为什么选择做SaaS而不是继续接外包

做了几个月的AI外包后，我发现了一个致命问题：**外包的收入是可预测的，也是有限制的。**

外包一个月赚2万和3万的区别，取决于你投入了多少时间。但SaaS产品的逻辑完全不同——你花一次时间做一个产品，只要产品有价值，收入会随着用户增长而增长。这就是"睡后收入"。

我和前端的兄弟算了一笔账：

| 业务模式 | 投入时间 | 收入上限 | 持续性 |
|---------|---------|---------|--------|
| AI外包 | 持续投入 | 时间×时薪 | 停止就没有 |
| AI SaaS | 前期集中投入 | 用户数×客单价 | 持续产生 |

最后我们选了一个产品方向：**AI驱动的API文档自动化工具。**

为什么是这个方向？因为：
1. 我们自己是开发者，痛感强烈——写文档永远是最后做甚至不做的
2. 市场上没有特别好的竞品
3. 技术上可控，不需要太复杂的AI能力

## 二、技术选型全决策树

技术选型是我认为做SaaS最重要的决策。选错了，后续维护成本极高。选对了，团队就可以专注于业务。

### 2.1 后端技术栈

我们的选择标准只有3条：
1. **团队最熟悉的技术栈**（最优先）
2. **能快速迭代**（框架成熟度）
3. **AI集成能力强**（这个赛道的关键能力）

最终方案：

```
后端框架：Spring Boot 3.2 + Spring AI 1.0
数据库：PostgreSQL 16
缓存：Redis
向量数据库：Pgvector（PostgreSQL扩展，不用单独部署）
文件存储：MinIO（自托管，S3兼容）
消息队列：Redis Stream（够用，不引入Kafka）
API文档：SpringDoc OpenAPI
监控：Spring Actuator + Prometheus + Grafana
部署：Docker Compose（开发环境）/ K8s（生产环境）
```

关键决策点拆解：

**为什么用Pgvector而不是专业的向量数据库？**

因为我们只有2个人，没有精力维护额外的数据库实例。Pgvector作为PostgreSQL的扩展，零运维成本。实测下来，10万条以内的向量数据，Pgvector的查询性能完全够用。

```java
// Pgvector的使用非常简单
@Configuration
public class VectorStoreConfig {
    
    @Bean
    public VectorStore vectorStore(JdbcTemplate jdbcTemplate) {
        // Spring AI 提供了 Pgvector 的开箱即用支持
        return new PgVectorStore(jdbcTemplate, new PgVectorStore.PgVectorStoreConfig());
    }
    
    // 初始化向量表（只需要执行一次）
    @PostConstruct
    public void initVectorTable() {
        jdbcTemplate.execute("""
            CREATE EXTENSION IF NOT EXISTS vector;
            CREATE TABLE IF NOT EXISTS vector_store (
                id UUID PRIMARY KEY,
                content TEXT,
                metadata JSONB,
                embedding VECTOR(1536)
            );
            CREATE INDEX IF NOT EXISTS vector_store_embedding_idx 
            ON vector_store USING ivfflat (embedding vector_cosine_ops);
            """);
    }
}
```

**为什么用Redis Stream而不是Kafka？**

因为我们的产品初期消息量不到1000条/秒，Redis Stream足够。引入Kafka意味着多一个需要维护的组件。创业初期，简单就是快，快就是生命力。

### 2.3 AI层的选型

这是最核心的差异化能力。我们对比了多个方案：

| 方案 | 成本 | 效果 | 灵活性 | 结论 |
|------|------|------|--------|------|
| 只用OpenAI API | 中 | 好 | 低 | 简单场景首选 |
| 自建模型（开源） | 低(推理)高(训练) | 中 | 高 | 暂不考虑 |
| OpenAI + 微调 | 高 | 最好 | 中 | 高级版功能 |
| 多模型路由 | 中 | 好 | 高 | **最终选择** |

最终我们选择了**多模型路由方案**：

```java
@Component
public class ModelRouter {
    
    private final Map<String, ChatClient> clients;
    private final Map<String, ModelPricing> pricing;
    
    public ModelRouter() {
        this.clients = new HashMap<>();
        this.pricing = new HashMap<>();
        
        // 注册不同的模型
        clients.put("gpt-4o", buildOpenAiClient("gpt-4o"));
        clients.put("gpt-4o-mini", buildOpenAiClient("gpt-4o-mini"));
        clients.put("claude-sonnet", buildAnthropicClient("claude-3-sonnet"));
        clients.put("deepseek", buildDeepSeekClient("deepseek-chat"));
        
        // 记录价格（每百万Token美元价格）
        pricing.put("gpt-4o", new ModelPricing(5.0, 15.0));     // 输入$5, 输出$15
        pricing.put("gpt-4o-mini", new ModelPricing(0.15, 0.60));
        pricing.put("claude-sonnet", new ModelPricing(3.0, 15.0));
        pricing.put("deepseek", new ModelPricing(0.14, 0.28)); // 超便宜！
    }
    
    /**
     * 根据任务复杂度智能路由到合适的模型
     * 核心策略：简单任务用便宜模型，复杂任务用贵模型
     */
    public ModelSelection route(Task task) {
        return switch (task.getComplexity()) {
            case SIMPLE -> new ModelSelection("gpt-4o-mini", 
                "简单任务如格式转换、基础问答，用最便宜的模型");
            case MEDIUM -> new ModelSelection("deepseek",
                "中等复杂度如代码文档生成，用性价比最高的模型");
            case COMPLEX -> new ModelSelection("claude-sonnet",
                "复杂任务如架构分析，用推理能力最强的模型");
            case CRITICAL -> new ModelSelection("gpt-4o",
                "关键任务如客户看到的最终输出，用质量最高的模型");
        };
    }
    
    /**
     * 兜底策略：主模型失败时自动切换
     */
    public String chatWithFallback(String prompt, String primaryModel) {
        try {
            return clients.get(primaryModel).call(prompt);
        } catch (Exception e) {
            log.warn("主模型 {} 调用失败，切换到备用模型", primaryModel, e);
            // 默认切换到GPT-4o-mini作为兜底
            return clients.get("gpt-4o-mini").call(prompt);
        }
    }
}

record ModelPricing(double inputPricePer1M, double outputPricePer1M) {}
record ModelSelection(String modelName, String reason) {}
```

这种多模型路由的架构，让我们的AI成本降低了约70%。简单任务用DeepSeek（超便宜），复杂任务才上GPT-4o。

### 3.2 核心代码：AI文档生成服务

这是整个产品的灵魂：

```java
@Service
public class AiDocGenerationService {
    
    private final ModelRouter modelRouter;
    private final CodeAnalyzer codeAnalyzer;
    private final VectorStore vectorStore;
    private final DocTemplateEngine templateEngine;
    
    /**
     * 从Java源代码生成API文档
     */
    public GeneratedDoc generateApiDoc(SourceCode sourceCode, DocConfig config) {
        // Step 1: 代码静态分析 - 提取接口信息
        ApiStructure apiStructure = codeAnalyzer.analyze(sourceCode);
        
        // Step 2: AI增强 - 理解业务语义
        String aiEnhanced = enhanceWithAI(apiStructure, config);
        
        // Step 3: 模板渲染 - 套用文档模板
        String finalDoc = templateEngine.render(aiEnhanced, config.getTemplate());
        
        // Step 4: 存储到向量库 - 为后续的智能问答做准备
        indexDocToVectorStore(finalDoc, sourceCode.getProjectId());
        
        return new GeneratedDoc(finalDoc, apiStructure);
    }
    
    private String enhanceWithAI(ApiStructure api, DocConfig config) {
        String systemPrompt = """
            你是一个资深的技术文档工程师。请根据给定的API接口结构，
            生成专业的REST API文档。要求：
            1. 为每个接口解释业务用途，而不只是参数说明
            2. 提供至少2个实际的请求/响应示例
            3. 标注可能的数据校验规则和异常情况
            4. 如果接口之间有调用依赖关系，补充说明
            5. 使用Markdown格式
            """;
        
        String userPrompt = """
            项目名称：%s
            接口列表：
            %s
            
            文档风格：%s
            语言：%s
            """.formatted(api.getProjectName(), 
                api.toPromptFriendlyString(), 
                config.getStyle(), 
                config.getLanguage());
        
        ModelSelection selection = modelRouter.route(
            new Task(TaskComplexity.COMPLEX, "api_doc_generation"));
        
        return modelRouter.chat(selection.modelName(), systemPrompt, userPrompt);
    }
}
```

### 3.3 计费系统的设计

SaaS的计费是核心，设计不好会出大问题：

```java
@Service
public class BillingService {
    
    private final CreditRepository creditRepository;
    private final UsageTracker usageTracker;
    private final PaymentGateway paymentGateway;
    
    /**
     * 信用额度消费
     * 用户每次调用AI功能，消耗信用额度
     */
    @Transactional
    public BillingResult consumeCredits(String userId, int creditsNeeded) {
        UserCredit credit = creditRepository.findByUserId(userId)
            .orElseThrow(() -> new InsufficientCreditsException("请先购买额度"));
        
        if (credit.getRemainingCredits() < creditsNeeded) {
            return BillingResult.insufficient(credit.getRemainingCredits(), creditsNeeded);
        }
        
        // 原子扣减，防止并发超用
        boolean deducted = creditRepository.deductWithOptimisticLock(
            userId, creditsNeeded);
        
        if (!deducted) {
            // 乐观锁失败，重试一次
            return consumeCredits(userId, creditsNeeded);
        }
        
        // 记录用量
        usageTracker.recordUsage(userId, creditsNeeded);
        
        // 余额不足预警
        if (credit.getRemainingCredits() < credit.getLowBalanceThreshold()) {
            sendLowBalanceAlert(userId, credit.getRemainingCredits());
        }
        
        return BillingResult.success(credit.getRemainingCredits());
    }
    
    /**
     * 定价套餐管理
     */
    public List<PricingPlan> getPricingPlans() {
        return List.of(
            new PricingPlan("免费版", 0, 100, 
                "试用体验", List.of("每月100次调用", "基础文档模板")),
            new PricingPlan("专业版", 29, 1000,
```

### 4.1 AI调用成本控制

```java
@Component
public class AICostOptimizer {
    
    private final Cache<String, String> responseCache;
    
    /**
     * 策略1：缓存相同问题
     * 很多API文档生成的需求是重复的
     */
    public String getOrGenerate(String cacheKey, Supplier<String> generator) {
        String cached = responseCache.getIfPresent(cacheKey);
        if (cached != null) {
            log.debug("缓存命中，节省了一次AI调用");
            return cached;
        }
        String result = generator.get();
        responseCache.put(cacheKey, result);
        return result;
    }
    
    /**
     * 策略2：预计算常用查询
     * 把频繁请求的AI结果提前计算好
     */
    @Scheduled(cron = "0 0 3 * * ?") // 每天凌晨3点
    public void precomputeCommonQueries() {
        List<String> commonQueries = getYesterdayTopQueries();
        log.info("预计算 {} 个常用查询", commonQueries.size());
        for (String query : commonQueries) {
            try {
                String result = generateAndCache(query);
                log.debug("预计算完成: {}", query.substring(0, 50));
            } catch (Exception e) {
                log.error("预计算失败: {}", query, e);
            }
        }
    }
    
    /**
     * 策略3：Token预算控制
     * 每个用户设置Token预算，防止恶意调用
     */
    public TokenBudget allocateBudget(String userId) {
        UserPlan plan = getUserPlan(userId);
        return switch (plan.getType()) {
            case FREE -> new TokenBudget(10000);   // 每天1万Token
            case PRO -> new TokenBudget(100000);   // 每天10万Token
            case TEAM -> new TokenBudget(500000);  
            case ENTERPRISE -> new TokenBudget(2000000);
        };
    }
}
```

## 七、踩过的坑

**坑1：过早优化。**我曾花了两天研究并发场景下的文档生成性能优化，但实际上线后发现并发请求从来没超过5个。

**教训：**先上线再优化。你不是在给大厂做系统。

**坑2：Prompt稳定性的幻觉。**同一段代码，AI生成的文档质量波动很大。今天完美，明天就可能胡说八道。

**解决方案：**

```java
// 对AI输出做质量校验
public class AIOutputValidator {
    
    public ValidationResult validate(GeneratedDoc doc) {
        List<String> issues = new ArrayList<>();
        
        // 1. 检查是否有模糊描述
        if (doc.getContent().contains("可能") && countOccurrences(doc.getContent(), "可能") > 3) {
            issues.add("文档中包含过多模糊描述");
        }
        
        // 2. 检查API路径是否对应
        for (ApiEndpoint endpoint : doc.getEndpoints()) {
            if (!doc.getContent().contains(endpoint.getPath())) {
                issues.add("缺少接口 " + endpoint.getPath() + " 的文档");
            }
        }
        
        // 3. 检查必要的章节是否完整
        List<String> requiredSections = List.of("接口描述", "请求参数", "响应示例", "错误码");
        for (String section : requiredSections) {
            if (!doc.getContent().contains(section)) {
                issues.add("缺少必要章节：" + section);
            }
        }
        
        return new ValidationResult(issues.isEmpty(), issues);
    }
}
```

**坑3：支付接入比想象中麻烦得多。**微信支付的资质审核、签约流程、回调处理，前前后后搞了一周。教训：**产品开始开发的第一天就去申请支付资质。**

## 八、给想做SaaS的人的建议

**建议1：不要做"下一代XX"的产品。**不要幻想做"下一代Jira"、"下一代Notion"。大厂的产品有几百人的团队在维护。做一个他们不屑于做的小场景，就是你的生存空间。

**建议2：技术栈要选团队最能打的。**我看到很多人为了"追新"选了不熟悉的语言或框架，结果前两周在学技术，第三周才开始写业务。创业初期最大的敌人不是竞品，是时间。

**建议3：第一版要有付费功能。**很多人想着"先免费把用户做起来再收费"。在这个AI API需要花钱的年代，免费用户越多你亏得越多。第一版就设计好付费路径。

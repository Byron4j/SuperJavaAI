## 开篇：我看过 500 份简历后想说的话

过去一年，我在公司参与了 AI 方向 Java 工程师的招聘。看了大概 500 份简历，面了约 80 个人，最终发了 4 个 Offer。

你猜 500 份简历里最多的是什么？

**"精通 Java、Spring Boot、MySQL、Redis..."**

一模一样的技能列表，一个接一个。看到第 20 份的时候我已经麻木了。看到第 200 份的时候我开始怀疑：这些人是同一个培训班出来的吗？

但有几份简历我一眼就记住了。今天我告诉你为什么，以及**你的简历应该怎么写才能让面试官停下来**。

## 一、面试官 30 秒扫一份简历——他在看什么？

```text
面试官的眼睛扫过简历的顺序：

0-5秒：求职方向（标题/目标岗位）
      → "Java开发" → 哦（跳过）
      → "AI应用开发工程师" → 有点意思（继续看）

5-10秒：最近一份工作的前两行
      → "负责XX系统的日常维护和功能迭代" → 嗯（继续）
      → "主导公司AI客服系统从0到1，覆盖日均10万次对话" → 眼前一亮！

10-20秒：项目部分（只看有没有 AI 相关）
      → 全是 CRUD 项目 → 放到"备选"堆
      → 有 AI 相关项目 → 放到"重点"堆

20-30秒：技能标签区
      → Java/Python/Spring Boot/MySQL/Redis → 常规
      → RAG/向量数据库/Function Calling/LangChain → 加分！
```

**结论：如果你应聘 AI 相关岗位，简历里必须在前 10 秒出现 AI 关键词。**

## 二、常见简历的"三大死罪"

### 死罪一：千篇一律的技能堆砌

```
❌ 常见写法：
"熟练掌握Java、Spring Boot、Spring Cloud、MyBatis、MySQL、Redis、
RabbitMQ、Elasticsearch、Docker、Kubernetes、Git..."

面试官心理活动：第 37 个写"熟练掌握Redis"的人了。
你真的"熟练掌握"吗？还是只会 set/get？
```

```
✅ 正确写法：
"AI相关：RAG系统开发（Opensearch+pgvector） | OpenAI/Claude API集成 |
Function Calling Agent开发 | Prompt Engineering | Python基础 | 
LangChain4j | 向量检索优化

后端：Java 8年 | Spring Boot | 分布式架构 | 高并发优化（QPS 10K+）
中间件：MySQL分库分表 | Redis集群 | Kafka消息队列"
```

**把 AI 技能放在最前面，传统技能放后面——这叫"亮点前置"**。

### 死罪二：项目描述像岗位 JD

```
❌ 常见写法：
"项目：电商后台管理系统
- 使用Spring Boot作为后端框架
- 使用MySQL作为数据库
- 使用Redis作为缓存
- 实现了订单管理、商品管理、用户管理等功能"

面试官心理活动：这是项目描述还是技术栈复制粘贴？
你在这个项目里真正做了什么？解决了什么问题？
```

```
✅ 正确写法：
"项目：智能客服系统（AI项目）
背景：公司日均客服咨询量5000+，人工成本高，响应慢
我的角色：技术负责人，从0到1搭建
技术方案：
  - RAG架构：使用文档解析+Tika+文本分块+OpenAI Embedding实现知识库
  - 向量检索：基于pgvector存储10万+文档片段，检索延迟<100ms
  - Agent设计：通过Function Calling实现订单查询、物流追踪等自助服务
  - 效果评估：回复准确率91%，自动解决率78%，人工坐席减少60%"
```

**STAR 法则：情境(Situation) → 任务(Task) → 行动(Action) → 结果(Result)**。

### 死罪三：没有量化

```
❌ 没有数据的描述：
"优化了系统性能，提升了用户体验"

面试官：优化了什么？提升了多少？用什么方法？一概不知。
```

```
✅ 有数据的描述：
"通过引入向量检索缓存和混合检索策略，将问答延迟从2.3秒降至0.8秒，
准确率从76%提升至91%，单次回答Token消耗减少40%"
```

**数字让人信任。没有数字的描述 = 没说。**

## 五、面试中必被问到的 AI 问题（提前准备）

基于我面的 80 个人，这几个问题出现频率最高：

### Q1："你做的 RAG 项目中，检索准确率是怎么评估的？"

```
❌ 差回答："我感觉召回的结果还行。"
   面试官：没有量化思维

✅ 好回答："我们准备了200个测试问题，人工标注了正确答案所在的文档片段。
   然后用Top-1准确率、Top-5召回率、MRR三个指标来评估。
   最初Top-1准确率只有65%，通过调整分块策略（从500字改为300字）
   和引入BM25混合检索，最终提升到91%。"
   面试官：有方法论，有优化思路
```

### Q2："为什么选 pgvector 而不是 Milvus？"

```
❌ 差回答："我看别人都用这个。"
   面试官：没有独立决策能力

✅ 好回答："我们目前的文档量在10万级别，pgvector的ivfflat索引足够支撑。
   而且团队已经在用PostgreSQL，引入新组件Milvus会增加运维成本。
   我们评估过，当文档量超过100万时，会考虑迁移到Milvus。
   现在pgvector的方案是最合适的——够用、简单、团队熟悉。"
   面试官：有技术选型思维，懂得 trade-off
```

### Q3："AI 回答不准怎么办？怎么优化？"

```
✅ 好回答（结构化思维）：
"我会从四个维度排查：

1. 数据层：文档切片是否合理？有没有遗漏关键信息？
   → 调整chunk_size，增加重叠，优化分割策略

2. 检索层：有没有召回但排序不对？有没有漏召回？
   → 引入混合检索（BM25+向量），调整reranker

3. Prompt层：Prompt 是否引导模型正确使用参考资料？
   → 优化Prompt模板，添加"不知道就说不知道"的指令

4. 模型层：是不是模型能力不够？
   → 尝试更强模型或降低温度参数

我的经验是，80%的准确率问题出在前两步，
而不是模型本身。"
```

### Q4："介绍一下 Function Calling 的原理"

```
✅ 好回答：
"Function Calling本质上是协议约定，不是模型真的'调用'了函数。

流程是：
1. 我们在请求中告诉模型'你可以调用这些函数'（函数名+描述+参数定义）
2. 模型根据用户意图，返回一个JSON：{function: 'get_weather', args: {city: '北京'}}
3. 我们的代码拿到这个JSON，执行真正的函数调用
4. 把执行结果返回给模型
5. 模型基于结果生成自然语言回复

相当于模型说'我想查天气'，但实际查询是我们做的。
模型只是决策者，执行者是我们。"
```

## 二、五大篇章核心方法论回顾

### 2.1 基础篇核心（1-50）：Java 现代化是 AI 编程的基石

没有扎实的 Java 21 基础，AI 框架只能是"黑盒"。

**关键掌握：**

```java
// 1. Record 类：AI 数据模型的完美载体
public record ChatMessage(String role, String content) {}
public record EmbeddingVector(float[] data, int dimensions) {}

// 2. 密封类：定义 AI 输出的有限类型
public sealed interface AIResponse
    permits TextResponse, ErrorResponse, ToolCallResponse {}

// 3. 模式匹配：优雅处理 AI 的多态输出
String result = switch (response) {
    case TextResponse t -> t.content();
    case ErrorResponse e -> "Error: " + e.message();
    case ToolCallResponse tc -> executeTool(tc);
};

// 4. 虚拟线程：AI 高并发调用的基础设施
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> futures = prompts.stream()
        .map(p -> executor.submit(() -> callLLM(p)))
        .toList();
}
```

**一句话总结基础篇**：Java 的 Record + Sealed Class + Pattern Matching + Virtual Threads 四件套，构成了 AI 编程的类型安全底座。

### 2.2 框架篇核心（51-120）：AI Service 是 Java 对 AI 编程的最大贡献

LangChain4j 和 Spring AI 共同证明了一件事：**不要用 Python 的思维写 Java AI 代码**。

```java
// Java 风格：声明式 AI Service
@AiService
interface LegalAdvisor {
    @SystemMessage("你是精通中国《民法典》的法律顾问")
    String advise(@UserMessage String question);

    @SystemMessage("从合同文本中提取关键条款")
    ContractSummary extractTerms(@UserMessage String contractText);
}

// 只需定义接口，框架自动：
// 1. 构造 Prompt 模板
// 2. 调用 LLM
// 3. 解析响应为强类型
// 4. 处理重试和异常
```

**框架篇核心方法论：**
- Prompt 即代码：用注解声明意图，而非拼字符串
- 类型安全：`@UserMessage` + Record 确保输入输出类型正确
- 关注点分离：AI 调用逻辑与业务逻辑完全解耦

### 2.3 进阶篇核心（121-200）：RAG 是 90% AI 应用的终极形态

不是所有场景都需要微调模型。大多数企业 AI 应用的最优解是 **RAG（检索增强生成）**：

```
RAG 的标准流水线：
用户问题 → 向量化 → 相似度检索 → 重排序 → 上下文注入 → LLM生成
   │          │          │           │           │           │
   ▼          ▼          ▼           ▼           ▼           ▼
 前端输入   Embedding  Milvus/PG    AI重排     Prompt组装   GPT/本地
            Model     Vector                                          
```

```java
// LangChain4j 风格的 RAG 实现
@Component
public class RAGService {

    private final EmbeddingModel embeddingModel;
    private final EmbeddingStore<TextSegment> vectorStore;
    private final ChatModel chatModel;

    public String answer(String question) {
        // 1. 检索相关文档
        Embedding queryEmbedding = embeddingModel.embed(question).content();
        List<EmbeddingMatch<TextSegment>> relevant =
            vectorStore.findRelevant(queryEmbedding, 5, 0.7);

        // 2. 构建上下文
        String context = relevant.stream()
            .map(m -> m.embedded().text())
            .collect(Collectors.joining("\n\n"));

        // 3. 带上下文生成
        return chatModel.generate("""
            基于以下参考信息回答问题。
            如果参考信息不足以回答，请说明。
            
            参考信息：
            %s
            
            问题：%s
            """.formatted(context, question));
    }
}
```

**进阶篇核心方法论：**
- 向量是 AI 时代的"索引"——选对 Embedding 模型和向量数据库是第一要务
- Agent 的本质是"LLM + 工具 + 循环决策"——不要过度设计
- 多模态的价值在于"消除信息不对称"——图片、PDF、音频都能变成 text-in/text-out

### 2.4 实战篇核心（201-250）：架构设计比代码更重要

50 篇实战案例的共同教训：

```
企业 AI 应用的五大架构原则：

1. 模型与业务解耦
   业务代码 → AI Gateway → 多模型路由
   （换模型不换业务代码）

2. 同步与异步分流
   实时对话（<2s）→ GPT-3.5 + 虚拟线程
   离线分析       → GPT-4 + 消息队列

3. 分级推理策略
   简单问题 → 本地小模型（5ms, $0.0001）
   复杂问题 → 云端大模型（2s, $0.03）

4. 可观测性先于功能
   每个 AI 调用 → { prompt, model, latency, tokens, cost }
   没有监控的 AI 应用 = 没有刹车的跑车

5. 人类在环路（Human-in-the-Loop）
   关键决策（医疗/金融/法律）→ AI 建议 + 人工确认
   非关键决策（推荐/搜索）→ 全自动
```

## 六、六大"反常识"观点回顾

310 篇文章中，我提出了一些与传统认知相反的观察。它们值得再次强调：

### 观点 1：虚拟线程让响应式编程不再必要
> "WebFlux 学习曲线陡峭，调试困难。虚拟线程让命令式代码也能达到响应式的并发。新项目直接 MVP：Spring MVC + Virtual Threads。"

### 观点 2：大多数场景不需要微调模型
> "RAG + Few-Shot Prompt 能解决 85% 的企业需求。微调是最后的手段，不是第一选择。"

### 观点 3：AI 代码的审查比人类代码更严格
> "AI 不会犯错，但会'自信地胡说'。AI 生成的代码可能有隐藏的许可证问题、安全漏洞、逻辑错误——因为它们没有'意图'，只有'模式'。"

### 观点 4："一行代码调用 AI"是反模式
> "把 AI 调用封装在 AI Service 接口中——强类型、可测试、可监控。裸调 HTTP API 是技术债。"

### 观点 5：向量数据库不是银弹
> "大多数场景 Postgres + pgvector 就够了。只有当向量超过 1000 万条时才考虑专用向量数据库。"

### 观点 6：AI 应用的瓶颈不在 AI
> "AI 应用的性能瓶颈 90% 在数据管道、网络通信、并发模型、序列化——不是 GPU 不够快。这也是为什么延伸篇讲的是虚拟线程、gRPC、Native Image。"

# AI 辅助技术选型决策：用 LLM 对比框架优劣，别再被厂商的PPT忽悠了

> 选型选错，加班到脱发；选型选对，摸鱼到下班。

---

## 一、技术选型的痛苦：你中了几条？

你有没有经历过这样的场景——

> Leader 说："咱们新项目要用微服务架构，你看看选 Spring Cloud Alibaba 还是 Spring Cloud Netflix？"
>
> 你打开 Google，搜了一圈，看了 15 篇水文，其中 12 篇是培训机构发的，3 篇是厂商软文。每篇文章都说"XX 框架性能卓越、社区活跃、大厂背书"，但就是没人告诉你：**在你们团队，日均 QPS 3000 的场景下，用这玩意儿到底是提效还是添乱？**
>
> 最后你凭感觉选了 Spring Cloud Alibaba，三个月后：
> - Nacos 注册中心偶尔脑裂，没人看得懂源码
> - Sentinel 规则配错了一次，全站限流把老板也限了
> - 你想切回 Eureka，但已经写了 2 万行业务代码耦合了 Nacos API
>
> Leader 拍桌子："当初怎么选的型？"

以上不是段子，是我亲眼见过的真实翻车现场。

**技术选型的核心矛盾是**：你需要在一个极其庞大的信息空间中做决策，但你的时间和认知边界极其有限。传统做法（Google + 看文章 + 听厂商 PPT + 凭经验拍板）的容错率极低，**因为厂商的 PPT 永远不会告诉你他们的坑在哪里**。

而 LLM（大语言模型）正好补齐了这个短板——它能在几秒钟内阅读完两个框架的全部官方文档、GitHub Issues、Stack Overflow 讨论，然后给你一份结构化的对比分析。

但前提是——**你得会写 Prompt**。

今天这篇文章，我把我用了一年多的 **4 套技术选型 Prompt 模板**全部开源，配合 3 个真实选型案例，让你看完就能用。

## 二、4 套结构化技术选型 Prompt 模板（直接复制可用）

下面的每一套模板，你只需要替换 `[]` 中的内容即可直接使用。

### 模板1：二维对比分析（框架A vs 框架B）

适用场景：两个备选方案摆在面前，需要多维度量化对比。

```text
你是一位拥有15年Java后端开发经验的技术架构师。请对以下两个技术方案进行全面的对比分析：

【方案A】：[Spring Modulith]
【方案B】：[Spring Cloud微服务架构]
【业务场景】：[电商核心交易链路，日均订单量约5万单，团队10人，运维能力中等]

请从以下18个维度进行对比，每个维度给出1-10分评分和理由：

1. 学习曲线（1=极陡，10=极平缓）
2. 开发效率（1=极低，10=极高）
3. 代码复杂度（1=极复杂，10=极简洁）
4. 部署运维复杂度（1=极复杂，10=极简单）
5. 本地开发体验（1=极差，10=极好）
6. 集成测试便利性（1=极难，10=极易）
7. 模块边界清晰度（1=极模糊，10=极清晰）
8. 独立部署能力（1=完全不能，10=完全独立）
9. 可扩展性（1=极差，10=极好）
10. 弹性伸缩能力（1=极差，10=极好）
11. 故障隔离性（1=无隔离，10=完全隔离）
12. 数据一致性保障（1=无保障，10=强保障）
13. 事务管理复杂度（1=极复杂，10=极简单）
14. 团队技能匹配度（1=需要全学，10=几乎不需要学）
15. 社区成熟度（1=极小众，10=极成熟）
16. 长期维护成本（1=极高，10=极低）
17. 中间件依赖数量（1=极多，10=极少）
18. 整体适用度（1=极不适合，10=极适合）

输出格式要求：
- 先用一个总览表格展示18个维度的评分
- 然后逐一解读差距最大的5个维度（差距≥3分）
- 最后给出针对性建议，明确在给定业务场景和团队条件下推荐哪个方案
```

**为什么是18个维度？** 因为多数人做选型只看"性能"和"社区活跃度"两个维度，而忽略了部署复杂度、测试便利性这种会在日常开发中持续消耗团队时间的隐性成本。

### 模板3：版本升级风险评估

适用场景：框架/中间件大版本升级，想知道有哪些 Breaking Changes 和迁移成本。

```text
你是一位拥有15年Java后端开发经验的技术架构师。请对以下版本升级进行全面的风险评估：

【升级路径】：[Spring Boot 2.7.x → Spring Boot 3.2.x]
【当前技术栈】：
- JDK 11 → 需要一并升级到 JDK 17
- Spring Cloud 2021.x
- MyBatis-Plus 3.5.x
- Spring Security 5.x
- 使用 javax.* 包名
- 部分模块使用了 Spring Cloud Gateway
- 自定义了若干 Security Filter
- 使用了 Swagger 2 (springfox)

请按以下结构输出评估报告：

1. **Breaking Changes 清单**（按影响程度排序）
   - 必须修改的项（不修改编译不过）
   - 建议修改的项（Deprecated API）
   - 需要重新测试的项

2. **依赖升级路线图**
   - 列出每个依赖的当前版本和目标版本
   - 标注不兼容的组合（如 A 升级了但 B 还没适配）

3. **代码迁移工作量估算**（按模块拆分）
   - 全局搜索替换（如 javax → jakarta）
   - 需要手动修改的类/方法数量
   - 配置文件变更

4. **风险清单与缓解措施**
   - 高风险项（可能导致生产事故）
   - 中风险项（功能异常但可降级）
   - 低风险项（仅影响开发体验）

5. **灰度升级方案建议**
   - 建议的分批升级顺序
   - 回滚预案

6. **预估时间线**（含开发+测试+回归）
```

### 模板4：技术栈组合兼容性分析

适用场景：已经选了几个组件，想知道它们合在一起有没有坑。

```text
你是一位拥有15年Java后端开发经验的技术架构师。请分析以下技术栈组合的兼容性和潜在冲突：

【技术栈组合】：
- Spring Boot 3.2.x + JDK 21 虚拟线程
- Spring Cloud Gateway (Reactive) 作为网关
- Spring Data JPA (Hibernate 6.x) 作为 ORM
- Redis (Lettuce 客户端) 作为缓存
- Apache Pulsar 作为消息队列
- Resilience4j 作为熔断限流
- Micrometer + Prometheus 作为监控
- 使用 GraalVM Native Image 编译

请从以下角度分析：

1. **已知兼容性问题**
   - JDK 21 虚拟线程与其他组件的已知冲突
   - Reactive 栈（Gateway）与 Servlet 栈（JPA）在同一个项目中的线程模型协调
   - GraalVM Native Image 对各个组件的支持情况

2. **线程模型冲突分析**
   - 虚拟线程 vs 响应式编程的线程模型差异
   - 哪些库内部使用了 ThreadLocal 可能导致虚拟线程 pin 住
   - 哪些库的线程池配置需要调整

3. **序列化与类加载冲突**
   - Native Image 下反射、动态代理的限制
   - Hibernate 的懒加载代理在 Native Image 下的表现

4. **性能反模式预警**
   - 用了缓存但缓存策略不当导致缓存穿透
   - 用了熔断但未配置合理的降级逻辑

5. **替代方案建议**
   - 如果存在严重的不兼容问题，推荐替换哪个组件、用什么替代

6. **最小可行技术栈建议**
   - 如果砍掉一些组件来降低复杂度，建议砍掉哪些
```

### 案例1：Spring Modulith vs 纯微服务 vs 单体——电商项目架构选型

#### 需求背景

> - 项目：一个垂直电商平台（二手奢侈品交易），MVP 阶段
> - 团队：8 人（3 前端 + 5 后端），后端开发年限 3-7 年
> - 运维能力：中等（有 K8s 经验但不深，没有专职 SRE）
> - 预期用户量：第一年 DAU 3 万，日订单 500-1000 单
> - 业务模块：用户、商品、订单、支付、IM、搜索、推荐、运营后台
> - 关键约束：3 个月内上线 MVP，预算有限

#### 用模板1让 AI 做对比分析

使用上面的**模板1**，把【方案A】设为 Spring Modulith，【方案B】设为 Spring Cloud 微服务，场景填入上述信息。

#### AI 输出的核心对比表

| 维度 | Spring Modulith | Spring Cloud 微服务 | 差距 |
|------|:---:|:---:|:---:|
| 学习曲线 | 8 | 4 | **+4** |
| 开发效率 | 9 | 5 | **+4** |
| 代码复杂度 | 8 | 4 | **+4** |
| 部署运维复杂度 | 9 | 3 | **+6** |
| 本地开发体验 | 10 | 4 | **+6** |
| 集成测试便利性 | 9 | 4 | **+5** |
| 模块边界清晰度 | 7 | 9 | -2 |
| 独立部署能力 | 3 | 10 | **-7** |
| 弹性伸缩能力 | 4 | 9 | -5 |
| 故障隔离性 | 5 | 9 | -4 |
| 事务管理复杂度 | 9 | 3 | **+6** |

（表格为精简版，实际 AI 输出了完整的 18 维度评分）

#### AI 的分析摘要

> **差距最大的5个维度解读**：
>
> 1. **部署运维复杂度（差距+6，Modulith胜）**：Spring Cloud 微服务需要独立部署每个服务，涉及服务注册发现、配置中心、API 网关等中间件，而 Modulith 是一个可部署单元，只需部署一个 JAR。对于没有专职 SRE 的团队，Modulith 的运维负担显著更低。
>
> 2. **本地开发体验（差距+6，Modulith胜）**：微服务架构下本地开发需要启动多个服务，即使做了 Mock 也经常因为依赖链断裂而调试困难。Modulith 可以在一个 IDEA 窗口中启动和调试所有模块。
>
> 3. **事务管理复杂度（差距+6，Modulith胜）**：电商核心交易链路涉及用户扣款、库存扣减、订单创建，在微服务架构下需要使用 Saga 或 TCC 等分布式事务方案，复杂度极高。Modulith 可以直接使用本地事务 + 事件表模式（Event Publication）处理跨模块操作。
>
> 4. **独立部署能力（差距-7，微服务胜）**：这是微服务的核心优势，Modulith 单体部署无法做到独立发布、灰度上线某个模块。
>
> 5. **弹性伸缩能力（差距-5，微服务胜）**：微服务可以针对高负载模块（如订单服务）单独扩容，Modulith 只能整体扩容。

#### 最终决策和理由

**我们选了 Spring Modulith，理由：**

1. **MVP 阶段，快速上线是第一优先级**。微服务的运维复杂度会显著拖慢交付速度
2. **日订单 500 单的场景下，弹性伸缩是伪需求**——一个 4C8G 的实例跑 10 万 QPS 都绰绰有余
3. **团队没有 SRE**，微服务的分布式事务、链路追踪、日志聚合会让 5 个后端天天救火
4. Modulith 的**模块化事件机制**为未来拆分微服务留了后路——每个模块内部通过应用事件通信，未来拆成独立服务时只需把事件改为消息队列投递

**关键洞察**：Modulith 不是"不拆分"，而是**推迟拆分**。在业务边界还没跑清楚的时候就拆微服务，等于是在信息最少的时候做了最重要的架构决策。

### 案例2：Redis vs Caffeine vs Hazelcast——缓存方案选型

#### 需求背景

> - 项目：一个 SaaS 租户管理系统
> - 缓存场景：
>   - 场景A：租户配置数据（高频读、极低频写，单条数据 < 5KB，总量 < 1 万条）
>   - 场景B：用户 Session 信息（高频读写，需要过期淘汰，需要持久化避免重启丢失）
>   - 场景C：限流计数器（极高频率写，精度要求不高，允许少量丢失）
> - 部署环境：单机房，3 个应用节点
> - 约束：不想引入太多中间件，运维要简单

#### 用 AI 做分场景选型

我把上述三个场景分别喂给 AI，要求按以下格式输出：

```text
请对以下缓存方案进行分场景对比：Redis vs Caffeine vs Hazelcast

场景A：...
场景B：...
场景C：...

对每个场景，请给出：
1. 最推荐方案及理由
2. 备选方案及理由
3. 不推荐方案及理由（如果有）
```

#### AI 输出的核心结论

| 场景 | 最推荐 | 理由 |
|------|--------|------|
| 场景A（租户配置） | **Caffeine** | 数据量小、变化少，本地缓存零网络开销，配合 `@Cacheable` 注解 5 分钟代码量 |
| 场景B（Session） | **Redis** | 需要跨节点共享、持久化（AOF/RDB）、过期淘汰策略成熟，是 Session 管理的标准答案 |
| 场景C（限流计数） | **Redis** | 单线程模型保证计数原子性，Lua 脚本实现滑动窗口限流，性能足够且数据一致性有保障 |

**额外推荐：场景A + 场景C 可以组合使用 Caffeine + Redis**

```text
┌─────────────────────────────────────┐
│           应用节点 (3个)              │
│  ┌──────────┐      ┌──────────────┐ │
│  │ Caffeine │─────▶│ Redis (共享) │ │
│  │ (本地L1) │ 回源  │   (远程L2)   │ │
│  └──────────┘      └──────────────┘ │
└─────────────────────────────────────┘
```

L1 Caffeine 承载 90% 的读请求（微秒级响应），L2 Redis 做跨节点共享和持久化。这个组合在<5 万 QPS 的场景下几乎不需要调参。

#### 最终决策和理由

**我们最终选了 Caffeine + Redis 双层缓存，Hazelcast 放弃。**

| 组件 | 决策 | 理由 |
|------|------|------|
| Caffeine | ✅ 采用 | 本地缓存 TOP1，W-TinyLFU 淘汰算法业界最优，Spring Cache 开箱即用 |
| Redis | ✅ 采用 | Session 管理和限流计数没有更好的替代方案 |
| Hazelcast | ❌ 放弃 | 分布式缓存在 3 节点场景无优势，引入组播发现和脑裂风险，运维复杂度高于 Redis |

**关键洞察**：很多人选缓存时会"一口价"选 Redis，但忘了**本地缓存 + 远程缓存可以组合**。把 1 万条配置数据放本地 Caffeine，每次读取从网络 IO 变成内存寻址，RT 从毫秒级降到微秒级。Redis 只做那些"必须共享"的事情。

### 案例3：RestTemplate vs WebClient vs HttpExchange——HTTP 客户端选型

#### 需求背景

> - 项目：一个 API 网关，需要调用 20+ 个下游服务
> - 调用模式：大部分是同步调用（请求-响应），少量需要 SSE 流式消费
> - 并发量：峰值 5000 QPS
> - JDK 版本：17，已确定要升到 21
> - 团队技能：熟悉 Spring Boot 但没用过响应式编程（WebFlux）

#### Prompt 输入

```text
你是一位拥有15年Java后端开发经验的技术架构师。请对以下三种Spring HTTP客户端方案进行对比：

【方案A】：RestTemplate（同步阻塞）
【方案B】：WebClient（响应式非阻塞）
【方案C】：HttpExchange（声明式HTTP接口，Spring 6+）
【接入方式】：在现有的Spring MVC（Servlet栈）项目中集成

请从以下维度对比，并附上代码示例：

1. 并发性能（线程资源占用）
2. API 易用性
3. 与现有 Spring MVC 项目的集成成本
4. JDK 21 虚拟线程的兼容性展望
5. 可维护性（代码量、可读性）
6. 错误处理和重试
7. 超时配置灵活性
8. 连接池管理

最后请给出：在当前场景下（5000 QPS、同步调用为主、团队不熟悉响应式编程），你的推荐排序及理由。
```

#### AI 输出的核心对比表

| 维度 | RestTemplate | WebClient | HttpExchange |
|------|:---:|:---:|:---:|
| 并发性能 | 4 | 9 | 6 (依赖底层实现) |
| API 易用性 | 8 | 5 | 10 |
| 集成成本 | 9 | 4 | 8 |
| JDK 21 虚拟线程兼容 | 10 | 6 | 10 |
| 可维护性 | 6 | 5 | 9 |
| 错误处理/重试 | 7 | 6 | 8 |
| 连接池管理 | 8 | 8 | 7（依赖底层） |
| **综合推荐度** | 7 | 5 | **9** |

#### AI 的分析摘要

> 在当前约束下（同步调用为主、团队不熟悉响应式编程），**首推 HttpExchange，次选 RestTemplate + 虚拟线程，WebClient 不推荐**。
>
> 理由：
> 1. **HttpExchange**：声明式接口写法最简洁，与 Feign 类似，团队学习成本极低。底层默认使用 RestClient（Spring 6.1+），在 JDK 21 下可以配合虚拟线程获得接近 WebClient 的并发性能，同时保持同步编程模型
> 2. **RestTemplate + 虚拟线程**：Spring Boot 3.2 已经可以用虚拟线程替代 Tomcat 线程池，RestTemplate 的阻塞调用在虚拟线程下几乎等价于异步非阻塞。唯一劣势是 API 设计老旧，代码量略大
> 3. **WebClient**：优势在纯 Reactive 场景（端到端非阻塞），但在 Servlet 栈中集成是"半吊子"——Controller 是阻塞的，只有 HTTP 调用非阻塞，收益有限但心智负担翻倍

#### 代码对比（AI 输出的一部分）

```java
// RestTemplate：经典但啰嗦
String url = "https://api.example.com/users/{id}";
ResponseEntity<User> response = restTemplate.exchange(
    url, HttpMethod.GET, null, 
    new ParameterizedTypeReference<User>() {}, userId);
User user = response.getBody();

// WebClient：需要 subscribe / block，和 MVC 模型格格不入
Mono<User> userMono = webClient.get()
    .uri("/users/{id}", userId)
    .retrieve()
    .bodyToMono(User.class);
// 在 MVC Controller 中被迫 block()，失去非阻塞优势
User user = userMono.block();

// HttpExchange：声明式，和 Feign 一样简单
@HttpExchange("/users")
interface UserClient {
    @GetExchange("/{id}")
    User getUser(@PathVariable Long id);
}
// 调用时完全透明
User user = userClient.getUser(userId);
```

#### 最终决策和理由

**我们选了 HttpExchange + JDK 21 虚拟线程。**

| 因素 | 权重 | HttpExchange 得分 | 说明 |
|------|:---:|:---:|------|
| 团队学习成本 | 高 | 9 | 声明式接口，Spring 开发者零门槛 |
| 长期可维护性 | 高 | 9 | 代码量最少，编译器校验 URL 参数 |
| 并发性能 | 中 | 8 | 配合虚拟线程，5000 QPS 无压力 |
| Spring 官方趋势 | 高 | 10 | RestTemplate 已标记为 Deprecated，HttpExchange 是官方力推方案 |
| 代码量 | 中 | 9 | 比 RestTemplate 少 60% 代码量 |

**关键洞察**：很多人选 WebClient 是冲着"非阻塞 = 高性能"的光环去的，但忽略了**响应式编程的传染性**——用了 WebClient，你的 Service、Controller、Filter 全得 Reactive，否则 `block()` 一调用，全是虚假的非阻塞。在 Servlet 栈中，HttpExchange + 虚拟线程是更务实的方案。

## 四、AI 选型的局限性：三个 AI 不会告诉你的盲区

LLM 再强，它也只能基于**公开文档和社区讨论**做分析。以下三个因素，AI 永远无法替代你的判断：

### 盲区1：AI 不知道你的团队能力

AI 推荐你用 Flink 做实时计算，但它不知道你的团队 4 个人全是 Spring Boot 一把梭，连 Hadoop 都没搭过。一个需要 3 个月学习才能上手的技术，对于 1 个月要上线的项目就是死刑。

**补充方法**：在 Prompt 中明确写出团队技能矩阵。比如：
> 团队5人：2人精通Spring全家桶，1人熟悉MySQL+Redis，1人前端转后端（初级），1人刚入职

### 盲区2：AI 不知道你的运维水平

AI 推荐你用 Kubernetes + Istio + Prometheus + Grafana + ELK + SkyWalking，但它不知道你们公司只有一个半吊子运维，连 K8s 的 StatefulSet 和 Deployment 的区别都说不清楚。

**补充方法**：在 Prompt 中加上运维约束。比如：
> 运维能力：只能独立部署 Spring Boot JAR + 配置 Nginx 反向代理，没有 K8s 环境，数据库和 Redis 走云服务商的托管方案

### 盲区3：AI 不知道你的基础设施现状

AI 推荐你用 Pulsar 做消息队列，但它不知道你们现有 3 个项目全用 RabbitMQ，运维团队有成熟的 RabbitMQ 监控和巡检脚本。引入一个新中间件 = 引入一个新的故障域。

**补充方法**：在 Prompt 中列出已有基础设施。比如：
> 现有基础设施：MySQL 8.0（自建，主从）、Redis 7（自建，哨兵）、RabbitMQ 3.12（自建）、Nginx + Spring Boot 应用部署在 5 台物理机上

## 五、附：用 AI 生成"技术选型评审 PPT"的 Prompt

技术选型做完后，你通常需要在评审会上向 leader / 架构组汇报。以下 Prompt 可以直接生成一份评委挑不出毛病的 PPT 大纲：

```text
你是资深Java架构师，需要向技术委员会做一次技术选型评审汇报。请根据以下信息生成一份PPT大纲（10页，Markdown格式，每页包含标题和3-5个要点）：

【选型主题】：[API网关选型：Spring Cloud Gateway vs Kong vs APISIX]
【业务场景】：[电商平台，日均10亿次API调用，需要限流、鉴权、灰度路由、协议转换]
【团队情况】：[8人后端，熟悉Java和Spring生态，有K8s运维经验]
【预算约束】：[开源优先，如果商业版性价比高也可以考虑]
【已有基础设施】：[K8s集群、Prometheus+Grafana监控、ELK日志]

PPT结构要求：
第1页：选型背景与目标
第2页：业务需求分析（功能需求+非功能需求）
第3页：候选方案概览
第4页：多维对比矩阵（至少12个维度）
第5页：性能基准测试数据（如果AI没有数据请标注"需实测"）
第6页：迁移成本与风险分析
第7页：团队匹配度分析
第8页：总拥有成本（TCO）估算
第9页：推荐方案及分期落地计划
第10页：风险应急预案

输出时每页用 === 分隔，输出完整可复制内容。
```

这个 Prompt 生成的 PPT 大纲，我个人在三次评审会上用过，每次都能让架构组直接放行。（当然，前提是你把业务场景描述得足够详细）

## 六、总结：AI 辅助选型的正确姿势

回到开头的问题——**LLM 能不能帮你做技术选型？**

答案是：**能辅助，但不能替代。**

把 AI 视为一个**信息压缩和结构化分析的工具**，而不是替你拍板的决策者。正确的使用姿势是：

```
1. 用模板1（二维对比）快速扫盲，了解每个方案的优劣势
2. 用模板2（场景驱动）让 AI 推荐候选方案，缩小选择范围
3. 用模板3（风险评估）排查 Breaking Changes 和迁移成本
4. 用模板4（兼容性分析）确认候选方案之间的组合没有坑
5. 结合团队能力、运维水平、基础设施现状做最终决策
6. 用 PPT Prompt 生成评审材料，说服架构组
```

**AI 负责信息广度，你负责决策深度。厂商的 PPT 会骗你，但结构化的 Prompt + AI 输出，至少能让你在选型表上把每个维度都看清楚。**

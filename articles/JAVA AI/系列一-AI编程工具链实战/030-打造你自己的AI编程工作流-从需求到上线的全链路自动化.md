## 一、开篇：一个理想的工作日

**9:00** 到公司，打开电脑。AI 助手已经把昨晚生产环境的 3 条告警分析完毕，整理成了带优先级的处理清单，还标注了根因推测："`order-service` 的慢查询与昨天上线的批量导出功能有关，建议今天第一优先级处理。"

**9:30** 站会。你不需要从记忆里挖昨天的进度——AI 已经根据昨天的 Git 提交记录和 Jira 状态变更，总结了每位成员的进展："张三完成了地址管理的数据模型设计，李四的支付集成通过了 95% 的测试用例。"

**10:00** 你打开今天的需求："用户模块的地址管理功能——支持省市区三级联动、默认地址设置、最多 20 个地址。" 你对 AI 说："根据这个 PRD，帮我拆解开发任务。"

接下来的 6 个小时，你做的事情是：**确认 AI 的输出、做关键决策、处理复杂的业务边界。** 重复性的代码编写、测试生成、文档更新——AI 包了。

## 三、节点 1：需求理解——PRD → 开发任务拆解

### 痛点

传统模式：你拿到一份 8 页的 PRD 或一段 Jira Ticket 描述，花 1-2 小时理解需求、拆解任务、估时。然后发现理解偏了，返工。

### AI 方案

把 PRD 喂给 AI，让它输出结构化的开发任务清单。

### Prompt 模板

```
你是一个资深 Java 后端开发工程师。请根据以下需求文档，完成开发任务拆解。

要求：
1. 将需求拆解为可独立开发的子任务，每个子任务 2-4 小时工作量
2. 标注每个任务的依赖关系（前置任务）
3. 标注每个任务的难度（S/A/B/C 级）
4. 给出每个任务涉及的数据表（如需新建，给出字段建议）
5. 给出每个任务涉及的后端接口（API Endpoint 建议）

需求文档：
[贴入 PRD 或 Jira Ticket 描述]

技术栈：Spring Boot 3.x + MyBatis-Plus + MySQL 8.0 + Redis
```

### AI 输出示例

```
## 开发任务拆解：用户地址管理

| 任务ID | 任务描述 | 预估工时 | 难度 | 前置任务 |
|--------|---------|---------|------|---------|
| T1 | 创建 address 表，编写 DDL 和索引 | 1h | C | 无 |
| T2 | 生成 Address Entity + Mapper + Service | 2h | B | T1 |
| T3 | 地址 CRUD 接口（新增/删除/修改/查询列表） | 3h | B | T2 |
| T4 | 省市区三级联动查询接口 | 3h | A | T2 |
| T5 | 默认地址逻辑（设置/取消/查询默认） | 2h | B | T3 |
| T6 | 地址数量上限校验（最多20个） | 1h | C | T3 |
| T7 | 单元测试 + 集成测试 | 3h | B | T3-T6 |
| T8 | API 文档（Swagger 注解） | 1h | C | T7 |

### 数据表建议

```sql

    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT NOT NULL COMMENT '用户ID',
    receiver_name VARCHAR(50) NOT NULL COMMENT '收件人姓名',

    province VARCHAR(50) NOT NULL COMMENT '省',
    city VARCHAR(50) NOT NULL COMMENT '市',

    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

```

### API 设计

| 方法 | Endpoint | 说明 |
|------|----------|------|
| GET | /api/address/list | 查询用户地址列表 |

### 关键收益

- 拆解时间从 **1-2 小时**压缩到 **10 分钟**（你只需要审核 + 微调）
- AI 不会遗漏常规 CRUD，人类反而容易漏掉"地址上限校验"这种非功能需求
- 数据表设计和 API 设计直接在拆解阶段完成，减少沟通成本

> **进阶技巧**：如果你的公司用 Jira，可以把 AI 的输出格式化后直接通过 Jira API 批量创建子任务。我在 `.bashrc` 里写了一个函数，一行命令搞定。

## 四、节点 2：代码生成——Cursor Composer 的正确打开方式

### 工具选择

| 工具 | 适用场景 |
|------|---------|
| Cursor Composer (⌘+I) | 多文件联动修改、新建模块 |
| Cursor Tab | 单行/单方法补全 |
| Cursor Chat (⌘+L) | 理解代码、临时修改 |

### 工作流

**第一步：加载项目规则**

在项目根目录的 `.cursorrules` 文件中预设规则：

```
你是一个 Spring Boot 3.x 专家，项目使用以下技术栈：
- Java 17, Spring Boot 3.2, MyBatis-Plus 3.5
- MySQL 8.0, Redis 7, RabbitMQ
- Lombok, Hutool, MapStruct
- 统一返回格式：ApiResult<T>（code / message / data）
- 所有 Controller 继承 BaseController
- 严禁使用 `SELECT *`
- 所有 SQL 必须使用参数化查询
- 所有接口必须有 Swagger @Operation 注解
```

**第二步：用 Composer 生成基础代码**

```
根据以下任务清单，生成完整的代码。项目规则参见 .cursorrules。

任务：用户地址管理 - 地址 CRUD

请生成以下文件：
1. TUserAddress.java（Entity，包路径 com.example.entity）
2. TUserAddressMapper.java（Mapper，继承 BaseMapper）
3. AddressService.java（Service 接口）
4. AddressServiceImpl.java（Service 实现）
5. AddressController.java（Controller，继承 BaseController）
6. AddressRequest.java（请求 DTO）
7. AddressVO.java（响应 VO）

业务规则：
- 每个用户最多 20 个地址
- 设置默认地址时，自动取消其他默认地址
- 删除地址时，软删除（status=1）
- 所有操作需要校验用户身份（从 ThreadLocal 获取 userId）
```

**第三步：审查 + 手动调整**

Cusor Composer 会一次性生成全部文件。你需要：
1. 检查包名、导入是否正确
2. 检查业务逻辑是否符合预期
3. 补充 AI 遗漏的边界条件
4. 调整代码风格与项目保持一致

### 实际效率

以地址管理模块为例（8 个文件，约 300 行代码），AI 生成耗时 **3 分钟**，人工审查 + 微调耗时 **15 分钟**。传统手写至少 **2 小时**。

## 五、节点 3：代码审查——GitHub Actions 自动 AI Review

### 场景

人工 Code Review 的问题：reviewer 可能遗漏、可能敷衍、可能忙得根本没看。AI Review 可以作为"第一道防线"，在人工 Review 之前过滤掉低级别问题。

### 实现方案

```yaml
# .github/workflows/ai-review.yml
name: AI Code Review

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  ai-review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: AI Code Review
        uses: coderabbitai/ai-pr-reviewer@latest
        with:
          openai_api_key: ${{ secrets.OPENAI_API_KEY }}
          model: 'gpt-4-turbo'
          review_instructions: |
            请按以下规则审查 Java 代码：
            1. 安全问题：SQL 注入、XSS、敏感信息泄露（P0）
            2. 性能问题：N+1 查询、未使用索引、不必要的对象创建（P1）
            3. 代码规范：命名、注释、异常处理（P2）
            4. 业务逻辑：边界条件、空值处理、并发安全（P1）
            5. 测试覆盖：关键路径是否有测试（P2）
            如果发现问题，请给出具体的修复代码建议。
          exclude_paths: |
            **/*.xml
            **/*.json
            **/*.md
```

### 你也可以用纯脚本方案

如果你不想引入第三方 Action，自己写一个调用 OpenAI API 的 Python 脚本：

```python
# ai_review.py
import os
import requests

API_KEY = os.environ["OPENAI_API_KEY"]
GITHUB_TOKEN = os.environ["GITHUB_TOKEN"]

diff = os.popen("git diff origin/main...HEAD -- '*.java'").read()

prompt = f"""请审查以下 Java 代码变更，关注：
1. 安全问题（SQL 注入、敏感信息泄露）
2. 性能问题（N+1 查询、资源未释放）
3. 异常处理（空指针、异常吞吃）
4. 代码风格（命名规范、重复代码）

变更内容：
{diff}

请按以下格式输出审查意见：
### 问题 1：[严重程度] 问题描述
位置：文件名:行号
建议：[修复代码]
"""

response = requests.post(
    "https://api.openai.com/v1/chat/completions",
    headers={"Authorization": f"Bearer {API_KEY}"},
    json={
        "model": "gpt-4-turbo",
        "messages": [{"role": "user", "content": prompt}]
    }
)

review = response.json()["choices"][0]["message"]["content"]
# 将 review 作为 PR Comment 提交到 GitHub
print(review)
```

### 效果

我们团队接入 AI Review 后发现：**人工 Review 的"低级问题发现率"从 30% 提升到 85%**——不是人变厉害了，而是 AI 在人工 Review 之前就把低级问题全揪出来了。人工 Review 可以专注于架构设计、业务合理性这些更高价值的事情。

## 六、节点 4：测试生成——单元测试 + 集成测试

### Prompt 模板（单元测试）

```
请为以下 AddressServiceImpl 生成完整的单元测试。

要求：
1. 使用 JUnit 5 + Mockito
2. 覆盖所有 public 方法
3. 每个方法至少覆盖：正常路径、边界条件、异常路径
4. 使用 @ExtendWith(MockitoExtension.class)
5. 使用 @Mock 注入依赖，@InjectMocks 注入被测试对象
6. 测试方法命名格式：test_{方法名}_{场景描述}
7. 代码覆盖率目标：行覆盖 ≥ 90%，分支覆盖 ≥ 80%

目标代码：
[贴入 AddressServiceImpl.java]
```

### AI 输出示例

```java
@ExtendWith(MockitoExtension.class)
class AddressServiceImplTest {

    @Mock
    private TUserAddressMapper addressMapper;

    @InjectMocks
    private AddressServiceImpl addressService;

    @Test
    void testAddAddress_underLimit_shouldSuccess() {
        // given: 当前地址数 5（未达上限 20）
        when(addressMapper.countByUserId(1L)).thenReturn(5);
        when(addressMapper.insert(any())).thenReturn(1);

        AddressRequest request = new AddressRequest();
        request.setReceiverName("张三");
        request.setReceiverPhone("13800138000");
        request.setProvince("广东省");
        request.setCity("深圳市");
        request.setDistrict("南山区");
        request.setDetailAddress("科技园路1号");

        // when
        addressService.addAddress(1L, request);

        // then
        verify(addressMapper).insert(any());
    }

    @Test
    void testAddAddress_exceedLimit_shouldThrowException() {
        // given: 当前地址数 20（已达上限）
        when(addressMapper.countByUserId(1L)).thenReturn(20);

        AddressRequest request = new AddressRequest();
        request.setReceiverName("张三");

        // when & then
        assertThrows(BusinessException.class,
            () -> addressService.addAddress(1L, request));
        verify(addressMapper, never()).insert(any());
    }

    @Test
    void testSetDefaultAddress_shouldCancelOldDefault() {
        // given
        TUserAddress oldDefault = new TUserAddress();
        oldDefault.setId(1L);
        oldDefault.setIsDefault(1);
        when(addressMapper.selectDefaultByUserId(1L)).thenReturn(oldDefault);
        when(addressMapper.updateById(any())).thenReturn(1);

        // when
        addressService.setDefaultAddress(1L, 2L);

        // then: 验证旧默认地址的 is_default 被置为 0
        verify(addressMapper).updateById(oldDefault);
        // then: 验证新地址的 is_default 被置为 1
        verify(addressMapper).updateById(any());
    }
}
```

### Prompt 模板（集成测试）

```
请为以下 AddressController 生成集成测试。

要求：
1. 使用 Spring Boot Test + MockMvc
2. 使用 @Sql 加载测试数据
3. 测试完整的 HTTP 请求-响应链路
4. 验证状态码、响应 JSON 结构、数据库变更
5. 生成测试数据的 SQL 脚本

目标 Controller：
[贴入 AddressController.java]
```

### 效果

传统写测试的时间比写业务代码还久。AI 生成的测试代码，我只需要：
- **30%** 的测试直接采纳（简单 CRUD 的测试非常标准化）
- **30%** 需要补充边界条件（AI 对并发场景、事务回滚场景的覆盖不够）
- **30%** 需要重写（复杂业务逻辑的 mock 设置 AI 经常搞错）
- **10%** 的测试 AI 完全遗漏（需要你自己发现的隐藏路径）

**测试生成时间从 4 小时压缩到 1 小时。**

## 七、节点 5：文档生成——API 文档 + CHANGELOG

### API 文档

这一步最简单也最容易被忽略。你在写 Controller 的时候，顺手让 AI 加上 Swagger 注解：

```
请为以下 Controller 添加 Swagger/OpenAPI 3 注解。

要求：
1. 类级别添加 @Tag(name = "xxx", description = "xxx")
2. 方法级别添加 @Operation(summary = "xxx", description = "xxx")
3. 请求参数添加 @Parameter 注解
4. DTO 字段添加 @Schema(description = "xxx", example = "xxx")
5. 响应状态码通过 @ApiResponses 标注

目标代码：
[贴入 Controller]
```

如果你连注解都不想手写，可以直接让 AI 生成完整的 Swagger YAML/JSON：

```
请根据以下 Controller 的代码，生成 OpenAPI 3.0 规范的 YAML 文件。
包括：paths, components/schemas, 请求/响应示例。
```

### CHANGELOG 自动生成

```
请根据以下 git diff 内容，生成 CHANGELOG.md 更新条目。

要求：
1. 格式使用 Keep a Changelog 规范（https://keepachangelog.com/）
2. 分类：Added / Changed / Fixed / Removed
3. 每条变更一句话，用中文
4. 序号使用 - 而非 *

Git Diff：
[贴入 git diff 内容]
```

### 效果

文档不再是你"上线之后补"的累赘，而是 **CI 流水线的自动输出**。每次合并到 main 分支，自动生成 CHANGELOG 更新 + Swagger 文档部署。

## 八、节点 6：部署检查——K8s 配置、环境变量、依赖版本

### 场景

你改了一行代码，部署上去，报错了——因为你忘了一个新的环境变量。或者你升了一个依赖版本，但 K8s 的资源限制没跟上。

### Prompt

```
请根据以下 Spring Boot 项目，检查部署所需的配置完整性。

检查项：
1. application.yml 中引用的所有 ${变量} 是否都有对应的环境变量或默认值
2. pom.xml 中的依赖版本是否存在已知 CVE 漏洞（提示：你不需要联网查询，只列出常见高危依赖如 Log4j < 2.17.1, Spring Framework < 5.3.18 等版本区间风险）
3. 如果项目使用 MySQL/Redis/RabbitMQ，检查连接配置是否完整
4. 检查是否有未提交的敏感信息（如明文密码、API Key）

项目配置文件：
application.yml: [贴入内容]
pom.xml: [贴入内容]
```

### Dockerfile / K8s 配置检查

```
请根据以下 pom.xml 和项目结构，检查以下配置的合理性：

1. Dockerfile 的基础镜像版本是否过时（建议使用 eclipse-temurin:17-jre-alpine）
2. K8s Deployment 的 resources.requests 和 resources.limits 是否匹配 Java 应用的典型需求
3. 检查是否配置了健康检查探针（livenessProbe / readinessProbe）
4. Service 的端口映射是否正确

项目结构：
[贴入 tree 输出]

pom.xml: [贴入内容]
k8s/deployment.yaml: [贴入内容]
Dockerfile: [贴入内容]
```

### 自动化集成

把部署检查脚本集成到 CI 流水线中——每次 PR merge 前自动跑一遍，发现配置缺失直接阻断合并。相信我，这会避免大量的"部署事故"。

## 九、节点 7：线上监控——AI 日志分析与告警归因

### 场景

凌晨 2:30，手机响了。"order-service 的 P99 延迟飙到 3 秒。"

打开 ELK，面对几千条日志，你一条一条翻，试图找出根因。半小时后定位到是某条慢 SQL，临时加了个索引，已经 3:15 了。

### AI 方案

把 Prometheus 告警 + 对应时间段的日志一起喂给 AI。

### Prompt

```
以下是一段时间内的应用日志和监控告警。请分析：

1. 这段时间内发生了哪些异常？
2. 异常之间是否存在因果关系？
3. 根因是什么？
4. 建议的修复方案是什么？
5. 是否需要立即处理（P0/P1/P2）？

告警信息：
[贴入 Prometheus AlertManager 告警]

日志片段（前后 5 分钟）：
[贴入异常时间段的日志，可截取前 500 行]

应用架构：
- order-service（Spring Boot 3.x，端口 8080）
- MySQL 8.0（主从，读写分离）
- Redis 7（缓存层）
- RabbitMQ（异步消息）
```

### 进阶：自动化告警分析脚本

```bash
#!/bin/bash
# analyze_alert.sh —— 自动分析生产告警

ALERT_MSG="$1"
SERVICE_NAME="$2"
TIME_RANGE="${3:-5m}"

LOGS=$(kubectl logs "deployment/$SERVICE_NAME" --since="$TIME_RANGE" --tail=500)

RESPONSE=$(curl -s https://api.openai.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d "$(jq -n --arg alert "$ALERT_MSG" --arg logs "$LOGS" '{
    model: "gpt-4o",
    messages: [
      {role: "system", content: "你是一个 SRE 专家，擅长分析 Java 应用的线上问题。请用中文回答，结论先行。"},
      {role: "user", content: "告警：\($alert)\n\n日志：\($logs)"}
    ]
  }')")

echo "$RESPONSE" | jq -r '.choices[0].message.content'
```

使用方式：

```bash
./analyze_alert.sh "order-service P99 > 2000ms" order-service "10m"
```

### 效果

- 告警分析时间从 **30 分钟手动翻日志**到 **2 分钟自动报告**
- 凌晨 2:30 的告警，你可以看一下 AI 的分析报告再做决定，而不是爬起来翻半天日志
- 累积的告警分析报告自动归档，形成团队的问题知识库

## 十一、总结：AI 编程工作流的本质

很多人以为 AI 编程就是"让 AI 写代码"。错了。

**AI 编程工作流的本质，是重新定义你每天把时间花在哪里。**

| 昨天 | 今天（AI 工作流） |
|------|-------------------|
| 30% 阅读需求 + 拆解任务 | 5% 审核 AI 的拆解结果 |
| 40% 编写代码 | 10% 审查 AI 生成的代码 |
| 15% 编写测试 | 5% 补充 AI 遗漏的测试 |
| 10% 写文档 | 2% 审核 AI 生成的文档 |
| 5% Code Review | 3% 处理 AI Review 标记的问题 |
| **100% 在干活** | **25% 在做决策** |

多出来的 75% 时间，你可以用来：
- **深入思考架构设计**（AI 目前还做不好的事）
- **分析线上问题**（比救火式响应高效得多）
- **学习新技术**（不学就要被淘汰）
- **准点下班陪家人**（这才是最终目标）

最后分享三条心得：

1. **AI 是你的 10x 生产力倍增器，不是你的替代品。** 你仍然是那个做决策、担责任、写核心逻辑的人。
2. **工作流大于工具。** 单独的 Copilot 或 Cursor 只能提效 30%，把这 7 个节点串起来才是真正的质变。
3. **先僵化、后优化、再固化。** 先用这篇文章的 SOP 跑两周，再根据自己的习惯调整，最后固化成你的肌肉记忆。

## 技巧一：用 `//TODO` 引导 AI 生成你想要的代码方向

> **难度：** 🟢 新手友好 &nbsp;&nbsp;|&nbsp;&nbsp; **效率提升：** 代码生成准确率 + **40%**，返工时间减少 **60%**

**痛点：** 你让Copilot生成一个"用户注册方法"，它给你写了20行代码——但没做参数校验，没加事务，密码直接明文存了。你不得不再花5分钟改。

**解法：** 在方法体内先写一个（或多个）`//TODO`，精确描述你希望AI生成什么逻辑，再按下Tab。

```java
@Service
public class UserService {

    public ResultVO<UserDTO> register(RegisterRequest request) {
        // TODO: 1. 校验手机号格式（正则：1[3-9]\d{9}）和密码长度(8-20位)
        // TODO: 2. 检查手机号是否已注册，已注册则抛出 BusinessException("手机号已被注册")
        // TODO: 3. 使用 BCrypt 加密密码
        // TODO: 4. 保存用户到数据库（userMapper.insert），需要 @Transactional
        // TODO: 5. 发送注册成功短信（异步，用 @Async）
        // TODO: 6. 返回 ResultVO.success(userDTO)
    }
}
```

Copilot/Cursor 读到这段 `//TODO` 列表后，会逐条生成对应实现，而且顺序、边界条件全都覆盖到了。

**进阶用法 —— 用 `//FIXME` 标注待修复点：**

```java
public BigDecimal calculateOrderTotal(List<OrderItem> items) {
    BigDecimal total = BigDecimal.ZERO;
    for (OrderItem item : items) {
        // FIXME: 未处理 item.getPrice() 为 null 的情况，会 NPE
        // FIXME: 折扣计算逻辑缺失，当前按原价累加
        total = total.add(item.getPrice().multiply(BigDecimal.valueOf(item.getQuantity())));
    }
    return total;
}
```

AI 会自动补全 null 检查和折扣计算逻辑，比你自己翻代码再改快得多。

**核心原理：** LLM 对注释中的指令非常敏感，`//TODO` 是一个强信号，告诉它"这里需要按步骤生成代码"。注释越具体，生成质量越高。

## 技巧二：在文件名中写注释来引导 AI

> **难度：** 🟢 新手友好 &nbsp;&nbsp;|&nbsp;&nbsp; **效率提升：** 上下文理解准确率 + **50%**，减少反复提示次数

**痛点：** 你打开一个项目，让 AI 帮你写一个带缓存和限流的 UserService。AI 生成了 200 行代码，但既没加 `@Cacheable`，也没加 RateLimiter——因为它不知道你的意图。

**解法：** 在文件名中加入"需求描述"，AI 会把这个文件名当作上下文的一部分来理解。

```
# 普通文件名（AI 只能猜到最泛化的实现）
src/main/java/com/example/service/UserService.java

# 加了"需求注释"的文件名（AI 秒懂你的需求）
src/main/java/com/example/service/UserService_需要加上Redis缓存和令牌桶限流.java
```

实际使用时，先创建一个带描述的文件名，让 AI 在其基础上生成代码骨架，完成后再重命名为正式文件名。

**进阶用法 —— 文件夹级别的需求描述：**

```
src/main/java/com/example/payment/
├── PaymentStrategy_需要支持微信支付宝银联三种渠道.md      ← 接口设计引导
├── PaymentStrategyImpl_WechatPay.java
├── PaymentStrategyImpl_AliPay.java
└── PaymentStrategyImpl_UnionPay.java
```

那个 `.md` 文件里空着就行，甚至可以写一句话：

```markdown
需要实现策略模式，支持微信、支付宝、银联三种支付渠道。
要求：每种渠道独立实现类，通过 PaymentStrategyFactory 获取。
所有实现类必须记录支付耗时日志。
```

当你打开这个文件夹用 Cursor/Copilot 时，AI 会自动读取这些"需求注释文件"作为上下文。**比写一份几百字的 Prompt 快 10 倍。**

## 技巧三：用 `.cursorrules` 设置"不要过度设计"

> **难度：** 🟡 进阶玩家 &nbsp;&nbsp;|&nbsp;&nbsp; **效率提升：** 减少无效代码生成 **80%**，每月省 **$5-10 API 费用**

**痛点：** AI 最爱干什么？**加设计模式。** 你让它写一个简单的 FileParser，它给你生成一个 `FileParserFactory` → `AbstractFileParser` → `CsvFileParser` → `FileParserContext` 四层抽象，代码量翻了 5 倍，实际只需要一个带 `switch` 的工具类。

**解法：** 在项目根目录创建 `.cursorrules`，用"反模式"规则约束 AI 的行为。

```yaml
# .cursorrules
rules:
  - name: "Java代码风格约束"
    description: "防止AI过度设计"
    globs: "**/*.java"
    version: "1.0"
    alwaysApply: true

    rules:
      - "除非明确要求，否则不要引入任何设计模式（工厂、策略、观察者等）"
      - "优先使用简单的 if-else 或 switch，不要动辄抽象接口"
      - "单个方法不超过 30 行，超过时先拆分再生成"
      - "不要自动引入 Lombok 以外的第三方依赖（MapStruct、Hutool 除外）"
      - "不要在 Service 层直接返回 Entity，必须返回 DTO/VO"
      - "日志使用 @Slf4j，不要用 System.out.println"
      - "异常处理使用统一的 BusinessException，不要吞异常（空 catch）"
```

**效果对比：**

| 场景 | 不加规则 | 加了规则 |
|------|---------|---------|
| "写一个CSV解析器" | 产出 5 个类、2 个接口、1 个工厂 | 1 个类，30 行 |
| "写一个短信发送服务" | 产出策略模式 + 阿里云/腾讯云/华为云三套实现 | 1 个 Service + 1 个 Util |
| Token 消耗 | ~12000 tokens | ~2500 tokens |

**额外技巧：** 在 Cursor 的 Chat 框里输入 `@rules` 可以看到当前生效的所有规则，方便调试。

## 技巧四：把 API 响应 JSON 贴给 AI 让它生成 POJO

> **难度：** 🟢 新手友好 &nbsp;&nbsp;|&nbsp;&nbsp; **效率提升：** POJO 编写速度提升 **10 倍**（30分钟 → 3分钟）

**痛点：** 对接第三方 API 时，响应 JSON 有 50 个字段，你一个个手写 POJO + `@JsonProperty` + 注释，半小时起步。嵌套对象更是一场噩梦。

**解法：** 把 API 文档里的 Response JSON 直接贴给 AI，3 分钟搞定。

**输入（直接复制自 Swagger/Postman）：**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "orderId": "ORD202501010001",
    "userId": 10086,
    "productList": [
      {
        "skuId": "SKU001",
        "skuName": "iPhone 16 Pro Max",
        "quantity": 1,
        "unitPrice": 9999.00,
        "discountAmount": 500.00
      }
    ],
    "totalAmount": 9499.00,
    "orderStatus": "PAID",
    "createdAt": "2025-01-01T12:00:00+08:00",
    "paidAt": "2025-01-01T12:01:30+08:00"
  }
}
```

**Prompt（一句话）：**

```text
根据以下JSON生成完整的Java POJO类，要求：
1. 使用 Lombok @Data
2. 使用 Jackson @JsonProperty 映射所有字段
3. 日期字段使用 LocalDateTime
4. 金额字段使用 BigDecimal
5. 为每个字段添加中文注释
6. 状态字段(orderStatus)用枚举
```

**AI 产出（节选）：**

```java
@Data
public class OrderResponse {
    @JsonProperty("code")
    private Integer code;

    @JsonProperty("message")
    private String message;

    @JsonProperty("data")
    private OrderData data;
}

@Data
public class OrderData {
    /** 订单ID */
    @JsonProperty("orderId")
    private String orderId;

    /** 用户ID */
    @JsonProperty("userId")
    private Long userId;

    /** 商品列表 */
    @JsonProperty("productList")
    private List<OrderProduct> productList;

    /** 订单总金额 */
    @JsonProperty("totalAmount")
    private BigDecimal totalAmount;

    /** 订单状态 */
    @JsonProperty("orderStatus")
    private OrderStatusEnum orderStatus;

    /** 创建时间 */
    @JsonProperty("createdAt")
    @JsonFormat(pattern = "yyyy-MM-dd'T'HH:mm:ssXXX")
    private LocalDateTime createdAt;

    /** 支付时间 */
    @JsonProperty("paidAt")
    @JsonFormat(pattern = "yyyy-MM-dd'T'HH:mm:ssXXX")
    private LocalDateTime paidAt;
}

public enum OrderStatusEnum {
    @JsonProperty("PENDING")  PENDING,
    @JsonProperty("PAID")     PAID,
    @JsonProperty("SHIPPED")  SHIPPED,
    @JsonProperty("COMPLETED") COMPLETED,
    @JsonProperty("CANCELLED") CANCELLED;
}
```

**我自己的 SOP（标准操作流程）：** Postman里调通接口 → 复制Response → 贴给Cursor → 输入 `@command generate POJOs` → 3 分钟内所有类生成完毕，`@JsonProperty` 一个不漏。

## 技巧五：用 AI 快速生成枚举类

> **难度：** 🟢 新手友好 &nbsp;&nbsp;|&nbsp;&nbsp; **效率提升：** 枚举编写速度提升 **8 倍**（10分钟 → 1.2分钟）

**痛点：** 项目中经常需要维护国家代码、货币类型、HTTP 状态码、业务错误码等枚举类。手动编写不仅枯燥，还容易遗漏。

**解法：** 一句话让 AI 生成完整的枚举类。

**示例 1 —— 国家代码枚举：**

```text
生成一个Java枚举类 CountryEnum，包含所有ISO 3166-1国家代码和中文名称，
要求：code为2位大写字母，name为中文名称，实现根据code查找的静态方法。
只生成前20个常用国家。
```

```java
@Getter
@AllArgsConstructor
public enum CountryEnum {

    CN("CN", "中国"),
    US("US", "美国"),
    JP("JP", "日本"),
    KR("KR", "韩国"),
    GB("GB", "英国"),
    DE("DE", "德国"),
    FR("FR", "法国"),
    IT("IT", "意大利"),
    CA("CA", "加拿大"),
    AU("AU", "澳大利亚"),
    SG("SG", "新加坡"),
    TH("TH", "泰国"),
    VN("VN", "越南"),
    MY("MY", "马来西亚"),
    PH("PH", "菲律宾"),
    ID("ID", "印度尼西亚"),
    IN("IN", "印度"),
    BR("BR", "巴西"),
    RU("RU", "俄罗斯"),
    AE("AE", "阿联酋");

    private final String code;
    private final String name;

    private static final Map<String, CountryEnum> CODE_MAP =
            Arrays.stream(values()).collect(Collectors.toMap(
                    CountryEnum::getCode, Function.identity(),
                    (a, b) -> a, LinkedHashMap::new));

    public static CountryEnum fromCode(String code) {
        CountryEnum result = CODE_MAP.get(code);
        if (result == null) {
            throw new IllegalArgumentException("未知国家代码: " + code);
        }
        return result;
    }
}
```

**示例 2 —— 业务错误码枚举（我实际项目里的 Prompt）：**

```text
生成一个Java枚举类 BizErrorCodeEnum，包含以下错误码：
- 成功: 0
- 参数错误: 1001-1005（缺少必填字段、格式错误、长度超限、类型不匹配、取值范围错误）
- 用户相关: 2001-2005（未登录、token过期、无权限、用户不存在、用户已禁用）
- 订单相关: 3001-3005（订单不存在、订单已取消、订单已支付、订单已过期、库存不足）

要求：每个枚举值包含 code(int)、message(String)、httpStatus(int)。
提供静态方法 fromCode(int) 用于根据code获取枚举。
```

AI 会瞬间生成 20+ 个枚举值，格式统一、注释齐全。

## 技巧七：用 AI 进行依赖冲突分析

> **难度：** 🟡 进阶玩家 &nbsp;&nbsp;|&nbsp;&nbsp; **效率提升：** 依赖冲突排查速度提升 **20 倍**，代码质量提升 **60%**

**痛点：** 项目跑着跑着突然报 `NoSuchMethodError` 或 `ClassNotFoundException`。你知道是 Jar 包冲突，但对着一棵 3000 行的 `mvn dependency:tree` 无从下手。

**解法：** 把依赖树扔给 AI，秒级定位冲突。

**Step 1：导出依赖树：**

```bash
# 将依赖树输出到文件
mvn dependency:tree -DoutputType=text -DoutputFile=dependency-tree.txt

# 如果只想看冲突的部分
mvn dependency:tree -Dverbose -Dincludes=com.fasterxml.jackson -DoutputFile=jackson-deps.txt
```

**Step 2：把输出喂给 AI：**

```text
以下是一个 Spring Boot 项目的 Maven 依赖树片段。
请分析：
1. 找出所有版本冲突的依赖（同一个 groupId:artifactId 出现多次不同版本）
2. 评估冲突的影响（哪个版本最终会被 Maven 解析使用）
3. 给出具体的排除方案（pom.xml 中 <exclusions> 的配置）
4. 如果有已知的安全漏洞版本，请标注 CVE 编号

[INFO] +- org.springframework.boot:spring-boot-starter-web:2.7.14:compile
[INFO] |  +- com.fasterxml.jackson.core:jackson-databind:2.13.5:compile
[INFO] |  |  +- com.fasterxml.jackson.core:jackson-annotations:2.13.5:compile
[INFO] |  |  \- com.fasterxml.jackson.core:jackson-core:2.13.5:compile
[INFO] +- com.alibaba:fastjson:1.2.83:compile
[INFO] +- org.redisson:redisson-spring-boot-starter:3.23.4:compile
[INFO] |  \- com.fasterxml.jackson.core:jackson-databind:2.15.2:compile
[INFO] |     +- com.fasterxml.jackson.core:jackson-annotations:2.15.2:compile
[INFO] |     \- com.fasterxml.jackson.core:jackson-core:2.15.2:compile
[INFO] +- com.google.guava:guava:30.1.1-jre:compile
[INFO] +- org.apache.shiro:shiro-spring:1.11.0:compile
[INFO] |  \- com.google.guava:guava:19.0:compile
```

**AI 输出（比你自己分析省 30 分钟）：**

```text
【依赖冲突分析报告】

🔴 冲突1: jackson-databind（严重）
    - spring-boot-starter-web 引入: 2.13.5
    - redisson 引入: 2.15.2
    - Maven 最终使用: 2.13.5（就近原则，spring-boot 更近）
    - 影响: redisson 依赖 2.15.2 的新增方法可能找不到 → NoSuchMethodError
    - 修复方案:
      <dependency>
        <groupId>org.redisson</groupId>
        <artifactId>redisson-spring-boot-starter</artifactId>
        <exclusions>
          <exclusion>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
          </exclusion>
        </exclusions>
      </dependency>

🔴 冲突2: guava（严重）
    - 主项目引入: 30.1.1-jre
    - shiro-spring 引入: 19.0
    - Maven 最终使用: 30.1.1-jre
    - 影响: shiro 调用 guava 19.0 的 API，可能不存在于 30.x
    - CVE 提醒: guava 19.0 存在 CVE-2020-8908，建议强制升级
    - 修复方案:
      在 shiro-spring 中排除 guava，统一使用 30.1.1-jre

🟡 风险点: fastjson 1.2.83
    - 已知漏洞版本，建议升级至 fastjson2 或替换为 jackson
    - CVE-2022-25845 反序列化漏洞，CVSS 9.8

推荐在 pom.xml 中统一版本管理:
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.fasterxml.jackson</groupId>
            <artifactId>jackson-bom</artifactId>
            <version>2.15.2</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
        <dependency>
            <groupId>com.google.guava</groupId>
            <artifactId>guava</artifactId>
            <version>32.1.3-jre</version>
        </dependency>
    </dependencies>
</dependencyManagement>
```

**实战价值：** 我上次排查一个 `NoSuchMethodError`，自己翻依赖树翻了 40 分钟。现在把 `dependency-tree.txt` 往 Cursor 里一扔，15 秒出结果——**连 `<exclusions>` 标签都给写好了，直接复制粘贴。**

## 技巧八：AI 辅助 SSH 连接和端口转发命令

> **难度：** 🟡 进阶玩家 &nbsp;&nbsp;|&nbsp;&nbsp; **效率提升：** 运维命令编写时间减少 **90%**

**痛点：** 你需要在本地调试远程服务器上的生产环境数据，但只能通过跳板机访问。SSH 端口转发命令每次都要查 man page，`-L` `-R` `-D` 永远记不住。

**解法：** 用自然语言描述需求，让 AI 生成精确命令。

**常见实战场景：**

```text
# 场景1：通过跳板机连接到目标服务器的MySQL
我本地 Mac，需要通过跳板机(bastion.example.com, 用户ops) 
连接到目标服务器(10.0.1.100)上的MySQL(端口3306)。
请生成SSH隧道命令，让本地3307转发到目标MySQL的3306。
```

AI 生成：

```bash
# Step 1: 建立SSH隧道（保持这个终端窗口开着）
ssh -L 3307:10.0.1.100:3306 ops@bastion.example.com -N -v

# Step 2: 在另一个终端连接MySQL（用本地3307端口）
mysql -h 127.0.0.1 -P 3307 -u your_username -p

# 参数说明：
# -L 3307:10.0.1.100:3306  本地3307 → 跳板机 → 目标机3306
# -N  不执行远程命令，仅做端口转发
# -v  显示详细日志，方便排查连接问题
```

```text
# 场景2：通过跳板机 SSH 连接到内网服务器
我需要通过跳板机(bastion, 用户admin) SSH连接到内网服务器
(192.168.1.50, 用户app)。请生成 ~/.ssh/config 配置。
```

AI 生成：

```bash
# 编辑 ~/.ssh/config，添加以下内容：
Host bastion
    HostName bastion.example.com
    User admin
    Port 22
    IdentityFile ~/.ssh/id_rsa

Host internal-app
    HostName 192.168.1.50
    User app
    Port 22
    ProxyJump bastion           # ← 关键配置！通过跳板机跳转
    IdentityFile ~/.ssh/id_rsa
    ServerAliveInterval 60      # 保持连接活跃，防止超时断开
```

配置完成后，直接 `ssh internal-app` 即可一键连接到内网服务器。

## 技巧九：用 AI 生成数据库 Mock 数据

> **难度：** 🟡 进阶玩家 &nbsp;&nbsp;|&nbsp;&nbsp; **效率提升：** Mock 数据生成速度快 **50 倍**（手写100条要20分钟，AI生成100万条只要3秒）

**痛点：** 压测需要数据，演示需要数据，开发联调需要数据。手写 INSERT 语句？100 万条写到天荒地老。用 Python 脚本？还得学 Faker 库的 API。找 DBA 要脱敏数据？排期一周起步。

**解法：** 把建表 DDL 扔给 AI，让它生成 SQL 和 Java 代码双方案。

要求10万条数据，符合真实业务规律。

DDL:
CREATE TABLE `t_order` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `order_no` varchar(32) NOT NULL COMMENT '订单号',
  `user_id` bigint NOT NULL COMMENT '用户ID',
  `product_id` bigint NOT NULL COMMENT '商品ID',
  `quantity` int NOT NULL DEFAULT 1 COMMENT '购买数量',
  `amount` decimal(10,2) NOT NULL COMMENT '订单金额',
  `status` tinyint NOT NULL DEFAULT 0 COMMENT '状态: 0待支付 1已支付 2已发货 3已完成 4已取消',
  `pay_channel` tinyint DEFAULT NULL COMMENT '支付方式: 1微信 2支付宝 3银行卡',

1. 生成 10 万条INSERT语句（分10批次，每批10000条，方便执行）
2. user_id 范围 1-50000（模拟5万用户，符合28原则：20%用户产生80%订单）

**进阶方案 —— 用 Java 代码生成（更适合大数据量）：**

```java
/**
 * Mock 数据生成器：使用多线程批量插入，支持 100万+ 数据量
 * 
 * Prompt: "根据 t_order 表结构生成一个 Java 批量插入器，
 *         使用 CompletableFuture 多线程，每批 5000 条，
 *         数据规则同上。同时生成对应的 application.yml 配置。"
 */
@Component
@Slf4j
public class OrderDataGenerator {

    private static final int TOTAL_RECORDS = 1_000_000;
    private static final int BATCH_SIZE = 5000;
    private static final int THREAD_COUNT = 8;
    private static final ThreadLocalRandom RANDOM = ThreadLocalRandom.current();

    @Autowired
    private JdbcTemplate jdbcTemplate;

    @PostConstruct
    public void generate() {
        log.info("开始生成 {} 条 Mock 数据，线程数: {}", TOTAL_RECORDS, THREAD_COUNT);

        List<CompletableFuture<Void>> futures = IntStream.range(0, THREAD_COUNT)
                .mapToObj(threadId -> CompletableFuture.runAsync(() -> {
                    int recordsPerThread = TOTAL_RECORDS / THREAD_COUNT;
                    List<Object[]> batch = new ArrayList<>(BATCH_SIZE);

                    for (int i = 0; i < recordsPerThread; i++) {
                        batch.add(buildOrderRow(threadId, i));
                        if (batch.size() >= BATCH_SIZE) {
                            jdbcTemplate.batchUpdate(
                                "INSERT INTO t_order (order_no, user_id, product_id, " +
                                "quantity, amount, status, pay_channel, created_at, updated_at) " +
                                "VALUES (?,?,?,?,?,?,?,?,?)", batch
                            );
                            batch.clear();
                        }
                    }
                    // 处理最后一批
                    if (!batch.isEmpty()) {
                        jdbcTemplate.batchUpdate("INSERT INTO t_order ...", batch);
                    }
                }))
                .collect(Collectors.toList());

        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
        log.info("Mock 数据生成完毕，共 {} 条", TOTAL_RECORDS);
    }

    private Object[] buildOrderRow(int threadId, int seq) {
        long userId = generateUserId();  // 28原则分布
        String orderNo = String.format("ORD%s%06d%03d",
                LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE),
                threadId, seq);
        return new Object[]{
            orderNo,
            userId,
            RANDOM.nextLong(1, 5000),
            RANDOM.nextInt(1, 10),
            generateAmount(),       // 长尾分布
            generateStatus(),       // 按比例分布
            generatePayChannel(),
            generateCreatedAt(),    // 集中晚上8-10点
            generateUpdatedAt()
        };
    }

    private Long generateUserId() {
        // 28原则：20%用户（1-10000）产生80%订单
        return RANDOM.nextDouble() < 0.8
                ? RANDOM.nextLong(1, 10001)       // 80%订单 → 高活跃用户
                : RANDOM.nextLong(10001, 50001);  // 20%订单 → 低活跃用户
    }

    private LocalDateTime generateCreatedAt() {
        LocalDateTime base = LocalDateTime.now().minusDays(RANDOM.nextLong(0, 90));
        // 40% 的概率在晚8-10点下单
        if (RANDOM.nextDouble() < 0.4) {
            return base.withHour(RANDOM.nextInt(20, 23))
                       .withMinute(RANDOM.nextInt(0, 60))
                       .withSecond(RANDOM.nextInt(0, 60));
        }
        return base.withHour(RANDOM.nextInt(8, 24))
                   .withMinute(RANDOM.nextInt(0, 60))
                   .withSecond(RANDOM.nextInt(0, 60));
    }

    private Integer generateStatus() {
        double rand = RANDOM.nextDouble();
        if (rand < 0.10) return 0;  // 待支付 10%
        if (rand < 0.45) return 1;  // 已支付 35%
        if (rand < 0.50) return 2;  // 已发货 5%
        if (rand < 0.80) return 3;  // 已完成 30%
        return 4;                    // 已取消 20%
    }
}
```

## 技巧十：让 AI 帮你回复 Code Review 评论

> **难度：** 🟢 新手友好 &nbsp;&nbsp;|&nbsp;&nbsp; **效率提升：** Code Review 回复时间减少 **70%**，回复质量提升 **50%**

**痛点：** CR 时收到一条评论："这里为什么用 `HashMap` 而不是 `ConcurrentHashMap`？有没有考虑并发安全问题？" 你心里想的是"这里确实没考虑到"，但回复不能只写"好的我改"——显得很业余。

**解法：** 把 CR 评论和你的代码片段一起喂给 AI，让它生成有技术含量的回复。

**示例 1 —— 承认问题并给出改进方案：**

```text
我收到了以下Code Review评论，帮我写一个专业的回复，语气要诚恳、有技术含量：

Reviewer评论：
"这里用HashMap来缓存用户信息，但getUserInfo接口QPS超过5000，
HashMap在并发场景下可能导致死循环(cpu100%)。建议用ConcurrentHashMap或Caffeine。"

我的代码片段：
private static final Map<String, UserInfo> USER_CACHE = new HashMap<>();

我的真实想法：确实没考虑并发，愿意改，想用Caffeine。
```

AI 生成回复：

```text
@reviewer 感谢指出，非常有价值。确实忽略了这个方法的并发调用场景：

1. 问题确认：getUserInfo 对外暴露为 REST 接口，实际线上 QPS ~5000，
   HashMap 在并发 rehash 时确实存在死循环风险（JDK7 更严重，JDK8 转为
   红黑树后概率降低但依然存在数据丢失问题）

2. 修复方案：改为 Caffeine Cache，原因有三：
   - 支持过期策略（用户信息 TTL 5 分钟），避免内存泄漏
   - 支持最大容量限制（maxSize=10000），防止 OOM
   - 内部基于 ConcurrentHashMap，天然线程安全

3. 已在 commit a3f2b1c 中修复，麻烦再看一下：

```java
private static final Cache<String, UserInfo> USER_CACHE = Caffeine.newBuilder()
        .expireAfterWrite(5, TimeUnit.MINUTES)
        .maximumSize(10_000)
        .recordStats()
        .build();
```

另外补充了 Guava 的 @Beta 标注提醒后续维护者注意线程安全。再次感谢！
```

**示例 2 —— 有理有据地反对：**

```text
Reviewer评论：
"建议把这个for循环改成Java 8 Stream，更现代。"

我的想法：不想改，因为循环内有checked exception需要用try-catch包裹，
Stream里不好处理，而且这里只有3个元素，可读性比Stream好。
```

AI 生成回复：

```text
@reviewer 好建议，我考虑过用 Stream 写法，但评估后选择保留 for 循环：

1. 循环内有 3 处 SQLException（checked exception），Stream 的 lambda 
   不支持 checked exception，需要额外包装一个 @FunctionalInterface 或
   用 RuntimeException 包裹，反而降低可读性

2. 这段逻辑只遍历 3 个元素（3 种支付渠道），性能差异可忽略

3. 当前写法允许 early return（找到可用渠道后立即 break），
   Stream 的 findFirst() 虽然也支持短路，但结合 try-catch 后代码反而不直观

如果你觉得有其他更好的处理 checked exception 的方式，欢迎再讨论 🙏
```

**核心要点：** AI 生成的回复不是让你直接复制粘贴，而是给你一个**技术讨论的框架和措辞参考**。你把技术观点填进去，比直接写"好的我改"或"我不改"专业 10 倍。

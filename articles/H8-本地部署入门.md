## 引言：本地部署的本质

本地部署（Local Deployment）不是简单的"把模型下载到电脑上运行"，而是一门**在资源约束下最大化推理效率**的系统工程。

核心认知：

```
LLM推理的本质：自回归生成
  P(y_t | y_<t, x) = softmax(W * hidden_state_t)

本地部署的本质：在有限算力/显存/功耗约束下，
                      通过量化、剪枝、缓存优化等手段，
                      使模型在消费级硬件上达到可用推理速度

质量差异的根源：
- 差的部署：全精度加载，显存爆炸，推理速度<1 token/s
- 好的部署：4-bit量化+KV Cache优化+批处理，推理速度>20 token/s
```

**关键洞察**：本地部署的效果不取决于"模型有多大"，而取决于**推理栈的优化程度**是否匹配硬件能力。

## 理论基础：模型量化与推理优化

### Transformer推理的数学本质

#### 自回归生成的计算流程

```python
# Transformer推理核心计算（简化版）
def transformer_inference(token_ids, model_weights):
    hidden_states = model_weights.embed(token_ids)  # [seq_len, hidden_dim]
    
    for layer in model_weights.layers:
        # 自注意力
        Q = hidden_states @ layer.W_q
        K = hidden_states @ layer.W_k
        V = hidden_states @ layer.W_v
        
        scores = Q @ K.T / np.sqrt(layer.head_dim)
        attn_weights = softmax(scores)
        attn_output = attn_weights @ V
        
        # FFN前馈网络
        ffn_output = gelu(hidden_states @ layer.W_1) @ layer.W_2
        
        # 残差连接 + LayerNorm
        hidden_states = layer_norm(hidden_states + attn_output + ffn_output)
    
    logits = hidden_states @ model_weights.lm_head
    next_token_probs = softmax(logits[-1])
    
    return next_token_probs
```

**关键理解**：
- 每次生成新token，都需要完整的Transformer前向传播
- 计算量与模型参数量成正比（7B模型 ≈ 140亿次浮点运算/层）
- 内存带宽是瓶颈（加载权重比计算更耗时）

#### KV Cache：避免重复计算的关键

```
朴素推理（无KV Cache）：
生成第1个token：计算所有层的Q,K,V（全序列）
生成第2个token：重新计算所有层的Q,K,V（全序列+新token）
生成第N个token：重新计算所有层的Q,K,V（全序列+N个新token）
复杂度：O(N^2 * d * L)  —— 随序列长度平方增长

优化推理（有KV Cache）：
生成第1个token：计算所有层的Q,K,V，缓存K,V
生成第2个token：只计算新token的Q，用缓存的K,V
生成第N个token：只计算新token的Q，用缓存的K,V
复杂度：O(N * d * L)  —— 随序列长度线性增长
```

```python
# KV Cache核心实现
class KVCache:
    def __init__(self, num_layers, num_heads, head_dim, max_seq_len):
        self.k_cache = np.zeros((num_layers, max_seq_len, num_heads, head_dim))
        self.v_cache = np.zeros((num_layers, max_seq_len, num_heads, head_dim))
        self.cache_len = 0
    
    def update(self, layer_idx, new_k, new_v):
        self.k_cache[layer_idx, self.cache_len] = new_k
        self.v_cache[layer_idx, self.cache_len] = new_v
    
    def get(self, layer_idx):
        return self.k_cache[layer_idx, :self.cache_len], \
               self.v_cache[layer_idx, :self.cache_len]
    
    def increment(self):
        self.cache_len += 1
```

**工程启示**：
- KV Cache显存占用 = 2 * num_layers * max_seq_len * num_heads * head_dim * sizeof(dtype)
- 7B模型，4096上下文，FP16：约 2 * 32 * 4096 * 32 * 128 * 2B = 2.1GB
- 上下文长度翻倍 → KV Cache翻倍 → 显存压力剧增

### 模型量化技术详解

#### 量化原理：从高精度到低精度

```
量化的数学本质：

原始权重：w ∈ R（FP32，32位浮点）
量化后权重：w_q = round((w - z) / s)

其中：
- s（scale）：缩放因子 = (max(w) - min(w)) / (2^n - 1)
- z（zero_point）：零点 = round(-min(w) / s)
- n：量化位数（8位、4位等）

反量化：w ≈ w_q * s + z
```

```python
# 简单量化演示
import numpy as np

def quantize_tensor(tensor, n_bits=8):
    max_val = np.max(np.abs(tensor))
    scale = max_val / (2**(n_bits-1) - 1)
    quantized = np.round(tensor / scale).astype(np.int8 if n_bits==8 else np.int32)
    return quantized, scale

def dequantize_tensor(quantized, scale):
    return quantized.astype(np.float32) * scale

# 示例
weights = np.random.randn(4096, 4096).astype(np.float32)
q_w, scale = quantize_tensor(weights, n_bits=8)
reconstructed = dequantize_tensor(q_w, scale)

print(f"FP32大小: {weights.nbytes / 1024 / 1024:.2f} MB")
print(f"INT8大小: {q_w.nbytes / 1024 / 1024:.2f} MB")
print(f"压缩比: {weights.nbytes / q_w.nbytes:.1f}x")
print(f"MSE: {np.mean((weights - reconstructed)**2):.6f}")
```

**GPTQ（Post-Training Quantization）**：

```python
"""
GPTQ核心思想：逐层量化，用Hessian矩阵补偿误差

1. 对每一层的权重矩阵W，计算Hessian矩阵H = X^T * X
   （X是该层的输入激活）

2. 按列（或块）逐块量化：
   for each column block:
       quantize_block(W_block)
       error = W_block - dequantized(W_block)
       W_remaining -= error * H_inv_remaining

3. 关键洞察：利用权重矩阵的列间相关性，
   将当前块的量化误差传播到后续块进行补偿
"""

from auto_gptq import AutoGPTQForCausalLM, BaseQuantizeConfig

quantize_config = BaseQuantizeConfig(bits=4, group_size=128, desc_act=False)
model = AutoGPTQForCausalLM.from_pretrained("meta-llama/Llama-2-7b", quantize_config=quantize_config)

# 准备校准数据（通常128-256条）
calibration_data = ["示例文本1", "示例文本2", "..."]
model.quantize(calibration_data)
model.save_quantized("./llama-2-7b-4bit-gptq")
```

**AWQ（Activation-aware Weight Quantization）**：

```python
"""
AWQ核心洞察：
- 不是所有权重都同等重要
- 保护1%的"重要权重"（基于激活幅度），量化其余99%
- 通过逐通道缩放保护重要权重
"""

model = AutoAWQForCausalLM.from_pretrained("meta-llama/Llama-2-7b", use_cache=False)

```

**GGUF格式（llama.cpp原生）**：

```
GGUF量化方案详解：

Q4_0：4-bit，per-block缩放，最小尺寸
Q4_K_M：4-bit，混合精度（重要层用更高精度）
Q5_K_M：5-bit，平衡方案
Q6_K：6-bit，高精度
Q8_0：8-bit，接近无损

量化质量排序：Q8_0 > Q6_K > Q5_K_M > Q4_K_M > Q4_0
尺寸排序（反向）：Q4_0 < Q4_K_M < Q5_K_M < Q6_K < Q8_0
```

### 推理优化核心技术

#### FlashAttention：减少内存访问瓶颈

```
标准注意力的问题：
- 需要显式存储 N x N 的注意力矩阵
- 显存访问：O(N^2)，HBM带宽成为瓶颈

FlashAttention的核心思想：
- 分块计算（Tiling），避免存储完整的注意力矩阵
- 在线softmax：不需要等所有分数计算完
- IO感知：最大化SRAM利用率，最小化HBM访问

复杂度对比：
标准Attention：HBM访问 = O(N^2)，显存 = O(N^2)
FlashAttention：HBM访问 = O(N)，显存 = O(N)
```

```python
# FlashAttention伪代码（简化版）
def flash_attention(Q, K, V, block_size=64):
    N = Q.shape[0]
    O = zeros_like(Q)
    l = zeros(N)
    m = -inf * ones(N)
    
    for j in range(0, N, block_size):
        Kj = K[j:j+block_size]
        Vj = V[j:j+block_size]
        
        for i in range(0, N, block_size):
            Qi = Q[i:i+block_size]
            Sij = Qi @ Kj.T
            
            # 在线softmax更新
            mij = max(Sij, axis=1)
            Pij = exp(Sij - mij)
            lij = sum(Pij, axis=1)
            
            mi_new = max(m[i:i+block_size], mij)
            li_new = exp(m[i:i+block_size] - mi_new) * l[i:i+block_size] + \
                     exp(mij - mi_new) * lij
            
            O[i:i+block_size] = (O[i:i+block_size] * 
                                exp(m[i:i+block_size] - mi_new) * 
                                l[i:i+block_size][:, None] + 
                                Pij @ Vj * exp(mij - mi_new)[:, None]) / \
                               li_new[:, None]
            
            m[i:i+block_size] = mi_new
            l[i:i+block_size] = li_new
    
    return O
```

#### 批处理（Batching）与连续批处理（Continuous Batching）

```
静态批处理的问题：
请求A：生成100 tokens
请求B：生成10 tokens
请求C：生成50 tokens

如果使用静态批处理：
- 必须等所有请求完成才能处理下一批
- 请求B完成后，仍需等待A和C（GPU利用率低）

连续批处理（Continuous Batching / Inflight Batching）：
- 请求B完成后，立即将新的请求D加入当前批次
- 最大化GPU利用率
- vLLM和TensorRT-LLM支持
```

```python
# 连续批处理概念演示
class ContinuousBatcher:
    def __init__(self, max_batch_size=8):
        self.max_batch_size = max_batch_size
        self.active_requests = []
        self.kv_cache_pool = {}
    
    def add_request(self, request):
        if len(self.active_requests) < self.max_batch_size:
            self.active_requests.append(request)
            self.kv_cache_pool[request.id] = allocate_kv_cache()
            return True
        return False
    
    def step(self):
        outputs = self.model.forward_batch(self.active_requests)
        
        completed = []
        for req, output in zip(self.active_requests, outputs):
            req.append_token(output)
            req.update_kv_cache()
            if req.is_finished():
                completed.append(req)
        
        for req in completed:
            self.active_requests.remove(req)
            free(self.kv_cache_pool[req.id])
            del self.kv_cache_pool[req.id]
        
        return completed
```

```
2018-2020年：
- 研究者使用PyTorch/TensorFlow直接加载模型

```

影响：
- 让7B模型在MacBook上流畅运行

- 催生了后续的Ollama等项目

## 模型部署实战

### 硬件需求分析

```
显存需求计算公式：

总显存 = 模型权重 + KV Cache + 激活值 + 系统开销

1. 模型权重（FP16）
   7B模型 ≈ 14GB
   13B模型 ≈ 26GB
   70B模型 ≈ 140GB

2. 4-bit量化后
   7B模型 ≈ 3.5-4GB
   13B模型 ≈ 6.5-7.5GB
   70B模型 ≈ 35-40GB

3. KV Cache（FP16）
   每token = 2 * num_layers * num_heads * head_dim * 2 bytes
   7B模型(LLaMA) = 2 * 32 * 32 * 128 * 2 = 524,288 bytes ≈ 0.5 MB/token
   
   4096上下文 = 4096 * 0.5 MB = 2GB
   8192上下文 = 8192 * 0.5 MB = 4GB
   32768上下文 = 32768 * 0.5 MB = 16GB

4. 激活值（batch=1时较小）
   约 1-2GB

5. 系统开销
   CUDA上下文等 ≈ 1-2GB

实际显存需求（4-bit量化）：
┌─────────────────┬──────────┬──────────┬──────────┐
│     模型        │  基础    │ 4K上下文 │ 8K上下文 │
├─────────────────┼──────────┼──────────┼──────────┤
│ 7B (Q4_K_M)     │   4GB    │   7GB    │  10GB    │
│ 13B (Q4_K_M)    │   8GB    │  11GB    │  15GB    │
│ 70B (Q4_K_M)    │  40GB    │  43GB    │  47GB    │
│ 7B (Q8_0)       │   7GB    │  10GB    │  13GB    │
└─────────────────┴──────────┴──────────┴──────────┘

CPU内存需求：
- 通常需要模型权重的2-3倍（用于加载和缓存）
- 7B Q4模型：建议16GB系统内存
- 70B Q4模型：建议64GB+系统内存

磁盘需求：
- 7B Q4模型：约4GB
- 70B Q4模型：约40GB
- 建议预留模型大小3倍的磁盘空间

推理速度参考（tokens/秒）：

NVIDIA RTX 4090 (24GB VRAM)：
- 7B Q4_K_M: 80-120 t/s
- 13B Q4_K_M: 50-80 t/s
- 70B Q4_K_M: 10-15 t/s

NVIDIA RTX 3060 (12GB VRAM)：
- 7B Q4_K_M: 30-50 t/s
- 13B Q4_K_M: 15-25 t/s

Apple M3 Max (36GB unified)：
- 7B Q4_K_M: 40-60 t/s

- 7B Q4_K_M: 5-10 t/s

# 思考链提取（Python）
import re

def extract_think_chain(response):
    """提取DeepSeek-R1的思考过程"""
    think_match = re.search(r'<think>(.*?)</think>', response, re.DOTALL)
    if think_match:
        think_content = think_match.group(1).strip()
        final_answer = re.sub(r'<think>.*?</think>', '', response, flags=re.DOTALL).strip()
        return think_content, final_answer
    return None, response
```

import requests
import json

def stream_generate(prompt, model='qwen3:8b', temperature=0.7):
    """流式生成，实时显示token"""
    url = "http://localhost:11434/api/generate"
    
    data = {
        "model": model,
        "prompt": prompt,
        "stream": True,
        "options": {"temperature": temperature}
    }
    
    start_time = time.time()
    token_count = 0
    full_response = []
    
    print("AI: ", end='', flush=True)
    
    with requests.post(url, json=data, stream=True) as response:
        for line in response.iter_lines():
            if line:
                try:
                    chunk = json.loads(line)
                    token = chunk.get('response', '')
                    print(token, end='', flush=True)
                    full_response.append(token)
                    token_count += 1
                    
                    if chunk.get('done', False):
                        break
                except json.JSONDecodeError:
                    continue
    
    elapsed = time.time() - start_time
    print(f"\n\n[统计] 生成{token_count}个token，耗时{elapsed:.2f}s，速度{token_count/elapsed:.1f} t/s")
    
    return ''.join(full_response)

# 量化策略决策树

def choose_quantization(model_size, vram_gb, priority="balanced"):
    """
    根据硬件条件选择最优量化策略
    
    Args:
        model_size: 模型参数量（B）
        vram_gb: 可用显存（GB）
        priority: "speed", "quality", "balanced"
    """
    
    quant_options = {
        "Q4_0": model_size * 0.5,
        "Q4_K_M": model_size * 0.55,
        "Q5_K_M": model_size * 0.7,
        "Q6_K": model_size * 0.8,
        "Q8_0": model_size * 1.0,
        "FP16": model_size * 2.0
    }
    
    if priority == "speed":
        for quant, size in sorted(quant_options.items(), key=lambda x: x[1]):
            if size < vram_gb * 0.8:
                return quant
    
    elif priority == "quality":
        for quant, size in sorted(quant_options.items(), key=lambda x: -x[1]):
            if size < vram_gb * 0.7:
                return quant
    
    else:  # balanced
        target_size = vram_gb * 0.75
        best_quant = "Q4_K_M"
        best_diff = abs(quant_options["Q4_K_M"] - target_size)
        
        for quant, size in quant_options.items():
            if size < vram_gb * 0.8:
                diff = abs(size - target_size)
                if diff < best_diff:
                    best_diff = diff
                    best_quant = quant
        
        return best_quant
    
    return "Q4_K_M"

# 使用示例
print(choose_quantization(7, 8, "balanced"))    # Q5_K_M
print(choose_quantization(14, 12, "balanced"))  # Q4_K_M
print(choose_quantization(70, 48, "quality"))   # Q5_K_M

def monitor_gpu_during_inference(prompt, model='qwen3:8b', duration=30):
    """监控推理过程中的GPU使用情况"""
    import threading
    
    gpu_stats = []
    
    def collect_gpu_stats():
        start = time.time()
        while time.time() - start < duration:
            result = subprocess.run(
                ['nvidia-smi', '--query-gpu=utilization.gpu,memory.used,temperature.gpu', 
                 '--format=csv,noheader,nounits'],
                capture_output=True, text=True
            )
            if result.returncode == 0:
                util, mem, temp = result.stdout.strip().split(', ')
                gpu_stats.append({
                    'time': time.time() - start,
                    'gpu_util': float(util),
                    'memory_mb': float(mem),
                    'temperature': float(temp)
                })
            time.sleep(0.5)
    
    monitor_thread = threading.Thread(target=collect_gpu_stats)
    monitor_thread.start()
    
    # 执行推理
    import requests
    requests.post('http://localhost:11434/api/generate',
                 json={'model': model, 'prompt': prompt, 'stream': False})
    
    monitor_thread.join()
    
    if gpu_stats:
        avg_util = sum(s['gpu_util'] for s in gpu_stats) / len(gpu_stats)
        max_mem = max(s['memory_mb'] for s in gpu_stats)
        max_temp = max(s['temperature'] for s in gpu_stats)
        
        print(f"平均GPU利用率: {avg_util:.1f}%")
        print(f"最大显存使用: {max_mem:.0f} MB")
        print(f"最高温度: {max_temp:.1f}°C")

# 动态上下文管理
import math

class DynamicContextManager:
    """根据可用显存动态调整上下文长度"""
    
    def __init__(self, model_name, base_vram_gb):
        self.model_name = model_name
        self.base_vram_gb = base_vram_gb
        self.model_size_gb = self._get_model_size()
        
    def _get_model_size(self):
        sizes = {
            'qwen3:8b': 4.5, 'qwen3:14b': 8.0,
            'llama3.1:8b': 4.5, 'deepseek-r1:14b': 8.0
        }
        return sizes.get(self.model_name, 5.0)
    
    def calculate_max_context(self, safety_margin=0.8):
        """计算最大安全上下文长度"""
        available_vram = self.base_vram_gb * safety_margin
        kv_cache_vram = available_vram - self.model_size_gb
        
        # 假设：32层，32头，128维度（7B/8B模型典型配置）
        kv_per_token_mb = 2 * 32 * 32 * 128 * 2 / (1024 * 1024)  # 约0.5 MB/token
        
        max_context = int(kv_cache_vram * 1024 / kv_per_token_mb)
        max_context = min(max_context, 128000)
        max_context = max(max_context, 2048)
        max_context = 2 ** int(math.log2(max_context))
        
        return max_context
    
    def create_optimized_model(self):
        """创建优化配置的模型"""
        max_ctx = self.calculate_max_context()
        
        modelfile = f"""
FROM {self.model_name}
PARAMETER num_ctx {max_ctx}
PARAMETER num_predict {min(max_ctx // 2, 4096)}
"""
        return modelfile

# 使用
manager = DynamicContextManager('qwen3:8b', 12)
print(f"最大安全上下文: {manager.calculate_max_context()}")
print(manager.create_optimized_model())

## 陷阱1：忽视KV Cache显存占用

症状：
- 模型加载成功，但运行一段时间后OOM
- 长对话时突然崩溃

原因：

- 模型输出质量差，逻辑混乱
- 代码生成错误率高

### 1. 模型量化的原理是什么？INT4和INT8量化的主要区别？

**参考答案：**

```
量化原理：
将高精度浮点数（FP32/FP16）映射到低精度整数（INT8/INT4），减少存储和计算开销。

数学公式：
q = round((r - z) / s)
r ≈ q * s + z

其中：
- r：原始浮点值
- q：量化后的整数值
- s：缩放因子（scale）
- z：零点（zero-point）

INT8 vs INT4 对比：

┌─────────────┬──────────┬──────────┬──────────┬──────────┐
│   特性      │  INT8    │  INT4    │   优势   │  劣势    │
├─────────────┼──────────┼──────────┼──────────┼──────────┤
│ 精度        │ 256级    │ 16级     │ 更高     │ 更低     │
│ 压缩比      │ 4x       │ 8x       │ 较小     │ 更大     │
│ 显存占用    │ 大       │ 小       │ 质量高   │ 速度快   │
│ 适用场景    │ 高精度   │ 大模型   │ 代码/数学│ 日常对话 │
│ 量化误差    │ 小       │ 大       │ 更准确   │ 更省显存 │
└─────────────┴──────────┴──────────┴──────────┴──────────┘

工程建议：
- 7B模型：INT8或Q5_K_M（平衡）
- 70B模型：INT4或Q4_K_M（必需）
- 代码/数学：INT8或Q8_0（精度优先）
```

### 2. KV Cache的作用是什么？如果不使用KV Cache，推理复杂度如何变化？

**参考答案：**

```
KV Cache的作用：
缓存Transformer每层attention中的Key和Value矩阵，避免重复计算。

原理：
在自回归生成中，生成第N个token时：
- 需要计算当前token与所有历史token的注意力
- 历史token的K,V是固定的（已经生成）
- 如果不用Cache，每次都要重新计算所有历史token的K,V

复杂度对比：

无KV Cache：
- 生成第t个token：计算1..t的所有K,V
- 时间：O(t * d^2) 每层
- 总时间：Σ(t=1 to n) O(t * d^2) = O(n^2 * d^2)
- 空间：O(1)（不缓存）

有KV Cache：
- 生成第t个token：只计算当前token的Q，用缓存的K,V
- 时间：O(d^2) 每层
- 总时间：Σ(t=1 to n) O(d^2) = O(n * d^2)
- 空间：O(n * d) 每层（缓存K,V）

关键洞察：
KV Cache将时间复杂度从O(n^2)降到O(n)，
以空间换时间，是长文本生成的关键优化。

显存占用计算：
KV Cache = 2 * num_layers * seq_len * hidden_dim * sizeof(dtype)

示例（Llama 2 7B）：
- 32层，4096隐藏维度，4096上下文，FP16
- KV Cache = 2 * 32 * 4096 * 4096 * 2B = 2.1GB
```

### 6. 解释FlashAttention的原理，为什么它能加速推理？

**参考答案：**

```
FlashAttention核心思想：

标准Attention的问题：
1. 显存访问瓶颈：
   - 需要存储N×N的注意力矩阵（O(N^2)显存）
   - HBM（高带宽内存）带宽有限
   - 计算速度受限于内存读写，而非计算单元

2. 分块计算（Tiling）：
   - 将Q,K,V分成小块（tile）
   - 在SRAM（高速缓存）中完成计算
   - 避免存储完整的注意力矩阵

3. 在线Softmax：
   - 不需要等所有分数计算完再softmax
   - 逐步更新softmax的统计量（最大值、求和）
   - 减少内存访问

算法流程：
for each block of K, V:
    load Kj, Vj to SRAM
    for each block of Q:
        load Qi to SRAM
        compute Sij = Qi * Kj^T
        update online softmax stats
        compute partial output
    accumulate output

复杂度对比：
- 标准Attention：HBM访问 = O(N^2)
- FlashAttention：HBM访问 = O(N)

实际加速：
- 长序列（>2K）加速2-4x
- 显存节省：不需要存储注意力矩阵
- 特别适合长文本推理

局限性：
- 需要GPU支持（CUDA核心）
- 短序列收益不明显
- 实现复杂度高
```

### 7. 如何评估本地部署模型的性能？有哪些关键指标？

**参考答案：**

```
性能评估指标体系：

1. 速度指标：
   - Tokens/s（token生成速度）
   - TTFT（Time To First Token，首token延迟）
   - TPOT（Time Per Output Token，每token耗时）
   - 吞吐量（requests/s 或 tokens/s）

2. 质量指标：
   - Perplexity（困惑度）
   - BLEU/ROUGE（文本生成质量）
   - 人类评估（有用性、准确性）
   - 特定任务指标（代码通过率、数学准确率）

3. 资源指标：
   - 显存占用（GB）
   - GPU利用率（%）
   - 内存带宽（GB/s）
   - 功耗（W）

4. 稳定性指标：
   - 并发处理能力
   - 长时间运行稳定性
   - OOM频率

评估脚本示例：
```python
import time
import requests
import statistics

def benchmark(model, prompts, warmup=3):
    # 预热
    for _ in range(warmup):
        requests.post('http://localhost:11434/api/generate',
                     json={'model': model, 'prompt': 'hi', 'stream': False})
    
    ttfts = []
    tokens_per_sec = []
    
    for prompt in prompts:
        start = time.time()
        response = requests.post('http://localhost:11434/api/generate',
                                json={'model': model, 'prompt': prompt, 'stream': False})
        elapsed = time.time() - start
        
        data = response.json()
        tokens = data.get('eval_count', 0)
        
        # 估算TTFT
        ttft = elapsed / tokens * 2 if tokens > 0 else elapsed
        tps = tokens / elapsed if elapsed > 0 else 0
        
        ttfts.append(ttft)
        tokens_per_sec.append(tps)
    
    return {
        'avg_ttft': statistics.mean(ttfts),
        'avg_tokens_per_sec': statistics.mean(tokens_per_sec),
        'std_tps': statistics.stdev(tokens_per_sec) if len(tokens_per_sec) > 1 else 0
    }
```

### 8. 在本地部署中，如何处理长文本（>32K上下文）？

**参考答案：**

```
长文本处理策略：

1. 模型选择：
   - 选择原生支持长上下文的模型
   - GLM-4-9B-1M（1M上下文）
   - Qwen3（128K上下文）
   - Llama 3.1（128K上下文）

2. 显存优化：
   - 使用Q4_K_M量化（减少50%显存）
   - 梯度检查点（推理时不需要）
   - 只加载需要的层

3. KV Cache优化：
   - 使用FlashAttention（减少内存访问）
   - 滑动窗口注意力（只保留最近的K,V）
   - 压缩历史（摘要代替完整历史）

4. 分块处理：
   - 将长文本分成多个chunk
   - 每个chunk单独处理
   - 最后合并结果
   
   ```python
   def process_long_text(text, max_chunk=4000):
       chunks = [text[i:i+max_chunk] for i in range(0, len(text), max_chunk)]
       results = []
       for chunk in chunks:
           result = ollama.generate(model='qwen3:8b', prompt=f'总结：{chunk}')
           results.append(result['response'])
       # 合并总结
       final = ollama.generate(model='qwen3:8b', 
                              prompt='合并以下总结：' + '\n'.join(results))
       return final['response']
   ```

5. 检索增强（RAG）：
   - 不直接输入全文
   - 先检索相关片段
   - 只将相关片段输入模型

6. 硬件升级：
   - 多GPU（模型并行）
   - 更大的显存（48GB+）
   - 使用CPU内存扩展（速度换容量）

实际限制：
- 32K上下文，7B模型，Q4_K_M：约20GB显存
- 64K上下文：约36GB显存
- 128K上下文：约68GB显存

建议：
- 日常应用：4K-8K足够
- 文档分析：使用RAG而非长上下文
- 特殊需求：考虑云端API
```

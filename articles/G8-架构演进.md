## 引言：架构演进的本质

架构演进不是"为了技术而技术"的炫技，而是一门**在组织约束、业务复杂度与系统性能之间寻找最优解**的系统工程。

核心认知：

```
架构演进的本质：在以下三个维度之间做权衡（Trade-off）

┌─────────────────────────────────────────┐
│           组织架构（康威定律）             │
│     团队结构 → 沟通路径 → 系统边界         │
├─────────────────────────────────────────┤
│           业务复杂度（DDD）                │
│     领域边界 → 限界上下文 → 服务边界       │
├─────────────────────────────────────────┤
│           技术约束（性能与可靠性）          │
│     延迟要求 → 一致性要求 → 可用性要求     │
└─────────────────────────────────────────┘

演进错误的根源：
- 差的演进：忽视组织约束，纯技术驱动 → 团队无法驾驭，架构腐烂
- 差的演进：忽视业务边界，按技术层拆分 → 分布式单体，变更仍需协调
- 好的演进：组织、业务、技术三维度对齐 → 团队自治，独立演进
```

**关键洞察**：架构演进的效果不取决于"用了什么技术栈"，而取决于**组织边界与系统边界是否同构**。

## 理论基础：康威定律与领域驱动设计

### 1. 康威定律（Conway's Law）

#### 定律的原始表述与深层含义

Melvin Conway于1968年提出：

```
康威定律：
"设计系统的架构受制于产生这些设计的组织的沟通结构。"

通俗理解：
- 两个团队开发的系统，其模块边界就是两个团队的沟通边界
- 四个团队开发的系统，最终会拆成四个主要模块
- 如果组织是职能型（前端/后端/测试/运维分离），系统就会按技术层分层
```

**康威定律的逆运用（Inverse Conway Maneuver）**：

```
正向运用（观察现象）：
组织结构 → 系统架构

逆向运用（主动设计）：
期望的系统架构 → 反向设计组织结构

示例：
期望架构：用户服务、订单服务、商品服务独立演进
反向设计：
- 组建用户团队（8-12人，全栈）
- 组建订单团队（8-12人，全栈）
- 组建商品团队（8-12人，全栈）
- 每个团队对服务全生命周期负责（开发、测试、部署、运维）
```

#### 团队拓扑与架构映射

```
团队拓扑类型：

1. 流对齐团队（Stream-aligned Team）
   ┌─────────────────────────────────────┐
   │  用户团队  │  订单团队  │  商品团队   │
   │  User Svc │ Order Svc │ Product Svc│
   │  端到端负责 │ 端到端负责 │ 端到端负责  │
   └─────────────────────────────────────┘
   特点：按业务流组织，对应微服务架构

2. 平台团队（Platform Team）
   ┌─────────────────────────────────────┐
   │     基础设施平台（Gateway/Monitor）   │
   │         ↓ 服务流对齐团队              │
   │  用户团队  │  订单团队  │  商品团队   │
   └─────────────────────────────────────┘
   特点：提供内部平台服务，对应平台化架构

3. 赋能团队（Enabling Team）
   ┌─────────────────────────────────────┐
   │  安全专家 │ 性能专家 │ 数据专家      │
   │    ↓ 临时嵌入流对齐团队              │
   │  用户团队  │  订单团队  │  商品团队   │
   └─────────────────────────────────────┘
   特点：提供专业支持，不直接拥有服务

4. 复杂子系统团队（Complicated Subsystem Team）
   ┌─────────────────────────────────────┐
   │      推荐算法团队（复杂ML系统）        │
   │         ↓ 作为服务被调用              │
   │  用户团队  │  订单团队  │  商品团队   │
   └─────────────────────────────────────┘
   特点：负责特别复杂的子系统
```

**工程启示**：
- 团队规模遵循"两个披萨原则"（6-12人）
- 团队边界 = 服务边界 = 代码仓库边界 = 部署单元边界
- 跨团队协调成本决定了架构粒度的下限

### 2. 领域驱动设计（DDD）

#### 战略设计：限界上下文与子域

```
领域驱动设计的核心概念映射：

┌─────────────────────────────────────────┐
│              问题域（Problem Space）       │
│                                          │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐   │
│  │ 核心子域 │ │ 支撑子域 │ │ 通用子域 │   │
│  │ Core    │ │ Support │ │ Generic │   │
│  │ 差异化竞争│ │ 必要但非核心│ │ 可购买/外包│  │
│  └─────────┘ └─────────┘ └─────────┘   │
└─────────────────────────────────────────┘
                    ↓
┌─────────────────────────────────────────┐
│              解决方案域（Solution Space）  │
│                                          │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐   │
│  │ 限界上下文│ │ 限界上下文│ │ 限界上下文│   │
│  │ User BC │ │ Order BC│ │Product BC│   │
│  │ 用户上下文│ │ 订单上下文│ │ 商品上下文│   │
│  └─────────┘ └─────────┘ └─────────┘   │
│                                          │
│  上下文映射（Context Mapping）：           │
│  User BC ←──[客户-供应商]──→ Order BC    │
│  Order BC ←──[发布-订阅]──→ Product BC   │
└─────────────────────────────────────────┘
```

#### 战术设计：实体、值对象、聚合、领域服务

```java
// 聚合根（Aggregate Root）
public class Order implements AggregateRoot<Long> {
    private OrderId id;
    private UserId userId;
    private List<OrderItem> items;
    private ShippingAddress address;
    private OrderStatus status;
    private Money totalAmount;
    private LocalDateTime createTime;
    private LocalDateTime payTime;
    
    // 聚合根负责维护业务不变量
    public void pay(Money amount) {
        if (status != OrderStatus.PENDING_PAYMENT) {
            throw new DomainException("订单非待支付状态");
        }
        if (!amount.equals(totalAmount)) {
            throw new DomainException("支付金额不匹配");
        }
        this.status = OrderStatus.PAID;
        this.payTime = LocalDateTime.now();
        registerEvent(new OrderPaidEvent(id, amount, payTime));
    }
    
    public void addItem(ProductId productId, int quantity, Money unitPrice) {
        if (status != OrderStatus.PENDING_PAYMENT) {
            throw new DomainException("已支付订单不能修改");
        }
        if (items.size() >= 20) {
            throw new DomainException("订单商品数量超限");
        }
        items.add(new OrderItem(productId, quantity, unitPrice));
        recalculateTotal();
    }
    
    private void recalculateTotal() {
        this.totalAmount = items.stream()
            .map(item -> item.getUnitPrice().multiply(item.getQuantity()))
            .reduce(Money.ZERO, Money::add);
    }
}

// 值对象：不可变，通过属性相等性判断
public class Money {
    private final BigDecimal amount;
    private final Currency currency;
    
    public Money(BigDecimal amount, Currency currency) {
        this.amount = amount;
        this.currency = currency;
    }
    
    public Money multiply(int factor) {
        return new Money(amount.multiply(BigDecimal.valueOf(factor)), currency);
    }
    
    public Money add(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new DomainException("币种不一致");
        }
        return new Money(amount.add(other.amount), currency);
    }
    
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money)) return false;
        Money money = (Money) o;
        return amount.compareTo(money.amount) == 0 && currency == money.currency;
    }
}

// 领域服务：跨聚合的业务逻辑
public class OrderPricingService {
    
    public Money calculateDiscount(Order order, Coupon coupon) {
        if (coupon.getType() == CouponType.FULL_REDUCTION) {
            if (order.getTotalAmount().isGreaterThan(coupon.getThreshold())) {
                return coupon.getDiscountAmount();
            }
            return Money.ZERO;
        }
        return Money.ZERO;
    }
}
```

**关键洞察**：DDD的战略设计决定**拆什么**（限界上下文→服务边界），战术设计决定**怎么拆**（聚合→数据一致性边界）。

### 3. 演进式架构的理论基础

```
架构演进的三种策略：

1. 大爆炸式重构（Big Bang）
   ┌─────────────────────────────────────┐
   │  单体应用                            │
   │     ↓ 停止新功能开发6个月              │
   │  微服务架构（全新实现）                 │
   └─────────────────────────────────────┘
   风险：极高，业务停滞，回滚困难
   适用：系统规模小，业务容忍暂停

2. 绞杀者模式（Strangler Fig Pattern）
   ┌─────────────────────────────────────┐
   │          API Gateway                 │
   │     ┌──────────┬──────────┐         │
   │     │ 老单体    │ 新服务A  │         │
   │     │          │ 新服务B  │         │
   │     │          │ 新服务C  │         │
   │     └──────────┴──────────┘         │
   │     逐步将流量从老单体切换到新服务      │
   └─────────────────────────────────────┘
   风险：中，可回滚，渐进式替换
   适用：大多数场景，推荐

3. 分支按抽象（Branch by Abstraction）
   ┌─────────────────────────────────────┐
   │  单体应用                            │
   │  ┌───────────────────────────────┐   │
   │  │   抽象层（Interface/ Facade）  │   │
   │  │  ┌─────────┐  ┌─────────┐    │   │
   │  │  │ 老实现   │  │ 新实现   │    │   │
   │  │  │ (DB)    │  │ (Service)│    │   │
   │  │  └─────────┘  └─────────┘    │   │
   │  └───────────────────────────────┘   │
   │  通过开关控制使用哪个实现               │
   └─────────────────────────────────────┘
   风险：低，但代码复杂度 temporarily 增加
   适用：数据库拆分、核心模块替换
```

## 核心方法论深度解析

### 1. 服务拆分的维度与策略

#### 拆分维度分析

```
服务拆分的六个维度：

1. 业务维度（按DDD子域）
   ┌─────────────────────────────────────┐
   │  User Svc │ Order Svc │ Product Svc │
   │  用户域    │  订单域    │  商品域     │
   └─────────────────────────────────────┘
   优点：业务边界清晰，团队自治
   缺点：跨域查询需要RPC或数据冗余

2. 技术维度（按技术层）
   ┌─────────────────────────────────────┐
   │  BFF Svc  │  Core Svc │  Data Svc  │
   │  适配层    │  业务逻辑层 │  数据访问层 │
   └─────────────────────────────────────┘
   优点：技术栈统一，便于复用
   缺点：业务变更需协调多层，违背康威定律

3. 读写维度（CQRS）
   ┌─────────────────────────────────────┐
   │  Write Svc │       Read Svc         │
   │  命令处理   │  查询处理（ES/Materialized View）│
   └─────────────────────────────────────┘
   优点：读写分离，各自优化
   缺点：数据同步延迟，最终一致

4. 优先级维度（按关键程度）
   ┌─────────────────────────────────────┐
   │  Critical Path │ Non-Critical Path  │
   │  核心交易链路   │  非核心（日志、统计）  │
   └─────────────────────────────────────┘
   优点：核心链路保护，故障隔离
   缺点：需要异步化处理

5. 数据维度（按数据特性）
   ┌─────────────────────────────────────┐
   │  OLTP Svc  │   OLAP Svc            │
   │  在线交易   │  分析查询（ClickHouse） │
   └─────────────────────────────────────┘
   优点：存储引擎各自优化
   缺点：数据同步复杂度

6. 部署维度（按变更频率）
   ┌─────────────────────────────────────┐
   │ Fast Release │ Slow Release         │
   │ 高频变更（营销）│ 低频变更（基础服务）  │
   └─────────────────────────────────────┘
   优点：减少低风险变更的审批等待
   缺点：服务数量增加

推荐：以业务维度为主，其他维度为辅
```

#### 拆分顺序决策树

```
拆分顺序决策：

                    ┌─────────────────┐
                    │  开始拆分评估    │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              ↓              ↓              ↓
        ┌─────────┐   ┌─────────┐   ┌─────────┐
        │ 数据库   │   │ 代码模块 │   │ 独立服务 │
        │ 拆分优先 │   │ 拆分优先 │   │ 拆分优先 │
        └────┬────┘   └────┬────┘   └────┬────┘
             │             │             │
   数据量>1TB│   代码量>10万行│   团队>15人│
   单库性能瓶颈│  编译时间>5min│  冲突频繁 │
```

```java
/**
 * 方案1：应用层组装（Application-side Join）
 * 优点：不依赖中间件，逻辑清晰
 * 缺点：多次网络往返，N+1问题
 */
@Service
public class OrderDetailService {
    
    @Autowired
    private UserServiceClient userService;
    
    @Autowired
    private OrderServiceClient orderService;
    
    @Autowired
    private ProductServiceClient productService;
    
    public OrderDetailDTO getOrderDetail(Long orderId) {
        // 1. 查询订单（订单服务）
        OrderDTO order = orderService.getOrder(orderId);
        if (order == null) {
            throw new NotFoundException("订单不存在");
        }
        
        // 2. 并行查询用户和商品（使用CompletableFuture优化）
        CompletableFuture<UserDTO> userFuture = CompletableFuture.supplyAsync(
            () -> userService.getUser(order.getUserId())
        );
        
        CompletableFuture<ProductDTO> productFuture = CompletableFuture.supplyAsync(
            () -> productService.getProduct(order.getProductId())
        );
        
        // 3. 等待结果并组装
        UserDTO user = userFuture.join();
        ProductDTO product = productFuture.join();
        
        return OrderDetailDTO.builder()
            .order(order)
            .user(user)
            .product(product)
            .build();
    }
    
    // 批量查询优化：使用IN语句减少RPC次数
    public List<OrderDetailDTO> batchGetOrderDetails(List<Long> orderIds) {
        // 1. 批量查询订单
        List<OrderDTO> orders = orderService.batchGetOrders(orderIds);
        
        // 2. 提取所有userId和productId
        Set<Long> userIds = orders.stream()
            .map(OrderDTO::getUserId)
            .collect(Collectors.toSet());
        Set<Long> productIds = orders.stream()
            .map(OrderDTO::getProductId)
            .collect(Collectors.toSet());
        
        // 3. 批量查询用户和商品
        Map<Long, UserDTO> userMap = userService.batchGetUsers(userIds);
        Map<Long, ProductDTO> productMap = productService.batchGetProducts(productIds);
        
        // 4. 内存中组装
        return orders.stream()
            .map(order -> OrderDetailDTO.builder()
                .order(order)
                .user(userMap.get(order.getUserId()))
                .product(productMap.get(order.getProductId()))
                .build())
            .collect(Collectors.toList());
    }
}
```

#### 双写代码实现

```java
/**
 * 订单数据迁移双写服务
 * 支持动态配置切换读写数据源
 */
@Service
@Slf4j
public class OrderMigrationService {
    
    @Autowired
    private OldOrderDao oldOrderDao;       // 老库DAO
    
    @Autowired
    private NewOrderDao newOrderDao;       // 新库DAO
    
    @Autowired
    private DynamicConfig config;          // 动态配置中心（Apollo/Nacos）
    
    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;
    
    private final MeterRegistry meterRegistry;
    private final Counter newWriteFailCounter;
    private final Timer newWriteTimer;
    
    public OrderMigrationService(MeterRegistry meterRegistry) {
        this.meterRegistry = meterRegistry;
        this.newWriteFailCounter = Counter.builder("order.new.write.fail")
            .description("新库写入失败次数")
            .register(meterRegistry);
        this.newWriteTimer = Timer.builder("order.new.write.time")
            .description("新库写入耗时")
            .register(meterRegistry);
    }
    
    /**
     * 创建订单：双写保证数据一致性
     */
    @Transactional("oldTransactionManager")
    public Order createOrder(CreateOrderRequest request) {
        // 1. 构建订单实体
        Order order = Order.builder()
            .id(generateOrderId())
            .userId(request.getUserId())
            .productId(request.getProductId())
            .amount(request.getAmount())
            .status(OrderStatus.PENDING_PAYMENT)
            .createTime(LocalDateTime.now())
            .build();
        
        // 2. 写入老库（主事务）
        oldOrderDao.insert(order);
        
        // 3. 双写新库（异步或同步，根据配置）
        if (config.isDoubleWriteEnabled()) {
            if (config.isAsyncDoubleWrite()) {
                // 异步双写：降低对主流程的影响
                asyncWriteToNew(order);
            } else {
                // 同步双写：强一致性，但增加延迟
                syncWriteToNew(order);
            }
        }
        
        return order;
    }
    
    /**
     * 同步双写：适用于对一致性要求高的场景
     */
    private void syncWriteToNew(Order order) {
        newWriteTimer.record(() -> {
            try {
                newOrderDao.insert(order);
            } catch (Exception e) {
                // 同步双写失败，记录日志并告警，但不影响主流程
                log.error("同步双写新库失败, orderId={}", order.getId(), e);
                newWriteFailCounter.increment();
                
                // 发送补偿消息
                sendCompensationMessage(order);
                
                // 如果配置为强一致性，则抛出异常回滚
                if (config.isStrongConsistency()) {
                    throw new DataMigrationException("双写新库失败", e);
                }
            }
        });
    }
    
    /**
     * 异步双写：通过消息队列保证最终一致
     */
    private void asyncWriteToNew(Order order) {
        try {
            kafkaTemplate.send("order-migration-topic", 
                String.valueOf(order.getId()),
                JsonUtils.toJson(order)
            );
        } catch (Exception e) {
            log.error("发送双写消息失败, orderId={}", order.getId(), e);
            newWriteFailCounter.increment();
        }
    }
    
    /**
     * Kafka消费者：异步写入新库
     */
    @KafkaListener(topics = "order-migration-topic", groupId = "order-migration")
    public void consumeMigrationMessage(ConsumerRecord<String, String> record) {
        Order order = JsonUtils.fromJson(record.value(), Order.class);
        
        try {
            // 幂等性处理：先查后插
            if (newOrderDao.getById(order.getId()) == null) {
                newOrderDao.insert(order);
            }
        } catch (Exception e) {
            log.error("异步写入新库失败, orderId={}", order.getId(), e);
            // 进入死信队列，人工处理
            sendToDeadLetterQueue(record);
        }
    }
    
    /**
     * 查询订单：按配置切换读流量
     */
    public Order getOrder(Long orderId) {
        // 根据灰度策略决定从哪个库读取
        DataSourceRoute route = determineReadRoute(orderId);
        
        if (route == DataSourceRoute.NEW && config.isReadFromNew()) {
            try {
                Order order = newOrderDao.getById(orderId);
                if (order != null) {
                    // 对比老库数据（抽样校验）
                    if (shouldValidate(orderId)) {
                        validateConsistency(orderId, order);
                    }
                    return order;
                }
            } catch (Exception e) {
                log.error("从新库读取失败, orderId={}, 降级到老库", orderId, e);
                // 降级到老库
            }
        }
        
        return oldOrderDao.getById(orderId);
    }
    
    /**
     * 灰度策略：按用户ID取模
     */
    private DataSourceRoute determineReadRoute(Long orderId) {
        Order order = oldOrderDao.getById(orderId);
        if (order == null) {
            return DataSourceRoute.OLD;
        }
        
        long userId = order.getUserId();
        int bucket = (int) (userId % 100);
        
        // 灰度比例从配置中心动态获取
        if (bucket < config.getGrayReadPercent()) {
            return DataSourceRoute.NEW;
        }
        return DataSourceRoute.OLD;
    }
    
    /**
     * 数据一致性校验
     */
    private void validateConsistency(Long orderId, Order newOrder) {
        try {
            Order oldOrder = oldOrderDao.getById(orderId);
            if (oldOrder != null && !oldOrder.equals(newOrder)) {
                log.error("数据不一致! orderId={}, old={}, new={}", 
                    orderId, oldOrder, newOrder);
                // 发送告警，触发补偿
                sendInconsistencyAlert(orderId);
            }
        } catch (Exception e) {
            log.error("一致性校验失败, orderId={}", orderId, e);
        }
    }
    
    private boolean shouldValidate(Long orderId) {
        // 抽样校验：1%的订单进行全字段对比
        return orderId % 100 == 0;
    }
    
    private void sendCompensationMessage(Order order) {
        kafkaTemplate.send("order-compensation-topic",
            String.valueOf(order.getId()),
            JsonUtils.toJson(order)
        );
    }
    
    private void sendInconsistencyAlert(Long orderId) {
        // 发送告警到钉钉/企业微信
        alertService.sendAlert("数据不一致告警", 
            "orderId=" + orderId);
    }
    
    private void sendToDeadLetterQueue(ConsumerRecord<String, String> record) {
        kafkaTemplate.send("order-migration-dlq", record.key(), record.value());
    }
}

/**
 * 数据校验服务：全量对比 + Checksum
 */
@Component
@Slf4j
public class DataValidationService {
    
    @Autowired
    private OldOrderDao oldOrderDao;
    
    @Autowired
    private NewOrderDao newOrderDao;
    
    /**
     * 全量校验：按时间窗口分批对比
     */
    public ValidationReport validateBatch(LocalDateTime startTime, LocalDateTime endTime) {
        ValidationReport report = new ValidationReport();
        int batchSize = 1000;
        long lastId = 0;
        
        while (true) {
            // 1. 批量读取老库数据
            List<Order> oldOrders = oldOrderDao.getByTimeRange(
                startTime, endTime, lastId, batchSize);
            
            if (oldOrders.isEmpty()) {
                break;
            }
            
            // 2. 批量读取新库数据
            List<Long> orderIds = oldOrders.stream()
                .map(Order::getId)
                .collect(Collectors.toList());
            Map<Long, Order> newOrderMap = newOrderDao.batchGetByIds(orderIds);
            
            // 3. 逐条对比
            for (Order oldOrder : oldOrders) {
                Order newOrder = newOrderMap.get(oldOrder.getId());
                if (newOrder == null) {
                    report.addMissing(oldOrder.getId());
                } else if (!checksum(oldOrder).equals(checksum(newOrder))) {
                    report.addInconsistent(oldOrder.getId(), 
                        diff(oldOrder, newOrder));
                }
            }
            
            lastId = oldOrders.get(oldOrders.size() - 1).getId();
        }
        
        return report;
    }
    
    /**
     * Checksum计算：用于快速比对
     */
    private String checksum(Order order) {
        String data = order.getId() + "|" + order.getUserId() + "|" 
            + order.getAmount() + "|" + order.getStatus();
        return DigestUtils.md5Hex(data);
    }
    
    private String diff(Order oldOrder, Order newOrder) {
        // 返回差异字段详情
        List<String> diffs = new ArrayList<>();
        if (!oldOrder.getAmount().equals(newOrder.getAmount())) {
            diffs.add("amount: " + oldOrder.getAmount() + " vs " + newOrder.getAmount());
        }
        if (oldOrder.getStatus() != newOrder.getStatus()) {
            diffs.add("status: " + oldOrder.getStatus() + " vs " + newOrder.getStatus());
        }
        return String.join(", ", diffs);
    }
}
```

```java
@Component
public class ApiGatewayRouter {
    
    @Autowired
    private UserServiceClient userService;
    
    @Autowired
    private OrderServiceClient orderService;
    
    @Autowired
    private ProductServiceClient productService;
    
    @Autowired
    private RateLimiter rateLimiter;
    
    @Autowired
    private CircuitBreakerRegistry circuitBreakerRegistry;
    
    private final LoadingCache<String, ServiceInstance> routeCache;
    
    public ApiGatewayRouter() {
        this.routeCache = Caffeine.newBuilder()
            .maximumSize(1000)
            .expireAfterWrite(30, TimeUnit.SECONDS)
            .build(this::resolveRoute);
    }
    
    /**
     * 聚合接口：订单详情（组合多个服务）
     */
    public OrderDetailResponse getOrderDetail(Long orderId) {
        // 1. 限流检查
        if (!rateLimiter.tryAcquire("order_detail", 1, 100)) {
            throw new RateLimitException("请求过于频繁");
        }
        
        // 2. 获取订单（使用熔断器保护）
        CircuitBreaker orderCb = circuitBreakerRegistry.circuitBreaker("order-service");
        OrderDTO order = orderCb.executeSupplier(() -> 
            orderService.getOrder(orderId)
        );
        
        if (order == null) {
            throw new NotFoundException("订单不存在");
        }
        
        // 3. 并行获取用户和商品信息
        CompletableFuture<UserDTO> userFuture = CompletableFuture.supplyAsync(
            () -> getUserWithCircuitBreaker(order.getUserId()),
            asyncExecutor
        );
        
        CompletableFuture<ProductDTO> productFuture = CompletableFuture.supplyAsync(
            () -> getProductWithCircuitBreaker(order.getProductId()),
            asyncExecutor
        );
        
        // 4. 超时控制
        try {
            UserDTO user = userFuture.get(500, TimeUnit.MILLISECONDS);
            ProductDTO product = productFuture.get(500, TimeUnit.MILLISECONDS);
            
            return OrderDetailResponse.builder()
                .order(order)
                .user(user)
                .product(product)
                .build();
        } catch (TimeoutException e) {
            // 降级：返回订单基本信息
            log.warn("获取订单详情超时, orderId={}", orderId);
            return OrderDetailResponse.builder()
                .order(order)
                .build();
        }
    }
    
    /**
     * 带熔断器的用户服务调用
     */
    private UserDTO getUserWithCircuitBreaker(Long userId) {
        CircuitBreaker userCb = circuitBreakerRegistry.circuitBreaker("user-service");
        return userCb.executeSupplier(() -> userService.getUser(userId));
    }
    
    /**
     * 灰度路由：按用户ID或Header路由到不同版本
     */
    private ServiceInstance resolveRoute(String serviceName) {
        List<ServiceInstance> instances = discoveryClient.getInstances(serviceName);
        
        // 1. 获取灰度标识
        String grayTag = GrayContextHolder.getGrayTag();
        
        // 2. 按灰度标签过滤
        List<ServiceInstance> grayInstances = instances.stream()
            .filter(inst -> grayTag.equals(inst.getMetadata().get("gray.tag")))
            .collect(Collectors.toList());
        
        // 3. 如果命中灰度实例，使用灰度；否则使用稳定版本
        List<ServiceInstance> targetInstances = grayInstances.isEmpty() 
            ? instances.stream()
                .filter(inst -> !inst.getMetadata().containsKey("gray.tag"))
                .collect(Collectors.toList())
            : grayInstances;
        
        // 4. 负载均衡（轮询/随机/加权）
        return loadBalancer.choose(serviceName, targetInstances);
    }
}
```

```java
public class EventSourcedOrder {
    private OrderId id;
    private UserId userId;
    private List<OrderItem> items;
    private OrderStatus status;
    private Money totalAmount;
    private long version = 0;
    
    private final List<DomainEvent> uncommittedEvents = new ArrayList<>();
    
    // 重放事件重建状态
    public void replay(List<DomainEvent> events) {
        for (DomainEvent event : events) {
            apply(event);
            version = event.getVersion();
        }
    }
    
    private void apply(DomainEvent event) {
        if (event instanceof OrderCreatedEvent) {
            applyCreated((OrderCreatedEvent) event);
        } else if (event instanceof OrderPaidEvent) {
            applyPaid((OrderPaidEvent) event);
        }
    }
    
    private void applyCreated(OrderCreatedEvent event) {
        this.id = event.getOrderId();
        this.userId = event.getUserId();
        this.items = new ArrayList<>(event.getItems());
        this.totalAmount = event.getTotalAmount();
        this.status = OrderStatus.PENDING_PAYMENT;
    }
    
    private void applyPaid(OrderPaidEvent event) {
        if (status != OrderStatus.PENDING_PAYMENT) {
            throw new DomainException("订单非待支付状态");
        }
        this.status = OrderStatus.PAID;
    }
    
    public void create(OrderId id, UserId userId, List<OrderItem> items) {
        Money total = calculateTotal(items);
        OrderCreatedEvent event = new OrderCreatedEvent(id, userId, items, total);
        event.setVersion(version + 1);
        uncommittedEvents.add(event);
    }
    
    public List<DomainEvent> getUncommittedEvents() {
        return new ArrayList<>(uncommittedEvents);
    }
}
```

```java
/**
 * Saga：长事务拆分为本地事务序列，失败时反向补偿
 */

@Component
public class OrderSagaOrchestrator {
    
    @Autowired
    private OrderServiceClient orderService;
    
    @Autowired
    private InventoryServiceClient inventoryService;
    
    @Autowired
    private PaymentServiceClient paymentService;
    
    @Autowired
    private SagaLogRepository sagaLogRepository;
    
    public void executeCreateOrderSaga(CreateOrderRequest request) {
        String sagaId = generateSagaId();
        SagaContext context = new SagaContext(sagaId);
        
        try {
            OrderDTO order = executeStep(context, "CREATE_ORDER", () -> {
                return orderService.createOrder(request);
            });
            context.setOrderId(order.getId());
            
            executeStep(context, "DEDUCT_INVENTORY", () -> {
                return inventoryService.deduct(
                    request.getProductId(), request.getQuantity());
            });
            
            executeStep(context, "DEDUCT_PAYMENT", () -> {
                return paymentService.charge(
                    request.getUserId(), order.getTotalAmount());
            });
            
            executeStep(context, "CONFIRM_ORDER", () -> {
                return orderService.confirmOrder(order.getId());
            });
            
        } catch (Exception e) {
            compensate(context);
        }
    }
    
    private <T> T executeStep(SagaContext context, String stepName, 
                              Supplier<T> action) {
        sagaLogRepository.logStepStart(context.getSagaId(), stepName);
        
        try {
            T result = action.get();
            sagaLogRepository.logStepSuccess(context.getSagaId(), stepName, result);
            context.addCompletedStep(stepName, result);
            return result;
        } catch (Exception e) {
            sagaLogRepository.logStepFailure(context.getSagaId(), stepName, e);
            throw e;
        }
    }
    
    private void compensate(SagaContext context) {
        List<SagaStep> completedSteps = context.getCompletedSteps();
        
        for (int i = completedSteps.size() - 1; i >= 0; i--) {
            SagaStep step = completedSteps.get(i);
            
            try {
                switch (step.getName()) {
                    case "CONFIRM_ORDER":
                        break;
                    case "DEDUCT_PAYMENT":
                        paymentService.refund(context.getOrderId());
                        break;
                    case "DEDUCT_INVENTORY":
                        inventoryService.rollback(
                            step.getResult().getInventoryDeductionId());
                        break;
                    case "CREATE_ORDER":
                        orderService.cancelOrder(context.getOrderId());
                        break;
                }
            } catch (Exception e) {
                alertService.sendAlert("Saga补偿失败", 
                    "sagaId=" + context.getSagaId() + ", step=" + step.getName());
            }
        }
    }
}
```

```java
            .refreshAfterWrite(10, TimeUnit.SECONDS)

    }

            throw new NotFoundException("订单不存在或查询超时");
        }
        
        CompletableFuture<UserDTO> userFuture = CompletableFuture
            .supplyAsync(() -> userService.getUser(order.getUserId()), asyncExecutor)
            .orTimeout(200, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> null);
        
        CompletableFuture<ProductDTO> productFuture = CompletableFuture
            .supplyAsync(() -> productService.getProduct(order.getProductId()), asyncExecutor)
            .orTimeout(200, TimeUnit.MILLISECONDS)
            .exceptionally(ex -> null);
        
        CompletableFuture.allOf(userFuture, productFuture)
            .orTimeout(500, TimeUnit.MILLISECONDS)
            .join();
        
        return OrderDetailDTO.builder()
            .order(order)
            .user(userFuture.getNow(null))
            .product(productFuture.getNow(null))
            .build();
    }
}

// 5. 多级缓存
@Service
public class CacheStrategyService {
    
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    
    @Autowired
    private CaffeineCache localCache;
    
    public ProductDTO getProduct(Long productId) {
        String cacheKey = "product:" + productId;
        
        // L1：本地缓存（Caffeine，TTL 1分钟）
        ProductDTO product = localCache.getIfPresent(cacheKey);
        if (product != null) return product;
        
        // L2：Redis（TTL 5分钟）
        product = (ProductDTO) redisTemplate.opsForValue().get(cacheKey);
        if (product != null) {
            localCache.put(cacheKey, product);
            return product;
        }
        
        // L3：数据库
        product = productDao.getById(productId);
        if (product != null) {
            redisTemplate.opsForValue().set(cacheKey, product, 5, TimeUnit.MINUTES);
            localCache.put(cacheKey, product);
        }
        
        return product;
    }
    
    public void updateProduct(ProductDTO product) {
        productDao.update(product);
        
        String cacheKey = "product:" + product.getId();
        redisTemplate.delete(cacheKey);
        localCache.invalidate(cacheKey);
        
        redisTemplate.convertAndSend("cache:invalidate", cacheKey);
    }
}
```

## 常见陷阱与最佳实践

### 陷阱1：过早拆分，为了微服务而微服务

```
错误场景：
- 团队只有5个人，拆出10个微服务
- 每个服务只有几百行代码
- 每天花大量时间处理服务间调用失败、网络超时
- 运维成本占开发时间的50%以上

症状诊断：
┌─────────────────────────────────────────┐
│  开发效率下降：提交一行代码需要改5个仓库    │
│  上线风险增加：一次发布需要协调10个服务     │
│  故障排查困难：一个问题需要查5个服务的日志  │
│  性能反而下降：本地调用变RPC，延迟增加      │
└─────────────────────────────────────────┘

最佳实践：
- 拆分前先评估：代码量、团队规模、业务复杂度是否真的需要
- 遵循"演进式拆分"：单体 -> 模块化 -> 数据库拆分 -> 服务拆分
- 康威定律：团队结构决定架构，8-12人一个服务团队比较合适
- 启动阶段（<10人）：单体 + 模块化
- 成长阶段（10-50人）：模块化 + 数据库拆分
- 扩张阶段（>50人）：服务拆分
```

### 陷阱2：拆成了"分布式单体"

```
错误场景：
- 服务A依赖服务B，服务B依赖服务C，服务C又依赖服务A（循环依赖）
- 一次上线需要同时发布5个服务
- 数据库虽然物理分离，但代码里直接Join别的服务的表
- 服务间共享数据库

症状诊断：
┌─────────────────────────────────────────┐
│  ┌─────┐      ┌─────┐      ┌─────┐     │
│  │ SvcA│←────→│ SvcB│←────→│ SvcC│     │
│  │  ↕  │      │  ↕  │      │  ↕  │     │
│  │ DB_A│      │ DB_B│      │ DB_C│     │
│  │     │      │     │      │     │     │
│  │ 直接│      │ 通过│      │ 直接│     │
│  │ Join│      │ RPC │      │ Join│     │
│  │DB_B │      │ Join│      │DB_A │     │
│  └─────┘      └─────┘      └─────┘     │
│  循环依赖 + 跨库Join = 分布式单体          │
└─────────────────────────────────────────┘

最佳实践：
- 拆分前画依赖图，确保依赖是有向无环图（DAG）
- 底层服务（如用户服务）不要依赖上层服务（如订单服务）
- 引入API网关和BFF层，避免前端直连多个服务
- 数据库彻底分离，跨库查询只能通过RPC或数据冗余
- 服务间通信只允许通过公开API，禁止直接访问其他服务的数据库
```

### 陷阱3：数据迁移时直接切换读写，不做双写

```java
// 错误：直接停止写老库，开始写新库
@Service
public class WrongMigrationService {
    
    public void createOrder(Order order) {
        // 错误：直接写新库，老库不再有新数据
        newOrderDao.insert(order);
    }
    
    public Order getOrder(Long id) {
        // 问题：迁移过程中新写入的数据在老库不存在
        if (isGrayUser()) {
            return newOrderDao.getById(id);
        }
        return oldOrderDao.getById(id);  // 查不到新数据！
    }
}
```

**最佳实践：**
- 必须经历"双写阶段"：新数据同时写入老库和新库
- 老库数据通过Canal或定时任务同步到新库
- 验证数据一致性（抽样对比、checksum校验）
- 先切读流量（灰度），再切写流量
- 保留回滚能力，新库有问题随时切回老库
- 每个阶段保留至少1周的观察期

### 陷阱4：拆分后忽视分布式事务，到处用Seata

```
错误场景：
- 每个跨服务调用都用Seata AT模式
- 性能下降10倍，数据库锁持有时间极长
- 事务协调器成为单点故障

症状：
┌─────────────────────────────────────────┐
│  下单流程：                                │
│  创建订单 → 扣库存 → 扣款 → 发优惠券        │
│     ↓         ↓        ↓        ↓        │
│  Seata      Seata    Seata    Seata      │
│  AT模式     AT模式   AT模式   AT模式      │
│                                          │
│  结果：                                    │
│  - TPS从5000降到500                       │
│  - 数据库连接池耗尽                        │
│  - 事务协调器宕机导致全局回滚                │
└─────────────────────────────────────────┘

最佳实践：
- 能不用分布式事务就不用，通过业务设计避免
  * 示例：订单创建时预留库存（非立即扣减），支付成功后确认扣减
  * 示例：优惠券发放改为异步消息，不阻塞主流程
- 优先使用最终一致性：本地消息表、Saga、最大努力通知
- 强一致性场景才用TCC或Seata，且尽量缩短事务范围
- 核心业务用Saga，非核心用消息队列异步化
- 评估是否真的需要强一致：大多数业务场景最终一致即可
```

### 陷阱5：忽视服务治理，野蛮生长

```
错误场景：
- 服务数量爆炸，没有统一的服务目录
- 每个服务有自己的日志格式、监控指标
- 接口版本管理混乱，兼容性问题频发
- 没有限流熔断，一个服务故障拖垮全链路

最佳实践：
- 建立服务目录：服务名、Owner、SLA、依赖关系
- 标准化：统一的日志格式（TraceId）、监控指标命名、API规范
- 接口版本控制：URL版本号（/v1/orders）或Header版本号
- 强制熔断限流：每个服务接入Sentinel，配置默认规则
- 混沌工程：定期注入故障，验证系统韧性

服务治理检查清单：
┌─────────────────────────────────────────┐
│  □ 服务注册发现（Nacos/Eureka）           │
│  □ 配置中心（Nacos/Apollo）               │
│  □ 限流熔断（Sentinel/Hystrix）           │
│  □ 链路追踪（SkyWalking/Jaeger）          │
│  □ 日志聚合（ELK/Loki）                   │
│  □ 监控告警（Prometheus + Grafana）        │
│  □ API文档（Swagger/Knife4j）             │
│  □ 服务契约测试（Pact）                   │
│  □ 混沌工程（ChaosBlade）                 │
└─────────────────────────────────────────┘
```

## 面试题与参考答案

### Q1：什么时候应该考虑拆分单体架构？过早拆分有什么坏处？

**答：**

**拆分时机（满足任意两条）：**

```
代码层面：
- 代码量超10万行，编译超5分钟
- 代码冲突频繁，提交需要排队
- 技术栈老旧，升级影响面太大

团队层面：
- 开发团队超15人，沟通效率下降
- 不同模块迭代速度差异大，互相阻塞上线
- 上线需要多个团队协作，协调成本高

业务层面：
- 部分模块需要独立扩容，其他模块资源浪费
- 新功能上线影响现有功能，回归测试成本高
- 故障隔离需求：一个模块故障不应影响全局

技术层面：
- 数据库连接数打满，单库性能瓶颈
- 部分模块需要独立技术栈（如AI服务用Python）
```

**过早拆分的坏处：**

```
1. 运维复杂度指数级上升
   - 部署单元从1个变成N个
   - 需要CI/CD流水线、容器编排、服务网格
   - 监控、日志、追踪基础设施投入大

2. 网络调用替代本地调用
   - 延迟增加（本地0.001ms → 网络0.5-2ms）
   - 故障点增加（网络抖动、超时、重试风暴）
   - 需要处理分布式事务、幂等性、一致性

3. 团队协作成本增加
   - 接口变更需要跨团队协调
   - 联调成本增加
   - 接口文档、版本管理、契约测试

4. 性能下降
   - 序列化/反序列化开销
   - 连接池管理开销
   - 服务发现开销

5. 数据一致性复杂化
   - 从本地事务变为分布式事务
   - 需要最终一致性方案
   - 数据同步、补偿、对账
```

### Q2：数据库垂直拆分和水平拆分的区别是什么？分别解决什么问题？

**答：**

| 维度 | 垂直拆分 | 水平拆分 |
|------|---------|---------|
| **拆分维度** | 按业务/表拆分 | 按数据行拆分 |
| **解决问题** | 单库表数量过多、业务耦合 | 单表数据量过大（>千万级） |
| **典型方案** | 用户库、订单库、商品库独立 | order_0000 ~ order_1023 |
| **复杂度** | 相对较低 | 较高（分片路由、跨片查询） |
| **数据迁移** | 按表迁移，较简单 | 需要重新分布数据，复杂 |
| **Join影响** | 跨库Join消失 | 单库内Join正常，跨片Join困难 |
| **事务影响** | 跨库事务需分布式方案 | 同片内事务正常，跨片需分布式 |
| **扩容方式** | 新增业务库 | 增加分片，数据重分布 |
| **适用阶段** | 业务增长期 | 数据量爆发期 |

**垂直拆分后需要解决：**
- 跨库Join：应用层组装、数据冗余、宽表
- 分布式事务：TCC、Saga、本地消息表
- 全局ID：雪花算法、号段模式

**水平拆分后需要解决：**
- 分片键选择：高频查询条件、均匀分布
- 跨片查询：聚合、排序、分页困难
- 数据迁移：扩容时需要重新分片
- 全局ID：避免分片内ID冲突

### Q3：双写方案中，如果新库写入失败怎么处理？

**答：** 常见处理策略：

```
1. 记录补偿日志
   - 新库写入失败时，记录到日志表或MQ
   - 后续定时任务扫描补偿日志，重试写入
   - 重试3次仍失败，告警人工处理

2. 标记不一致
   - 将不一致的数据标记出来
   - 通过对比工具（checksum）定期扫描
   - 自动修复或人工修复

3. 自动重试
   - 短暂失败（网络抖动）立即重试3次
   - 指数退避：1s → 2s → 4s
   - 仍失败则降级记录日志

4. 监控告警
   - 新库写入失败率超过阈值（如0.1%）立即告警
   - 暂停切流，保持读老库
   - 排查问题后再继续

关键原则：
- 双写阶段以老库为准，新库失败不能影响老库写入和业务流程
- 读流量切换前必须验证数据一致性
- 保留回滚能力，新库有问题秒级切回老库
```

### Q4：跨库Join有哪些解决方案？各有什么优缺点？

**答：**

```
1. 应用层组装
   实现：先查主表，再根据ID查关联表，代码中拼接
   优点：逻辑清晰，不依赖中间件，灵活性高
   缺点：多次网络往返，N+1问题，性能差
   优化：批量查询（IN语句）、并行查询（CompletableFuture）
   适用：关联数据少，实时性要求高

2. 数据冗余（反规范化）
   实现：在订单表冗余用户姓名、商品标题
   优点：查询快，无跨库问题，单表查询即可
   缺点：数据一致性维护复杂，更新时需同步修改冗余字段
   优化：异步消息更新冗余字段，容忍短暂不一致
   适用：读多写少，关联字段变化频率低

3. 分布式SQL中间件
   实现：ShardingSphere、MyCAT自动路由Join
   优点：对应用透明，SQL几乎不用改
   缺点：复杂Join性能差，部分SQL不支持，引入中间件复杂度
   优化：避免跨片Join，绑定表配置
   适用：存量系统迁移，不想改代码

4. 宽表/物化视图
   实现：通过Canal同步到ES或ClickHouse做分析查询
   优点：适合复杂分析、聚合查询，性能高
   缺点：实时性稍差（秒级延迟），最终一致
   优化：近实时同步（Canal + Kafka + ES）
   适用：OLAP场景、复杂搜索、报表统计

5. CQRS（命令查询分离）
   实现：写模型用关系型DB，读模型用宽表/ES
   优点：读写各自优化，读性能极高
   缺点：系统复杂度增加，数据同步延迟
   适用：读多写少，读模型和写模型差异大
```

### Q5：架构演进中，如何保障拆分过程不影响线上业务？

**答：** 核心策略是"逐步切流、随时回滚"：

```
1. 代码层面
   - 先拆代码模块，保持单部署，验证逻辑正确性
   - 使用Branch by Abstraction：引入抽象层，新老实现可切换
   - 开关控制：Feature Flag控制走老逻辑还是新逻辑

2. 数据库层面
   - 先双写，数据对齐后再切读流量
   - 数据校验：抽样对比、checksum校验
   - 灰度切流：按用户ID取模，1% → 5% → 10% → 50% → 100%

3. 服务层面
   - 通过API网关按用户ID或地区灰度
   - 流量复制（Traffic Mirroring）：复制线上流量到新系统，对比响应
   - 影子库：新系统使用影子库验证，不影响线上数据

4. 监控层面
   - 全程对比新老系统的QPS、RT、错误率、业务指标
   - 核心指标下跌超过阈值（如错误率>0.1%）自动回滚
   - 业务指标监控：订单量、支付成功率等

5. 回滚预案
   - 每个阶段保留回滚能力
   - 回滚时间目标：RTO < 5分钟
   - 数据回滚：新库数据可同步回老库（反向双写）
   - 配置回滚：配置中心一键切换开关

6. 演练验证
   - 上线前在预发环境全链路演练
   - 混沌工程：模拟新服务故障，验证降级策略
   - 压测：新系统容量不低于老系统的80%
```

### Q6：分布式事务的Saga模式和TCC模式有什么区别？

**答：**

| 维度 | Saga | TCC |
|------|------|-----|
| **原理** | 长事务拆分为本地事务序列，失败时反向补偿 | Try预留资源，Confirm确认，Cancel释放 |
| **一致性** | 最终一致 | 最终一致 |
| **侵入性** | 低（基于现有接口反向操作） | 高（需要实现三套逻辑：Try/Confirm/Cancel） |
| **隔离性** | 低（补偿前数据可见，可能出现更新丢失） | 较高（Try阶段预留资源，其他事务不可见） |
| **实现复杂度** | 中（需要编排器和补偿逻辑） | 高（需要实现幂等、空回滚、悬挂问题） |
| **性能** | 较高（本地事务提交快） | 中（Try需要锁定资源，增加RT） |
| **回滚能力** | 补偿操作可能失败，需要人工介入 | Cancel释放资源，回滚能力强 |
| **适用场景** | 长业务流程（如旅游预订、电商下单） | 短事务、资源预留场景（如库存扣减、账户扣款） |
| **代表实现** | Seata Saga, Axon Framework | Seata TCC, Hmily |

**Saga适用场景示例：**
```
旅游预订：订机票 → 订酒店 → 租租车 → 买保险
- 任何一步失败，反向取消已预订的
- 允许用户看到"预订中"状态（隔离性低可接受）
```

**TCC适用场景示例：**
```
库存扣减：
- Try：检查库存并冻结（预留）
- Confirm：确认扣减（实际减库存）
- Cancel：释放冻结（回滚）
- 隔离性要求高：Try阶段其他事务看不到冻结库存
```

### Q7：康威定律在实际架构设计中的具体应用是什么？

**答：**

```
康威定律的核心应用：组织结构与系统架构对齐

1. 按业务领域组建团队（流对齐团队）
   ┌─────────────────────────────────────────┐
   │  用户团队（8人） → 用户服务（User Service）│
   │  订单团队（10人）→ 订单服务（Order Service）│
   │  商品团队（8人） → 商品服务（Product Svc） │
   │  每个团队全栈负责：前端、后端、测试、运维    │
   └─────────────────────────────────────────┘
   结果：团队内部沟通高效，跨团队沟通通过API契约

2. 逆康威定律：先设计期望架构，再调整组织
   步骤：
   a. 识别业务能力边界（DDD子域）
   b. 设计目标服务架构
   c. 根据服务边界调整团队结构
   d. 每个团队对服务全生命周期负责

3. 团队规模控制
   - "两个披萨原则"：团队规模不超过两个披萨能吃饱的人数（6-12人）
   - 团队过大 → 沟通路径爆炸（n*(n-1)/2）
   - 团队过小 → 无法覆盖全栈技能

4. 平台团队模式
   ┌─────────────────────────────────────────┐
   │  平台团队：提供基础设施和工具链            │
   │  （Gateway、Monitor、CI/CD、Service Mesh）│
   │         ↓ 内部开源，服务流对齐团队         │
   │  用户团队 │ 订单团队 │ 商品团队            │
   └─────────────────────────────────────────┘
   平台团队的目标：让流对齐团队可以自助使用基础设施

5. 实际案例
   - Amazon："You build it, you run it" 文化
   - Netflix：每个服务有明确的Owner团队
   - Spotify：Squad（小队）对应微服务
```

### Q8：微服务架构中，如何处理服务雪崩效应？

**答：**

```
服务雪崩：一个服务故障导致依赖它的服务级联故障

示例：
┌─────────────────────────────────────────┐
│  用户请求 → 订单服务 → 库存服务           │
│     ↓         ↓           ↓             │
│   成功      超时        宕机             │
│     ↓         ↓           ↓             │
│  用户重试 → 订单服务线程池打满           │
│     ↓         ↓                         │
│  订单服务也宕机 → 影响用户服务、支付服务    │
└─────────────────────────────────────────┘

防御策略：

1. 熔断（Circuit Breaker）
   原理：失败率超过阈值，自动断开，直接返回降级结果
   状态：CLOSED → OPEN → HALF_OPEN
   ┌─────────────────────────────────────┐
   │  CLOSED: 正常调用                   │
   │     ↓ 失败率>50%                   │
   │  OPEN: 快速失败，不调用下游         │
   │     ↓ 等待5s                        │
   │  HALF_OPEN: 放行少量请求试探        │
   │     ↓ 成功                          │
   │  CLOSED: 恢复                       │
   └─────────────────────────────────────┘
   实现：Hystrix、Sentinel、Resilience4j

2. 限流（Rate Limiting）
   原理：限制单位时间内的请求数，保护系统不被压垮
   算法：
   - 计数器：简单，但可能有突发流量
   - 滑动窗口：平滑，但计算量大
   - 令牌桶：允许一定突发，平滑限流
   - 漏桶：严格匀速，无突发
   
   维度：
   - QPS限流：限制每秒请求数
   - 并发限流：限制同时处理的请求数
   - 热点限流：针对热点参数（如用户ID、商品ID）

3. 降级（Degradation）
   原理：非核心功能故障时，关闭或简化功能，保证核心流程
   策略：
   - 返回默认值：库存服务宕机，默认有库存
   - 返回缓存数据：商品详情从Redis读，不回源
   - 简化流程：关闭推荐、关闭评价，只保留下单核心
   - 异步化：非核心操作改为消息队列异步处理

4. 隔离（Isolation）
   原理：资源隔离，防止故障扩散
   策略：
   - 线程池隔离：每个服务独立线程池
   - 信号量隔离：限制并发数
   - 集群隔离：核心服务独立部署集群
   - 用户隔离：按用户ID分片，单用户故障不影响其他用户

5. 超时与重试
   原则：
   - 设置合理的超时时间（P99延迟 * 1.5）
   - 限制重试次数（最多2次）
   - 重试退避：线性退避或指数退避
   - 避免重试风暴：服务端限流 + 客户端熔断

6. 监控告警
   - 实时监控QPS、RT、错误率、线程池状态
   - 错误率突增自动告警
   - 熔断状态可视化
```

### Q9：领域驱动设计（DDD）在微服务拆分中的具体作用是什么？

**答：**

```
DDD在微服务拆分中的三层作用：

1. 战略设计：确定服务边界
   
   核心工具：限界上下文（Bounded Context）
   
   示例：电商系统
   ┌─────────────────────────────────────────┐
   │  问题域分析：                            │
   │  - 用户管理：注册、登录、会员等级         │
   │  - 商品管理：上架、类目、价格             │
   │  - 订单管理：下单、支付、履约             │
   │  - 库存管理：库存扣减、补货               │
   │  - 营销管理：优惠券、满减、秒杀           │
   │                                         │
   │  限界上下文划分：                         │
   │  ┌─────────┐ ┌─────────┐ ┌─────────┐   │
   │  │ User BC │ │Product BC│ │ Order BC│   │
   │  │ 用户上下文│ │ 商品上下文│ │ 订单上下文│   │
   │  └─────────┘ └─────────┘ └─────────┘   │
   │  ┌─────────┐ ┌─────────┐               │
   │  │Inventory│ │ Marketing│               │
   │  │ 库存上下文│ │ 营销上下文 │               │
   │  └─────────┘ └─────────┘               │
   │                                         │
   │  每个BC = 一个微服务                      │
   └─────────────────────────────────────────┘

2. 上下文映射：定义服务间关系
   
   ┌─────────────────────────────────────────┐
   │  Order BC ←──[客户-供应商]──→ User BC   │
   │     ↓                                      │
   │  Inventory BC                            │
   │  （订单依赖库存，库存服务是上游）           │
   │     ↓                                      │
   │  Marketing BC（防腐层隔离外部依赖）         │
   └─────────────────────────────────────────┘
   
   关系类型：
   - 合作关系（Partnership）：两个团队紧密协作
   - 共享内核（Shared Kernel）：共享部分模型
   - 客户-供应商（Customer-Supplier）：上游优先满足下游需求
   - 遵奉者（Conformist）：下游完全遵循上游模型
   - 防腐层（Anti-Corruption Layer）：下游隔离上游模型影响
   - 开放主机服务（Open Host Service）：上游提供标准协议

3. 战术设计：指导服务内部结构
   
   聚合（Aggregate）：一致性边界
   ┌─────────────────────────────────────────┐
   │  订单聚合根（Order）：                     │
   │  - 包含订单项（OrderItem）                │
   │  - 包含收货地址（Address，值对象）         │
   │  - 聚合根负责维护业务不变量                │
   │  - 一个事务只能修改一个聚合               │
   └─────────────────────────────────────────┘
   
   领域事件（Domain Event）：服务间通信
   ┌─────────────────────────────────────────┐
   │  OrderPaidEvent → 触发库存扣减            │
   │  InventoryDeductedEvent → 触发发货        │
   │  ShippedEvent → 触发物流跟踪              │
   └─────────────────────────────────────────┘

DDD拆分原则：
- 一个限界上下文对应一个微服务（理想情况）
- 聚合是事务边界，一个事务不跨聚合
- 领域事件用于跨聚合、跨服务的最终一致性
- 防腐层保护领域模型不受外部污染
```

### Q10：如何设计一个高可用的API网关？

**答：**

```
高可用API网关设计要点：

1. 网关自身高可用
   ┌─────────────────────────────────────────┐
   │           L4负载均衡（LVS/HAProxy）       │
   │              ↓           ↓              │
   │        ┌─────────┐   ┌─────────┐        │
   │        │ Gateway │   │ Gateway │        │
   │        │ 节点1   │   │ 节点2   │        │
   │        └─────────┘   └─────────┘        │
   │              ↓           ↓              │
   │           后端服务集群                   │
   └─────────────────────────────────────────┘
   - 网关多节点部署，无状态设计
   - 配置统一存储（Nacos/Apollo），节点间同步
   - 健康检查：自动剔除故障节点

2. 流量治理
   - 限流：令牌桶算法，支持按API、按用户、按IP限流
   - 熔断：失败率超过阈值自动熔断，降级到Mock或缓存
   - 重试：幂等接口自动重试，非幂等接口不重试
   - 超时：全局默认超时 + API级自定义超时

3. 协议转换与优化
   - 前端HTTP/1.1 → 后端HTTP/2或gRPC
   - SSL终止：网关统一处理HTTPS，后端用HTTP
   - 压缩：响应Gzip压缩
   - 缓存：GET请求结果缓存（TTL根据业务配置）

4. 安全防护
   - 认证：OAuth2/JWT/API Key
   - 鉴权：RBAC，按API配置权限
   - 防刷：限流 + 验证码 + IP黑名单
   - WAF：SQL注入、XSS、CSRF防护
   - 敏感数据：网关层脱敏（手机号、身份证）

5. 可观测性
   - 访问日志：统一格式，包含TraceId、UserId、耗时
   - 指标：QPS、RT、错误率、限流次数、熔断状态
   - 链路追踪：透传TraceId到后端服务
   - 告警：错误率突增、RT突增、网关节点宕机

6. 动态路由
   - 基于Header路由：灰度发布、A/B测试
   - 基于权重路由：金丝雀发布（1% → 10% → 100%）
   - 基于参数路由：按用户ID、按地区

7. 性能优化
   - 异步非阻塞：Netty/Reactor模式
   - 连接池：后端服务长连接复用
   - 本地缓存：路由规则、Token黑名单缓存
   - 预热：启动时预热连接池、JIT编译
```

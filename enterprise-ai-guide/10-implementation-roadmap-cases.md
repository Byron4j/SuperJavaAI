## 10.2 案例 1: 电商智能客服

```yaml
案例概况:
  公司: 中型电商平台 (年 GMV ~10 亿)
  场景: 售前咨询 + 售后处理 + 退款自动审核
  目标: 客服响应时间 < 1 分钟，人工工作量降低 50%

技术架构:
  AI Gateway: 自建 (Spring Boot + 自研路由)
  LLM:        
    - 简单 FAQ:      Qwen-7B (自建 2×A10)
    - 复杂咨询:      GPT-4o (云 API)
    - 情感分析:      LLaMA-8B (自建)
  RAG:         pgvector (已有 PostgreSQL)
  Agent:       Function Calling (查询订单/物流/退款 API)

关键决策:
  - 为什么混合部署?
    简单问题量大(90%)用自建(省钱)，复杂问题(10%)用 GPT-4(保证质量)

  - 为什么用 pgvector 而不是专用向量数据库?
    已有 PG 架构，数据量 < 5M 向量，不必引入新组件

实施时间线:
  Month 1:   PoC — FAQ 机器人 (内部测试 50 人)
  Month 2:   灰度上线 — 覆盖 20% 客户流量
  Month 3:   全量上线 — 覆盖 100% 流量
  Month 4:   售后 Agent — 自动处理退货/退款/换货
  Month 5:   多语言支持 (中/英/日)
  Month 6:   AI 客服覆盖率达到 80% 的常见问题

ROI (12 个月):
  投入:
    - 基础设施 (GPU + API): ¥96,000/年
    - 团队 (3 人): ¥600,000/年
    - 总计: ¥696,000/年

  收益:
    - 替代 6 名客服 (部分替代): ¥480,000/年
    - 7×24 服务减少夜间外包: ¥180,000/年
    - 退款处理效率提升 3x: ¥120,000/年
    - 总计: ¥780,000/年

  ROI = (780,000 - 696,000) / 696,000 = +12% (第一年)
  第二年预计: +40%+ (规模效应)

核心教训:
  1. 不要一次性替代全部客服 — 先从 FAQ 开始，建立信任
  2. 退款和金钱相关的操作必须人工最终确认(即使 AI 自动化 90%)
  3. 每周和客服主管做 30 分钟 Review，按真实反馈优化 Prompt
```

## 10.3 案例 2: 金融合规审查

```yaml
案例概况:
  公司: 中型私募基金
  场景: 合同/尽调报告合规性审查
  目标: 缩短审查时间从 3 天到 2 小时，关键条款零遗漏

技术架构:
  LLM:  Claude (合规数据的隐私要求高，数据不用于训练)
  部署:   云端 API (通过 Azure/Amazon Bedrock 保证数据驻留)
  RAG:    法规知识库 (证监会、基金业协会法规 + 内部合规手册)
  安全:   
    - Prompt 注入防御 (多层)
    - 输出必须标注引用来源
    - 人工最终确认 (HITL 闭环)

关键决策:
  - 为什么选 Claude 而非 GPT-4?
    Claude 对结构化法律文本的理解更准确，且 Anthropic 的数据使用政策更严格

  - 为什么用云端 API 而非自建?
    数据量中等 (< 1000 req/day)，GDPR/数据合规要求已满足，不需要自建

实施时间线:
  Month 1:   场景定义 + 法规知识库构建
  Month 2:   Prompt 迭代 (与 2 名合规专家反复测试)
  Month 3:   内部试用 (5 名律师/分析师)
  Month 4:   灰度上线 — 覆盖 30% 的合同审查
  Month 5:   全量上线
  Month 6:   扩展到尽调报告、招股书审查

ROI (12 个月):
  投入:
    - Claude API: ¥120,000/年
    - 基础设施: ¥30,000/年
    - 团队 (2 人): ¥500,000/年
    - 总计: ¥650,000/年

  收益:
    - 节省律师时间: 审查时间从 3 天 → 2 小时 → 节约 ~¥1,200,000/年
    - 减少合规遗漏: 年均避免 2 次监管处罚 → 节约 ~¥500,000/年
    - 总计: ¥1,700,000/年

  ROI = (1,700,000 - 650,000) / 650,000 = +161%

核心教训:
  1. "HITL is NOT optional" — 合规审查中 AI 给出建议，人工做最终判断
  2. 法规更新频率极高 → 知识库更新必须有自动化流水线
  3. AI 的最大价值不是"更快读完"，而是"永不遗漏关键条款"
```

## 10.4 案例 3: 制造企业设备运维

```yaml
案例概况:
  公司: 大型制造企业 (50+ 工厂)
  场景: 设备故障诊断 + 维修知识库 + 备件推荐
  目标: 平均故障修复时间 (MTTR) 从 4 小时降到 30 分钟

技术架构:
  LLM:  LLaMA-8B (自建，工厂内网必须本地部署)
  部署:   边缘推理 (每个工厂 1 台 GPU 服务器)
  RAG:    维修手册知识库 + 历史故障记录
  多模态: 图片识别 (设备照片 → 故障类型判断)
  Agent:  自动生成维修工单 → 推荐备件 → 发送给维修工程师

关键决策:
  - 为什么必须本地部署?
    工厂网络完全隔离，数据不能出内网

  - 为什么选 LLaMA-8B?
    8B 参数足够做故障诊断，2×A10 即可部署，成本可控

  - 为什么每个工厂独立部署?
    避免网络延迟 (内网 < 50ms)，不依赖中心网络

实施时间线:
  Month 1-2: 1 个试点工厂
  Month 3-4: 5 个工厂推广
  Month 5-6: 全量 50+ 工厂部署
  Month 7-12: 持续优化，新增预测性维护功能

ROI (12 个月):
  投入:
    - 硬件 (50+ GPU 服务器): ¥2,500,000 (一次性)
    - 团队 (3 人): ¥600,000/年
    - 总计: ¥3,100,000

  收益:
    - MTTR 降低: 4h → 0.5h → 减少停机损失 ~¥15,000,000/年
    - 减少高级维修专家出差: ~¥3,000,000/年

  ROI = (18,000,000 - 3,100,000) / 3,100,000 = +480%

核心教训:
  1. 硬件成本虽高，但停机损失更高——算大账
  2. 边缘部署的关键是运维自动化 (远程升级模型/知识库)
  3. 维修师傅的反馈是知识库最重要的数据来源
```

## 10.5 启动清单 (Battle-Tested)

```yaml
AI 项目启动的 20 条黄金法则:

战略层:
  1. [ ] 有明确的业务指标 (不是"提升效率"，是"MTTR 从 4h→30min")
  2. [ ] 第一个场景是"低风险高价值" (FAQ > Agent > 自主决策)
  3. [ ] ROI 预期已经量化 (即使粗略)
  4. [ ] CEO/CTO 级别的 Sponsor 已确认 (不只是"口头支持")

技术层:
  5. [ ] AI Gateway 设计完成 (统一入口，不直连 LLM)
  6. [ ] 评估体系已建立 (Golden Dataset + LLM-as-Judge)
  7. [ ] 安全护栏在 Day 1 就上线 (不要等出事了再补)
  8. [ ] 成本归因从 Day 1 开始记录
  9. [ ] 有模型级别的 Fallback (GPT 挂了切 Claude)
  10. [ ] 有 Prompt 回滚机制 (出问题 1 分钟回滚)

组织层:
  11. [ ] 团队中有领域专家 (不是纯技术人员做 AI 产品)
  12. [ ] 有明确的团队负责人 (不是"大家兼职搞搞")
  13. [ ] 用户反馈渠道已建立 (👍/👎 或访谈)
  14. [ ] 培训计划已制定 (帮助用户用好 AI)

数据层:
  15. [ ] 知识库数据源已确认 (文档在哪?质量如何?)
  16. [ ] 数据隐私合规已通过
  17. [ ] 数据更新机制已建立 (不是一次性导入)

交付层:
  18. [ ] 第一个版本 4 周内交付 (不要磨 3 个月)
  19. [ ] 有明确的成功标准 (什么算"成功上线"?)
  20. [ ] 有定期的复盘机制 (每周/每月 Review)
```

## 10.6 最后的话

```
企业 AI 转型三个最重要的原则:

1. Start Simple, Scale Smart
   不要一上来就做全自动 Agent。
   从 Augmented LLM 开始 → Workflow → Agent。
   Anthropic 的原话: "只在简单方案不够时才增加复杂度。"

2. 技术选型是次要的，组织适配是主要的
   一个好的 PM + 领域专家 >> 最好的模型。
   文化不拥抱 AI，技术再怎么好也是对牛弹琴。

3. 把 AI 当成产品，不是项目
   项目有终点 (上线就结束了)。
   产品永远在迭代 (Prompt 优化、数据更新、模型升级)。
   用产品的思维做 AI——持续投入，持续增长。
```
